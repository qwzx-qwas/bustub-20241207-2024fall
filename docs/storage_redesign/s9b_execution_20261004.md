## 1. 对话落实与实现选择

- Entry 解码出的 frame_id 分别用于 Header 管理信息与 Arena 正文定位，不是多层转发正文。b 不修改旧 FrameHeader/PageGuard；c 统一迁移调用方。
- FrameArena 创建匿名映射后、交付前建议 THP。正常复用槽位不重新申请；建议结果与 smaps 实际占用分开报告，不能归属的 VMA 返回未知。不默认预热、不调整全局内核配置。
- 新增 Linux `FrameArena` 与 `TranslationDirectory`，共用私有 RAM 所有权/尺寸计算辅助；没有新服务或设备队列。A/B 旧路径未改。每个目录对象对应独立运行上下文，访问守卫保留其内部状态，不能跨到新目录。
- 8/7/16、frame+1、24 位翻译版本、8 位短锁、组级访问门沿 S9.1a。正常目录路径通过 acquire 读取已发布指针；父槽 mutex 只处理首次发布。守卫只覆盖短查找/修改，不跨内容等待和 IO。
- 目录控制与已构造组计入显式预算，候选先预留再分配；失败/竞争落败归还。叶地址空间按需保留，不等于已占 RAM。预算计管理分配字节，不能冒充进程 RSS（分配器额外开销、内核页表单独观察）；全节点预算仍归 F31 后续。
- b 的内部组件暂未被业务调用，属于已批准的 b/c 分步交付；不增加通用空接口，不同时维护两份生产驻留目录。Frame()/Access()/SetFrame() 是 c 的真实接入能力，非测试 getter；Layout/ObserveMemory 对应正式布局和大页使用报告。

来源：Calico v1 的数组/紧凑条目/按需内存思路；Linux mmap/madvise/THP 的匿名内存和请求/生效区分，链接沿共同协议 §13。没有复制第三方源码或引入新依赖；本地同步、预算与生命周期是本项目实现。

## 2. 先于测试的代码逻辑审查

本节在新增阶段测试前记录。

1. 核对位拆分只接收合法非负 int32 页号；不同 prefix/suffix 分开，frame 0 编码为 1。撤销保留版本，无帧判断不比较整个字。
2. 查找先持有 owner，后取组共享门与条目短锁；销毁按条目解锁→组门退出→owner 释放。没有裸原子引用逃出守卫；c 仍必须在守卫内核对并固定 FrameHeader。
3. 组首次构造在独占门内复核，先取得预算再 placement-new，叶析构只结束已构造条目的寿命；控制块不在可回收叶内。d 增加实际回收时必须重新核对升级/降级门之间的状态。
4. 先审发现候选对象在预留前分配，已改为 Create 中先持 Charge 再分配；发现正常父槽查询仍拿 mutex，已改为 acquire/release 发布指针。根固定大小在分配前检查额度。候选销毁在父槽锁外。
5. FrameArena 同时保证基址和槽步长对齐，不改变数据库页大小；乘加/取整检查只保护外部几何参数与内存容量。madvise 建议失败如实报告；普通策略先区分内核不支持 THP 与实际区域失败；后者传播错误（本次复审修正见 §9）。不存在吞 IO 错误/清零继续的路径。
6. smaps 只累计完全归属当前区域的 VMA；合并到外部区域、缺少数据或不可读取则未知，不把建议成功当作实际大页。不强制大页大小或性能倍数。

## 5. 重复、低价值及跨阶段交接

- T1 验证帧内存布局；T2 使用 Arena 是为了给不同页配不同正文，独有目标是寻址/身份。没有重复逐个字段的编码套件。
- T3 处理候选首次发布；T5 处理已存在条目的并发更新；两者可能都表现为丢值，但发生阶段和错误机制不同。
- T4 的 40 次故障用于累积泄漏直到破坏后续合法请求，不是重复堆 40 组无新意义参数。第一次访问后的 mincore 检查保护按需触碰承诺，不测试 mincore 本身。
- 不复制 F01/F02 的 Direct/许可/队列测试，也不重复旧 BufferPool 的驱逐/脏页场景。本轮旧 BufferPool 源码/接口未改，仅重新编译同一 `bustub_buffer` 目标；没有把未运行的旧套件记为通过。
- c 将 T2 的人工“目录+帧”组合改接正式 PageGuard/页后端；补同页合并、独立 IO、写回完成、关闭等风险。d 接管 RAM 归还再初始化，e/共同 C/P 接管完整生产内容。不能让测试侧实现缺失的生产加载流程来冒充接入。

## 9. 本次复审：普通内存回退与测试判断（2026-10-04）

先复查生产逻辑及 Linux 文档，再修改测试。发现无 THP 支持时 `MADV_NOHUGEPAGE` 也不可用；原 FrameArena 普通策略和翻译叶都直接抛错，与方案的普通内存回退矛盾。已在私有 Region 集中处理：实际调用 EINVAL 后作零长度能力探测，仅确认 advice 不支持才继续；支持却失败仍抛出原错误。两种内存组件共用该逻辑，无新增 public API、默认参数或测试 hook。依据为 [madvise Linux 能力探测约定](https://man7.org/linux/man-pages/man2/madvise.2.html) 及 [Linux v6.12 的 advice 校验和零长度处理](https://github.com/torvalds/linux/blob/v6.12/mm/madvise.c)。

逐项复核还覆盖 owner/组门/条目锁的销毁顺序、候选发布、预算归还和寻址；未发现需扩大到 c 的修改。c 尚未接入真实页生命周期，不能把本次组件守卫当作已经完成的帧 pin。
