## 1. 先审生产逻辑

执行顺序：读取总方案/F36/F26 交接及生产调用链 → 补充 F36 §6.6 → 实现 → 推演锁、引用、异常与恢复 → 编写阶段测试 → 实测、定向变异及再次审查。不能以测试绿灯反推设计成立。

本轮修正及原因：

1. `TablePage` 分离逻辑删除与物理空槽（offset=0），整理存活正文时保持 slot 编号；旧版只根据末 slot 算空间的办法不再成立，改为计算有效正文边界。删除计数按实际槽内容重算，兼容旧版计数不完整的问题。
2. `TableHeap` 增加可重建的有序空闲摘要；插入先寻找已有页，Open 时随页链重建。实际页锁内复查，失败获取页面不丢弃原提示。新页初始化成功后才接到页链，无法装入单页的输入先拒绝。
3. `TableIterator` 跳过物理空槽，保留逻辑 tombstone 给 MVCC；在扫描寿命内禁止回填旧位置，避免新插入行进入既有物理扫描。移动迭代器转移保护，构造失败不留下计数。
4. `BusTubStateMachine::ApplyUpdate/ApplyDelete` 在独占 visibility 区间内先删旧索引、再标删除并回收旧记录。保持逻辑命令、旧值验证和 fail-stop 不变。
5. 普通 SQL 的显式 GC 在没有 RUNNING/TAINTED 事务时，每表每次回收至多 128 条。先退出全部历史索引键，再清 undo 入口，最后复用 RID；活跃事务的跨语句 RID 使用不能只由页面 pin 或删除时间戳判断。
6. GC 保留活跃 SERIALIZABLE 事务仍要检查的已提交写集合。插入没有 undo，原先只按 undo 存活性回收可能漏掉 phantom 冲突；普通快照事务的 undo 清理约定仍保留。

锁顺序：表结构/摘要修改锁 → PageGuard；迭代器创建/退出使用表锁，但不长期持互斥锁。普通物理 GC 使用 commit 锁 → txn map 锁，确认无活跃事务并阻止新 Begin；索引操作和页操作分开，不持页写锁删除索引。该入口保留原停止业务访问的契约，不包装成后台并发 vacuum。

页与恢复：8 字节页头、24 字节 slot、RID 编码不变；新代码读旧页，旧程序不能读已写出空槽的新页。正文在一页临时映像中整理完成后替换，PageGuard 使并发读/写回不看到半次整理。活动页仍不是 A 的一致 checkpoint；当前业务恢复依赖已发布快照和已提交日志。

## 8. 限制与后续

- 普通 GC 仍需显式调用且保持停止业务访问的契约；有活跃事务时不复用 RID。原 undo 扫描及二级键桶扫描仍可能较重，每批 128 条不是总维护延迟上限。S12 才进一步做后台游标与共享预算。
- 没有跨页搬迁、完整 HOT、变长 MVCC 原地更新或 A WAL。
- 没有释放空页/缩小设备文件；B+Tree 删除产生的页退役也不因本轮自动接入物理回收。S9.3 继续处理页链与 F26/F22/F12 的安全释放。
- 本轮文件路径、进程/组件重开不是裸设备、真实断电或整轮性能基线。
- A/B 仍独立上下文；F36 不改 B 私有页格式/WAL。

## 9. 二次审查：物理回收后的向量候选（2026-10-05）

### 9.1 先从代码确认的问题

`DeleteObsoleteEntries` 原先只退出向量索引的 active_entries。`ScanKey` 会排除 inactive 项，但 `SearchVector` 有意返回历史候选，供执行器做 MVCC/键版本复核。因此，普通 GC 或 Raft Apply 释放 slot 后，最近邻执行器可能先通过旧 RID 读物理空槽，尚未走到版本过滤就抛错。原测试的精确查询通过不能证明最近邻路径安全。补充真实旧事务查询后还确认：ValueFactory 缺少 VECTOR 空值导致旧版本重建抛异常；IVFFlat 根据比例自动重建会过早丢掉历史。这两项是原有实现缺口，不是本轮新增退休标记本身导致。

### 9.2 本轮实际修改

- HNSW：在现有内存图节点上区分物理退休与逻辑 stale；按待回收 RID 退休全部历史版本。查询保留遍历旧节点的能力，但退休节点不占结果队列；插入建图仍可借助旧节点连接，避免全部退休后新节点不可达。不改磁盘格式，不暴露新 public API。
- IVFFlat：标记待回收 RID 的全部历史条目，最近邻排名前剔除；旧事务仍需要的逻辑 stale 条目不受物理退休过滤影响。新增私有退休计数，只有全部 stale 都已获物理回收授权才允许 active-only 重建，否则保留历史；避免首次读返回正确、自动重建后第二次读丢行。原先仅按 stale 比例重建的问题本来就存在，本轮补齐回收边界时一起修正。
- ValueFactory：已有 GetNullValueByType 补上 VECTOR 分支，使用 Value 已有的空值构造；修复删除后 ReconstructTuple 为旧版本建立占位时报 UNKNOWN_TYPE。没有新增接口或为测试改变默认行为。
- Raft：独占 Apply 内对向量索引调用物理退休维护接口，再释放表槽；标量索引仍走现有精确删除，避免每次 Apply 无必要地遍历全部标量键桶。

## 10. 三次审查：重建与查询去重的交接（2026-10-05）

### 10.1 先审逻辑与本轮改动

## 11. 四次审查：搜索上限与重建的交接（2026-10-05）

### 11.1 先从生产逻辑确认

1. `IVFFlatIndex::GetMaxAnnSearchBudget` 读取 `centroids_` 未持锁，而 `SearchVector` 可以在持锁时重建并替换该容器。普通 BusTub 的 catalog 锁在执行前已释放，不能替代索引锁；当前 Raft 包装器虽然串行化读请求，也不能把这个索引接口的并发前提交给所有外层调用者隐含保证。
2. `VectorIndexScanExecutor` 原来只在查询开始时取得一次上限。空表建 IVF 后再插入，实际目录初期可能只有一桶；GC 后首轮查询自动重建为多个桶。即使给 getter 加锁，旧上限仍会阻止后续轮次扩展探测，过滤查询可能返回不足的行数。这是状态变化的交接错误，不是索引损坏或底层 IO 失败。
3. HNSW 的动态上限已有锁；其 BuildFromEntries 正式调用发生在 Catalog 发布新索引之前，不在查询路径中自动重建。没有为类比而扩大修改其编号协议。

### 11.2 本轮实际修改

- **生产：** GetMaxAnnSearchBudget 复用已有索引互斥锁；执行器在首轮取得上限，并在每轮候选处理后、决定是否扩展搜索之前更新本查询已见到的最大上限；增长会跟进，缩小不撤销旧目录上尚未完成的搜索。读取返回后不持索引锁做 SQL 过滤或页面 IO；未增加锁层级、公共 API、默认参数、getter、test hook、后台调度或静默 fallback。
- **测试：** 增强原 `IvfRebuildPreservesFilteredMultiRoundQuery`，将建索引移到插入之前，配置 nlist=4/nprobe=1，保留 8 行输入、删除后四行和 SQL 预期 `2、3、4`。SQL 自己触发维护，不读取内部桶数、编号或重建次数。Raft 原有向量场景补充索引类型的失败定位信息。测试总数不增加；一个实际业务场景同时保护两项交接条件。
- **变异：** 保留候选编号回退变异，增加“搜索上限固定为当前探测预算”的变异，分别要求同一业务判据检出。锁是否覆盖同一容器由读写位置和调用链审查确认；本轮功能测试不能代替 TSan 或证明所有并发调度。
- **方案：** 总方案与 F36 §6.6 补齐动态目录/预算约定；保持 S9.2 范围，未实施整页释放或并发 vacuum。
