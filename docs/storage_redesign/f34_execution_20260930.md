## 1. 先审生产逻辑，后写测试

### 1.1 实现及职责

| 实现 | 正式职责 |
| --- | --- |
| `NodeStorage::Impl::Begin` | 依次打开设备/执行器/引导，恢复 B，验证后才启动修复和发布本地能力；Create/Open 严格分开 |
| `StorageContext` | 唯一拥有设备→执行器→引导→B/Journal，上层先关闭，设备最后关闭；部分启动也收尾 |
| `Acquire / Call / Finish` | 接纳一个正式调用并保持上下文寿命；关闭之后的新调用拒绝，已有调用可完成 |
| 内部 `NodeStateController` | 短锁内汇总阶段、并存条件、主原因和能力；运行代次阻止旧完成重新开放服务 |
| `State` | 发布整体视图，读取 F03 的短锁状态以汇总异步修复，不另建轮询线程 |
| `Commit/Writeback/Checkpoint` | 调用原 B 实现；据实际结果报告故障/准入压力，不重写提交、恢复、页写回 |
| `Close` | 先关接纳和发布资格，再等实际调用退出，关闭 B/F03/F02/F01，报告关闭错误 |

状态计算不持锁等待 IO。StartRepair 在本轮每个新上下文只首次调度，现有 F03 此路径不会等待旧修复 worker；将调度与 Close 的停止决定串行，避免取消后启动新后台工作。修复结果由 State 读取，修复失败保留原异常但不独自阻断仍有有效来源的 B。后续定期维护/修复重调度不在这次新增实现中。

### 1.2 代码推演发现并处理的事项

1. B 恢复结束时 Close 可能已经到达。发布前检查代次，把修复首次调度也纳入该决定；未获发布资格则收尾并返回 NotReady。
2. 关闭先换代，已有写入随后失败仍属于正在排空的这一轮。保留原 IO 故障，但不将 Draining 改回 Serving/Failed。
3. 主动关闭取消启动不是恢复故障。取消单独标识，不留下 RecoveryFailed；真实 B 恢复失败仍原样报告。
4. 部分启动在清理时也可能收到设备 Close 错误，不能只靠析构吞掉它。显式收尾保留该错误，并交给正在等待的 Close；原恢复错误仍作为启动调用的首要异常。
5. B 的快照是不可变 RAM 页，可在 owner 关闭后继续读。它不持有裸设备 IO 许可，不能据此无限阻止关闭。

这些修改先由调用关系、锁顺序和异常传播分析确定，再落实相应测试断言。未靠扩大生产 API、默认参数、静默重试或自动格式化让测试变绿。预算/格式/身份仍交由原组件校验；没有堆叠逐字段复验。

## 3. 逐项：目标 → 输入 → 路径 → Oracle → 失败含义

共同路径：`NodeStorage` → 实际 B/Bootstrap/Journal → F05/F06/F04/F02/F01 → Direct 文件。数据生成、独立 `std::map` 模型、临时设备 fixture 复用 S5 压缩包中的原代码；不复制或修改其 oracle。测试的原始磁盘观察不调用生产 codec。

### 3.1 完整恢复与能力发布

- **目标：** 恢复没有完成，就没有可用的元数据能力；完成后读到完整成功输入。
- **输入：** 8 MiB 独立设备文件、9013 字节与 47 字节的不同内容，成功提交和 checkpoint 后关闭；暂停重开时真实 Journal 读取。
- **路径：** 正式 Create/Commit/Checkpoint/Close/Open/Read；故障门只暂停实际系统调用。
- **Oracle：** 暂停点已进入后，phase 为 Recovering、能力为 false、Read 抛 NotReady；释放后逐键 Get/Scan 对比独立输入模型，再修改/重开；旧 RAM 视图仍等于原模型。
- **失败含义：** 开放顺序、生命周期身份、数据恢复或视图寿命不正确。模型不依赖生产序列化，不会同错同过。

### 3.2 损坏恢复链不能触发修复或格式化

- **目标：** 先验证目标，再决定是否修复引导副本；损坏不能被隐藏。
- **输入：** 正式非空 checkpoint；破坏较旧引导副本及当前 checkpoint 的必要 Journal 单元，保留原校验码。
- **路径：** 正式 Open 选择唯一有效引导，再由 B/Journal 验证实际目标。
- **Oracle：** 抛 JournalError，phase Failed、RecoveryFailed 且无可读写能力；Read 拒绝；前 2 MiB 引导区域与故障前保存的字节完全一致。
- **失败含义：** 开放/失败发布、过早修复或自动格式化错误。不能仅凭此一例证明全部任意损坏均可检测，原格式验证由 S5/F07 接管。

### 3.3 取消启动、真实排空与关闭错误

- **目标：** 取消只撤销发布资格，不能当作 IO 已停止；取消与真实故障分开。
- **输入：** 非空数据与一份待修复引导；暂停恢复读，另一个调用发起 Close。两个输入分别是正常清理、真实 close 返回 EIO。
- **路径：** Open 正在实际 B 恢复中，Close 将其置为 Draining；恢复返回后进行正式组件清理。测试侧 close 包装先真正关闭 fd，再返回 EIO，符合 F01 已声明的不能盲目重试关闭行为。
- **Oracle：** IO 未释放时 Close 不能返回；迟到 Open 抛 NotReady，最终 Stopped，损坏引导没有被修复；正常取消不带 RecoveryFailed。清理失败时 Close 必须抛原系统错误并保留 IOFault，随后正式重开仍核对模型。
- **失败含义：** 取消被当成功、未排空、取消被误报故障、部分启动关闭错误丢失。原始字节只判断是否发生未授权修复，不假设未来正常修复的线程排程。

### 3.4 checkpoint 排空和禁止新调用

- **目标：** 关闭不能越过实际 Flush；在途调用失败仍须保留原因。
- **输入：** 非空成功提交和保留视图，暂停 checkpoint 的 Journal Flush，期间发起 Close。分别让暂停的 Flush 成功、返回 EIO。
- **路径：** 正式 Checkpoint、Close、Read；真实 F02/F01 IO，错误通过原 B 结果传回。
- **Oracle：** Draining 后 Read 拒绝，维护能力关闭；checkpoint 与 Close 均未完成；释放后成功分支 durable，失败分支非 durable、同一异常指针保留为 IOFault；最终 Stopped，重开对比模型，旧 RAM 视图不变。
- **失败含义：** 准入门、排空或排空期间故障发布有误。两种输入保护不同错误路径，不是仅换数据测同一成功行为。

### 3.5 修复独立、条件并存与故障隔离

- **目标：** 有有效来源时修复不能成为前台同步依赖；展示主原因不能清掉其他事实。
- **输入：** 非空 checkpoint、一份损坏引导，暂停其真实修复写；持续非空有效更新直到小 Journal 拒绝，再让 checkpoint 的实际 Journal Flush 返回 EIO。
- **路径：** 正式 Open/Commit/Checkpoint/State/Read/Close/Open；资源压力来自真实容量拒绝，不用空参数或模拟控制器。
- **Oracle：** 修复暂停时 Open 已返回且 Get/Scan 正确；资源拒绝后仍允许维护；IO 失败后 phase Failed，IOFault、ResourcePressure、BootstrapRedundancyLost 同时存在，主原因是 IOFault，错误指针等于实际结果，新 Read 拒绝；老视图及重开结果等于输入模型。
- **失败含义：** 修复同步阻塞、条件覆盖、错误优先级或故障准入不正确。仅观察到的资源拒绝不等于实时容量测量，状态不代替 B 的实际接纳判断。

## 7. 稳定性、资源和运行限制

- 每例独立 8 MiB 文件，RAII 删除；显式 F02 三 worker、16 MiB 工作额度，B/Journal 使用 S5 已审查的小容量预算，顺序执行。
- 非空输入公式和种子固定，大小不同；设备对齐实际查询，测试 unit 取 4096 与查询对齐的公倍数。生产没有统一写死 Direct IO 对齐。
- 故障门先确认进入真实 IO；失败路径的释放守卫先于 future 析构运行，避免断言失败后永久挂起。
- 10 秒事件 watchdog、100 毫秒“尚未完成”观察只用于已握手场景，不作性能指标。早退变异检查实际 future 已完成，不把漏掉一个短暂状态后的等待超时算检出。
- 没有 sleep 猜测 IO 顺序；State 的等待使用有界 yield。极端主机调度仍可能触发 watchdog，须据日志区分资源饥饿与生产错误。
- 故障门是测试进程内共享状态，串行运行用例；不能把同一二进制改为并行执行这些场景而不改门隔离。
- 暂停修复但允许 Open 返回由真实挂起的写验证；若错误实现同步等待它，外层 watchdog 会终止该次运行并记录失败，不计入变异检出数字。
- 只测试声明的 Linux Direct 文件路径，不能推定硬件断电、跨主机或整套业务可用性。没有新增性能测量。

### 9.1 先分析生产逻辑：关闭遗漏最终修复状态

`NodeStorage::Impl::Close` 等待 B/F03/F02/F01 收尾后，原先直接释放 context。F03 修复可能在此期间失败；如果调用方没有恰好查询 State，控制器保存的仍是排空前状态，停止后无法再取得原始修复错误。这违反 F34 §11.2 的完整状态和错误保留要求。

修正在原 Close 的短状态锁内、context 释放前调用已有 RepairStatus 汇总最终事实。此时 F03 worker 已退出，Status 仅取得其短状态锁，不发生 IO；没有增加后台线程、重试、共享状态 getter 或第二套修复机制。关闭是否完成仍由实际排空决定，不由状态位推测。

### 9.2 测试全景、输入、路径与判断依据

本轮没有新增测试数量，仍为五个正式本地组件集成场景，复用原 S5 八项回归。

| 本轮修改的测试 | 目标、输入和 production 路径 | 独立 Oracle 与失败含义 |
| --- | --- | --- |
| RealRecovery / InvalidRecovery / CloseCancels / CheckpointClose / RepairAndConditions 中的拒绝断言 | 原非空数据、真实恢复/排空/失败链不变；沿 NodeStorage 正式接纳门调用 | 从只要求 MetadataError 收紧到要求错误码 NotReady；若返回 ResourceUnavailable 等错误也会失败，不能把错误分类混淆当成功 |
| RepairIsIndependentAndFailureConditionsRemainVisible | 保留原修复暂停、资源拒绝、Journal Flush 故障；关闭时让已挂起的真实修复 pwrite 返回 EIO，并等待实际退出 | 在释放修复后不轮询 State，等 Close 返回才读取；必须 Stopped、保留原数据 IO 错误和冗余不足，并带 repair_error_ 的 EIO。漏汇总最终事实就失败；Close 提前返回也失败 |

修复 IO 仍调用正式 NodeStorage/F03/F02/F01，只有暂停点的 pwrite 在测试二进制中注入已声明的 EIO。其余真实文件读写不替换。返回 NotReady 的 expected 来自生产接纳契约，EIO 来自明确注入；二者不调用生产状态转换算法产生答案。非空数据模型仍直接复用 S5 原模型，重开后核对原成功输入。

### 9.3 Production 与接口污染

本轮生产改动只有 Close 收尾汇总，删掉测试也必须保留，以免上层漏掉设备修复错误。公有 API、默认参数、配置、ABI、可见内部状态均未新增；原测试链接包装增加对已挂起修复写的返回错误能力，只存在于临时二进制。

NodeStorage 当前的正式业务接入仍待 S8/S9，这个限制没有改变；不能称它已经是 SQL/Raft E2E。原有 public 入口的生命周期所有权、准入和错误汇总职责见 §4，本轮没有新增只为测试服务的抽象。

### 9.4 重复、杀伤力、稳定性和退出

- 收紧原拒绝断言，不另加枚举/错误码矩阵；在原修复场景内验证最终收尾，不复制 F03 单模块修复矩阵。
- 新增定向变异 `drop_final_repair_status`：只删除 Close 中最终汇总，指定判据为“Close must retain the final repair error”。它针对本次逻辑缺陷；编译失败/超时不计检出。
- 静态杀伤力示例：把接纳门 NotReady 改成 ResourceUnavailable，现有 ExpectNotReady 明确比较 Code()，会失败；不虚称该示例另有一次实测。
- 故障门先等待实际 pwrite 进入，关闭等待用真实 Draining 和有界 future；没有 sleep 猜测顺序。释放后不再轮询，避免测试帮生产补采集最终状态而掩盖缺陷。release 守卫先于 future 析构释放，防止失败路径遗留挂起。
- 复验中发现测试自身的竞态：坏实现可能先发布 Stopped、稍后才使 Close future 就绪。旧测试有时把这个明确提前结束归到“drain event watchdog”，严格变异 runner 因未命中指定判据而拒绝计数。改为保存一次观察状态，Stopped 明确归为提前结束，真正等不到 Draining 仍走独立 watchdog 判据；未修改 production 来迎合测试。
- 并存错误分别保留：数据 IO 失败仍是原 error_，修复失败保存在 repair_error_；故障事实不因 Close 停止成功而清除。修复停止不被误当作整个节点 Close 失败。
- 仍依赖 Linux Direct 普通文件、调度和 watchdog；未加入裸设备、硬件掉电、TSan 或业务 E2E 结论。
