# S13.1 / S13.2a 业务准备与协议执行交接

> 本文保留 S13.1/S13.2a 的已验证边界；多客户端提案由 [S13.2b 协议](s132b_protocol.md) 接续，单提案限制不再是最终设计。


2026-10-09：用户已授权本轮方案、实现和测试。F35 为唯一归属，协作 F26/F31/F34；S12 历史失败保留原归属；本轮实际结果见 [执行审查](s13_execution_20261009.md)，不因部分门槛通过就将整体性能验收标为完成。本文接续此前“待确认”讨论；多客户端提案、单客户端多结果窗口和不可变正文乐观读取不属于本轮。

## 1. 本轮契约

- UPDATE/DELETE 只执行候选读取计划，复用 Optimizer/Executor；同一受保护业务状态中取得完整旧行、版本和完整谓词结果，保留原复制格式及错误语义。RID 不跨节点复制。
- 保留单个未解决业务写提案。异步接纳不等于 durable、Raft commit 或业务发布。
- 节点锁不跨 SQL、存储或业务安装。协议进度来自已消费的完成结果，不在 Tick/Receive 中同步取得状态机生命周期锁。
- 首步业务操作仍有序，长查询可以延迟 Apply，但不能占住协议处理。ReadIndex 是下界，执行侧在取得状态保护后选择当前已发布位置，核对不小于下界；不假装支持任意历史读。
- 下游保存输入、额度及完成位置才算认领；无需等 worker 开始运行。队满保留有界 pending，已接纳工作不得因客户端超时而遗失。
- 日志、term/vote 与确认消息的持久化依赖不变。Apply、安装按序，进度在完成之后发布。观察到更高任期后禁止旧 Leader 继续确认；已经发生的持久化和已提交 Apply 仍需接续。
- Follower 的提交上限是本次 AppendEntries 确认匹配的位置（`prev_log_index + entries.size`），包括空心跳；本地更长的未匹配后缀不是提交依据。旧 Leader 失去任期后退出对应客户端等待，不能把新任期发布同一 index 当作旧请求已经执行；实际存储工作继续由 Raft 持有，同身份重试沿用 SessionTable 去重。

## 2. 实现组织

复用原 SnapshotTasks 的有界执行机制，抽取共用执行器；快照正文仍有自己的工作额度，F02 继续执行设备 IO。业务执行与存储执行分别串行，避免数据库等待占满设备完成通道。共用调度实现不等于所有任务混在同一 FIFO。

Raft 的串行协议操作在耗时步骤处挂起，后台只执行固定的存储/状态机工作，完成由协议拥有者恢复。内部挂起表示用于保留已有顺序，不建立第二套持久日志。存储操作在途时只使用此前已确认的日志边界处理心跳；依赖新状态的消息有界保留/由发送方重试，不把未持久日志作为匹配依据。读取、提案和快照入口使用明确的进行中状态，不能并发读正在变更的 Store。

关闭停止接纳新业务，继续消费已接纳工作与完成，随后退出执行器、引用和存储。不得先停止完成处理再等待需要它推进的 worker。

## 3. S13.1 的访问路径

Binder/Planner → 原写计划的只读子计划 → Optimizer → 扫描/索引/完整过滤 → 完整旧行与版本 → CommandBuilder。复用现有索引等值能力，补充合法 AND 主键等值候选；不能证明适用时扫描。索引必须满足实际键形状，NULL/类型遵循现有表达式语义；不执行 Update/DeleteExecutor。

等值候选与范围候选同样需要满足键类型约定。Binder/Planner 不会自动把比较常量转换为列类型，而 Tuple 按 Value 自身类型编码；因此本轮只将同类型常量编码为索引键。混合类型条件保留正常扫描及表达式比较，不做可能截断或改变语义的强制转换。OR 必须覆盖所有分支，不能只取其中类型匹配的一支。

## 4. 验证与清理

先代码逻辑审查：所有权、锁顺序、挂起期间存储访问、迟到结果、持久化确认、关闭。确认后测试，失败先分析原因，不先堆回归测试，不放宽原 C/P 判断。

原 C1、低缓存 P2 首先复验，C2/C3 验证线性一致性，C4/C5 验证重启与追赶。只补共同场景不能覆盖的确定性交接风险，Oracle 来自输入业务模型或独立持久事件，不以队列名、内部调用次数断言正确。每项新增/修改测试按总方案八项审查；阶段源码、结果按 F35 压缩归档并原位替换，删除展开测试和构建产物。

性能按相同资源/负载报告，准备未完成不得生成吞吐。既有失败证据保留原版本归属。本轮完成状态由执行记录与真实结果决定。

## 5. 已确定的接口与交接细节

- `RaftNode::Propose` 返回接纳的 index；不再暗示调用返回时该 entry 已 durable。异步准入失败通过 `TakeProposalError(index)` 消费，普通非法命令不能导致 fail-stop；存储结果不明确仍沿原错误路径停机。
- `CreateSnapshot` 返回是否接纳，完成结果从既有 `LatestSnapshot` 观察。原已验证候选继续用于 Install，不恢复“验证后销毁、安装时再构造”的重复路径。
- 共用 `TaskExecutor` 保留输入、完成槽及 ResourceCharge；执行完但结果尚未消费仍占名额。一个存储执行通道、一个业务执行通道；快照编码沿原两个 worker/四个任务上限。网络 pending 上限 32，未接纳消息由协议重传，任期观察不依赖正文排队成功。
- 协议操作用私有 C++20 coroutine 保留顺序；执行器只设置结果并唤醒，不在 worker 上恢复 coroutine。正式节点由已有串行 owner 调用 Poll，不增加第二个协议线程。除原 F26 的 C++23 翻译存储目标外，本轮仅 Raft target 提升至 C++20。
- 日志身份替换/安装期间，不能用此前缓存的 tip 提前确认心跳；新内容完成并更新确认边界后才允许。慢 Apply 期间可对已确认前缀响应，commit 推进仍按序执行。
- SQL Prepare、查询和 Apply 暂时共用串行业务角色；Prepare 捕获状态后，交给协议前复核 term 和 published index。ReadIndex 是查询的最低执行进度，结果携带实际读取的 published index。
- 正常关闭先停止外部请求与协议入口，排空已认领任务及回调，再关闭状态机/底层。客户端超时只停止观察；已提交任务的输入和缓冲继续由执行上下文持有。

计账边界：队列/结果持有期纳入 ResourceAccount，读取结果按既有 16 MiB 上限预留，快照正文沿原块预算；数据库执行器内部临时对象仍属于原 SQL 工作内存边界。本轮不把这些计数称为整个进程的 RSS，也不宣称已解决任意大 SQL 计划的内存预算。

### 5.1 低缓存 P2 暴露的有界读取成本

首次 S13 低缓存 P2 已消除此前的任期持续变化，但装载后按128行校验一个范围仍扫描整张2万行表，准备阶段超过原300秒期限。因此本轮沿同一个 Optimizer/IndexScan/B+Tree 接续有界读取，不修改共同负载、模型或超时：

- 单列整型、已有受支持键布局的 B+Tree，从已绑定的 AND 比较中收集上下界；类型不匹配或无法证明安全时保持原扫描。OR 的某一分支不能单独作为限制。
- 复用原索引快照枚举：定位下界，达到上界停止；普通全索引扫描使用同一方法的空边界。非唯一桶仍返回全部 RID，MVCC/旧键核对与完整谓词继续负责可见性。
- 上下界不通过整数加减构造，保留开闭语义；不假定请求起点是已有键。没有新增范围缓存、独立索引或第二个 SQL 执行器。
- 用非零、稀疏且跨叶范围核对内容；原 P2 的范围校验继续充当真实链路 oracle。测试通过后仍不能把此次吞吐称为完成所有范围查询优化。

### 5.2 关闭中的工作空间退役

P2 的真实关闭复验显示：协议/执行线程已排空，随后 `WorkingState` 析构同步执行整个 `ObjectPageStorage::Retire`，其大量元数据提交拖住退出。正常关机只关闭缓存与实际在途工作，最终活动工作空间保留已有持久 registry；下次 Open 复用 `RetireAbandoned` 接续清理，不需要新增退役清单。状态机运行中更换工作状态仍按原规则退役旧空间。关机保留的是可识别、可恢复清理的临时空间，不是新的业务恢复入口；业务恢复仍由正式 checkpoint/快照及日志决定。

这是生命周期策略，不能用忽略持久化错误或放宽共同测试关闭期限代替。缓存关闭仍须完成已接受工作；不会在正常业务期间无限积累工作空间，也不把本轮称为已完成按预算后台清理所有历史工作空间的调度优化。

### 5.3 进展通道被占用时保留待接纳事务

原 C1 在并行维护时暴露另一条真实错误：F19 的进展通道只有一个已接纳名额，F35 的 HardState/日志工作与维护竞争时，`RaftObjectStorage::Commit` 把尚未接纳的 Full 抛成节点错误。修正限定在此处：同步 Store 调用保留未被消费的同一事务，在锁外执行角色短暂退让并重新请求接纳。F19 已接纳后不再次提交；Stopped、永久超限、真实 IO 及结果不明确仍报错。F22/GC/F02 保有独立进度，不等待协议角色发放下一条任务才能释放该名额。没有增加第二套进展配额或重复提交队列。
