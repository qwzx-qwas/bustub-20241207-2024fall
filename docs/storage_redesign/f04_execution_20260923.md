## 2. 逐项：目标 → 输入 → 执行 → Oracle → 失败含义

### 2.1 共同 setup

每个 Store 创建专用 16 MiB 临时文件，全文件先写由位置和 seed 确定的非恒定内容，仅两个 F03 槽位置零。正式 F03 Create/Open 初始化。两种 layout 使用同样容量但不同非零身份及区域位置：metadata 起点 2/3 MiB、Journal 4/5 MiB、data 8/9 MiB；保留间隙。每次最多两设备文件、2 IO worker/设备、8 个成员、1 MiB 自有缓冲/1 MiB 外部许可额度；构建 -j2。数据 IO 长度按实际偏移对齐将 4 KiB 向上取整，不硬编码设备对齐能力。

expected 的设备位置由测试定义的常量和相对偏移计算，不调用 RegionManager::Resolve/Subrange；对照整文件，含引导槽/间隙/未访问区域。初始化使用生产 F03 不是独立格式 oracle，所以这里只证明区域层没有改坏初始化后的镜像；F03 格式本身的正确性由原八项独立编码测试继续保护。

独立 POSIX pread 全镜像只作为观察器，不绕开被测请求路径。setup 的原始 pwrite/fdatasync 不计作被测持久化；故障注入仅在测试链接侧，生产没有 hook。

### 2.2 RegionsUseIndependentPhysicalOraclesAcrossLayouts

- **目标**：同一批跨三个区域读写正确，两个布局都按自己的位置寻址；需要 Flush 的请求不能变成普通写。
- **输入**：Metadata 首部、Journal 非零偏移、Data 最后一个合法处理单元，三个不同位置相关正文；换第二布局重复验证。不是只换无关参数，第二布局专门检测硬编码基址。
- **执行**：manager.Region → TryPrepare → 既有 IOBatch 填充 → 原 IOExecutor::TrySubmit/完成 → 正式区域读取。读写都走生产链路。
- **Oracle**：写后用独立 fd 读全镜像，对照固定基址计算的 expected；读结果与原 payload 比较。检查 writes_durable 和测试侧观察到至少一个成功 fdatasync，不绑定调用次数。不能用“错误地址写，再错误地址读”自证。
- **失败含义**：镜像错误说明寻址/写入范围或内容不符；成功 Flush 缺失说明持久化要求丢失；读取内容错误说明读路径不符。组件测试不负责把下层异常都定位到某一行。

### 2.3 InvalidBindingOrMemberRejectsTheWholePreparation

- **目标**：区域身份与边界不能因装在同一设备容量下而混淆；准备失败不消费外部缓冲许可。
- **输入**：未 Open 和已 Close 的 F03；另一设备、同设备另一 manager、manager 销毁后仍持有的 handle；有效前成员+非法后成员（绑定身份场景故意使用不重叠范围，避免被下层冲突检查误挡）；恰好末端再写、整数极值、空范围、未知 kind，以及设备要求时的非对齐偏移。
- **执行**：调用正式构造、Region、两种 TryPrepare；关闭后拒绝是 F03/F04 新连接处的风险。没有窥视私有 context 地址。
- **Oracle**：明确 logic_error/invalid_argument；被拒外部 leases 仍有一项、release 尚未调用，并将同一许可用于合法写入，确认真实完成和 durable。全镜像只有最后明确提交的写入改变，第二设备完全不变。
- **失败含义**：异常缺失表示非法绑定/范围被接受；许可丢失表示 F04 在接纳前破坏上层所有权；镜像变化说明范围/设备误用。零长度是负面边界，不用于伪造成功业务请求。

### 2.4 F02AdmissionLeasesAndDeviceFailuresKeepTheirMeaning

- **目标**：F04 的地址翻译不能改变执行器的既有准入、所有权和失败语义。
- **输入**：用正式准备占满八成员；同一有内容写请求分别走自有/外部路径；接纳后一次写 EIO、一次 Flush EIO；外部读和停止后的准备。
- **执行**：所有被测 IO 经 F04/F02/F01；只在测试 syscall 边界注入 EIO。暂留 Prepared 批次制造 Full，无 sleep、无新 getter。
- **Oracle**：Full/Stopped 原样返回，外部许可拒绝不消费；写失败携带 EIO 和独立计算的物理范围，不报 durable。Flush 失败时正文已可读但仍报 Failed/flush_error，证明不能用可读性抵消失败。外部读前把缓冲清零，再与非零 payload 比较，避免未读取也通过。完成后的 release 次数对应许可所有权，而非绑定线程/调用次数。
- **失败含义**：丢失/改写 F02 返回值、错误范围翻译、提前消费或归还许可、吞 Flush 错误。注入写 EIO 在 syscall 执行前，因此该分支预期镜像不变；不据此宣称真实失败写永不部分修改。

## 10. 再次审查（2026-09-23）

发现并修正两个**测试自身**的问题。

第一处：2.3/2.4 的四处外部许可回调按引用捕获栈上 `releases`。正常完成时安全，但 `Finish` 在接纳后等待超时会抛异常；销毁 IOBatch 观察句柄不等于取消在途 IO，计数器可能先于回调销毁。这是源码审查发现的潜在悬空引用，不是本次运行已经触发的 production 故障。现在计数器使用 `shared_ptr<atomic<unsigned>>`，回调按值持有，与已有缓冲寿命一致；保留原三场景与原断言，不为该修正新增常驻微测试。

第二处：2.3 的有效前成员和错误绑定后成员原来都使用相对偏移 0。跳过绑定检查时，下层仍可能因两段写范围重叠而抛出同类型异常，导致部分绑定断言假通过；旧变异仅由后面的外部许可分支发现。现在前成员移到下一个 IO 单元，三个错误身份场景都与后成员不重叠。重新运行删除绑定检查的变异，三个原先被遮蔽的断言也直接失败。只修正输入，不增加重复测试或生产接口。

方案逐项复核：F03 私有绑定连接同一执行器；handle 身份不可伪拼且区分 manager；整批先做区域包含检查；两个缓冲入口复用 F02；没有新增 IO 队列、磁盘格式或原子事务。未发现需要修改生产代码的问题，12 个相关生产文件与上一轮最终哈希一致。生命周期仍由上层保证 executor/device 有效，后续 F34 的关闭/重建接入不能据本次组件结果标成完成。
