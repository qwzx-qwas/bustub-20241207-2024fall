## 1. 实际实现与参考内化

```text
正式 BufferPool 请求接纳
  → 有界维护点（尚未持有页/条目权利）
  → PathCache：检查 owner 身份 → prefix 命中叶路径
                未命中 → 原 8/7/16 多级目录
  → 组共享门 → TranslationEntry → 既有帧固定/内容/IO 协议

空组退出提示
  → 根/中层/组 bitmap → 轮转候选
  → try-lock 组独占门 → 检查零存活条目
  → 结束原子对象寿命 → MADV_DONTNEED → 成功后归还预算
  → 下次访问按原初始化路径重新构造
```

- `translation_directory.cpp` 实现线程本地 8 项 LRU 路径，最多缓存最近一个目录；弱 owner 身份验证先于叶指针访问，缓存不保活大目录，不缓存条目指针或可直接使用的帧号。
- 同一 `directory_bytes_` 计入路径、三级候选、控制区和物化组；缓存预算不足走原数组查找，压力下先退出可选缓存，再做一次至多 64 个候选的回收重试。每线程每 64 次 BufferPool 请求维护至多 16 个候选，没有新增设备 worker 或每请求线程。
- 回收访问者及组门均 try-lock，忙则稍后处理。提示位不证明可释放；驻留、Loading、Evicting/写回仍有映射和存活计数。保留组控制块和虚拟地址，成功后扣减物化内存；实际 OS 错误恢复空原子对象、保留预算和候选并上报。
- 组构造改为循环核验：独占初始化后再次拿到共享门时，可能已被另一个线程回收，必须重查，不能继续使用已结束寿命的条目。
- `BufferPoolManager` 在真实请求入口调用维护；维护失败会归还调用计数。新页登记前的目录申请失败会归还私有暂占空帧，防止回收错误或预算压力留下无法使用的帧。
- A/B、设备页布局、Raft 恢复权威、Common/F02 发布语义不变。F12 是设备分配事实；本轮 bitmap 是易失 RAM 提示，不抽取缺少共同消费者的“通用分配器”。

参考 [Calico §4–5](https://arxiv.org/html/2604.00423v1) 的路径缓存/冷翻译内存机制，解决稀疏数组反复寻址与冷 RAM 占用；本项目使用既有页身份、组门和请求边界，没有引入作者库。依据 [Linux madvise](https://man7.org/linux/man-pages/man2/madvise.2.html) 按实际 OS 页归还匿名私有映射，保留地址。8 项缓存沿冻结方案；64/16/64 的维护节奏是本项目首轮有界选择，不是论文性能保证，后续 S12 再依据测量调整。

## 2. 先进行的代码逻辑审查

实现后、写测试前先核对：owner→组→条目→帧的锁序、候选标记的子层到父层发布、消费后重挂、弱引用退出和预算扣还。

逻辑审查发现并修正两处接续问题：

1. 不能把周期维护塞进任意 `Access`。淘汰已经进行一半时，维护报错可能遗留 Evicting；改在 BufferPool 接纳后、页工作之前维护。只有真实物化预算不足才在寻址中回收重试，并补登记前暂占帧的释放。
2. b 的初始化“独占构造→释放→取得共享门”在没有回收器时成立；d 必须重新核验，否则回收可能发生在两个门之间。现复用同一构造函数，正常重用和 OS 回收失败恢复都保证合法原子对象寿命。

缓存与物化竞争最后一份预算时，先退出优化；不是把预算异常一概忽略。OS 回收失败明确传播，页正文未在此路径改变。没有新增永久回收队列、无界 owner 注册表或备用恢复权威。

## 9. 再次审查：批量准备失败的完整收尾

本轮先复查调用/锁/所有权，再修改生产代码和补强测试。发现 `BufferPoolState::Flush` 的异常收尾只包住 `storage_->Write`，其前面的组批循环不在其中。它已经可能固定前几页（pin++、io=true）；如果后续目录重新物化申请或准备阶段抛错，vector 析构只能释放 C++ 容器，不能替它清除帧状态。d 增加组回收/重建后，这种准备失败必须与 IO 失败同样处理。

实际改动：将整段组批循环与最终 Write 放入同一 try/catch。共用原收尾，逐个解除当前批次帧的 IO 使用权/pin、释放任务额度；有错误就保留脏版本并传播原异常。没有新增 public API、生产 wrapper、hook、默认值或吞错重试。之前已完成的批次仍按既有语义完成，FlushAll 不是跨批原子事务。

### 本轮测试设计审查

- **目标**：批次准备失败后，先前保留的帧必须全部可重新使用；不能只检查“抛了异常”。
- **输入/路径**：复用 `TranslationMemoryReclaimsReusesAndReportsOSFailure`。真实文件后端、3 帧和不同非空正文；先让三页驻留，测试侧 `PreparationFault::WriteDomain` 在准备第三项时抛 bad_alloc。所有 Read/Write 仍委托正式文件后端；这是准备边界的确定性故障模型，不宣称真实触发了 OS 内存耗尽，也没有创建假数据库。
- **Oracle**：断言注入确已发生；随后读取另外三页并一直保留三个 ReadPageGuard，逐字节比较原输入。少归还帧会令后续 CheckedReadPage 无法接纳，由断言失败定位，不用 getter 检查内部 pin，也不靠等待超时发现死锁。最终仍正常 Flush/Close。
- **重复/去重**：把这一收尾风险合入现有场景，不增加场景数。原 FailedWrite 覆盖已进入数据 IO/Journal 后的失败，本项覆盖第一笔数据 IO 前已经保留部分批次的失败，边界不同。
- **杀伤力**：新增 `leak-prepared-batch` 变异跳过这次准备失败的收尾；要求“已保留帧无法复用”断言命中，超时/崩溃不能计检出。
- **稳定性**：准备失败的注入计数只在全部并发读取 join 后设置；不会与读者竞争。继续沿用原额度/时间上限，无 sleep 或随机选择。
- **Production pollution / 接口**：只改 Flush 的异常范围。唯一新增测试包装在压缩包内，删除测试不影响 production；生产 PageStorage 未扩展。
- **最终建议**：现有 RAM 场景保留并补强；已有 4+6 场景数量不变，无需再建小测试。跨层 E2E、性能和设备限制仍按 §8。

本轮结果：ASan/UBSan/LSan 的 6 项页场景、11 项课程、8 项 S8 均通过；TSan 的 6 项页场景通过；11 个页变异均由指定断言检出。`leak-prepared-batch` 在新判据 `g.has_value()` 处明确失败，提示 `failed batch retained a frame`，不是崩溃或超时。未改变的基础组件证据沿用；当前总数和来源见 §8。
