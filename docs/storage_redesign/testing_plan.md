## 2. 必须遵守的测试与代码原则

校对顺序遵守[主方案 §1.7](README.md#17-控制防御性代码先分析逻辑再验证)：先从代码逻辑分析，再决定必要验证；不要一开始就编写回归测试来代替原因分析。避免过度纠缠假设边界、堆叠防御性代码或用兜底掩盖问题；保留本项目已承诺安全边界的必要检查。既有验收要求不变，本轮实测与历史证据复核分开记录。

每次新增或修改测试及测试工具后，必须执行[主方案 §1.5：测试设计审查](README.md#15-每次新增或修改测试后的强制设计审查)。全景、目标到 oracle 的解释、生产污染、接口污染、重复、最小变异、稳定性和最终矩阵八项均需检查；运行通过不能替代设计审查。问题修正后复核受影响项，记录分析与实际执行的区别。详细规则统一维护在主方案，现有和新建子模块及其 prompt 均须遵守。

> 代码要考虑复用性，间接性，安全性，不要破坏别的模块和层次的production级代码。

> 当本次任务接续上一次任务后，需要在完成前检查之前的代码是否因为当前改动有冗余的地方，有的话可以删除，也要检查是否有根本没用到的接口或函数之类的，也需要删除。

> 测试应该保护“这个项目自己承诺的行为和风险边界”，而不是给每一层实现细节、第三方库行为和历史重构痕迹都建立一套测试。

落实要求：

- 先检查已有可复用接口、调用者和数据归属，通过明确接口隔离层次；正式代码不得反向依赖测试辅助设施。
- 清理范围是本次改动及其引起的旧路径冗余。检查虚函数、模板、注册入口和对外契约，确认无用后删除声明、实现和相关引用；不能仅因单次文本搜索没有调用就删除生产接口。
- 保留仍被现有正式路径依赖的行为，不覆盖或清理用户已有的未提交改动。
- 对每项新增、保留、修改或删除的测试，说明它保护的项目承诺或风险及验证它的边界；避免重复覆盖和自证式断言。
- 完成前报告清理结果、受影响契约与验证证据；没有可删项时记录检查范围及原因。

> 当遇到方案中未提到的部分时，先不要自作主张去写,而是汇报当前遇到的问题（注意先不要堆砌专有词汇，用我能看的懂的话去讲当前情况，有需要时再用专有词汇）。

测试里的适配、故障控制或可观察性也遵守这条要求。不得为方便测试而修改生产 API、默认路径、默认语义或增加生产测试代码。正式架构确需的接口变更应在对应模块方案中独立讨论；缺少测试能力时先报告限制，不能以测试需求自动授权生产改动。

## 3. 先讨论项目到底承诺什么

以下都是待讨论的问题，不能当作已经确定的验收标准：

1. 一次对象写、原子批次、写入完成、本地 durable、版本发布、Raft commit 和客户端成功，各自承诺到什么边界？
2. 哪些部署和设备属于第一阶段支持范围？文件模拟后端的证据能覆盖什么，不能覆盖什么？
3. 单节点对象操作和三节点业务操作分别提供什么一致性；旧读者、快照和 Deferred 数据的可见性怎样描述？
4. 崩溃恢复允许丢弃哪些未提交内容，哪些已经承诺的内容绝不能丢失？
5. 空间释放承诺到逻辑删除、可复用还是设备 discard？何时算作 GC 完成？
6. 结果不确定、超时和重试如何对用户表达？哪些情况不得作为普通失败后直接重新执行？

## 4. 故障与独立判定依据

待讨论：

- 区分进程退出、系统崩溃、掉电、短读写、撕裂、介质损坏等模型；不能用一种实验声称覆盖所有故障。
- 哪些故障能通过确定性模拟表达，哪些需要真实 IO/进程链路，哪些暂不在首期承诺内？
- 验证持久化时如何避免依赖旧进程内存、缓存或仅有的成功回调？
- 如何为磁盘格式、恢复状态和业务结果提供独立预期，而不是用同一生产编码/解码逻辑生成 expected？
- 哪个模块最接近需要保护的行为边界？跨层恢复或真实业务链路还需要补什么证据？
- 哪些故障可以通过已有协议、配置、进程控制或外部网络/设备环境实施？无法从外部实施或确认的阶段应列为覆盖缺口，不能为此自动新增生产接口。
- 模拟持久化屏障能验证调用协议，但实际设备兑现 durable 的能力需要什么额外证据？

每个条目回答：

1. 如果删掉它，哪个项目承诺会失去保护？
2. 是否只是检查实现私有步骤、调用次数、第三方库行为或过时路径？
3. 是否和另一层测试重复，还是确实保护不同的跨层风险？
4. 当前重构后，旧测试应保持、改写还是删除？删除的依据是什么？

不要为全部模块预先固定同样数量的单元、组件、集成测试。必要的跨层验证可以覆盖多个模块，不要求给每层实现细节再建立镜像测试。

2026-09-22 后续取舍以[主方案 §1.6](README.md#16-测试演进跨模块复用与阶段退出)为准：常驻主线是共同生产 E2E 正确性／性能套件；开发期小测试验证后默认删除或按模块压缩归档，不因风险仍有效而自动长期常驻。F00 与 T0 的小测试已转为[模块源码压缩包](../../test/archives/README.md)，尚未由 E2E 接管的边界及已知自检缺口保留在归档清单；归档不等于这些问题已修复。课程和旧 Raft 回归不在本轮整体处理范围。

跨模块按稳定场景／风险标识登记唯一内容维护者、相关模块、当前模拟或真实路径、待接入能力／阶段、关联 E2E、覆盖差异和退出方式。后续生产能力就绪时先复用输入及独立 oracle，再通过测试侧适配接入真实链路；同一场景不按模块复制。手写预期可以服务真实 E2E，脚本响应的工具自检不会自动变成数据库测试。真实模型、驱动和报告工具继续随共同套件保留。

小型测试源码压缩包随仓库保存，大型运行结果仍只保留本地压缩证据，规则见 [结果归档入口](../../test-results/README.md)。恢复小测试使用仓库外的隔离目录和记录的源版本，不加入默认发现；恢复／修改后仍执行 §1.5 八项审查。

每个模块的具体收尾顺序遵守[主方案 §1.6.5：单个模块的测试交付约定](README.md#165-单个模块的测试交付约定)：先关联共同场景，开发期必要验证，审查并记录证据，阶段小测试退出，后续接入真实生产并归并重复内容。不得把长期维护模块小套件作为默认完成标准。

### 11.1 内容、适配与生产分离

```text
测试内容层：初始数据、操作规则、故障计划、预期/历史模型、计时和判定
                              ↓
测试适配层：协议编码、结果规范化、正式配置映射、进程与外部环境控制
                              ↓
生产层：正式客户端入口 → 三节点 Raft → BusTub → 实际存储与恢复
                                  └→ Log / HardState / Snapshot 持久化
```

- 内容层不依赖生产类、对象/文件格式、文件名或私有方法；不硬编码旧日志文件布局为业务正确性的证据。
- 新旧接口的差异在测试侧适配。工作负载、独立预期、故障定义、超时/重试及计时规则保持相同；适配器不能补刷盘、把异步成功改成同步成功，或把新错误隐藏为成功。
- 有序结果按顺序比较，无序结果按约定规范化；不能丢弃重复行、错误字段或版本差异。先核对操作能力和语义，不支持的项目明确记录，不能静默跳过后宣称通过。
- 测试运行器、适配器、监控代码使用独立测试侧目标/目录；生产代码和正式工具不得反向依赖这些设施。具体目录和语言仍待讨论。
- 已有正式 CLI 可设置专用数据目录、BufferPool 与快照阈值，见 [bustub-node.cpp](../../tools/bustub-node/bustub-node.cpp)。使用配置不等于修改默认路径。控制脚本只管理自身创建的进程和数据。

### 11.2 正确性验收与防止空跑

- E2E 使用真实节点进程、正式客户端请求、实际数据目录/设备和真实存储后端。内存磁盘、Mock 或直接调用下层组件不能替代这项证据。
- 初始数据必须有效且非空；确认成功装入后再开始操作。更新/删除要命中目标，读取需核对值、版本、存在性和必要的行数，而不只是返回码。
- 不把全空表、零请求、零完成量、缺失的预期结果当成通过。预期删除后为空是有效结果；空参/非法输入的专门负面测试与有效工作负载分开。
- 顺序操作由测试侧维护独立状态；并发和故障场景记录调用、完成、响应及请求身份，依据项目承诺检查历史。最终值正确不足以证明中途没有旧读或部分发布。
- 超时或断连表示可能已执行，不能自动视为未提交；重试是否允许、是否沿用原请求身份在内容层定义。已确认操作仍可能被后续合法修改覆盖，应按完整历史核对。
- 既有必要课程/组件测试可以继续保护其原风险，但不能替代真实链路验收，也不为每个新模块机械增建一组相同 E2E。

### 11.3 性能场景归属与比较约束

- 每个场景登记唯一主要问题。通过相同链路不是重复测试；仅换名称、指标或所在层次重复跑同一目标则需要合并。
- 同次负载采集吞吐、延迟、错误、CPU、内存和 IO。前台与后台工作按场景共同运行；无关压测、编译及重型校验不同时占用主机。
- 统计重复事先约定并保留全部结果；失败后重跑到成功不属于统计重复。现有回归门禁“单次、无重试”规则不能被性能采样次数覆盖。
- 新旧使用同一机器/等效资源配置、拓扑、构建类型、数据集、操作规则和保证。换机器时重新运行旧版；同规格云实例仍应记录实际环境与波动。
- 固定数据生成种子与每客户端操作规则，不要求并发执行恰好产生相同交错。保存实际历史以解释差异。
- 预热、装载、正式计时、排空在途请求和收尾校验分段记录。异步提交不能以“已放入队列”冒充完成；统计请求完成边界由正式契约决定。
- 测试负载生成器自身饱和时不能把其上限当成服务器上限。连接复用、编码成本、重试和排队计时必须一致；负载模式先明确是固定并发还是固定到达速率。
- 全量结果校验一般放在计时之外，错误和超时仍在运行中记录。性能运行发现错误时保留数据，但不能把该数字作为正确系统的优化收益。

## 13. 硬件条件与资源核算

### 13.1 当前环境记录与证据范围

2026-09-20 的只读检查：WSL2 内可见约 7.6 GiB 内存，检查时约 5.3 GiB 可用、2 GiB Swap；CPU 显示 Ryzen 9 7945HX 和 32 个逻辑 CPU。虚拟 ext4 显示约 920 GiB 剩余。它们是环境观察，不是容量或性能验证，也不表示 CPU 独占。

- WSL 默认内存上限为宿主内存的约一半；实际值应以运行配置核对，不能认为测试可使用宿主全部 16 GB。[WSL 配置](https://learn.microsoft.com/en-us/windows/wsl/wsl-config)
- WSL 虚拟磁盘显示的容量不等于 Windows 实际剩余空间。正式运行前需要确认宿主剩余容量、介质和写入路径。[WSL 磁盘说明](https://learn.microsoft.com/en-us/windows/wsl/disk-space)
- 本机适合小规模真实进程 E2E 和本机条件下的对比。文件模拟设备的结果不能直接证明裸设备性能；三个本机进程不能代表三个独立磁盘/主机。
- 当前 [SnapshotStore](../../src/include/raft/snapshot_store.h) 将单个快照大小保护上限设为 1 GiB；这不是精确数据库容量。规模需给编码、Catalog 等留余量，不能为压测擅改生产限制。

### 13.2 选机建议的落点

先确定场景预算再选设备。GPU 不承担当前 SQL/Raft/存储计算；GPU 套餐仅作为 CPU、系统内存和存储组合比较，显存不替代系统内存。云主机可作为候选，尚未决定购买或租用。

| 参考 | 对本项目的意义 | 仍须现场核实 |
| --- | --- | --- |
| [阿里云 ECS 按量付费](https://help.aliyun.com/zh/ecs/pay-as-you-go-1) | CPU 实例不必按月租，可按测试时段使用；估算需包含实例、盘和网络 | 实际地域/规格价格、停止及释放后各资源收费 |
| [AutoDL 资源分配](https://www.autodl.com/docs/gpu/) | GPU 套餐中 CPU/内存随 GPU 数量分配，可比较有效资源总成本 | CPU 配额、系统内存、磁盘性能及保留规则、网络与设备权限；容器 root 不等于可访问裸设备 |

### 13.3 统一资源账本

```text
内存 = 三节点的业务页、元数据、日志/IO缓冲和其他内存
     + 相关系统页缓存 + 客户端/运行器/检查器 + 环境余量

空间 = 三节点各自的数据/索引 + 保留日志 + 保留快照
     + FS 元数据/Journal + COW/整理临时空间 + 测试产物与余量
```

- 新旧统一总资源边界；节点 RSS 与系统页缓存分别记录，不能重复相加已计入 cgroup 的页缓存。无法准确归属的部分说明口径与限制。
- 冷/热必须说明是哪层缓存。工作集大于 BufferPool 不保证从设备读取，重启进程也不保证清除操作系统或宿主缓存。
- 设备提交字节数不等于 NAND 物理写入量；进程写入计数不等于 durable 字节数；预分配文件/裸设备总容量不等于有效占用。
- 回收要区分逻辑删除、内部可复用空间与归还给 OS/设备的空间。没有可用的正式统计接口时记录限制，可通过固定容量内持续复用观察业务效果，但不能伪造内部回收量。
- 不从吞吐或内存下降直接推断少了多少次内存复制；确需归因时讨论外部性能采样，不能为测量添加生产计数接口。
- 同一机器一次只运行一个重型构建/测试；本地 CMake `-j1`，沿用 [执行交接](../../raft_execution_handoff.md) 的主机资源约束。场景内计划的并发客户端和后台任务不受此禁止。

## 14. 执行顺序、证据与故障限制

1. 审查候选场景：明确项目承诺、非空输入、独立预期、故障与资源，以及每项主要评价目标。
2. 审查测试实现：核对内容/适配依赖、正式调用链、防空跑、计时和错误处理；不能先运行再追认结果。
3. 经讨论后做小规模资格运行，确认装载、资源、观察能力和客户端余量；此结果不是正式基线。
4. 固定内容版本与配置，再运行旧系统，保留原始请求/结果、环境、源码版本及未提交差异、二进制/测试内容标识、构建配置和全部失败。旧版实际缺陷单独报告，不通过修改判定掩盖。
5. 按主方案逐模块改造，按需保留与受影响契约有关的验证；同一套内容继续复用。
6. 同条件复测新版。若内容、机器或关键条件必须改变，应记录变更并重跑旧版，不能直接接续旧数字。

故障证据限制：

- 终止进程保留了内核和可能的设备缓存，不证明掉电安全；虚拟机重启也必须说明宿主是否仍保留缓存、关机是否优雅完成。
- 外部网络代理或隔离可以作用于真实节点，记录确实施加的链路故障；健康吞吐场景若不用代理，不能与经过代理的结果混为同环境。
- 快照发布、裁剪、GC 等阶段须用已有正式状态或可审查的外部证据确认发生；未观察到则标为未覆盖，不能等一个固定时长就宣称命中了该阶段。
- 某个 Follower 仍落后时，向 Leader 成功查询不足以证明它已恢复；需使用正式进度/已追平边界及该节点的业务结果，或讨论另一种可观察证明。
- 短写、撕裂、掉电丢写及介质损坏需要独立环境和明确模型；若只能模拟，标注模型保证，不代替真实物理设备证据。
- 失败、环境限制、未覆盖和通过分开记录；不能将未覆盖写成通过，也不能为获得通过自动更换故障目标或放宽时限。

| C3/C5/P4 的故障与事件证据 | 进程存在、等待一段时间或 Leader 读成功不能证明隔离、快照或目标副本恢复已发生 | 为每个变体给出外部触发、生效确认、完成条件和超时处置；复用代理与正式状态，观察不到的事件明确标记未覆盖 |
| P3/P4 的负载与统计 | “循环更新”或“后台发生恢复”不能直接决定周转量、稳态、排队和计时 | P3 固定每轮有效操作与正文总量边界、停发后观察规则；P4 固定到达速率、队列/在途上限和发不出的请求计量，复用已有负载及追赶判定 |
| 测试侧实现边界和结果格式 | 新旧版本适配、计量开销、异常分类与复查依赖共同约定 | 测试内容使用业务操作；适配器负责正式调用和结果转换；固定原始历史、环境、故障时间线、统计结果的最小字段。优先复用正式客户端及既有进程/代理工具，不直接沿用旧单脚本基线 |

### 16.3 核对发现的具体限制

1. [SqlCommandPreparer::PrepareUpdate](../../src/distributed/sql_command_preparer.cpp) 当前在准备阶段遍历表并计算修改；按主键条件 UPDATE 不代表整条写入路径仅做索引点访问。P2 必须标注这种成本，D1 的装载/运行时间和瓶颈需资格确认；不能为测试改生产查询路径，也不能直接将 CPU 扫描成本归因于 FS。
2. 现有 [进程 harness](../../test/support/raft_process_harness.sh) 的 `raft_current_snapshot_index` 读取旧版 CURRENT 文件，注释明确指出 status 的 snapshot base 未必等于最新发布快照。这个文件格式断言不能直接成为新旧共同内容。优先核对协议快照传输/完成与已发布进度能证明哪些事件；无法证明的精确阶段保持覆盖缺口。
3. 测试驱动可考虑在测试侧复用 `DistributedClient::Send`，通过真实网络访问节点；业务预期仍独立生成。性能驱动优先避免每请求启动一个 CLI 进程，并在资格阶段核对客户端自身是否限速；具体实现组织待收敛，不新增生产便捷接口。
4. 本机较大工作集可能仍命中 OS/宿主缓存；首期 E2E 能比较给定条件下的业务成本，不能据此自动证明冷设备 IO、消除了多少内存复制或掉电安全。正式块设备比较的部署与设备边界需要在运行前明确；更换环境后旧版也要重测。

### 16.4 可留到运行前校准及后续阶段的事项

- 数据规模、超时具体值、采集时长、预定重复次数和资源限额可以作为显式配置。在相关规则明确并审查代码后做资格运行，确认内存、空间、快照大小、耗时和生成器余量，再冻结基线配置；不得把资格运行追认为正式结果。
- 资格运行前仍需明确其最大时间/空间、退出条件和预期；不能借“校准”无上限运行。文件系统显示的可用空间不替代实际宿主空间核实。
- 正确性应有明确通过条件：业务和历史满足模型，必要事件发生，有效操作非零；不满足前置条件、环境失败、未覆盖和无法判定分别记录，均不能作为通过证据。
- “新版提升多少”不必成为开始编写测量代码的前提。先确定指标与统计方法，依据旧版波动讨论性能门槛，并在观察新版结果前固定；不能事后选择门槛。
- S13 单客户端多请求能力、FS Journal/COW/RMW/Deferred 的专门恢复风险，在对应模块方案中设计验收，不阻塞当前共同 F0/F1 基线的测试实现；首期不声称已经覆盖撕裂、介质损坏或掉电。

### 16.5 建议的首批实现范围

先收敛共同数据/请求/结果契约和 C1、P2 两张场景卡，作为第一批代码范围：共用数据生成、真实接口适配、进程生命周期、历史/指标记录、C1 独立结果核对及 P2 并发曲线。它们同时检验正确性和性能框架能否走通正式链路。

随后按缺口收敛其余 C/P 场景，复用同一基础；首批通过不代表整个 T0 已完成。C2 的检查器与 C3 的故障判定不能在首批实现中用占位成功代替。每批仍依次遵守“明确范围与场景卡 → 编写 → 用户审查 → 经约定资格运行 → 冻结配置 → 正式旧基线”。详细目录、语言、参数和测试 prompt 待首批方案收敛后明确。


## 17. 2026-09-21 改进方案的比较边界

保留旧系统、S9.1 FS/页 IO 接入、S9.2/S9.3 F36 空间复用、S13 只读访问路径、S13 并发流水线的可复查版本边界。需要复测时沿用同一内容与计量口径，避免把 SQL/并发收益统算为 FS 收益，不为每个版本复制一套测试。

F36 优先复用 C1/C4/C5/P3，F35 复用业务正确性/重试历史与 P2/P3，F26 复用内容及恢复检查。已有内容不能覆盖的并发、旧版本或引用风险，先在对应模块明确承诺与独立判定，再决定必要补充；不把固定 slot 排列、executor 类型、队列名称或某个开源实现的内部行为作为测试目标。
