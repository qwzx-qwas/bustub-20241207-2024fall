## 1. 结论与本阶段改动

未发现阻止提交当前 S12.1 范围的新问题。结论只覆盖下列实现及查阅的上下游，不是全仓无缺陷证明。逐项代码变更与八项测试审查继续以 [S12 执行记录](s12_execution_20261007.md) 为准。

| 已完成改动 | 此次复核的关键约束 |
| --- | --- |
| ResourceBudget / ResourceAccount / ResourceCharge，接入 F02、B、F19/F27 | 局部额度不足才向节点申请；回收闲置额度时不持节点锁反调账户；真实所有者退出才归还；借用帧不重复记 RAM |
| F02 普通/进展名额与逐次拒绝原因 | 异步批次保存接纳时的类别；局部暂满与共享 RAM 暂满分别返回；全局 Pressure 只作状态提示 |
| Deferred 完成重试 | Data durable 后先释放无用正文和 IO 批次；资源暂缺不撤销已提交任务；完成重试不重复写 Data |
| 独立 GarbageLoop | CommitLoop 中旧周期物理回收已删除；候选受阻仍推进游标；不持 B 旧视图跨轮等待 |
| F14 活动调用名额暂满返回 Busy | F22/F19 消费同一个已有错误契约；单次扫描或编码超限没有被无条件吞掉 |
| LRU-K 驻留命中合并入口 | 每次访问仍记录历史，仅第一次 pin 取消可淘汰；未改变替换策略，未宣称乐观正文读取已完成 |

关闭顺序仍是停止新请求、排空已接纳工作、退出对象服务，再关闭 B、执行器和设备。持久 Deferred 未完成任务沿既有恢复协议接续，不能把超时或关闭当作丢弃依据。

## 5. 下一步建议：S12 / F29 日志段整理（待用户确认）

沿 [F29 既有子方案](modules/log-segment-cleaner.md) 接续，仍与 F23/F22/F31/F14/F12 配合，不新增同职责模块。本次只说明提议，不启用实现 prompt、不开始编码或测试。

当前 `ObjectLogStore::Base/Replace` 已能改变段的有效范围，整个旧段退出后由 Collect 和 F14/F12 回收。缺口是仍被少量有效 entry 占住的段；F29 将这些 entry 原样搬到新段，持久化并发布新目录后，才退出旧段引用。示例：一个 8 MiB 段只剩 1 MiB 有效日志，整理的候选收益是移走这 1 MiB 后解除旧对象；实际可回收量仍由分配单位和引用决定。

实施前需要在原 F29 文档冻结以下协议：

1. **选择与预算：** 区分整段直接退役和部分有效搬迁；按有效字节、预计可释放空间与本轮 IO/内存上限选择。扫描有界、无收益不搬，先预检最终控制事务容量。
2. **段目录顺序：** 当前 Open 按 Control 的对象编号顺序恢复段，位置索引通过有序段目录寻找跨段后继。搬到新编号后，不能再用编号大小推断日志先后；须明确新的顺序表达及旧格式兼容，不能只替换某个物理地址。
3. **并发与发布：** 固定源目录和内容使用权，后台读取/复制；发布前复核目录代次及有效范围。其间若发生 Append、冲突后缀替换或裁剪，应放弃过期计划或重规划，不能覆盖新的日志历史。依旧只有 F23 一个有效目录/位置权威。
4. **完成与清理：** 新正文 durable → 原子提交目录和所有权 → 发布内存位置索引 → 旧使用者退出后回收。失败候选沿现有 Own/Collect 清理；提交结果不明确时按现有恢复协议处理。
5. **测试：** 对照独立 entry 序列核对 term/index/正文及重开；覆盖跨段记录、复制期间后缀替换、失败候选不发布、旧读取保护和释放后的真实空间再利用。复用 S8/F19/F14，不重复测试 bitmap 或 CRC 算法。

F29 只整理 Raft 的普通对象日志段，不接管 FS Journal 回收，不合并业务命令。普通资源压力在 Store 维护中的退让、后台统一节奏仍须与 F22 接续一起定义；当前 DistributedNode 维护捕获异常后会停止节点，不得把 S12.1 的本地进展能力宣传成所有上层维护已具备压力重试。
