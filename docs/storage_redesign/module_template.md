## 5. 测试方案与验收

沿用已讨论的共同测试及其已归档证据边界，补充本模块新增行为的必要验证。具体实现方案与测试须按用户当轮要求完成讨论和认可；模板存在不等于允许实现或执行测试。

- 项目承诺和真实风险。
- 验证场景、所属边界及独立结果判定依据。
- 为什么需要这项测试、是否已有足够覆盖。
- 受影响正式路径的必要回归。
- 性能比较条件和可得结论（若涉及）。
- 当轮约定的验收方式与实际结果记录。
- 需要删除或改写的历史测试及原因。

具体用例依据[总体测试设计](testing_plan.md)和模块讨论确定，不能套用一套覆盖所有实现细节的固定清单。

必须沿用总体测试设计的三层隔离、有效输入 E2E、独立预期、禁止测试侵入生产、同条件比较及故障证据边界。优先说明本模块风险由哪个既有场景保护；确有缺口再讨论新增场景。不得将[候选场景和资源](testing_scenarios.md)当成已批准的参数。

每次新增或修改测试及测试工具后，必须执行[主方案 §1.5 的八项测试设计审查](README.md#15-每次新增或修改测试后的强制设计审查)，记录测试全景、逐项 oracle、生产／接口污染、重复、最小变异、稳定性和最终矩阵。修正问题后复核受影响项；设计结论、实际运行及未覆盖风险分别说明，不能用“全部通过”代替审查。本模块保存审查记录或链接，不复制第二套审查规则。

按[主方案 §1.6](README.md#16-测试演进跨模块复用与阶段退出)补充下表。同一风险由一处维护内容，各模块引用；生产支持后复用输入／oracle 并接入正式路径，不能将模拟通过自动升级为真实证据。常驻主线是共同 E2E／性能，阶段小测试验证后删除或按模块压缩归档；写明未被接管的风险和恢复入口。

本模块交付按[§1.6.5](README.md#165-单个模块的测试交付约定)逐项说明共同场景关联、必要阶段验证、审查证据、退出清理和后续真实接入，不以新增一套永久运行的小测试作为默认验收目标。

## 6. 必须复制到子模块文档的要求

遵守[主方案 §1.7](README.md#17-控制防御性代码先分析逻辑再验证)：不要过多纠结于边界条件和防御性编程，防止可能出现的问题被掩盖；校对先分析代码逻辑，确认处理正确后再决定必要的测试。保留已承诺安全边界所需的检查，禁止用兜底掩盖错误。

> 代码要考虑复用性，间接性，安全性，不要破坏别的模块和层次的production级代码。

> 当本次任务接续上一次任务后，需要在完成前检查之前的代码是否因为当前改动有冗余的地方，有的话可以删除，也要检查是否有根本没用到的接口或函数之类的，也需要删除。

> 测试应该保护“这个项目自己承诺的行为和风险边界”，而不是给每一层实现细节、第三方库行为和历史重构痕迹都建立一套测试。

落实要求：

- 先检查已有可复用接口、调用者和数据归属，通过明确接口隔离层次；正式代码不得反向依赖测试辅助设施。
- 清理范围是本次改动及其引起的旧路径冗余。检查虚函数、模板、注册入口和对外契约，确认无用后删除声明、实现和相关引用；不能仅因单次文本搜索没有调用就删除生产接口。
- 保留仍被现有正式路径依赖的行为，不覆盖或清理用户已有的未提交改动。
- 对每项新增、保留、修改或删除的测试，说明它保护的项目承诺或风险及验证它的边界；避免重复覆盖和自证式断言。
- 完成前报告清理结果、受影响契约与验证证据；没有可删项时记录检查范围及原因。

```text
缺项处理：
当遇到方案中未提到的部分时，先不要自作主张去写,而是汇报当前遇到的问题（注意先不要堆砌专有词汇，用我能看的懂的话去讲当前情况，有需要时再用专有词汇）。

清理前确认调用、模板、注册和对外契约，不覆盖用户已有改动，不误删仍有用途的正式代码。

失败路径与边界：
[填写当轮约定；缺失时汇报，不自行选择默认值或隐藏重试。]

优先阅读 / 修改的文件：
[区分已有阅读入口与实际讨论确定的修改范围。]

测试要求：
校对先从代码逻辑分析正常、失败、并发和资源归属，确认逻辑及修法，再决定是否补测试；不得一开始就编写回归测试来代替分析。复用有效证据，不机械增测；已约定验收仍须完成。
测试应该保护“这个项目自己承诺的行为和风险边界”，而不是给每一层实现细节、第三方库行为和历史重构痕迹都建立一套测试。
[当轮约定的场景、判定依据、运行条件及必要回归。]
旧的未经审查结果不作为本阶段验收基线。
测试内容与版本适配分离，适配代码留在测试侧。不得为测试方便修改生产 API、默认路径或持久化语义，也不得增加生产测试分支；现有能力不足时汇报，不在适配器中补做功能。
E2E 使用有效非空数据和真实链路，以独立预期/历史核对结果；声明故障模型、资源及计时口径。优先复用已审查场景，不为每层重复建立相同保证的测试。
每次新增或修改测试及测试工具后，按主方案 §1.5 完成八项测试设计审查；修正问题后复核受影响项。交付审查矩阵、问题处理、实际验证与剩余限制；不得以运行通过替代设计审查，不得隐去已知 oracle 或覆盖缺口。
按主方案 §1.6 维护跨模块场景归属和接入表，生产就绪后复用内容接入真实路径，避免重复场景及不兼容完成语义。阶段小测试验证后删除或按模块压缩归档，保留未覆盖风险；共同生产 E2E／性能及其实际工具继续维护。

验收标准：
[约定功能、失败边界、验证和代码清理结果。]

输出要求：
说明改动、原因、验证及局限、冗余/未用接口清理、开源参考本地落点和剩余问题。
同步主方案、模块介绍和阶段状态；满足完整约定范围后在模块介绍下写“已完成”。
```

## 8. 完成证据与讨论记录

- 本轮测试设计审查：变更范围、审查矩阵、问题处理及复审、实际验证与未覆盖项的记录或链接。
- 场景的真实接入、跨模块复用、被接管与剩余风险，以及阶段测试压缩归档／删除的位置和证据。

- 日期与当轮范围。
- 用户讨论决定及剩余问题。
- 代码版本和改动位置。
- 实际验证及不能支持的结论。
- 被当前改动替代的旧路径、未用接口/函数与测试清理。
- 仍保留的兼容入口及理由。
- 开源参考最终落点。
- 主方案与阶段表同步结果。
