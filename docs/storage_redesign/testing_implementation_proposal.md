## 3. 测试结构与复用边界

当前代码集中在 `test/storage_acceptance/`（correctness/performance 按目的分文件，旧回归归档于 `test/legacy_raft`，共享工具在 `test/support`），保留一个明确的测试侧构建入口，不混入生产库或默认生产启动流程：

```text
内容：业务操作、种子、场景卡、故障时间线、独立预期
                         ↓
测试侧驱动 / 版本适配：生成 SQL、正式请求、解码结果、进程及代理控制
                         ↓
真实网络 → 三个 bustub-node → Raft / BusTub → 正式存储

驱动原始历史 ─→ Python 顺序结果核对 / 指标汇总
             └→ Go + Porcupine 离线检查 C2/C3
```

- C++ 长驻驱动使用 [DistributedClient::Send](../../src/include/distributed/client.h)，不为每次请求新建 CLI 进程；仍按现有协议每请求建立 TCP 连接，不改变生产连接语义。线程数按客户端/在途上限有界，不为每个操作创建线程。
- 内容只使用 CreateSchema、InsertRows、ReadPoint、ReadRange、Bump、ReplacePayload、Delete 等业务操作。适配器映射为正式 SQL/协议；C1 保留少量字面 SQL 和预期作为可审查样例。适配器不直接调用状态机、页接口或内部恢复代码。
- 编排使用 Python；进程/代理先审查现有 `test/legacy_raft/e2e/` 工具再复用。所需的规则生效确认、消息观察等扩展只修改测试侧工具，保持旧场景兼容，不复制第二套协议代理。
- C1/P3/C4 的顺序预期由测试模型从已知初始记录和操作输入推导；不从生产返回值反向生成 expected。正式协议编解码可以复用，业务答案不得调用 BusTub 执行器生成。
- 计划、配置和结果各自带格式版本，结果采用 JSON/JSONL。驱动输入的编码细节保持测试侧私有；必须可完整表示正文及请求身份，不靠字符串分割丢失内容。跨语言转换用少量字面样例验证，避免再写生产协议的第二套实现。
- Porcupine 是新增的测试侧依赖，当前 PATH 未找到 Go；确认本提案后为离线工具准备工具链，记录确切版本，不自动升级生产环境。缺少工具时报告不可执行，不能换成永远通过的检查器。

## 4. 共同数据和操作契约

### 4.1 表与数据

建议使用一张业务表，只建立主键索引：

```sql
CREATE TABLE bench_state(
  id INT PRIMARY KEY,
  tenant_id INT,
  kind INT,
  version INT,
  last_op BIGINT,
  payload VARCHAR(1024)
);
```

- D0 固定 2,048 行；本机 D1 提议 20,000 行。所有字段均提供有效值，version、last_op 初始为 0，tenant_id 从 32 个值选择，kind 从 4 个值选择。本轮按用户要求修复生产列长度截断、复制/快照的旧宽度上限及正文边界判断；不缩短共同正文或新增测试专用 API。旧系统正式基线须使用这次修复后的版本，并记录 revision/diff，不能将修复收益归到后续 FS 改造。
- 正文长度 64/256/1,024 字节，数量比例 60%/30%/10%。使用最大余数法补齐整数条数，再按种子确定性打乱。正文为 ASCII，避免把字符数误当字节数。
- 50% 记录使用有限的配置/订单备注模板全文，50% 在模板中加入合成记录字段；按目标长度生成，内容字典版本固定。相同正文与不同正文共存，不使用真实个人数据。
- 主种子固定 `20260920`；数据、访问、故障和各客户端的随机流分别派生。保存生成器版本、数据清单及哈希；关键生成样例另列字面结果。新旧使用同一内容版本和相同种子。
- 按 id 升序、每次最多 64 行批量 INSERT 装载；最后一个批次只装实际剩余行。装载走正式业务接口，不复制生产数据目录作为新版初态。
- 完整核对按 id 范围每批最多 128 行，使用 ORDER BY，检查全部列、重复键及缺失；不依赖一个巨大响应。读取当前正式结果上限为 16 MiB，因此必须保留分批约束。

C1 的操作版本为 `c1-resize-1`：更新行按 64→256、256→1024、1024→64 改写正文；必须同时观察到增长和缩短。初始数据版本 `t0-a-1`、初态哈希及 P2 请求流不变，C1 版本单独写入运行配置。

### 4.2 操作定义

| 操作 | 本项目语义 | 核对重点 |
| --- | --- | --- |
| ReadPoint | 按主键读取整行 | 数据存在、字段和值完整；性能与历史测试均用 LINEARIZABLE |
| ReadRange | 静止业务边界下按范围及 id 排序读取 | 全记录精确核对；不把不同时间的多个分页拼成一次原子读 |
| Bump | 一条 SQL 将 version 加 1，并设置 last_op；正文保持 | 必须由数据库表达式递增，禁止测试侧先读再计算新 version |
| ReplacePayload | 一条 SQL 递增 version、设置 last_op 并替换正文 | 真实正文修改与长度变化，完整 tuple 原子可见 |
| Delete / InsertRows | 删除已知存在的记录；插入已知空位 | 不用零命中冒充成功；删除与后续重插是两次操作 |

例如 Bump 映射为 `UPDATE bench_state SET version = version + 1, last_op = 1001 WHERE id = 7;`。last_op 来自测试逻辑操作编号，正文重复不影响操作身份。范围、键集合、正文和编号在重试时不重新生成。

当前 [PrepareUpdate](../../src/distributed/sql_command_preparer.cpp) 仍遍历表来准备修改。P2/P3 测的就是这个真实路径，必须记录 CPU 和数据规模，不能标成纯设备小写微基准，也不为测试修改生产查询路径。

### 4.3 成功、未知与重试

- 写成功要求外层 COMMITTED、合法内层结果及匹配的请求身份；成功发生在业务应用并完整发布之后。状态字段用于关联及边界等待，不作为独立业务答案。
- 基线每客户端一个未解决写，client_id 非零、request_id 从 1 连续增长。装载、预处理和正式工作者使用不同身份。
- 写会话的连续序号与读取/状态查询的关联编号分开管理；读和状态查询不消耗下一次写序号，也不能用同一编号暗示它们共享写去重语义。
- TIMEOUT、断连及结果不明确的持久化错误保留 UNKNOWN；写入返回 NOT_LEADER 时也保留 UNKNOWN，因为本次尝试可能先追加再失去 Leader 身份。语法、身份、结果解码错误不作为普通可重试失败隐藏。
- 健康性能场景不自动重试业务写；若出现未知写，停止该写客户端继续前进，记录失败/未知及实际速率。故障场景通过重新发现 Leader，以原身份原正文重试。
- 建议节点业务等待 5 秒、单次客户端 IO timeout 参数 6 秒；每条故障逻辑请求最多 8 次尝试，总解决窗口 60 秒，退避为 100/200/400/800/1,000 毫秒后封顶，无随机抖动。只在预算允许时开启下一次尝试。
- 当前客户端 timeout 用于连接/读写等待，不是严格的整条请求总截止。测试驱动记录真实时长；外部运行器以绝对截止加有限退出宽限终止自己创建的进程，剩余请求保留未知，不能伪造恰好 6 秒完成或取消。
- 原始历史至少保存 scenario/version、逻辑操作 ID、client_id/request_id、attempt、操作输入与正文标识、目标节点、调用/返回时刻、原始状态/错误和业务结果。成功吞吐按逻辑操作只计一次。

## 5. C2/C3：具体怎样检查历史

参考 etcd 的独立顺序模型和未知结果处理，借助 Porcupine 搜索；模型只包含本项目的单键业务及去重行为，不导入 etcd 的完整 KV 模型。

1. 一个场景只检查一个共享键的 Bump/ReadPoint；C2 为 4 客户端、每个 16 次交替写读，共 64 次逻辑操作；使用预先指定的 3 个种子分别建立完整历史。记录是否实际出现调用区间重叠及有效读写，缺少并发不能算并发目标通过。
2. 模型状态为 `(version, last_op, payload, 已应用的请求身份及对应结果)`。首次请求使 version 增加一次，同身份重试不增加。读必须对应某个完整合法状态，不能读到不匹配的 version/last_op。
3. 调用和返回由同一驱动进程的单调时钟记录；保留全部尝试。成功响应后的新调用必须遵守真实时间先后；不使用 Raft index 为模型指定正确执行顺序。
4. 未知写的实际完成时间可能晚于网络超时，不能把网络超时时刻作为业务线性化的上界。检查输入中将其保留为待定调用，允许它到场景观察末尾仍未执行或已经执行；原始超时时刻单独保留。若同身份后来确认成功，则至少有一次尝试必须解释这次执行，其他尝试只能是重复或无效果。
5. 为表示上述重叠，检查器内部的历史流 ID 可与生产 client_id 分开；生产身份始终放在模型输入中。不能因此改变真实请求身份，也不能把多个重试压成一条新请求。对明确拒绝的单次尝试按无业务变化处理，仍保留早先未知尝试。
6. 模型用非确定状态表达未知尝试的两种可能，并用去重集合限制最多一次生效；未知读不提供数值约束。检查器准备输入的规则用独立的超时后才执行、重试后读、重复执行和旧读历史样例验证。
7. C3 每份历史最多 128 次网络尝试。每份离线检查上限 30 秒，并使用上下文/进程预算约束模型计算。Ok 只表示这份历史可解释，Illegal 表示违反模型，Unknown 或资源超限表示未完成；不拆掉跨故障区间或未知请求来凑通过。
8. 场景整体通过还要求恢复服务、未知逻辑写在截止前解决、有效完成量及故障覆盖满足要求。即使历史可解释，全部超时、目标故障没发生或恢复超时都不能整体通过。

## 6. C1–C5 场景卡

| 场景 | 输入与步骤 | 独立预期与必须留下的证据 |
| --- | --- | --- |
| C1 业务结果 | D0；更新 id%4=0，正文按 64→256、256→1024、1024→64 改变长度；删除 id%4=1；重插 id%8=1；逐阶段点查和全量范围核对 | 最终 1,792 行，并逐行比较完整结果；未触及记录不变，删除/重插无旧值复活。每个操作类别都有非零成功量 |
| C2 并发可见性 | D0，一个共享键，4 客户端×16 次操作、3 份预定历史；尾部停止写后读一次 | 第 5 节模型通过，并且有实际重叠与成功读写；不以最终计数替代历史 |
| C3 成员及网络故障 | D0；杀 Leader、双向隔离 Leader 两个变体各采用 4 客户端×16 次交替写读，累计确认第 16 次 Bump 后触发故障；第三个独立变体对专用键的一次 Bump 丢响应后原样重试 | 终止需 waitpid 证据；隔离需代理规则确认、实际阻断记录及多数派服务；隔离生效后向旧 Leader 发出的全新身份写，在隔离持续期间不能 COMMITTED。丢响应变体从 10 增加到 11，不能到 12；代理证据不能伪造成客户端收到成功 |
| C4 全节点进程重启 | D0；快照阈值配置为 64，最多 256 次 Bump 等待正式状态出现非零恢复基点，再追加 16 次确认修改；停止新业务并解决未知，保留客户端身份；SIGKILL 三进程，原目录重启 | 与独立最终模型逐行一致；重试保留的最后已提交身份返回原业务结果且不重复递增，再能继续读写。只需承诺已确认边界，不预先要求所有 Follower 已 Apply；证明范围仅为进程崩溃恢复 |
| C5 两种追赶 | 独立运行短落后与长落后。目标初始发布位置为 L，停止该 Follower；短路径快照阈值 10,000，落后 16 次确认修改；长路径阈值 64，先执行 256 次确认修改，必要时在既定上限内继续到正式恢复基点大于 L；再启动目标 | 短路径观察有效 AppendEntries 及成功响应，无快照安装；长路径观察真实 InstallSnapshot 请求及匹配的非 stale 成功完成响应。停止新写并解决未知，取得 K，等待目标 published>=K，再直接向目标做 STALE 全量核对，最后继续正常业务 |

### 外部故障控制的具体补齐

- 复用 [raft_message_proxy.py](../../test/support/raft_message_proxy.py)。测试侧补充规则代次/生效确认、按发送方/接收方的阻断计数、AppendEntries 与快照响应的摘要观察。控制切换需排完旧转发动作；不把写出控制文件等同于所有规则已生效。新规则覆盖所有节点间连接，客户端入口保持可访问。
- 保留已有故障脚本需要的原行为；新观察模式只记录元数据和时间，避免把整份快照复制进监控文件而改变性能。若需要摘要校验，明确额外开销，不在 P4 默认做完整正文复制。
- 快照请求、分块及完成响应必须关联同一身份、节点和请求；一次请求出现不等于安装完成，stale 完成也不算本次新安装成功。协议版本转换留在适配层。
- 本次使用真实协议与发布位置证明追赶，不以旧 CURRENT 文件布局为共同判定。C5 不额外声称证明目标副本接管后的全部会话语义；该扩展需另列明确场景。
- 建议单次选主/进程恢复/副本追赶绝对截止 60 秒，状态采样 100 毫秒；故障后必须成功完成至少 8 次有效业务请求。C1/C4 包括装载的总预算 10 分钟，C5 长路径最多 1,024 次准备修改；达到预算而未触发则报告未覆盖，不无限追加请求。
- 进程停止、代理规则和协议事件共同形成故障时间线。杀 Leader 不承诺精确命中某条设备写的中间阶段；响应丢失变体独立保证发生客户端未知结果。

## 7. P1–P4 场景与计量

### 7.1 共用过程

参考 Ceph CBT，将初始化、预处理、测量与收尾分开。每次参数点使用新目录、同一逻辑初态、相同正式配置；数据和全量校验不混入正式计时。P3 的连续状态是被测对象，中途不重建库。

- 建议本机 D1=20,000 行，业务 BufferPool 每节点 256 页（1 MiB），默认正常快照阈值 10,000；这些是待确认测试配置，不修改生产默认值。20,000 行正文约 4.15 MiB，另有行头、索引和历史。资格运行验证热点/全工作集实际占用；不称冷盘测试。
- P1 读预热 30 秒；P2 写预处理固定为 1,000 次 Bump 并排空，用独立客户端按确定序列执行，避免按时间预热导致新旧初态不同。
- P1/P2 正式窗口各 180 秒，每个参数点预先安排 3 次独立重复。停止发新请求后记录在途结果，最多观察 60 秒；未结束的请求保持未知。重复全部保留，不挑最好值，不因失败自动重新跑到通过。
- 记录窗口内实际成功完成的吞吐；从窗口内开始的请求另统计完整耗时及排空尾部，不能把排空后的成功数除以原窗口时长。超时、错误和未结束分别报告；分位数按各运行原始样本计算。
- 每秒采集进程 CPU/RSS、可归属的缓存/IO和主机设备计数；资源上限和采集开销同时记录。协议历史与资源采集的输出尽量分离于被测数据盘；同盘时说明观测 IO 污染，不能据此声称精确写放大。

### 7.2 四个主要问题

| 场景 | 建议冻结的内容 | 输出和边界 |
| --- | --- | --- |
| P1 读取/缓存 | 4 客户端，强一致整行点查；一次均匀访问全表，一次 80% 请求访问固定连续 5% 键范围，使用同一数据 | 吞吐、延迟、CPU/操作、内存、外部读量；热点概率不是命中率，OS/宿主缓存未排除，不能称冷设备结果 |
| P2 写入容量 | Bump；1/2/4/8 客户端分别运行；每客户端一个未解决写，均匀覆盖各自不相交的键范围，使整体覆盖全表；每档重建相同初态 | 成功吞吐与 p50/p95/p99、错误/未知、CPU/操作和设备写入/操作；如实呈现当前单提案及扫描路径限制 |
| P3 空间周转 | 一个写客户端，每组 20 次操作：14 次正文更新、3 次删除、3 次重插；删除/插入配对。14 次更新为 7 对长度互换，配对结束后正文总字节数保持不变；同组选择不同键。每轮 N 次操作、共 10 轮，N 为行数 | 以累计有效操作和时间双轴记录空间、吞吐和尾延迟。这里一轮是固定操作量，不声称每行都恰好更新一次；组边界保持行数与正文总量，记录中间短暂波动 |
| P4 副本追赶干扰 | 80% 强一致读、20% Bump；4 个读工作者、2 个写客户端，总在途≤6、待发≤64。恢复开始前的逻辑落后目标为 256 次已确认业务写，实际边界记录；试验前健康前台窗口 30 秒，恢复结束后再观察 30 秒 | 固定计划到达速率，比较事件前/中/后的延迟、排队、错误与恢复时间。以恢复目标 K 的发布与目标业务核对确认追平；C5 判定复用，不复制第二套恢复逻辑 |

P4 的准备：先让健康前台运行，再停止 Follower，保持相同前台到达计划，记录离线后的确认写数量；接近 256 时暂停派发新的写，排完这些已派发写以固定落后边界，读与到达计划继续。恢复目标并恢复写派发，记录这一测试侧屏障的时间，不能把它隐去。前台内容及保留策略新旧相同；自然快照等额外背景活动也记录，不能宣称完全隔离了所有后台工作。

追赶耗时的共同边界是“发出重启操作 → 目标发布到重启前固定位置 K0”；另记进程就绪时刻和随后的落后量。这只表示追到 K0，不能声称已追到持续变化的最新位置。前台结束后停止新写、解决未知，取得最终 K，再核对目标进度和全部业务数据；该收尾校验不混入前台延迟。

### 7.3 固定到达速率与慢请求

借鉴 YCSB intended start，P4 每个操作记录计划时刻、实际 Send 起点及完成时刻。新旧使用相同绝对速率；初始建议取旧版 P2 单客户端健康资格吞吐的 50%，冻结具体数值后复测，不分别按各自峰值换算。

- 以固定的 8 读/2 写操作块维持比例；到达队列满则记录未发出/过载，不能悄悄减少计划请求。
- 写队列按客户端排序，请求号在首次实际派发时分配；未派发操作保留独立的计划 ID，不消耗生产请求号。已未知的客户端停止后续派发，不能换身份绕开。
- 同时报计划到完成及实际发出到完成耗时；对未发出的请求没有伪造延迟。场景结束后不丢弃长尾。
- 资格阶段若客户端本身无法维持目标时序，则标注生成器受限，不能把结果作为服务器容量。必要时调整驱动预算并让新旧一起重测。
- 资格阶段也用冻结速率估算积累 256 次确认写所需时间；若连准备过程都超出 P4 的 10 分钟总预算，报告预算不匹配并调整共同配置，不能私下提高新版速率或降低落后量。

### 7.4 P3 的稳态和空间口径

借鉴 fio 的滚动窗口思想，提议在完成 10 轮后，以最后 5 个完整轮次的有效占用/轮次峰值判断有限观察窗口内的稳定：线性斜率绝对值不超过均值的 1%/轮，窗口极差不超过均值的 5%；同时在该最后 5 轮窗口内至少观察到 3 次相关日志/快照保留边界推进。数值是本项目待确认规则，不是 fio 默认值，也不保证没有更长期泄漏。

- 若预算耗尽、保留周期未覆盖或内部占用不可观察，则只报告趋势/未达到判定条件，不能伪造稳态。固定预留容量不能当成“已用空间平稳”。
- 旧版统计专用目录内文件实际分配块；新版裸设备只有存在正式可用的已分配/可复用统计时才报告内部空间。没有该能力时保留指标缺口，不能为测试加生产私有计数器；可以报告同预算下完成的业务周转量，但不据此推算内部释放字节。
- 停发后统一再观察 60 秒，不要求生产接口强制 GC；后台未排空需标注。各版本只在共同完成的累计操作范围比较，不能将新版多做的工作误认为空间退化。

### 7.5 快照构建耗时的明确限制

现有 status 暴露的是恢复基点，未必等于最新快照，也没有构建起止事件。首版 P4 以可确认的副本追赶为必做项，其中需要快照的追赶可测传输/安装阶段。自然快照引起的 E2E 波动仍留在 P1–P4 的时间线中。

精确本机快照构建耗时暂不作为首版通过条件。未来若正式诊断能力或经验证的外部观测能提供该事件，再复用 P4 增加对应变体；不以读取旧 CURRENT 或人为等待替代，也不通过增加生产测试钩子补齐。该限制需要随本提案一起确认。

## 8. 资源、资格运行及结论

- 本机单次只运行一个重型构建/场景，构建 `-j1`。使用 Release 构建做性能比较，正确性使用同一真实进程链路；已有必要 sanitizer 回归另外运行，不混入性能数字。
- 提议三节点合计预算 3 GiB、运行器/驱动 512 MiB；离线检查独立运行，预算 1 GiB。若 cgroup 不可用则这些仅为观测停止预算，不能声称已施加硬限制；系统可用内存低于 1 GiB 停止继续发请求并保留结果。
- 本轮专用目录的实验数据与产物预算 10 GiB，开始前核实宿主真实剩余空间并保留额外余量；只清理本轮明确拥有且已按约定归档的产物，不覆盖旧测量。容量预算与累计写入量是不同指标。
- 审查代码后，资格运行按 D0 正确链路、D1 装载、短 P2 和故障观察能力依次验证；每项有 10 分钟时间和上述空间上限，整个资格批次上限 30 分钟。P3 正式单次上限 60 分钟，P4 单次总上限 10 分钟；达不到预定工作量如实记录。
- 资格运行用于核对 SQL、快照/响应大小、资源及客户端余量，不作为正式基线。预算不满足时报告具体消耗，调整需更新配置并对新旧统一执行，不能静默缩小场景。
- 性能首期报告各次结果及中位数、范围，不预设提升百分比；p99 附样本数，成功样本少于 10,000 时只作探索性描述，不据此给细小尾延迟改善下结论。10,000 是报告规则，不是统计精度证明。
- 通过、正确性失败、恢复超时、未覆盖、环境受限和检查未完成分别报告。观察到旧版缺陷原样记录；正确性错误不能被吞吐提升抵消。性能回归门槛在旧版波动已知且未观察新版结果时另行冻结，不阻塞测量代码编写。
- 归档内容至少包括内容/配置版本、种子、源码提交及未提交差异、构建参数和二进制标识、机器/设备与配额、全部请求结果、故障证据、资源曲线、检查器结论与失败可视化。同环境共同负载至少记录旧版、进入 S13 前的版本、F35 后版本，复用同一套测试。

## 9. 确认后的实施顺序与 prompt 边界

| 批次 | 实现范围 | 验收内容 |
| --- | --- | --- |
| A | 数据/操作、C++ 正式客户端适配、进程编排、历史与资源记录；C1 + P2 | 有效 E2E、独立业务预期、正确的成功/未知表示和计量，无生产修改 |
| B | Porcupine 本项目模型、故障代理观察；C2/C3/C4/C5 | 每种故障有证据；模型能识别独立的错误样例；重启及目标副本结果正确，未知/未覆盖不算通过 |
| C | 复用上述能力实现 P1/P3/P4，完成配置冻结和正式基线归档 | 每场景回答独立问题，资源可承担，对比口径完整，保留全部结果和限制 |

批准方案表示可以按约定批次编写测试，不表示已经批准未经审查的正式运行，更不表示 S0–S13 生产改造已开始。每批次完成后先展示代码与行为，用户审查后再执行约定验证。待首期场景全部完成且有效旧基线建立，才把 T0 标为完成。当前 A/B/C 代码已完成编写并审查；系统资格运行、配置冻结和正式基线未完成。

后续各批次 prompt 必须带上本批次输入/输出、场景卡、依赖、外部来源与本地落点，并逐字包含：

```text
当遇到方案中未提到的部分时，先不要自作主张去写,而是汇报当前遇到的问题（注意先不要堆砌专有词汇，用我能看的懂的话去讲当前情况，有需要时再用专有词汇）。

代码要考虑复用性，间接性，安全性，不要破坏别的模块和层次的production级代码。

当本次任务接续上一次任务后，需要在完成前检查之前的代码是否因为当前改动有冗余的地方，有的话可以删除，也要检查是否有根本没用到的接口或函数之类的，也需要删除。

测试应该保护“这个项目自己承诺的行为和风险边界”，而不是给每一层实现细节、第三方库行为和历史重构痕迹都建立一套测试。

不得为测试便利修改生产 API、默认路径、持久化语义或加入生产测试钩子；不得通过适配器补做业务、持久化或恢复。只实现已分配批次，代码先交用户审查，运行范围另按约定执行。
```

调研后用户已确认并授权按批次实施。当前 A/B/C 已形成完整测试侧代码，上一轮真实列长度及覆盖缺陷已修复；本轮 17 项 Python 自检及正式客户端/节点构建通过。三节点系统验证及正式基线尚未完成，完整记录见 [A/B/C 审查](testing_review_abc.md)。Go/Porcupine 只属于测试侧，不进入生产依赖。各批次参考均说明来源、所解决的问题及本地落点。
