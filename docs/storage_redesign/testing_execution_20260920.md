## 环境

WSL2、Release/Clang 14、三个本机进程；每节点 256 个 BufferPool 页。Linux 可用内存、输出空间由原运行器按约定采样。另用 Windows 只读查询确认虚拟磁盘所在 C 卷剩余 63,088,377,856 字节，起跑参数向下取 58.75 GiB。设备与进程采样不是硬资源隔离。

## 失败分析与处理

### 1. C1 首次运行：生产表页写越界

`C1-qualification` 在第 5 批装载时失败，三个节点均退出 139。前四批 256 行已经收到成功响应；第 5 批结果未知，不能断言完全没有生效。失败发生在正常装载，尚未进入故障注入。

用原始节点目录的副本重放已提交日志，Release 节点再次发生段错误，调用链经过 `TableHeap::InsertTuple` 和 `BufferPoolManager::CheckedWritePage`。后者是崩溃位置，不等于最初破坏内存的位置。

进一步只为诊断副本编译带符号的表页和缓冲池对象，GDB 在表页容量计算处截获：

```text
slot_end_offset = 913
tuple.GetLength() = 1057
num_tuples = 15
offset_size = 392
tuple_offset = 18446744073709551472
```

`size_t` 计算 `913 - 1057` 下溢，巨大的正数绕过容量判断，返回为 `uint16_t` 后变成 65392；随后向只有 4096 字节的页面外复制记录。1057 字节包含合法的 1024 字节正文及记录编码开销。

修复：[table_page.cpp](../../src/storage/page/table_page.cpp) 在减法前检查记录长度是否超过现有数据边界；不足时返回空间不足，由现有 TableHeap 换页。没有改变页格式、接口或测试数据。

复测 `C1-after-table-fix` 使用同一内容/种子/预算，通过全部阶段：455 行增长、57 行缩短、512 行删除、256 行重插，最终 1792 行全字段核对通过。此修复由原 C1 直接覆盖，不另写重复的每层内部函数测试。原失败文件、原 Release 二进制与调试日志均保留。

### 2. C2 首次启动：测试端口预检问题

紧接上一轮启动时，预检返回 `Address already in use`，业务场景未开始。生产 TCP 监听器使用 `SO_REUSEADDR`，测试预检未采用同样设置，不能正确处理刚结束运行留下的连接状态。

修复：[run.py](../../test/storage_acceptance/run.py) 的探测套接字与生产监听器保持一致。仍检查真实监听冲突；原有“探测不保证启动时无竞争”的边界保留。原启动失败控制台记录不删除，复测另存 `C2-r1-after-port-check`。

### 3. C5 长路径首次运行：测试误用分片续传字段

目标节点已把 `snapshot_base_index` 推进到 256、`published_applied_index` 推进到 290，代理也记录了 `success=1, complete=1, stale=0, match_index=256` 的真实安装响应。测试仍等到 60 秒截止，因为它额外要求响应的 `next_offset` 等于快照长度；现有生产协议在完成响应中将该续传游标置零。

修复：[faults.py](../../test/storage_acceptance/faults.py) 在完成确认分支使用完成标记、非 stale、关联的 term/request/from/to 与 match_index，不再把只用于未完成传输的游标当作安装条件。相应风险自检改为真实完成响应的形状，仍拒绝仅 stale 的证据。

原失败 `C5-long` 不重写为成功。`C5-long-after-evidence-fix` 重新执行全部装载、停机、256 次修改、安装证据、目标副本全表核对及继续写入，完整通过；不是仅离线修改旧报告。

### P2：现有生产执行方式阻塞 Raft 推进

正常资格运行首个范围读取耗时 **527.9 ms**，下一次读取收到 `NOT_LEADER`，任期从 1 变为 2。三节点 RSS 采样峰值约 39.3 MiB，可用内存约 5.1 GiB，没有触发内存或磁盘预算。此结果不是吞吐数字，也不是线性一致性反例。

为区分原因，另做一次明确标为 `diagnostic` 的运行，只启用已有外部 Raft 消息观察代理。数据、业务核对和节点超时不变，不将它用于基线。该运行再次在准备核对阶段换主：

- 两次读取耗时约 540.0 / 483.6 ms。
- 观察到原 Leader 向两个 Follower 发送 AppendEntries 的间隔约 559 ms，随后 Follower 发起选举，原 Leader 转入任期 2。
- [node.cpp](../../src/distributed/node.cpp) 中 `HandleRead` 在执行 `ExecuteReadSql` 期间持有节点 `mutex_`；`TickLoop` 与 Raft 接收回调需要同一把锁。因此慢读取会阻塞心跳及协议处理，与时间线一致。
- 测试当前配置的心跳间隔为 50 ms、选举超时为 300–600 ms。该组合在本机 D1 负载下未通过健康运行资格；不能仅凭此认定所有机器都必然失败，也不能简单归因于 16 GiB 内存不够。

证据见 `P2-c1-qualification/`、`P2-network-diagnostic/` 和 `diagnostics/d1-leadership-analysis.json`。两个失败均原样保留，没有重试直到成功，也没有减少 D1、放宽错误门槛或擅自调整选举超时。

下一步要先处理慢业务执行与 Raft 推进共锁的问题，或讨论适用于新旧两版的共同运行配置。不能简单在读 SQL 前解锁：需要保证读取期间的状态、Apply 与快照安装之间仍有正确的同步和版本边界。此项超出本轮表页容量检查的局部修复；本轮记录问题，不临时实施未讨论的并发架构。性能资格与正式基线仍未完成，T0 不标记“已完成”。
