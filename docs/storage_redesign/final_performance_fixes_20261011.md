## 1. 公共 CRC 与 B 页读取

保留 CRC32C 的多项式、初始/最终取反和 Extend/Combine 接口。x86 支持 SSE4.2 时一次选定硬件实现，否则使用可移植查表实现；不全局开启机器专属编译选项。批次内仍保留各持久单元的校验边界，固定正文后计算；已有分块校验可通过 Combine 合成，不能把独立单元改成一项延后校验。读盘校验必须先于使用。

B 冷页与 checkpoint 读取经 CheckDiskPage 后，解码正文、复用已验证页尾和 LSN，不再调用生成新页的 Seal 重算。内存正文和盘上正文不同，禁止整页拷回覆盖解码结果。新页/修改页继续 Seal。

## 2. F14/F22 有界哈希分组

同一对象最多 16 个 allocation 共用一次 PendingRange 扫描。游标携带固定发现视图及按 allocation 分组的候选记录；每轮扫描和每 allocation 保存记录都不超过既有 `max_scan_entries`。发现缓冲先取得 F31 额度，跨对象不混用身份。扫描完成即释放 B 视图，释放事务仍按当前版本核对记录、剩余所有权、共享引用和 IO/pin；直接引用分组结果，不再复制整组。发现结果不是新的权威索引，不持久化；冲突后复核，关闭丢弃。仍是一批共用一次扫描，并非哈希函数能直接从盘上找到全部旧记录。

## 3. F28/F25/F35 捕获与后台构造分离

在完整 Apply 边界固定 index/term、Catalog、Session、脏页副本和已持久范围保护。实际完成捕获且既有执行器接纳后台工作后，协议线程才解除业务收束。后台只使用捕获内容，不再读取活动数据库的最新版本。克隆、正文写入和 checksum 不占用 Apply 执行角色。

后台构造的是未发布候选；完成事件交回序列化协议所有者，复核目标是否仍适用，再沿原 Manifest 发布、日志保留和回收顺序推进。新任期不能使旧完成事件回滚状态；已安装更高快照时丢弃旧候选。关闭排空已接纳任务并处理候选，资源紧张时不把“排队未接纳”当成已交接。旧文件/KV 状态机不支持固定共享捕获时沿原路径。

允许捕获本身等待必要保护/IO，不承诺零暂停；目标是移出捕获后的耗时构造。F28 小恢复根的提交仍持生命周期锁、可能等待持久化；Clone/正文写入/checksum 不持该锁。独立 F28 请求保留现有有界预刷，Raft 共享捕获直接保存尚脏正文，不等待整轮刷出。正常快照触发不再同时安排独立 F28 候选。普通页版本、已捕获范围、候选与已发布恢复入口分别沿既有所有权管理，不取消必要保护。

## 4. F23 恢复探测复用

### 恢复流水线（F34/F23，配合 F35）

NodeStorage 完成 B/Journal 与对象服务恢复后，使用现有 TaskExecutor 并行准备 Raft StableStore/SnapshotStore/LogStore，与 A 的对象页及本地 checkpoint 打开重叠。两侧完成后才核对 checkpoint、snapshot、HardState 与日志边界；通过核对后移交同一个已验证 Store 候选。准备失败按现有恢复规则传播，不能跳过边界检查提前提供业务服务。

本地重放使用有界的双批次：主线程按 index 顺序 Apply 当前批，已有执行器预读下一批。只读到持久 commit；一个大 entry 仍按既有规则允许独立成批。额度随结果保留，当前批释放后才能重试未获额度的下一批。失败与退出等待已接纳读取完成。启动结束销毁预读执行器，正式 storage executor 仍是基线的一个在途名额；没有扩大日常提案或 Apply 并发。

这只重叠独立工作。B/Journal 打开仍是前置依赖，Apply 仍有顺序，不能预期恢复时间变成最长单阶段时间。

### 长连接（现有 DistributedClient/DistributedNode/TcpRaftTransport）

- 客户端按调用线程和 endpoint 缓存连接（最多 8 个），连续请求复用原 V1/V2 帧格式；一条连接一次处理一个请求，不增加客户端请求复用协议。
- 服务端用一个有界 poll 循环管理最多 128 条连接。收取不完整帧、等待业务任务、发送回复分别推进；SQL、持久化和 Apply 继续使用原任务执行器。每次收发最多 256 KiB，正文、输出和已接纳任务沿用 F31 额度。
- Raft 每 peer 独立发送队列、发送线程和连接；三节点下每节点两条发送线程。慢 peer 不阻塞另一 peer，保留全局及单 peer 排队上限。接收端可交错处理多条长连接。
- `FramedSocket` 只共用非阻塞帧收发和缓冲寿命，不另设任务调度器、预算或协议状态机。客户端与 Raft 仍各自负责接纳、协议判断和重试。
- 已知 EOF 可在新发送前重连；发送结果不明确时不在传输层自动重放业务写入。Raft 消息失败由原协议重试。关闭先停止准入，再排空已经接纳的实际业务工作。

### 完整优化版怎样处理 ReadIndex

旧版源码证据保存在 `.cache/rollback-previous-20261012-191457/before/`。它同时做了两项改变：

1. 在 `AdvanceReads()` 中申请 `next_read_context_ + 1`，只有 `StartReadIndex()` 实际接纳后才推进计数，避免编号顺序与接纳顺序倒置。
2. 已到达读取共享一个 `ReadRound`；接纳后封闭这一轮，后到请求进入下一轮。等待多数派确认及已发布 Apply 进度达到读取边界后，才提交 SQL；任期改变或读者退出仍清理原任务。

当前代码仍在 `StepRead()` 首次处理请求时先分配编号，而 `StartReadIndex()` 拒绝不大于 `highest_read_context_` 的编号。因此存在可由代码推导的交错：A 先取得 101 但未被接纳，B 取得 102 并先被接纳，A 再用 101 重试将持续遭拒。旧版的第一项修正针对这一问题；第二项减少独立读取确认轮数。旧版六轮 P1 重试为零，但缺少逐请求编号轨迹，不能断言当前 15 次超时全部来自这种交错。

### 是否导致 P2 四/八客户端下降

### 共同协议与实现

- `DistributedNode::StepRead()` 只把线性读加入当前尚未接纳的 `ReadRound`，保存任期；不提前给各请求分配独立编号。
- `AdvanceReads()` 在持有原节点锁时提交下一编号；仅在 `StartReadIndex()` 接纳成功后推进计数并封闭该轮。后到读取进入新轮，不复用已经发起的多数派确认。连接循环处理本轮帧后尝试推进，原 Tick 负责后续重试；不引入定时合批等待或新执行器。
- 同轮读者共享确认 index，分别在 `PublishedAppliedIndex >= index` 后交给原业务执行器。执行完成仍检查结果所属发布进度；STALE 读取沿原路径，不经过 ReadIndex。任期变化、失去 Leader 就绪或关闭时，未完成轮次失效。
- 请求完成、超时或断开只退出自己的轮次引用。待确认目录保存弱引用，最后一个读者退出才取消对应 Raft 确认；确认完成即移出目录。已被执行器认领的 SQL 仍由原任务寿命负责，不因连接退出提前释放。
- 状态均为有界连接/在途请求的内存控制信息，不持久化，不新增 GC 或另一份业务视图。没有读取的连接循环不额外取得读取维护锁；Tick 在已有锁内检查空目录。写入的准入、依赖、持久化与 checkpoint 策略保持不变。
