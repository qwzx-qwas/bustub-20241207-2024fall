# S10 原地覆盖与旧尾复用：实现及审查

范围基于 `50154cd` 后的工作区。用户确认先补本项，再统一验收。执行协议见 [S10 §12](s10_deferred_protocol.md#12-s10-接续原地覆盖与旧尾复用2026-10-10已授权先于统一验收)。前一轮未提交 Git、未跑共同 C/P。本次用户已授权：复核后接续既有收尾验收；新结果见 [统一验收记录](final_acceptance_20261010.md)。

## 1. 先分析生产逻辑，再写测试

先审查 Plan/Assemble、F14 Register/Reclaim/共享发布、Prepare/Apply、DeferredLoop、实际 IO 与校验。关键结论：

- 原 F14 的读许可只保证不释放，并不允许覆盖。有旧许可时必须 COW；没有旧许可时在同一 gates_ 表中禁止迟到旧读者进入。没有等待 IO 时持有范围 mutex。
- NodeStorage.ShareObjectRange 从注册读许可开始，一直保留到共享提交结束。复用门闩与共享申请因此不会同时成功；取得门闩后检查当前 SharedUnit，提交再检查最新 B 视图。
- 旧视图不等于物理 pin。新身份接管后，CheckOwnership 拒绝旧 allocation；它已经和释放后再分配采用同一规则。持久 checkpoint/快照由 SharedUnit 阻止覆盖，不能以 Stale 代替其保留承诺。
- 只复用一个完整、自有、全部存活的分配。局部退出、跨分配、未完成任务、过大的保留正文、尾部不足等继续 COW。追加不搜索历史碎片，不重新挂回已退役字节。
- 当前 Allocation/OwnedRange/Mapping/Checksum/Deferred 编码足以表达身份转交，不加格式。旧新 allocation 不同时拥有范围，位图没有空闲窗口。
- 发现并修正一条交接缺口：原 Apply 无 F12 reservation 的分支只传元数据。复用没有新 reservation，必须同时传 payloads，否则缺少完整恢复正文。
- F27 只消费已发布任务；WriteCommon 不为复用范围发 Data IO。失败前旧 Data 不变，提交后完整有效正文和确定的零填充足以重做整分配写入。

## 2. 具体修改

| 文件/入口 | 修改及用途 |
| --- | --- |
| `object_transaction.cpp::Plan` | 按实际修改、Deferred 阈值及已接纳的输入＋两个单位预算寻找候选；组装复用原 Assemble，不从 SQL 字段估算 |
| `object_mapping.cpp::PlanReuse/CanReuse` | 定位一个完整存活分配，检查共享/待落位及完整所有权；规划时判断可行，取得许可后与最终提交时复核当前事实 |

| `object_io.cpp::WriteCommon` | 仅给非复用部分申请 F12 预留；给复用部分计算完整单位校验，不提前覆盖；许可不足使用原 COW |
| `object_mapping.cpp::Prepare/Apply` | 新 allocation 身份原子接管原物理范围，更新有效长度/校验/任务，无预留也提交 Journal 正文 |
| 原 F27/F21/F12 | 复用现有持久任务、读取来源、后台 Flush/完成、回收接口，无新增实现模块 |

| 新测试（S10Reuse） | 目标 → 输入 → 执行 → Oracle → 失败含义 |
| --- | --- |

## 4. 八项测试设计审查

1. **全景和类型：** 如上；性能不在本轮范围，不以用例耗时或数量证明吞吐。
2. **Oracle：** 正文由独立 `Value(seed,position)`、vector 的插入/复制建立；撕裂磁盘用独立前半/后半模型核实。仅在要证明“没有新分配”时观察正式映射的物理位置和身份，不读取私有 metadata 编码拼 expected。
3. **生产污染：** 没有测试 hook、计数 getter、测试默认值或测试分支；故障/暂停/半写全在测试链接 wrapper。未为测试声明设备支持原子写。
4. **接口：** PlanReuse/CanReuse 在既有私有桥，TryOverwrite 是 ObjectIO 的私有协作；许可类型不提供外部构造和地址注入。真正调用者是生产规划、IO 和映射提交；删除测试仍必须存在。
5. **重复：** 原 F27 崩溃用例验证新目标；新撕裂用例验证已有 Data 被破坏，两者失败边界不同。原 F27 混合事务保留，新混合场景新增身份转交和迟到读者门闩。F19/F30 只恢复并复用其源码。全部阶段验证归档，未来由等价共同测试接管后简化。
6. **发现错误：** 对移除读者保护、共享检查、无预留正文提交、迟到读门闩、待落位限制做隔离源码变异；必须正常退出为断言失败并出现指定性质，编译错误/挂起/崩溃不计检出。实际结果在下一节。
7. **稳定性：** 使用条件变量在真实 syscall 处暂停，15 秒仅防挂起；RAII Cleanup 先释放 gate 再关闭节点。fork 在父节点关闭后进行；子进程 `_exit`，runner 超时杀整个进程组。固定 seed，临时唯一设备，无网络依赖。原测试仅给 EXPECT_FALSE 外的 if 加花括号，解决 GCC 的宏 dangling-else 警告，不改变判据。
8. **结论矩阵：** 六项均保留于唯一 F27 归档；原 F27/F19/F30 保留复用。主要风险分别为复用真实性、旧版本保留、迟到写、撕裂恢复、提交顺序、混合事务/迟到读；未发现仅测标准库或复制实现的新增测试。当前不是裸设备/真实掉电证据，未覆盖的统一验收不追认通过。

## 5. 执行证据与限制

最终共 39 个不同正常场景通过：F27 18（原 12＋新增 6）、F19 10、F30 11；5 个指定变异均被相应断言检出。F27 最终复验位于结果包 `verified/`；Common/F30 位于 `regressions/`，使用相同生产源码，后续仅改动未被这两组调用的 F27 新测试判据，因此未重复运行。满容量场景包含 4 KiB/16 KiB 两种单位，不重复计数。

测试审查中修正了两个工具问题：旧 EXPECT 宏外 if 缺括号触发 GCC 严格警告；首次“移除正文”变异被后台未开始的等待断言发现，但 runner 错误期待另一消息。现改为发布后立即解析来源，明确报出缺少 Journal body；五个变异重跑通过，诊断日志单独留存，不作为正常测试通过数。生产实现不因该工具问题增加错误吞咽逻辑。测试为 Release 实际组件路径；本轮未运行全库 ASan/TSan、完整性能或真实机器掉电，旧二进制读取新数据的反向兼容也未单独执行。当前格式重开、阈值零恢复和 F30 旧格式读取分别有实际验证。

归档入口：[本轮结果与清理](../../test-results/storage-f27-reuse-20261010/README.md)。F27 源码和结果各保留一份最终压缩包；旧 F27 包替换，其他模块有效依赖与历史说明保留。精确源文件、依赖与包内证据由 SHA256 校验。


## 6. 最终职责与一致性复核

- 新增的是原 CommonDataWrite 持有的覆盖许可、私有规划条件与原子身份转交；没有新的分配器、缓存、日志、回收器或线程。规划阶段检查固定视图，许可阶段检查竞争，提交阶段检查最新 B 事实，各自防止不同时间点的失效，不能简单删成一次检查。
- 当前主阶段表、F13/F14/F18/F27/F02 和 S7/S10 交接均引用同一 §12。历史“首轮仅新目标”保留日期；不把它当当前尚未实现。默认 Common 和 Raft Store common_only 不改变；必须启用现有 Deferred 阈值才进入复用选择。
- 本轮未承诺任意分配内子范围就地更新、拼接旧尾与新范围、原地覆盖共享版本、物理掉电测试或最优性能阈值。它们不是发现错误后悄悄降级的内容，而是已确认有界方案的明确范围。
- 已满足本轮实施与定向测试要求；下一步仍是先核对本轮变更，再按既有共同方案执行同版本统一验收，不能把这 39 项当作统一验收已完成。

## 7. 再次复查与统一验收前修正（当前）

本次先复查代码、复验原39项/5个变异，再继续核对 WriteCommon 与 WriteDeferred 的预算交接，发现复用分支绕过总写入上限。现将总写入量与新分配量分开；复用及新分配共同受原 max_write_bytes 限制，在 Journal 发布前拒绝，避免承诺无法落位的任务。

新增 `ReuseObeysWriteBudgetBeforePublication`：分别验证重开后降低写入上限，以及复用＋新分配合计超限；要求 NotCommitted、旧正文和控制记录不变、节点不故障，之后允许的写入及重启正常。新增 `reuse-budget` 变异移除此限制，必须在发布结果断言检出。先推导生产缺口，再加入测试；没有新增生产 getter/hook/配置或模块。

当前源码重新构建后 **40项正常场景、6个指定变异全部通过**（F27 19、Common 10、F30 11）。旧39/5是前一版本证据。共同验收按新授权接续，详细原始结果与限制见 [统一验收记录](final_acceptance_20261010.md)，不混入阶段计数。

## 8. 收尾 P3 暴露的完成额度背压修正

详见 [收尾验收 §5](final_acceptance_20261010.md#5-p3-暴露的实际阻塞定位中)。Journal 将已有 Deferred 完成预留导致的暂时不足正确分类为 Full；单请求自身超限和真实空间不足仍拒绝。提交角色关闭时不会等待已退出的 Deferred 线程释放额度。

先用实际失败状态及独立诊断确认额度和调用栈，再增加继续／关闭与单请求超限两项场景，并更新旧预留边界判据。当前42项正常测试通过、7个指定变异检出。F27源码包仍唯一，结果包当前复现源在 pressure-review（budget-review 与根目录源码为历史）。包内1561个证据文件已核对SHA256；共同C/P正在新版本下接续，不能提前宣称全部验收通过。
