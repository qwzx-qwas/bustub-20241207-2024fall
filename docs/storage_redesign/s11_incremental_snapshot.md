# S11 / F25：节点间增量快照

2026-10-07：用户已授权方案、实现与测试。本节接续 [共享快照](s11_shared_snapshot.md)，增量传输及自动追赶的本轮范围已完成；执行证据见 [本轮审查](s11_automatic_execution_20261007.md)。主责仍为 F25，配合 F28/F13/F14 及现有 Raft 传输，不新建同职责服务。

## 1. 已确认的取舍

- 传输发生在 Raft Leader 与 Follower 之间。发送端比较自己的两份固定快照；接收端复用自己的基础快照，物理地址不跨节点传递。
- 沿用 index/term/CRC32C 身份与现有格式/长度核对，不增加 SHA 或全局内容寻址。接受原校验的风险边界，不称 CRC 为无碰撞证明。
- 差异只按固定映射的原 owner、allocation 和范围判断。同一不可变内容可复用；无法证明相同就发送新正文。不做新旧正文比较，也不新增 changed bitmap。现有生成/接收完整校验仍保留。
- 传输描述可以增量，最终持久目录仍完整，恢复不追溯增量链。完整目标页面目录表达页面删除；Catalog/Session/恢复边界随完整头部传输。
- 格式限当前原页流 BSPAGE01；canonical/文件 Store 保留全量。压缩、跨重启续传及 F35 全面异步仍未在本轮启用。

## 2. 协议与资源

**2026-10-07 接续：基础保留及追赶策略已获授权。** 正常追赶始终先补日志；日志不足才以最新快照为目标。增量是构造同一完整目标的传输优化，不要求逐代安装旧 checkpoint。

1. Manifest v2 增加可选 transfer_base，读取兼容 v1 的 latest/previous。发布时把退出恢复保留的 previous 轮换成传输基础，至多一份，正文共享既有分配；按现有 max_snapshot_bytes 和 max_owned_objects 限额管理，不引入无界历史。基础不参与 OldestRetained，也不拖住历史 bridge log。接收端可从三种持久角色中匹配基础；角色退出仍须等待在途 lease。旧二进制不能打开新 v2 清单，不做降级写入。

2. 保留现有全量 RPC 字节编码，增加 Offer/OfferResponse 和增量分块类型。未获 Offer 确认，在一个 heartbeat 周期后走原全量；旧二进制不识别新 Offer 时也不依赖它处理增量。确认后错误不转换为 unsupported。
3. 每块明确目标逻辑偏移，包含 DATA 或 REUSE(基础偏移、长度)，最多 64 KiB，按数据库页边界组织；连续同类范围可合批。响应进度为已构造的目标逻辑前缀，不是网络正文累计量。
4. Offer 的 request id 标识会话，结合 term/leader/target 隔离迟到请求；重复块必须与已接受记录/正文一致，不能重复加引用。接收停滞、换 term、转选举和改走全量退出会话。每节点仅一个接收候选，每 peer 一个发送状态。接收端沿用发送端已有的递增请求号，保留当前 term 的快照请求边界；旧 Offer/旧全量块不能取消较新的会话。当前 Offer 重发并再次被接受时续期。会话结束后仍保留该边界，进入新 term 时清除，不持久化接收进度或新增网络字段。
5. 复用已有 max_snapshot_bytes、IO/提交额度；描述条数至多目标大小/页大小，正文工作缓冲至多一个有界块。基础与目标目录有相同上界；不收集整份正文到 RAM。
6. 增量协商确认前，沿用 S8 的最终清单预检：计入目标发布、私有正文退役及可能退出的旧入口。Raft 验证完成后才决定是否保留旧恢复入口，因此预检覆盖两种发布结果所需的最大额度。额度不足时，在创建新候选前明确失败，不先收正文再发现清单无法提交。此检查只针对已知配置上限，不承诺随后设备写入或动态空间申请必然成功。它保护新申请的容量及已发布状态；Raft 开始更新的协商时可以取消尚未发布的旧接收，不承诺新协商失败后继续旧接收进度。

## 3. 接收布局与发布

头部首先作为 DATA 接收。所有网络 DATA 按序写入私有正文对象；仅记录有界的目标范围→正文来源说明。写完后，新快照对象扩大逻辑长度，逐范围共享私有正文或本地基础正文。这个目标对象不再执行覆盖写，避免不同分配粒度下的扩展写与共享映射相撞。

私有正文不是第二份复制：最终快照直接共享新正文的分配，不再复制一遍正文；底层 Common 追加仍可能存在对齐/COW 写放大。私有对象随 Manifest 发布在同一提交中退役，F14 保护被引用的单位。目标目录和共享引用持久化、完整校验通过后，构建并验证 PreparedSnapshot 一次，持久发布及 Raft 边界更新后安装同一候选，再接续后缀。中断候选不成为恢复入口；重启沿原所有权登记清理候选，从零接收。阶段收尾关闭 lease 后才允许物理回收。

## 4. 开源参考与内化

- [Ceph RBD snapshot mirroring](https://docs.ceph.com/en/latest/rbd/rbd-mirroring/)：fast-diff 借助变化跟踪避免扫描全镜像正文。本项目先使用已有不可变映射身份筛选，不照搬新的 object-map/bitmap。
- [RocksDB BackupEngine](https://github.com/facebook/rocksdb/wiki/How-to-backup-RocksDB)：识别已有不可变 SST，备份各自保存完整文件清单。本项目保留完整目标页目录与独立引用，沿用现有身份而非新增哈希机制。
- [Btrfs send](https://btrfs.readthedocs.io/en/latest/dev/dev-send-stream.html)：发送 extent 复用说明而非正文，发送格式独立于两端物理布局。本项目 REUSE 指基础快照逻辑范围，接收端查询本地映射。

## 5. 实现顺序、审查及测试

先行逻辑审查：固定目录解析复用、内容身份比较、lease 交接、不同分配粒度、消息重复/换代、失败不发布、恢复和 GC。之后按顺序实现目录解析→F25 差异/候选→RPC/节点接入→生产路径验证。复用原 F25/S8/F28 测试，新增增量与全量同目标恢复、错误基础、删除/修改/新增、取消/GC/重启、重复块及网络传输量判据。原 C/P 内容不变；发送字节减少不等于已完成性能比较。

代码要考虑复用性，间接性，安全性，不要破坏别的模块和层次的production级代码；接续完成前检查冗余旧代码、未用接口并删除。不要过多纠结于边界条件和防御性编程，防止可能出现的问题被掩盖。先从代码逻辑分析，确认后再写必要测试；不要一开始通过编写回归测试检验。

测试应该保护“这个项目自己承诺的行为和风险边界”，而不是给每一层实现细节、第三方库行为和历史重构痕迹都建立一套测试。写完走总方案八项设计审查，禁止 production test hook/getter/默认路径污染；模块测试只压缩归档，替换本模块旧包，独立依赖包保留。

## 6. 本轮实现 prompt

按上述顺序执行已授权增量路径，不实现压缩或新强哈希；复用现有队列/引用/原子发布。先审逻辑再验证，报告实际改动与未覆盖边界。当遇到方案中未提到的部分时，先不要自作主张去写，而是汇报当前遇到的问题（注意先不要堆砌专有词汇，用我能看的懂的话去讲当前情况，有需要时再用专有词汇）。既有授权及本节已确定的实现选择无需重复确认。

## 7. 本轮自动追赶与去重接续（已授权）

实施顺序：清单角色/寿命 → 轻量协商及一次差异规划 → 有界传输会话 → 接收候选交接 → 合并正文遍历及引用提交 → 逻辑审查 → 生产路径测试和阶段归档。

### 7.1 选择与会话

- 发送前只取得固定目标/基础的使用权并识别格式；Offer 接受后才比较映射。Offer 当前也建立接收候选；如果收益不足，发送更大 request id 的全量首块，接收端沿已有取消路径退役增量候选，不能留孤儿对象。
- 同一 Store 保留至多一份目标/基础计划；相同 peer 请求共享不可变描述，发布/退役时退出缓存，活动会话自行保留 lease。不是长期正文缓存。
- 首轮采用可解释的保守成本代理：计算省下的正文、REUSE 描述（每消息按 32 字节预算）、相对全量新增的停等消息（每次按一页等价成本）。净节省至少目标大小 20% 才使用增量。它不是毫秒预测，也不是开源项目给出的性能数字；实际网络/IO 校准、共享元数据提交耗时进入后续性能评测，不宣称此规则在所有设备最优。不读取双方正文来估算。
- 每个 peer 只保留一个最多 64 KiB 的未确认块，心跳重发同一块；确认后丢弃。新快照发布本身不改会话目标。正常恢复日志下界若越过旧目标，先取消该会话再裁剪，下次重新选择 latest；因此不靠无限保留日志支撑慢传输。
- 没有基础/不支持格式/收益不足走全量；真实损坏和持久化失败不得伪装成 unsupported。

### 7.2 已确认的重复工作及本轮整改

| 重复来源 | 本项目落点 |
| --- | --- |
| Validate 构建销毁、Load 再构建 | RaftStateMachine::PrepareSnapshot 持有已验证数据库和 FSM；持久发布后 Install，失败取消候选 |
| 页流校验独立扫描后再加载 | 加载页时累计内部 CRC；外层传输校验仍有独立职责 |
| 发送端内部/外部 CRC 各读一遍正文 | 一次读取正文得到 CRC，按长度组合头部与正文 CRC；native 格式字节保持兼容 |
| 全量接收结束重读全部正文求 CRC | 只对首次接受的顺序正文累计 CRC；重发仍比较已接收内容 |
| 多个索引分别扫描，再扫描验证时间戳 | Catalog 先创建结构，一次表扫描验证记录并填充全部索引；向量索引仍按原批量 Build 规则 |
| Clone/共享快照/增量完成每页提交引用 | F13/NodeStorage 共用有界连续范围构建，64 KiB 上界，遇规划容量限制缩小；不能重试不确定提交 |
| 高水位内每个页号重新查询映射 | 按已有映射范围枚举有内容的页，跳过逻辑空洞 |
| 对象输入先变成 vector 再复制进帧 | SnapshotInput 支持带寿命许可的目标缓冲；native 恢复复用 F02/F26 借用帧路径，文件输入仍用兼容读法 |
| 同一块重试重读、同一目标重复规划 | 每会话一个块、同一固定目标一份不可变计划 |

正常重启对已发布恢复内容的完整性检查不因去重而删除。AppendEntries 多在途、协议线程与 SQL/IO 分离仍归 F35；S12 管统一后台预算；压缩和跨重启续传尚不在此次实现范围。

### 7.3 参考及边界

- [Ceph asynchronous recovery](https://docs.ceph.com/en/reef/dev/osd_internals/async_recovery/) 用日志/缺失内容估算恢复成本。本项目内化为先判断日志能否接续，再依据描述/正文量选择快照传输；不把 PG 日志等同于 Raft 业务命令，不引入 OSD/PG 协议。
- [RocksDB BackupEngine](https://github.com/facebook/rocksdb/wiki/How-to-backup-RocksDB) 共享不可变内容且备份保存完整清单。本项目内化为独立传输基础只保留内容、目标恢复仍完整，不维护链式增量恢复。
- [zlib crc32_combine](https://github.com/madler/zlib/blob/develop/crc32.c) 可从分段 CRC 和长度计算拼接结果。本项目以 CRC32C 的多项式实现组合运算，减少读取次数；未引入 zlib 依赖或把 CRC 当作强内容哈希。

新接口均需有本轮生产调用方，不能为测试新增 getter/hook。验证重点为自然 Leader 选择、轮换后重启/GC、低收益全量、候选只构建一次且失败不替换业务、所有既有校验仍有效。先审控制流与寿命再补场景；压缩归档时旧 F25 包直接替换，不保留失效包。


### 7.4 自动追赶验证接续

自动追赶的恢复验证应包含真实业务后缀，经 Leader 提交后重启接收节点，并由正式 Raft 启动应用后缀；不使用测试手工 Apply 代替该路径。固定目标的判据在正式发送消息上核对；进度超时单独记作无法推进，不能替代目标身份错误的直接证据。本轮再审及唯一验证记录见 [执行审查 §7](s11_automatic_execution_20261007.md#7-再次设计审查真实业务后缀与直接失败判据2026-10-07)。
