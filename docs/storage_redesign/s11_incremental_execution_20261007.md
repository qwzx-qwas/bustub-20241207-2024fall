基准 `d92829c`，协议见 [增量方案](s11_incremental_snapshot.md)。**整体未完成**：基础保留与真实自动追赶策略有待用户选择，不能用接收组件结果声称三节点自动增量追赶完成。以下记录已经执行的独立部分。

## 1. 先行逻辑审查与实际改动

- `ReadPageSnapshotDirectory`：从业务安装代码提取有界原页目录解析，安装和差异规划共用格式；CRC 正文校验仍由原安装/Store 承担，不在规划时读取两份正文比较。
- `ObjectSnapshotStore::PlanDelta`：比较同一节点固定快照的原 owner、allocation、范围，生成 DATA/REUSE；捕获源与目标 lease。相同字节但身份不同仍发 DATA，不新增哈希/去重数据库。
- `BeginDelta/StageDelta/FinishDelta`：确认本地基础后持有 lease；DATA 写私有正文对象，REUSE 记录本地基础逻辑范围。全部接收后通过现有 ShareObjectRange 建立目标映射，完整校验后才能成为完整候选。目标不混用扩大处理范围的 Common 写和共享映射，支持分配单位大于数据库页。
- `Publish/Cancel`：私有正文退役并入既有 Manifest 事务；取消同时退役候选/私有正文。重启由已有 ownership 清理，不持久化半份增量进度。
- `RaftRpcCodec/RaftNode`：保留旧全量编码，增加 Offer 和增量类型；Offer 未确认时全量，确认后错误不当作 unsupported。处理 term、会话、迟到响应、重复块、进度与到期退出；继续使用现有消息队列，没有新增服务、等待线程或全局锁。
- 在写测试前发现 `previous` 与 bridge log 的保留耦合，登记并询问策略；未以测试方便改变日志恢复规则。已编写的 sender 接续仍使用既有快照触发条件，该部分的正常集群收益没有验证结论。

### T1：目标 → 输入 → 执行 → Oracle → 失败含义

- 输入：38 条有差异的大正文记录保持不变，另一张表 UPDATE/DELETE/INSERT；接收端分配单位为基准的两倍。接收端额外生成一个合法中间恢复点，使协商的基础成为 previous，可以在接收中退出保留并执行 Collect。
- 执行：真实 Prepare/Apply/F28/Capture → PlanDelta → codec 编解码 → Begin/Stage → 原发布/Load → GC、重启和提交日志接续；每块重复发送一次。
- 判据：独立 SQL 构造的完整预期行、Session 回复的明确 request=7/term=3/commit=7，以及相同请求的 RETRY_LAST 分类、删除行不复活；目标流逐段等于同一全量目标（该字节比较只能作为组合判据，不能替代独立 SQL 预期）；发送正文少于目标正文并实际存在 REUSE。沿用测试 pwrite 观察器，在候选构造期间确认未变化正文没有再次写入接收端 Data 区；业务安装前关闭观察，不把现有安装复制误算为候选复制。重复块检查进度和最终内容，不能独立证明全部持久引用均已退出；本场景的退役/Collect 是在接收期间穿插执行，不是多线程同时调用 SnapshotStore。
- 失败表示：内容身份/目标偏移错误，旧基础缺失，共享所有权或安装恢复错误。组合测试不能唯一定位具体函数。传输字节断言只证明该场景避免了重复正文，不声称耗时更快。

### T2

- 输入：同 index 的基础描述改动 CRC；同一已收 DATA 改正文后重发；另一会话把合法 REUSE 指向基础头部，使最终正文错误。
- 路径：真实 Store 基础选择/重发校验/目标完整校验。
- 判据：拒绝、原 latest 不变、原 SQL 内容仍可读。没有使用被测编码器计算 expected 内容；CRC 仅是生产内部校验。
- 失败表示错误基础被选用、重试跳过比较或损坏候选被认为完整。

### T3

- 输入：真实接收一块后关闭并重启，保留已发布基础；重试旧会话，再建立新会话，并在新会话下重试旧块。
- 路径：ownership Open 清理 → SnapshotStore Open → Begin/Stage → 业务 Load。
- 判据：原基础仍是 latest，候选未发布，旧会话被拒绝，新会话恢复独立 SQL 预期。
- 边界：这是进程组件关闭/重开测试，不是真实掉电；已有 S8/F28 process-exit 测试复用，未额外冒充电源故障。

### T5：配置预算拒绝后的可用性

- 先审逻辑发现：全量 Stage 有最终清单预检，BeginDelta 漏掉；后者还多一个私有正文退役控制项。这里是既有 S8 资源契约遗漏，不新增恢复或基础保留策略。
- 输入：先按正常生产路径安装基础快照，再使用已有显式配置将操作上限设为 3。单候选创建和不保留旧入口的全量发布仍可完成，增量最终发布的最坏控制集合不能容纳。
- 路径：真实 Open/BeginDelta，连续拒绝 12 次；不执行 Collect，直接使用原全量 Stage/Publish，读回完整目标。
- Oracle：请求明确拒绝，原 latest 不变；后续合法全量工作成功，说明拒绝未消耗候选额度。不解码分配计数，不新增生产 getter，不断言对象编号。
- 新 failure mode：增量协商先创建对象，等全部正文收完后才发现无法发布；与原 S8 日志预检场景经过不同入口，不能由后者替代。

### T4

- 输入：真实 SQL 固定快照的差异，原始 Raft 节点作为接收端，两端 TcpRaftTransport 使用本机端口。
- 路径：测试驱动发送 F25 生成的 Offer/DATA/REUSE → 真实 TCP → codec → RaftNode::Receive/Install → Store/FS → SQL；随后真实 AppendEntries 接续。
- 判据：接收完成、正式快照边界、独立 SQL/Session 预期、后缀行和传输正文量；本轮进一步补入旧 Offer/旧全量分块隔离、重复协商续期和 term 换代，具体输入及 oracle 见 §9。
- **明确限制**：发送请求由测试驱动，未证明 Leader 在自然落后场景会自动选中共同基础。旧 S8 三节点测试验证原全量路径。本轮不能把两项拼成“自动增量 E2E”。

## 9. 接收会话复审（2026-10-07）

### 代码逻辑发现及修改

1. `Handle(SnapshotOfferRequest)` 原先将任意不同会话都当成替换：较早 Offer 迟到时，会取消新接收。增加当前 term 的快照请求编号边界；只在私有 RaftNode 状态保存，不增加 public getter、RPC 字段或持久日志。
2. 旧全量分块原先会无条件取消增量接收。全量也检查同一编号边界，迟到块被拒绝，当前候选保留；正常全量回退使用发送端已有的更新请求号。
3. 重复 Offer 原先返回 Accepted，却未更新接收期限；于是刚确认的会话仍可能按旧期限被取消。现复用新的 election deadline 续期。
4. 边界在会话关闭后保留，避免关闭的旧请求重新成为候选；在观察更高 term 或开始新选举时清除，允许新任期从较小请求号开始。没有添加队列、线程或重试服务。

同时纠正文档的预检范围：它保证超额请求不创建新候选、不更换已发布状态；此前“取消原候选前预检”只有 Store 内成立，Raft 新协商会先退出未发布的旧接收。现在明确不承诺新协商失败后保留旧接收进度，没有把它包装成支持断点续传。

### 测试设计复审

扩展原 T4 `TcpOfferAndDeltaInstallThroughRealRaftFollower`，不新增重复测试函数：

- 依次协商 90、100，再送达迟到的 Offer 90 和旧全量块 91。Oracle 是拒绝旧请求，以及会话 100 最终能够正确安装、恢复 SQL/Session 并接续日志。
- 生产配置的选举期限为 [1000,1800]。显式调用 Tick(900)，重发并接受当前 Offer，然后 Tick(1801)；当前请求必须仍能完成。判据来自配置范围，不读取私有 deadline，不用 sleep 猜时间。
- 随后发送新 term 的请求 1，基础/目标来自真实 SQL 和 SnapshotStore；必须正常确认，证明旧 term 的编号不会永久挡住后续任期。
- 四个定向变异分别去掉旧 Offer 隔离、旧全量隔离、续期、换 term 清理，指定同一个 T4；它们保护不同消息失序/期限风险，不增加四套相似测试。

这仍是发送端由测试驱动、接收端为真实 RaftNode/TCP/Store/FS 的集成测试。自动 Leader 增量追赶与基础保留决策继续未完成。没有新增 production 测试 API、默认配置或 test-only 控制流；复用现有请求号、Tick 和正式配置。
