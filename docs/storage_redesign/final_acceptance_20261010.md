## 3. 本次实际修正：复用不能绕过写入上限

`ObjectIO::WriteCommon` 原先在取得覆盖许可后直接跳过新分配计数，也跳过了该处唯一的 Data 写入总上限检查。比如旧配置创建 8 KiB 分配，重开后写上限降为4 KiB；原地更新可能先提交8 KiB Deferred，而后台 WriteDeferred 随后拒绝，造成已承诺任务无法落位。

现在分别累计总写入量和新分配量：所有目标先受同一个写入上限约束，仅非复用目标向 F12 申请空间。检查在 Journal 发布之前完成；没有新增预算模块或配置，也没有把后台真实错误改成无限重试。

先从 WriteCommon 与 WriteDeferred 的容量检查推导问题，再新增一项场景（两个配置）：降低限额后的整范围复用；复用＋新分配各自可接受、合计超限。必须 NotCommitted、控制记录不发布、原正文不变、节点不故障，随后正常写入和重启仍可用。增加一个移除复用预算检查的隔离变异，要求在指定发布结果断言失败。

修复前 C1 和 C2 第一个种子已通过，第二个种子由本轮主动中断以重新冻结版本，不记作产品失败或通过。全部原始记录留在 pre-budget-fix；修复后从 C1 重新执行。

### 9.3 停顿与持续退化分别分析

慢写在 turnover 开始后约 1191.6 秒发起。观察者在请求已慢约 10.2 秒后才附加，故停顿早于 GDB。Leader 栈显示 `WriteSharedSnapshot → DrainCheckpoint` 等待，而 checkpoint 线程在 `ShareObjectRangeBatched → ProtectRead → MetadataCache::LoadLocked → IOBatch::Wait`；另外两节点的 checkpoint 线程处于 Clone/Share 的 B 提交和 Journal 等待。当前 `MaybeCreateSnapshot` 的 `snapshot_draining_` 与 `RunSnapshot` 的 Busy 状态会限制新写准入；耗时任务虽已移出节点锁，这个逻辑限制仍会等待整个快照流程。这条依赖链已有证据，不能仅删锁或取消版本保护。35.23 秒含采样干扰，不代表无采样固有暂停长度。

更长时间的持续变慢同样明确。按五分钟统计，前 15 分钟约 16.34 / 17.16 / 16.83 次/秒，35–40 分钟为 1.35，40–45 分钟为 1.10，50–55 分钟为 0.93。Leader 的 B 页加载从 20 分钟附近约 7.5 万次增至结束时 3526719 次，淘汰 3529156 次，页描述 1894，驻留正文 512。数据空闲仍约 805 MiB；整个观察期 WSL 内可用 RAM 最低约 4.77 GiB（不是 Windows 宿主物理内存统计）。证据支持 B 缓存频繁换入换出及扫描负载放大，不能称为设备空间耗尽或整个进程内存耗尽。当前没有后半小时 CPU 栈，不能将那段所有时间强行归给某一个函数。

### 9.4 已定位的具体改进点

- **CRC 成本。** 60 秒窗口中 `Crc32cExtend` 自身占用户态 CPU 样本 61.84%；这是采样窗口、三节点合计的运行时间比例，不是整轮墙钟耗时。`src/common/byte_codec.cpp:126` 每字节执行八次逐位迭代。优先在原公共 CRC 接口内改用同格式的高效实现，保留增量计算语义与必要校验，不新建另一套校验模块。
- **B 冷页重复计算。** `metadata_engine.cpp:863` 的 CheckDiskPage 已核验完整磁盘正文；同次加载到 :871 又调用 Seal 对相同磁盘正文重算 CRC。应复用已验证的页尾/校验结果来建立内存页状态；解码会变更内存表示，不能直接用磁盘正文覆盖解码后的页。新页或修改后重新持久化仍须计算新校验。
- **GC 扫描放大。** `object_reference.cpp:540` 的回收游标每换一个 allocation 都从该对象 PendingRange 起点重新扫描，再筛选 allocation。它把长扫描分摊到多轮，尚未消除多个 allocation 各扫同一批记录的重复成本。样本中 GarbageLoop 含子调用占 24.92%、Reclaim 占 21.80%，与 MetadataCache 热点重叠，不能相加。建议复用既有游标，按对象扫描一批记录，给有界候选分组复用；释放前仍用当前视图复核身份、持久引用和在途保护，不新增权威回收表。
- **快照工作边界。** 进一步区分捕获一致状态与后台 Clone/Share/发布的寿命；评估固定版本保护成立后，能否更早解除业务收束，并复用 Capture 已保护的范围，减少重复 Resolve/Protect。跨任期、候选失效和旧引用退出须随原流程处理，不能直接把 `snapshot_draining_` 或 Busy 检查删除。

上述 CPU 数据来自现有 `perf.data` 的离线展开，另存 `profile/capture-1/perf-self.txt` 与 `perf-inclusive.txt`。后者是含子调用统计，部分栈未完整解析，不用于推算精确 IO 等待比例。
