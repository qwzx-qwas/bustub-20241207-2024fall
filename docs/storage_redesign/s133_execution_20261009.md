## 1. 具体改动与逻辑检查

| 路径 | 实际变化与理由 |
| --- | --- |
| `Node::clients_ / ReconcileActiveWrite` | 单个 sequence 改为每客户端按请求号索引的有界集合。尚未开始 Prepare 的请求等待较小编号；已开始的任务继续推进，后来收到的旧重试不能反过来卡住它。依赖仍由原 TableWrites 管理。 |
| DDL 屏障 | 等待已形成业务计划、准备结果或提案的前序工作；缺号且尚无业务范围的请求不成为 DDL 前置依赖，避免“后号等前号、前号 DDL 又等后号”的循环。原分析任务串行交接保留。 |
| SessionTable | 新模式保存最多8条原指纹/结果，按编号查找；确认后擦除结果容器节点但保留退休边界。CLOSE 留墓碑，不允许旧身份再次执行。旧模式仍只保存最后结果。 |
| 原命令/客户端 codec | 显式 WINDOW_WRITE、SESSION_CONTROL 帧；CommandBatch V3 增加 WRITE/REJECT/ACK/CLOSE，仍使用原 Raft COMMAND_BATCH。旧 V2 编码及原黄金字节测试继续有效。结果格式2携带可恢复拒绝原因；原结果格式1保持。 |
| 业务拒绝 | 明确的 SQL 输入、约束和容量拒绝使用 SqlRequestError。新窗口将其变成持久 REJECT 结果，再允许下一号准备。普通 IO/未知异常不转成终局业务拒绝；旧协议继续原拒绝行为。 |
| 确认与结果观察 | `InspectRequest` 在一次生命周期/可见性保护内取得分类及原结果，避免分类后被 ACK 回收。`InspectSessionControl` 返回是否需要提交及观察到的已发布边界；重复 ACK/CLOSE 不重复写日志，也不在协议发布进度追上前回复。 |
| 控制任务 | 同一个 ActiveWrite/TaskExecutor/Raft 路径中保留一个控制名额，使用4 KiB进展额度；结果窗口满不挡 ACK。piggyback ACK 先完成其独立提交，再接纳 SQL；任一半都可用原身份重试。 |
| 恢复 | SessionSnapshot V3 同时保存结果、退休/关闭状态及其提交位置，防止确认状态越过快照边界；纯旧会话继续输出 V2。原 A checkpoint、canonical/shared snapshot 直接复用该 codec。 |
| CLI | 原 `write` 保持；增加 `window-write --ack-through`、`ack`、`close`。仍一连接一请求；应用可并发 Send，应用负责保存 client_id、原 SQL、未知请求和连续确认承诺。没有暗中新增客户端状态文件服务。 |

新窗口会话（含墓碑）上限4096。首个请求建立会话时串行通过节点的开窗入口，保证批次校验与 Apply 之间不会把全局会话上限超发；建立后的不同会话继续原依赖流水线。这个一次性串行成本明确保留，不能据此宣称首请求也完全并行。结果数量/错误正文上限是硬边界；现有 SQL 工作额度仍是估算，不宣称完整 C++ 堆/RSS 已精确计账。

### 3.2 生产与接口污染

未新增测试 getter、等待钩子、测试分支或线程池。`InspectRequest` 的真实调用者是生产 Node 的分析/结果阶段；它替代拆开的分类/读结果交接。`InspectSessionControl` 服务幂等控制处理；新 SessionTable 操作由生产 FSM/快照 codec 调用。SqlRequestError 用于决定可持久化的业务拒绝。删除测试后这些接口仍是本功能必需。先前试写的分离 `GetResponse` FSM 转发器已删除，避免重复接口。

旧 `ClassifyRequest/GetLastResponse` 保留已有兼容接口和单节点/原回归用途；新 Node 不使用分离观察来读取窗口结果。

### 3.3 重复、检错、稳定性及最终判断

组件和TCP均检查退休边界，但组件隔离编码/边界错误，TCP检查复制与发布，当前不是互相替代。文件TCP与Direct脚本部分重叠；后者才覆盖正式CLI、对象、F28恢复与低预算，前者能有意停多数派检验尚未提交阶段，暂保留同一归档。不复制集群fixture；脚本导入原Cluster，不复制启动、设备格式化或业务实现。

新三项实际变异分别让退休号重新成为NEW、取错历史结果、漏写CLOSE，均指定断言失败。节点顺序测试在提前准备下一号时将观察到提前拒绝/追加或最终值错误；Direct测试若新会话快照丢失结果/退休状态，原收据和关闭检查失败。这两项为逻辑推演，未另声称实际运行对应变异。

稳定性：业务数据确定；网络超时只用于制造无多数派和限制挂起，不按毫秒快慢宣称性能。复用原fixture的回环端口分配仍有短暂端口竞态风险；本轮无该故障。Direct快照等待改用实际发布边界，两个重启明确是SIGKILL进程，不等于设备掉电。结束核对退出状态，归档后删除设备与编译临时文件。

结论：上述5个新增场景有各自失败边界，保留在F35阶段压缩包，不新增长驻CMake目标；原共同套件不复制。没有为测试改变生产完成语义或新增同职责组件。

## 6. 2026-10-10 复审：业务拒绝错误分类

### 先从逻辑定位

沿 `Analyze → Prepare → CommandBuilder → Node` 检查发现：上一版将部分明确的输入错误留给内部编码/定义校验抛出普通 `runtime_error`。窗口模式为避免掩盖 IO/未知错误，会将普通异常上报为节点故障；因此同条 INSERT 重复主键、NULL 主键及不支持的索引定义可能使节点停止接纳请求，违反终局业务拒绝协议。旧测试只有“主键已存在于表中”和语法错误，未覆盖这些路径。

### 本次具体修正

- INSERT 复用已有主键提取和排序，在去重前拒绝重复 VALUES 主键；不新增另一套键索引。
- 在 INSERT 输入、UPDATE 新主键处明确处理 NULL。UPDATE 的既有“不允许修改主键”约束继续保持。
- 新 DDL 在 SQL 边界调用原纯定义校验，并把其输入拒绝转为 `SqlRequestError`；未改恢复、已提交命令校验，也未把整个 Prepare 的异常都转换为业务拒绝。
- 共同协议补充终局拒绝与未准入拒绝的区别：只有带持久收据的 DURABLE_REJECTED 消耗编号。

### 测试调整及审查

扩充现有 `SessionWindowGapsAndTerminalInputErrorsDoNotStallProgress`，没有另建同义用例/fixture：请求4—7分别为同条重复主键、INSERT NULL、重复索引列、UPDATE NULL；要求逐条持久拒绝且重试得到原收据。请求8合法插入43/59两行，读取并核对 `(27,14)、(43,21)、(59,34)`，同时证明请求编号继续推进、错误输入未留下半条数据、合法多行插入仍可使用被拒绝的键。

新增4个隔离变异，分别撤掉上述错误分类；每个必须由指定节点场景的断言检出，异常/崩溃/超时不算。使用真实 SQL/客户端/Raft/FSM 路径，预期来自输入；没有新增测试 hook、getter、线程池或持久状态。已有结果窗口、ACK/CLOSE、切主和恢复场景继续复用。

### 本次复验结果与结论

- Release/GCC16.2.0 相关目标重新构建成功；66项既有回归全部运行并通过，无失败/跳过。
- 10组件＋7真实TCP节点场景全部通过；扩展的是原有输入错误场景，没有通过增加同义测试堆数量。
- 22项隔离变异均由指定断言检出，包括原18项重跑和本次4项；异常/超时/编译失败均不计检出。
- 本次未重跑正式 Direct/C1，旧证据及对应源快照放在结果包 `prior-20261009/`，不与新成绩混用。

| 检查项 | 代码依据与结论 |
| --- | --- |
| 同客户端顺序 | `clients_`按请求号索引；未开始的新请求等待前号退出。已经认领的工作不因后来到达的旧号重试而倒退，业务成功仍等Apply发布。原节点场景以非交换运算和最终115验证。 |

| 关闭交接 | `HandleSession`在节点锁内检查同客户端在途写，登记CLOSE后`HandleWrite`阻止该客户端新准入，直到控制任务退出；持久关闭状态由SessionTable检查。 |
| 超时与切主 | 等待超时不删除已认领工作；任务捕获ActiveWrite并持有额度到实际退出。Node检查提案任期，Raft在异步校验后再次核对任期，迟到结果不能追加为新任期命令。 |
| 控制任务进展 | ACK/CLOSE复用原任务及Raft路径，有单独的一个控制名额和4KiB进展额度；不受结果窗口已满限制，也没有新增控制线程池。 |
| 恢复及错误分类 | 快照保存结果、退休边界、关闭状态及控制发布位置。SQL边界只转换明确输入错误，内部页/索引异常、IO及未知错误不统一降级为业务拒绝。 |
