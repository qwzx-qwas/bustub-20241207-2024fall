## 2. 统一术语

| 名称 | 职责 | 不应混淆的内容 |
| --- | --- | --- |
| 数据库页 | 保存表、索引或 B 元数据内容；缓存、版本和写回单位 | A 的 4 KiB 页大小不是设备 IO 对齐要求 |
| 日志记录 | FULL 保存 B 页映像，PATCH 保存基于指定版本的修改等 | B 的 FULL 不等于 F07 分片类型中表示“未分片记录”的 FULL |
| CommitBatch | 一次完整恢复/提交的逻辑单位，可含多条记录 | 多个 batch 共用 Flush 不变成一笔事务 |
| Journal 段 | 管理一轮日志内容的追加、保留与回收 | 一条记录或一个 batch 可以跨段；段不是若干数据库页的固定分组 |
| Journal 槽位 | 段使用的固定物理区域；回收后可交给另一段身份 | 不等于引导槽 0/1，也不等于表页中的 tuple slot |
| checkpoint | 建立可靠恢复起点的操作及描述记录 | 不必另存完整数据库副本，也不自动授权全部旧日志回收 |

B 的最终页位于 Metadata 区域，FULL/PATCH 和 checkpoint 描述位于 Journal 区域，引导区定位 checkpoint。最终页与日志有关联但不是同一物理位置；不要画成 checkpoint→段→所有数据库页的包含关系。

## 3. 顺序与寻址分离

### 3.1 当前代码及必须一起修改的调用者

改造前及保留的 v1 格式中，`JournalResult::begin_` 同时是 Journal 相对物理位置和 LSN；F07 向后追加，满后拒绝。此约定在旧追加格式中成立；本轮 v2 将顺序与物理位置分开。

循环复用后，120 MiB 之后可以写到 8 MiB，因此物理偏移不能继续比较提交新旧。逻辑日志位置必须单调；物理位置可以循环。本轮采用“段序号 × 段大小＋段内偏移”的 64 位逻辑位置，物理定位及编号耗尽规则见 §9.2.1，不静默回绕。

| 消费者 | S5 必须保持的语义 |
| --- | --- |
| F07 结果与批次前驱 | 表达逻辑顺序，不能把小物理偏移误判成旧提交；最大完成序号不等于连续 durable |
| F08 页 LSN、`Replay`、PATCH 基版本 | 统一使用逻辑顺序；PATCH 仍核对准确基页身份和版本 |
| F09 最终页编码 | 持久化的是对应已提交版本，不由物理槽位置推断新旧 |
| F10 覆盖边界、周期首改 FULL | 与页 LSN 在同一个逻辑地址空间比较 |
| F03 checkpoint 引用与 F11 定位 | 可从已知入口直接找到目标，并核对 Journal/段身份；既不能只有可复用物理偏移，也不能只有无法定位的逻辑号码 |

编号预留上界只证明号码不重复，不证明这些段已加入有效链。例：提前记录 100～199 已领走，用到 123 重启后从 200 领取新身份；跳过的编号不占物理槽。已有段继续同一轮追加与把空闲槽分配给新身份是不同操作。

### 3.2 身份有效性分三层

1. **历史保留范围：** 持久恢复/裁剪依据决定哪些历史已退出；范围限定在同一 Journal 身份中。
2. **当前位置归属：** 当前有效段信息决定某个槽位属于哪次使用；读取单元必须与预期身份相符。
3. **完整提交：** 长度、批次片段、前驱关系和提交验证决定该内容是否有效。

不能选全设备数值最大的段号并把其他段都视为过期。103、104、108 可以同时有效；109 可能只是预留号。格式版本、Journal 身份、段使用身份、checkpoint 发布代次与数据库页代次不能混为同一个计数。

## 4. 长期保留与临时占用

`pin == 0` 只说明没有相应的在途使用，不能说明恢复不再需要日志。

- F10 提供 B 的恢复保留依据。checkpoint 后仍需首改 FULL、后续 PATCH 及完整批次。
- F07 汇总同一 Journal 的保留范围，并将边界回退到完整恢复必需的批次/片段起点，再按整段确定可回收前缀。
- S10 的 Deferred、PayloadRef 从同一保留协议接续；未可靠落位的数据即使无人读取仍须保留。本轮不手写假 Deferred 作为已接入证明。
- 临时访问许可覆盖实际使用期间，退出后释放。回收先关闭旧身份的新访问，再等待已接纳访问与设备 IO 退出；关闭入口、计数检查、重分配须协调。
- 临时 pin 不逐次写盘。长期需求从有效 checkpoint、持久待落位目录等重建。保留边界推进后不能再次创建依赖已退役历史的新持久引用。

当前 B 是 Journal 唯一所有者，恢复扫描发生在开放前，正常运行没有任意 Journal 读接口；B 旧视图持有不可变内存页。不要为了本轮假设出一个全局 pin 服务，也不要让这些纯内存读视图阻塞 Journal 段回收。已有访问门和实际 IO 排空足以表达的职责应复用。

## 5. Checkpoint 与回收的发布协议

已定顺序：

```text
新 checkpoint 的页面、描述及入口可恢复
  → 汇总全部持久保留需求
  → 禁止旧身份的新访问，排空已有 IO
  → 可靠发布旧恢复入口失效/裁剪依据
  → 整段变为可复用
  → 为新一轮分配身份并追加
```

用户倾向持久化一条规则说明哪些旧入口不再可用。概念上控制状态关联 Journal 身份、有效 checkpoint 引用、保留起点和控制发布代次；这些职责不等于必须重复存多组同义字段。新 checkpoint 不一定推进保留起点，例如未来 Deferred 可能仍依赖更早内容。

控制依据必须直接可定位，不能依赖尚待恢复的 B 普通对象映射，不能只放在即将覆盖的段中。任何仍可能被接受的恢复入口均不得依赖已复用日志。规则自身无法验证时明确失败，不能仅因某个旧引导副本 CRC 正确就接受其旧规则。

普通 Journal 正文仍为单份，多个 batch 共用一次 Flush。不恢复“每组正文＋两份边界共三次 Flush”的已撤回方案。控制记录的具体编码、发布时点和恢复选择已在 §9 落定；不能把控制信息写入、读回可见当作 durable。

本轮为前缀整段回收。仍需恢复的跨段批次保留全部必要片段；不在活段任意覆盖小洞。逻辑释放不要求缩小宿主文件或全段清零。F12 普通 extent 分配、F26 HPArray 归还 RAM、文件系统 punch-hole 均不是本轮 Journal 使用权复用。

## 6. 旧尾部、范围与校验边界

范围描述可用“身份＋起点＋长度”，但地址和长度不能单独识别复用前后的内容。每个可独立校验的写入单元核对所属段身份；一个单元可以含多条片段，不要求每个小片段再放同一份完整头。

| 读取事实 | 处理 |
| --- | --- |
| 已证明有效范围之外的旧身份内容 | 作为旧残留排除；不要求整段清零 |
| 必须存在有效日志的位置出现旧身份、损坏或缺片 | 拒绝恢复，不能当正常尾部截掉 |
| 尚不能证明当前位置是否必须有效 | 不凭“旧号”或 CRC 失败自行忽略；先明确尾部协议 |

身份只能证明“不属于这轮”，不能独自证明“这里本来不该有新数据”。封闭段的结束信息、追加尾段的完整批次及失败规则必须共同说明有效范围。单份日志的 CRC/身份无法识别任意完整介质回滚或整个后缀一致消失；保留现有已声明限制，不用无限增加副本掩盖这一点。

实际提交的对齐缓冲及 padding 必须初始化；这不等于预先擦零整段。若未来加入 discard/清零，其实际 IO 也必须在重新分配前排空。

校验按格式所有权集中：F07 处理身份/长度/CRC/片段/批次，B 处理页与 PATCH 基版本，F03 处理引导记录。复用编解码入口，不让每层重算同一份 CRC 或重建同义状态。错误保持原原因，不做默认填充、静默回退、跳过坏批次或隐式重试。

## 7. 合并和回收的区别及本轮取舍

- **合并 IO：** F07 多 batch 共用持久化屏障，各 batch 原子边界不变。
- **落实修改结果：** F09 将包含多次修改结果的页面可靠写回，F10 建立新恢复起点。
- **回收历史：** F07/F06 在保留条件解除后复用旧段。
- **重写有效历史：** 主动将 FULL/PATCH 合成新日志需要维护跨页事务、引用和入口切换，本轮不实现；不能把 Raft 命令历史擅自合成最终效果。F29 仍只管理 Raft 日志整理。

例如 FULL 510（x=11）与 PATCH 520（x=12）：仅出现 520 不授权删除 510；写回 x=12、建立 C51 并解除其他依赖后，才考虑回收相应旧段。少量有效内容拖住整段是初版明确代价，先推进真正阻塞的 checkpoint/引用，后按测量评估搬迁。

## 9. 代码前推演、待明确事项及顺序

### 9.1 本轮已发现的真实衔接点

1. `JournalService::Impl::Append/Scan/Encode` 用物理 `cursor_`、段槽号和连续区域末尾确定顺序；环回必须同步修改定位、链验证与扫描终止。
2. `MetadataEngine` 的 FULL/PATCH、Replay、页写回与 checkpoint 使用同一 LSN。不能只修改 F06。
3. F03 v2 将 checkpoint 位置限制在 Journal 区域内；单调逻辑位置可能超出该大小。需要格式标记和可验证定位，不能仅删除范围检查。
4. 目前仅靠引导代次选择新入口且保留全部旧日志。段覆盖后必须让 F11 拒绝依赖退役历史的旧入口，包括仅剩旧引导副本可校验的场景。
5. B checkpoint 的描述是一条有界记录，当前先排空业务提交/页写回。本轮先据这条真实路径计算空间、完成槽、IO 和缓冲预算；不为未实现的消费者预设无意义常量。

### 9.2 格式兼容（用户已选第一种）

新 `Create` 默认 Journal v2；`Open` 识别并保留 v1 原有追加、页写回、checkpoint、恢复和容量耗尽行为。本轮不原地迁移、不在打开失败时重新格式化。F03 v1 表示无 checkpoint、v2 表示旧 Journal 物理位置、v3 表示新 Journal 逻辑位置。业务 A 尚未改为本存储后端，不改它的现有数据库文件。

### 9.2.1 本轮编码与发布细化

- 一个单调 64 位逻辑位置为 `segment_sequence * segment_bytes + offset`，offset 处于段内。序号耗尽明确失败，不静默回绕；物理槽是 `1 + (sequence - 1) % data_slot_count`，不增加依赖 B 的映射索引。逻辑顺序可跨编号空洞，不能据此声称连续提交。
- 物理槽 0 保留控制区。新格式至少两个数据槽，每个段首单元保存独立校验的段身份，后续单元沿用 F07 分片/批次结构并标记 v2。段头和本批正文一起参与原组 Flush，正常批次不多一次边界 Flush。段头、数据单元和批次校验各有职责，复用 v1/v2 的同一个片段解析器。
- 控制单元保留原几何/身份/输入上限，v2 将偏移 80 的 u64 用作段编号预留上界，偏移 104 新增 u64 保留起点。头/余量/CRC 按既有单元规则；控制区是单份独立可定位记录，损坏拒绝打开，没有“找旧控制副本继续”的分支。更新时写完整对齐单元并 Flush；更新失败隔离实例。
- 预留上界按数据槽数量的整数倍推进，必须从实际下一个号码起至少覆盖完整一圈；起点接近区间末尾时，会多领不足一圈的余量。控制记录先 durable 再使用。重开可继续已有段未使用的位置；为以后新段跳过旧预留余量，并按下一物理槽选择新号码。旧编号较小但仍位于保留链中的段继续有效。重开预留更新也可能失败，不能报告 Ready。
- 新格式 checkpoint 描述仍是 B 的有界单记录，不复制页面。先最终页 durable，再 checkpoint 批次 durable，再 F03 v3 引用 durable，最后独立控制单元中的退役边界和新编号预留 durable。控制边界不大于已发布入口；遇旧入口落在边界之前拒绝，不回退或自动修复该恢复链。这里的维护 Flush 不改变普通 batch 共用一次 Flush 的承诺。若在引导引用发布后、控制更新前中断，B 重开先验证 checkpoint、页面及后缀，再补完退役控制，随后才开放写入；避免最后维护单元已经使用却无法继续回收。
- 此阶段真实消费者只有 B。`Checkpoint` 已排除新 B 修改，F07 再关闭追加门并等待实际队列/活动 IO 退出，然后发布控制依据、释放整段资格。不新增通用 pin API；MetadataSnapshot 的纯内存页不延长 Journal 引用。
- 已封闭的较早段必须连续写满数据单元，唯一追加尾段允许全零或能校验为已退役旧身份的尾部；尾部之后再出现本轮数据、跨段半批或必要内容损坏均拒绝。扫描按有效段序列进行、逐批有界解码。段头属于定位目录，必须可验证；旧前缀的普通正文不重放。单份尾部整体回滚/消失仍受原故障模型限制。
- 一条 B checkpoint 编码在一个数据单元内（最低 unit=256 时，可用188字节，48字节正文＋16字节记录头＋40字节提交片段共104字节）。普通准入保留一个数据单元；新段头容量另外扣除。维护先排空 B 现有提交及写回，释放其 IO/缓冲与完成名额，不为未来 Deferred 假设固定配额。跨段头也计实际 IO、组大小及在途字节。新格式 group 至少容纳一个段头和一个数据单元。

1. 按已确认 §9.2/§9.2.1 实施，先分析跨段、空间耗尽、控制发布失败、重开编号及旧格式兼容。

## 10. 必要测试与八项审查要求

使用真实 B→Journal→F06/F04/F02/F01 Direct 文件路径和独立输入模型。共同业务 C/P 尚未接入这些存储组件，本轮不声称 SQL/Raft E2E 或性能改进，不改共同内容层。

资源按阶段集成测试控制：单例使用独立临时文件，镜像上限先限 64 MiB，Journal 刻意缩小以触发多轮复用，缓存/在途 IO 显式有界；故障用握手触发，进程 watchdog 只防挂起，不能作为性能或成功判据。本轮单设备 8 MiB，基础 Journal 为 16 个槽、每槽 4 个查询后对齐的单元；复用旧测试时沿用其原预算，不启动新的长期压力/性能基线。

| 场景 | 独立预期及新增失败模式 |
| --- | --- |
| 小容量、非空混合元数据、多轮 checkpoint/复用、关闭重开 | 累计追加量超过可用 Journal 容量仍可运行；每次重开与输入模型一致；实际物理槽换代，不能仅测一次无环回追加 |
| 复用后短写、跨段批次、FULL/PATCH | 旧尾部不复活，完整批次全部恢复；必要片段被破坏要拒绝，不能只用正常 reopen 自证 |
| 回收控制发布失败与旧恢复入口 | 未取得持久许可不覆盖旧有效段；复用后旧入口不得重放被退役历史；失败结果不伪报成功 |
| 在途访问/IO 与关闭 | 真实完成前不得复用或释放缓冲；测试侧可控握手确认前提，不以 sleep 推测竞态 |
| 普通空间压力下维护进展 | 普通提交明确拒绝或背压，必要 checkpoint/回收仍有已推导的空间；不靠无限等待通过 |
| 新旧格式按确认范围恢复 | 用旧格式真实镜像/独立字节依据验证兼容，不把新编码器的输出作为旧格式 oracle |

有相同 invariant、故障和 oracle 的场景应归并，表格不是必须增加六个独立 test 的数量指标。复用相关 F03/F07/F08/F09/F10 归档测试，按实际接口变化维护测试侧适配，不复制各层整套矩阵；必要风险变异先明确逻辑，再验证断言能抓住。

维护持久化故障必须区分“控制写失败”与“控制写完成、Flush 失败”；后者即使能读回新边界也不能确认成功。可在同一故障场景复用输入/oracle，等待场景暂停于 Flush，避免增加重复套件。后续节点、业务及设备故障验证的接入条件见[执行审查 §9.2](s5_execution_20260930.md#92-这次验证与后续接入的关系)。
