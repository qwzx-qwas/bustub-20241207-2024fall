# S13.2b 多客户端提案流水线（2026-10-09 执行协议）

本轮按用户确认实施 F35；替换单个未完成提案限制，保留每客户端一个未完成请求及现有会话结果格式。S13.3 不在本轮。本文接续 `s13_protocol_execution.md`；其中“仅一个未完成业务提案”是 S13.2a 阶段边界，不再作为本轮最终约束。

## 1. 登记与读取视图

两者职责不同：登记约束同时在途的修改，读取保护保证 Prepare 读到完整的已发布状态。登记键为本状态机的表编号和规范化主键，不能加入行版本或 RID；否则同一行的新旧版本会错过冲突。版本、schema、任期属于请求校验，不是另一张地址表。

复用 Binder/Planner 生成一次计划，在读取候选行之前取得依赖：INSERT 登记包括尚不存在的主键；UPDATE/DELETE 只有能证明有限主键集合时才按键登记（AND 可以收窄，OR 两边都须有限，混合类型不能误转换）。其他谓词按整表登记，DDL 使用全局目录屏障。完整谓词仍交现有优化器/执行器处理。schema 或工作空间变化时重新分析，不能用旧计划继续读取。

查找用表 → 主键的索引，整表和目录等待者有独立屏障；多键一次全部取得。等待者挂到实际阻挡它的请求，释放时定向唤醒，不逐对遍历所有请求。允许遍历有界窗口处理完成事件。登记不是持久锁表，也不复制元数据、缓存或 FS 冲突表。

Prepare 的读事务及页保护在生成自有命令后退出，不跨网络复制保活。依赖直到 Apply 完整发布或确认未提案失败才释放；客户端超时不能释放已经认领的工作。短读事务无写集和 undo，实际使用结束即从事务管理器移除，不等待扫描整张表的 MVCC GC。普通事务历史、页和设备范围继续服从原有回收协议。

## 2. 执行与批次

协议仍由一个 owner 推进，复用现有 business/storage TaskExecutor。不同客户端独立请求的准备可与其他请求的持久化、复制重叠；Apply 保持日志顺序。已就绪请求可以在同一次 LogStore Append 中提交，各自保留 entry、请求身份和业务原子性，不故意等待凑批。

所有请求（包括等待依赖、任务完成未消费）共同受数量和字节上限约束；同一缓冲只由所有者计账。普通 Prepare 不能用尽业务执行器名额；Apply/完成工作保留名额并优先调度。批次不超过现有对象 LogStore 的条目/字节限制，超过单次容量明确拒绝，不能等到写了一半才发现。

Follower 追赶在读取日志之前限制单批数量/字节，不能先复制全部后缀再截短。历史上单条较大的合法日志可以单独发送，仍受既有日志/RPC 的绝对上限约束。

达到 checkpoint/快照阈值后停止接纳新请求，排空已接纳的有限窗口，再交原 F28/F25 生成流程；持续新写不能使快照饿死。已接纳但尚未执行的工作也属于窗口，不在收束时丢弃。

## 3. 失败与回收

未提案的准备失败释放登记及预算；切主使旧任期请求失效，已接受的实际任务仍由执行器持有至结束，迟到结果不能操作新请求。Journal/日志持久化不明确继续沿现有失败处理，不能当成未提交自动重发。成功仍要求多数派提交、按序 Apply、完整发布。读取继续服从 ReadIndex。重启依靠日志、快照、会话恢复，不恢复内存登记或临时视图。

关闭停止入口并排空实际认领的任务；内存登记随请求退出，无需新增 GC 周期。持久结果仍由原会话/快照/日志模块管理。

## 4. 审查和验证

先检查依赖取得顺序、原子接纳、版本校验、批次失败、任期失效、快照收束及关闭寿命，再运行测试。重点验证独立请求确实同时在途、相同键重新准备、缺失键/范围/DDL、切主与重试、低预算完成推进、快照和短读清理。有限键验证要覆盖 OR 后续键、AND 剩余条件和准备失败后的完整登记释放；不能只用单键场景代替。复用原共同 C/P 判据；阶段验证替换 F35 旧压缩包，不把组件验证当完整生产性能结论。

不为测试增加 getter、延时分支或另一套执行器/冲突模块。测试应明确独立判据、能发现的错误、与共同测试的分工及尚未覆盖的 failure mode。

## 5. 本轮配置与计账

`DistributedNodeConfig` 默认窗口上限32个请求、32 MiB请求额度、单请求1 MiB命令容量；都是部署参数。对象部署还须满足原 `raft.max_batch_entries/bytes`，日志帧开销也计入批次。当前每请求预留 `4 × 命令容量 + 4 × SQL字节数`：覆盖计划/命令及编码交接时的主要工作正文；Prepare 逐行累计正文和命令描述开销，达到容量即拒绝，不能先收集全表再发现超限。这个额度不是整个进程的 RSS，也不替代现有帧、元数据缓存和 IO 预算。

这里的预留是工作内存估算，不是每次堆分配都经过的硬限制。`Analyze()` 的 Binder/Planner 和 INSERT VALUES 求值发生在逐行命令计账之前；SQL 长度及窗口限制不能证明这些临时对象全部小于上述额度。当前保证是请求准入额度、在途数量和命令构造受限，不能表述成 SQL 处理的全部内存已严格封顶。执行器的进展优先级也只作用于尚未执行的任务，不抢占正在运行的长扫描。

额度随请求所有者和被执行器认领的工作释放。TaskExecutor 不重复计算已经由请求保留的正文；业务执行器8个名额中，普通工作最多占7个，进展任务优先于尚未执行的普通任务，同类保持 FIFO。只有一份分析结果在等待登记；这是为了先登记 DDL 屏障再绑定后续语句，不妨碍其他请求的 Prepare 与既有日志持久化/复制重叠。

快照收束沿用阈值配置。`Stop()` 支持保留同一个节点对象再 `Start()`，因此暂时停服不会抛弃尚未解决的提案依赖；实际工作已排空，恢复运行后依任期/发布结果退出，节点析构则释放全部内存状态。另起进程由正式持久状态恢复，不重建内存登记。
