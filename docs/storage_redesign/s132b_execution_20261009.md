## 1. 具体改动

- `SqlCommandPreparer::Analyze/Prepare`：一次绑定/计划，先求逻辑依赖再读取行；INSERT保留VALUES，UPDATE/DELETE复用原只读执行器。有限主键集合支持AND收窄、OR合并，不能安全提取时整表保护，混合类型不误编码。完整谓词与旧值检查保留。
- `DistributedNode::AcquireWrite/ReleaseWrite/ReconcileActiveWrite`：单槽改为有界请求窗口。表→主键索引负责点冲突，整表/DDL屏障负责扩大范围；等待者登记在阻挡请求上。准备视图结束即释放，依赖到Apply发布才退出。全局published变化不再无条件拒绝独立请求。
- `RaftNode::ProposeBatch/RunProposal`：多个独立请求分别形成entry，先验证完整批次再交原LogStore持久化；允许已持久但未提交的独立提案继续在途，Apply和成功语义不变。新领导任期清理孤立的旧拒绝结果，避免同一index复用时错误拒绝新提案。
- `LogStore::Entries/ObjectLogStore::Entries`：在读取/复制正文之前限制后缀条目数和字节量。未改变日志格式或段顺序；单条旧格式大日志仍可单独发送。
- `TaskExecutor::Submit`：原执行器增加进展名额保留与同类FIFO优先调度，没有新增线程池。请求正文跟随F31额度，任务交接不重复计账。
- `MaybeCreateSnapshot`：到阈值后收束有限窗口，再走原F28/F25，避免持续接纳新写让快照饿死。
- `TransactionManager::ReleaseRead`及FSM `ShortRead`：读取结束后的事务对象也退出事务表，不再积累到全表GC。原EndRead仍保留“先检查结束状态、再明确释放”的接口；异常也在执行器退出后释放，不能删除还在使用的上下文。

## 2. 逻辑审查先发现的问题

1. 取消请求时不能重置工作线程正在读取的计划；改为工作持有不可变计划的独立shared_ptr。
2. 下一条语句不能在CREATE的目录屏障登记之前就绑定不存在的表；分析结果先交回owner登记，再开始下一次绑定。
3. 旧任期的拒绝结果不能仅凭相同index作用于新提案；新领导任期清理该临时结果。
4. 暂停同一个节点对象再启动时，仍可能有未提交日志；保留对应依赖，不能将Stop当成可丢弃未知提案的理由。
5. 快照文件出现不代表CURRENT已发布。旧恢复测试的文件计数等待存在竞态，改为先等待正式快照边界再损坏恢复文件。

首轮真实TCP验证还发现错误文本退化：合并请求身份错误改变原PAYLOAD_MISMATCH响应，已恢复原提示。

### 4.1 证据如何计数

`stage-complete/` 是当前13项正常测试；组件变异由 `stage-final/` 隔离构建，随后复跑这 10 个二进制，在 `mutation-verified/` 逐项保存退出码和指定断言；节点变异取 `stage-nodes/` 的当前复验。前一轮节点场景曾错误等待最旧保留快照的边界，后来改为等待 CURRENT 指向的最新已发布快照，再通过最终 3 项节点场景；不把那一轮整体标成通过。修正前的失败日志放在 diagnostics，错误测试源码不进入当前源码包。

原共同 runner 有排他锁；一次与 C5 同时启动的 C1 在建输出目录前被锁拒绝（EAGAIN），之后按 runner 约定顺序重跑，未修改测试以绕开隔离要求。

### 4.2 去重与重要未覆盖项

- 原节点回归负责 DDL、会话重试、切主、恢复；阶段测试补足“无多数派时独立请求仍能追加、冲突必须等待”的确定性交错；共同 C/P 负责真实对象后端和业务判据。不能互相代替，但没有再复制 bitmap、IO、CRC 或 SQL 执行器测试。
- 本轮不包含 ASan/TSan、设备掉电、C3-isolate/drop、C4、C5-long、完整性能矩阵和长时高并发压力。特别需要后续覆盖大量范围/DDL 混合、反复切主与低预算同时发生的组合。
- 每客户端仍只允许一个未解决请求；S13.3 多结果窗口未实施。business worker 仍单线程，Prepare 与持久化/复制重叠，不能宣称多个 SQL Prepare 同时执行；单次长扫描仍可能延后同角色的 Apply，优先队列不抢占正在执行的任务。
- 请求额度覆盖主要命令及交接正文，不是 SQL planner 全部堆内存的精确上界，更不是进程 RSS。F26 不可变正文乐观短读仍待独立接续。
