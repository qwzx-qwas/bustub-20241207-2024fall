## 首次 A/B 审查已修正的地方

1. A 的失败写状态改为保留 pending intent：健康路径仍不重试，B 才显式重发同一身份/SQL。删除旧 `_poisoned` 状态，避免两套会话推进逻辑。
2. 格式错误、请求号不匹配不按普通传输丢失重试；原始失败仍保留。
3. 重启资源汇总按 `(pid, start_ticks)` 分生命周期计算，不把新 PID 查不到旧样本误判为报告错误，也不把新旧 CPU/IO 累加计数直接相减。
4. 代理规则切换等待旧转发动作结束、核对 ACK 中实际规则；仍用全新写验证隔离，避免把 ACK 当成服务器所有旧消息已经消失。
5. 追赶证据按节点/任期/请求号对应；拒绝 stale 完成，不把心跳当成有内容的短追赶。用索引配对替代对全部事件反复做两层扫描。
6. 观察程序预算纳入代理；退出前最后一次采样报告的超限不能被忽略。Go 检查器在节点清理后独立运行。
7. 保留未知原始返回时刻，检查模型才延长其允许生效区间；缺失观察结束边界不能通过。业务历史达到 128 次尝试后停止，不删样本或切片凑通过。
8. 场景按 correctness/performance 文件拆分，共享装载/核对，删除旧 `scenarios.py` 和新增未用导入。旧探索脚本移至归档，原位置的生成缓存清理。

## 本轮追加审查与修复

| 问题 | 后果 | 本轮处理 |
| --- | --- | --- |
| `Column::TypeSize` 返回 uint8_t | VARCHAR(1024) 被截断为 0，全部场景无法建表 | 返回类型与保存字段统一为 uint32_t |
| 复制建表和目录快照解码仍限制 255 字节 | 只修 Column 后，复制或重启依然拒绝宽列 | 同步移除两处过时上限；保留非零、类型、VECTOR 对齐及现有索引容量校验；协议字段原本就是 U32，不改编码格式 |
| Tuple 解码把内部尾零计入正文上限 | 声明 VARCHAR(1024) 却拒绝 1024 字节正文 | 以正文长度比较声明上限；1025 字节仍拒绝，不能靠把测试列改大绕开 |
| C1 只做等长替换 | 声称覆盖长度变化却未触发 | 更新行按 64→256、256→1024、1024→64 改写，要求增长/缩短均非零并继续逐阶段核对全表 |
| 未知/错配的成功状态被归为 NOT_LEADER | 离线模型可能把非法响应解释成无效果，而不是明确失败 | 严格区分 INVALID_RESPONSE；补充错误分类自检 |
| 写入 NOT_LEADER 被模型归为无效果 | 节点追加后失去 Leader 身份也可能返回它，可能误判合法故障历史 | 写入按 UNKNOWN 保留；原始时间/状态不改写；只在搜索时允许未知写晚生效 |
| C5 的同请求号响应表用最后响应覆盖前者 | 快照块合法重传后的 stale 响应可能抹去先前真实安装证据，误报未覆盖 | 构造索引前筛除未完成/stale 的快照响应；自检同时验证“真安装后重复”和“只有 stale”两种历史 |
| P2 在测量期间持全局模型锁并分配新行对象 | 测量路径增加与生产无关的串行工作 | 每客户端只计已确认前缀长度，排空后从同一种子重建独立预期；任何失败/未知仍不能伪装成无效果 |
