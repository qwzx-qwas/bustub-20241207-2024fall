# S13.1 / S13.2a 执行与测试设计审查（2026-10-09）

## 1. 范围与代码审查顺序

执行 [共同协议](s13_protocol_execution.md)。保留已有 S12 工作区改动，基准仍为 `87f4357`。本轮没有扩大写提案数量、客户端会话窗口或实现乐观页正文读取。

先审查 Prepare 使用的业务视图、协议锁与 Store 锁、异步输入/结果寿命、持久化确认和关闭，再选择验证。发现问题后先解释调用链原因，再修正与复验，没有用大量微型回归代替逻辑分析。

具体变化：

| 位置 | 原问题 → 本轮行为 |
| --- | --- |
| `SqlCommandPreparer`、`BusTubRaftStateMachine::PrepareSql` | 写准备手工扫描表 → 复用只读优化计划与执行器，在受保护的 published 状态取得完整旧行/时间戳；不运行写执行器。 |
| `OptimizeSeqScanAsIndexScan`、`IndexScanExecutor::Next` | AND 中等值候选不能利用索引 → 可用单列等值限制候选，执行器仍检查完整条件，OR 必须完整覆盖。删除准备器重复过滤。 |
| `BPlusTreeIndex::GetEntriesSnapshot`、IndexScanBounds | P2每个128行范围仍扫描2万行 → 复用同一枚举接口的可选边界，支持单列整型有界候选；空边界沿用全扫描。 |
| `RaftNode::Slow/Operation/Poll` | 存储、Apply/快照安装直接占住协议调用 → 在耗时步骤挂起，已有协议 owner 消费结果后继续。worker 不操作 Raft 状态，不恢复 coroutine。 |
| `TaskExecutor`、`SnapshotTasks` | 快照专用线程队列 → 抽取共用有界实现；快照编解码仍保留独立适配与正文额度。存储与业务有独立执行进度，设备 IO 仍属 F02。 |
| `DistributedNode::HandleWrite/HandleRead` | 锁内获取状态机生命周期锁并运行 SQL → 提交到业务角色，客户端等待释放节点锁；读结果携带实际视图进度。 |
| `MakeResponse`、Raft 日志边界 | 返回状态仍可能取 Store 锁 → 使用协议侧已确认的 tip/base；日志身份替换期间禁止依旧边界提前 ACK。 |
| `TickLoop` | 固定 tick 才消费每层结果 → 完成唤醒；逻辑时钟按 steady clock 实际经过时间推进，避免唤醒越多选举时间越快。 |
| 普通准入错误 | 后台校验异常可能被当作存储失败停机 → `TakeProposalError(index)` 消费持久化前的拒绝；真正持久化失败仍 fail-stop。 |
| `WorkingState` 最终关闭 | 析构同步退役整个活动页空间、拖住退出 → 正常关机保留现有持久 registry，下次 Open 原清理路径接续；运行中替换旧状态仍退役。 |
| `RaftObjectStorage::Commit` | 未接纳 Full 被当作节点故障 → 保留同一未消费事务，在锁外执行角色等待名额；接纳后不重复提交。 |
| `Stop/Drain` | 异步工作可能晚于依赖对象析构 → 先停新入口，再消费/排空已认领任务及唤醒回调，然后退出依赖。 |

`TaskExecutor` 同时保留完成结果名额和进展类别：进展属性随任务进入 worker，再由原 F31/F02 传递，不能只给任务壳预留额度却让下游完成工作使用普通额度。

## 3. 目标 → 输入 → 路径 → Oracle → 失败含义

1. **慢 Apply。**正常选主并提交 NOOP；提交 `k=v` 后用状态机已有虚函数接口阻塞 Apply。直接调用未经同步包装的生产 RaftNode，驱动 Tick，检查发给两个 peer 的空心跳、commit=2 而 published=1；解除阻塞后检查实际 `k=v` 和 published=2。预期来自规定的两条 entry，不来自队列计数。失败定位为协议阻塞或业务发布过早；它不证明真实网络性能，真实部署由 C/P 接管。
2. **迟到准备。**阻塞 `ValidateProposalPayload` 后送入更高任期投票请求，再释放准备。检查新任期生效、日志仍只有原 NOOP、业务 key 不存在。经过真实异步提案、StableStore 与文件 LogStore；只用已有状态机接口控制交错。删掉任期复核将留下额外日志，测试能定位该问题。
3. **持久化 ACK。**在已有 DurableStorage 适配器的 durable append 返回前阻塞；发送携带 NOOP 的 AppendEntries。检查没有成功 ACK、确认 tip/published 仍为0；释放后检查同一 request_id 的成功 ACK及进度1。阻塞点是协议要求等待的持久化边界，测试没有模拟自己的一套 Raft；仍不是设备掉电证据。
4. **索引准备。**真实 parser/binder/optimizer/executor/command commit/reopen；主键17、43、91，AND 命中键但剩余谓词不匹配、完整匹配、DELETE不匹配、OR命中两个键。输入与预期整数独立，检查无关行不变、重开内容；删除完整谓词检查会错误修改43或删除17。不同输入覆盖额外 failure mode，未堆叠大量0起点。
5. **范围读取。**512行键为1000+3i，覆盖多个叶子；分别修改含残余条件的区间、反向书写的开闭区间，执行矛盾范围和两端均命中的OR删除，并删除起止都不是已有键的短范围。真实SQL/Prepare/IndexScan/Apply/reopen后逐行与整数公式核对；非唯一桶使用原索引实现，不新增另一份索引。该场景检查边界语义；真实范围性能由P2完整装载/核对接管。
6. **既有测试适配。**`SynchronousTestNode` 仅让历史确定性故障调度在每次本地工作完成后推进，不能把它们解释为异步吞吐证据。原快照重传场景增加协议协商超时和后台编码等待；模拟早先发送者的 request id 必须早于当前发送者，原900/901会被现有 anti-stale 规则正确拒绝。保留分块正文、重复块、丢 ACK、发布和日志后缀断言，没有删除保护规则以迁就旧 fixture。

## 5. 重复设计与重复测试

- SnapshotTasks 是编解码适配器；共用 TaskExecutor 是调度实现，F02 是设备 IO，职责不同。删除原快照线程/队列实现，避免两套通用 worker。
- 协议挂起帧保存控制流程与输入寿命；Store 仍唯一保存持久状态。确认 tip/base 只是避免持锁跨层读取的摘要。
- 业务执行仍串行，保留状态机生命周期锁保护其他正式调用者；不能因外层有队列就删除仍被 checkpoint/API 使用的锁。
- 投票日志新旧比较只读取已确认 tip/term，不再额外投递 worker；删除未使用的 prepared_at 字段。
- 正常关闭的退役策略只增加私有 WorkingState 生命周期标志，没有新增可配置开关或测试接口；现有 registry 是唯一持久清理依据。
- 定向异步交错测试补足 C/P 不能稳定制造的边界；不重复 F02 对齐、bitmap、CRC 或第三方 coroutine 行为。
- C1 的完整行比较与阶段的少量残余谓词检查部分重叠；阶段包保留最小故障定位，常驻主线仍为 C/P。
- 不因为加入同步等待适配就增加另一组相同故障矩阵。旧测试的 oracle 保留，测试名字/故障排列没有机械复制。

## 6. 杀伤力与稳定性

最小变异：持久化返回前发送成功 ACK；提前发布 Apply 进度；删除迟到提案的任期检查；删除 IndexScan 的完整谓词过滤；错误排除包含式范围上界。实际变异执行结果见 §9。禁止把构建失败或任意崩溃统计为检出。

Gate 使用条件变量确认已进入指定阶段；5秒只是挂死上限，不靠 sleep 猜测交错。协议时间由测试显式推进。每个 fixture 在析构时先释放 Gate、排空节点，再删除文件；修正原 Kv fixture 先删文件再析构节点的顺序。测试顺序不共享设备。网络 E2E 受环境和调度影响，真实失败保留，不能直接归类 flaky。

## 8. 验收中发现并修正的问题

1. 原低缓存 P2 首次仍超过准备期限，原因是每段范围验证全表扫描。沿同一索引枚举补上有界查询后，20,000行装载、预写及完整内容验证通过。
2. 两次 P2 内容通过但关闭失败。调试器从进程启动、捕获 TERM 后线程栈，定位 `WorkingState::~WorkingState → ObjectPageStorage::Retire → ObjectTransactionTicket::Wait`；IO仍推进，没有把它误报成协议死锁。正常关机保留既有可恢复清理登记。
3. 原 C1 观察到 `Raft object admission is full` 并停机。代码确认 F19 进展名额被另一来源暂占且输入尚未消费，故只在接纳前保留事务并退让。未重试未知持久结果，也未扩大配置容量掩盖问题。
4. 原 TCP 用例指出请求身份冲突的提示回退，恢复明确的 payload mismatch / sequence gap 语义。
5. 续跑先审析构顺序发现：正常 Stop 已排空，但异常退出时 `RaftNode` 原先晚于完成唤醒所用的条件变量/原子字段析构。将私有成员声明移到这些依赖之后，使执行器先析构并等待回调退出；没有增加关闭分支、公开接口或第二套排空机制。

失败轮与调试轮不计为通过的性能证据。续跑时环境的 `/tmp` 已被清空，上述早先观察的原始日志、构建和未归档阶段源码丢失；代码与方案保留。因此这些记录仅说明修正原因，不能充当可复核的通过证据。本轮在项目忽略目录重建阶段源码和验证环境，重新运行并归档最终结果。

## 9. 首轮实际运行结果与证据

- 六组既有回归实际重跑通过：SQL Prepare 3、业务状态机 4、Raft 核心 31、故障调度 16、BusTub 集群 2、TCP 节点 9，共 65 项。

## 11. 再次逻辑审查：匹配前缀与任期失效

本节是随后一次独立复查，§9 保留上轮运行归属，不把旧工作树的 E2E 成绩自动记到修正后的代码。复查先读协议/节点控制流、结果寿命与测试源码，确认以下原因后才补测试。

### 11.1 具体修正

1. **Follower 不能提交未匹配的旧后缀。**原 `Handle(AppendEntriesRequest)` 用 `min(leader_commit, durable_tip)`，这是从同步版本继承的错误。例如本地有1–3，Leader本次只核对到1却告知commit=3，本地2–3可能仍属旧Leader。现在使用 `min(leader_commit, prev_log_index + entries.size)`；空心跳同样只能证明其前缀。没有新增水位线、配置或副本。
2. **新任期发布同一 index，不等于旧请求已执行。**`ReconcileActiveWrite` 原先可能在旧提案被新Leader的NOOP覆盖后，以“该index已经published”推导出“旧请求必须有会话结果”，并错误停机。现在统一在处理结果之前退出任期已失效的客户端等待，返回NOT_LEADER；真正接纳的存储工作继续由Raft持有，同身份重试由既有SessionTable去重。删除同一方法后面重复的任期检查；相同任期却缺失结果仍报告错误，没有吞掉真实不一致。
3. **变异判断收紧。**原runner仅看退出码1和`FAILED`测试名，这不足以区分断言与测试体抛异常。现在还要求断言的文件位置/`Failure`标记，并排除C++异常；编译失败、崩溃、超时均不计检出。上轮归档的五项确实有断言，但自动判定也应符合这项要求。

## 12. 再次逻辑审查：等值键类型与测试实际执行

### 12.1 本次具体改动
