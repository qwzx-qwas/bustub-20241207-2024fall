## 二、逐项：目标 → 输入 → 执行 → Oracle → 失败含义

共同正式路径：`SubmitObjects → ObjectTransactionPipeline → F12/F13 + MetadataEngine → Journal/F02/F01`；读取经 `ReadObject → F14/映射 → Data 或 Journal → CopyTo`；重启调用真实 `NodeStorage::Open`。测试中的 syscall 包装仅暂停或制造指定 IO 错误；实际正文仍由正式实现写入真实文件，不模拟数据库。fixture 复用 S5 的 Image/Value；Value 是按 seed 和位置生成的独立非空字节序列，不调用生产编解码计算 expected。

### T1：正文与旧视图

- 目标：三种来源组合、提交后可读、checkpoint 保留与旧视图均不丢数据。
- 输入：6u 原始内容扩大为 9u（尾部空洞）；从 `2u+117` 改 `2u+193` 字节，覆盖非零起点与不对齐边缘；同时提交非空控制值。
- 执行：暂停后台 Data write；提交后读取；固定旧 B 视图并 checkpoint；放开落位、再次 checkpoint，再从固定旧视图和重启后读取。
- Oracle：测试 vector 用 `std::copy` 替换输入、扩展部分为零；逐字节比对整对象和内部范围，控制值与明确输入相等。没有使用生产 Resolve 生成期望正文。
- 失败含义：错读来源、切片、保留或恢复之一有问题；单次字节断言不能独自定位全部层次，结合当前暂停阶段定位。

### T2：重叠修改

- 输入：先写 5u，再在 `2u+53` 改 713 字节，两份内容 seed 不同。
- 执行：先暂停旧后台目标写入，提交后一修改（保留字节需从旧 Journal 读取），再让旧任务完成、等待新任务完成并重开。
- Oracle：只在模型对应区间替换，当前/重开结果均等于新模型。
- 失败含义：旧任务复活映射或新修改丢失。两次修改在前台提交有明确顺序，测试不要求随机调度。未宣称本例覆盖丢弃未完成票据；该风险沿用 S7。

### T3：持久引用重建

- 输入：在 `3u+29` 写 `9u+131` 字节，跨多个小 Journal 段。
- 执行：子进程走真实 Create/Commit/Checkpoint，后台 Data 被暂停时 `_exit`；父进程确认退出码，再以阈值零打开，验证未落位读取，最后放开并重开。
- Oracle：输入字节与返回字节比较；成功状态必须来自真实返回。没有手工填 checkpoint/目录。
- 失败含义：正文保留、跨段定位、重建顺序或关闭新选路的含义不正确。进程退出不等于机器掉电，内核/设备缓存未被破坏。

### T4：已确认后的故障

- 输入：偏移 291、7731 字节，故障为后台 Data pwrite 的 EIO。
- 执行：先获得 durable 成功，再放开故障；读取现有 NodeStorage 状态，关闭重开完成任务。
- Oracle：原票据仍 Durable；节点 `error_` 存在、phase Failed、新事务能力关闭；重启正文等于输入。
- 失败含义：错误传播/隔离或恢复正文丢失。不是仅断言“抛了某个异常”。

### T5：目标保留与物理再分配

- 输入：Data 区只设 2u，先在逻辑 `4u` 写满唯一 2u 物理容量，然后截断对象到 u。
- 执行：后台被暂停时发正式 Reclaim，必须释放 0；放开后继续 Reclaim；再给另一对象写 2u。
- Oracle：先 0、后 2u，另一对象实际写入与读取成功，实际范围等于唯一可用原范围。容量受限使结果不依赖“恰好先选哪个空闲地址”的分配器实现。
- 失败含义：过早释放或完成后仍泄漏空间。复用现有 F14 不再复制 bitmap 位测试。

### T6：完成额度

- 输入：小 Journal（128u），一个未落位对象正文，连续不同控制值压到前台明确 NotCommitted 边界。
- 执行：随后放开后台，等待完成、checkpoint，再提交合法控制更新并读取正文。
- Oracle：必须观察到压力拒绝；已有任务仍完成、checkpoint durable，后继写和正文正确。终止上限只用于判定停顿，不作为性能 SLA。
- 失败含义：维护额度/回收进展有问题。该例不能证明所有配置都拥有最优额度。

### T7：写出与持久化

- 输入：偏移137、7927字节，暂停后台 Data write 之后的 fdatasync。
- 执行：提交确认后观察正式映射范围，读取正文，再允许 Flush/完成提交。
- Oracle：Flush 被真实调用但未返回时，来源仍为 Journal；正文等于输入，完成后仍正确。观察来源是本阶段持久化协议的一部分，不断言私有状态机步号。
- 失败含义：Write 被误当作 durable，或最终 Flush 被遗漏。

### T8：所需正文损坏

- 输入：偏移257、10373字节，先 checkpoint，再让后台 EIO，保留唯一恢复正文。
- 执行：关闭后在真实 Journal 区匹配提交正文的一段64字节，翻转一个位并 fdatasync，再 Open。
- Oracle：必须先找到真实输入模式；Open 报 JournalError，不能返回旧 Data/零。
- 局限：这是“所需恢复范围损坏”用例，whole-batch CRC 可能先报错，不能单独证明每条 PayloadRef 检查均有独立覆盖。

### T9：混合原子发布

- 输入：两个有空洞的对象，`20u+17` 大写与 `2u+31` 小写，以及一个控制记录；均非零偏移。
- 执行：大写按阈值走 Common，小写走 Deferred；暂停 Common 的真实 Data IO；检查旧内容/未完成结果，再放开完成与重启。
- Oracle：暂停时仍为全旧/无控制值；成功及重开后两份输入和控制值同时可见。
- 局限：覆盖一个事务中多个 mutation 混合；未证明单个 mutation 的大块/尾部已拆分选路。

### T10：提交边界故障

- 输入：已有12317字节 Common 内容，从731替换8317字节，并提交独立73字节控制值。
- 执行：分别在 Journal pwrite 与随后 fdatasync 处暂停并返回 EIO；确认不会提前成功，再真实重开。
- Oracle：不能得到 Durable；能打开时，以控制记录是否发布判断应比对完整旧模型或新模型；明确 NotCommitted 时禁止新控制记录。部分 pwrite 破坏链时允许明确 Corrupt + Failed + 禁止读取；不接受任意异常，也不静默截尾。
- 失败含义：违反提交/恢复约定。故障时磁盘实际已留多少内容可能受 IO 完成顺序影响；断言按协议允许集合，而非固定单一恢复版本。

### T11：丢弃读票据后的错误

- 目标：真实 Journal IO 错误不依赖调用者继续等待、CopyTo 或保留票据才能汇报。
- 输入：偏移379、9173字节的真实正文；暂停后台 Data write（保证其 Journal 读取已结束），只让随后前台 Journal pread 返回一次 EIO。
- 路径：正式 SubmitObjects、ReadObject、F02/F01。读请求成功接纳后立即丢弃票据；后台仍暂停，因此错误必须来自此次前台读取。
- Oracle：现有 NodeState 的 error/Failed 及读写能力关闭，新的正常读取被拒绝；放开并重启后的正文等于输入。测试不读 callback 指针或新增生产状态。
- 失败含义：IO 完成错误未进入节点既有故障通道，或错误处理破坏 durable 正文。与 T4 的后台写故障、T8 的启动校验故障不同。

### T12：混合来源的永久超限

- 目标：请求本身超出部署总 IO 预算时不能声称“等一等就可以”。
- 输入：F02 自有缓冲总额度64u；先 Common 写63u，后将8u起的16u改为 Deferred。完整读取需保留 Data 结果和带日志封装/元数据的 Journal 批次，合计超过64u；单独小读可以装下。
- 路径：正式对象写读及现有配置，不直接调用预算计算接口。后台 Data write 暂停，确保混合来源窗口。
- Oracle：小 Journal/Data 读取与独立模型相等；大读必须得到非 ObjectIOBusy 的 ResourceUnavailable，节点不是 IOFault；落位后同一大读按 Data 路径成功且正文等于模型。未断言某个内部计数或固定日志编码大小。
- 失败含义：永久超限与暂时占用混淆，或来源切换后泄漏预算。不能据此证明 S12 的全节点调度公平性。

## 四、接口审查

PayloadRef 与对象 format v3 是生产功能的真实格式变化，不是测试 ABI。A/B 实例仍独立；没有把 SQL 交给 B。旧二进制拒绝 v3，当前实现接受旧 v2 的 Common 读写，但拒绝在 v2 上打开新 Deferred 选路；不自动迁移。Journal 服务的 NextAppendPosition/保留/读取组装仅供 B 的私有 friend 访问；调用方从已发布 B 视图获得引用，不暴露可猜物理地址的公共分配 API。

原来普通 B Commit 和 F12 Commit 仍用于真实普通事务，增加重载不删除现有生产消费者。对象内部 Apply 的可选空正文仅兼容内部 Common 语义，不是测试注入点。现有 Common 快路径、Raft Store 与页帧路径保留并复跑；Deferred 读暂需工作缓冲，未假称零拷贝。

## 五、重复与风险接管

- T1/T7 都涉及提交后读取，T7 独有 Write 已完成、Flush 未完成的窗口；两者 failure mode 不相同。
- T3/T4 都重开；T3 验证跨 checkpoint 的引用重建/选路关闭，T4 验证已确认后的运行期 EIO 与错误状态，不合并成只做一次 reopen。
- T5 与 F14/S7 回收有交集，但新增“持久后台写者”保护及唯一容量再分配，复用 F14 协议而非重测位图。
- T9 与 S7 原子事务相似，但新增大/小两种 durable 依赖；T10 新增恢复正文与控制记录的同批不确定结果。没有复制 S7 的队列接收、票据释放、对象排序测试。
- F36 测试文件已经 include F26 的9项，runner 只通过合并套件运行一次，避免再跑一遍 F26 而虚增数量。
- 历史 S5 fixture 在当前 BufferPool 头文件链上遇到新类型名；runner 只给其旧 producer 隔离基线 object/data allocator 声明，保留历史 B/Journal writer 和测试正文。S8 使用已有 F26/F36 的部署适配，输入、故障和 oracle 不改。
- 全部阶段源码仅保留 F27 压缩包。未来共同 E2E 接管相同业务/故障窗口后，简化或退出相应阶段案例，不给每层再复制一套。本轮不改变共同 C1–C5/P1–P4 的内容及历史结果。

## 六、最小 mutation

隔离修改生产源副本并链接同一测试对象；正式生产源码不被变异替换。只有编译/链接成功且目标测试产生实际断言失败，才算检出。计划/执行项见最终 `mutations.json`：漏掉 Journal 来源而错误补零、丢范围内偏移、忽略 Journal pin、提前释放目标、遗漏恢复引用、遗漏最终 Flush，以及本次新增的吞掉前台读错误、漏算混合来源预算。T6/T9/T10 没有各造一个同构变异来凑数量，故障输入本身检查其风险边界。变异检出不证明不存在其他 bug。

## 七、稳定性与环境

固定 seed 的非空输入；每例独立 mkstemp 镜像及 NodeStorage；gate 只在单个测试进程内有效，Cleanup 析构先释放再关闭对象，避免断言失败时永久阻塞。没有用 sleep 猜“后台大概写好了”，以真实 syscall 到达和正式状态为依据；15秒期限用于终止挂起，慢机器仍可能超时，不能当性能结论。T3 fork 在创建该例 NodeStorage 前进行，子进程明确 `_exit` 模拟崩溃；不是主机断电。

Direct 对齐从 BlockDevice 实查，u 按能力构造；测试镜像8MiB，Data通常2MiB，T5特意2u，T6缩小 Journal。fixture 对超过自身资源预算的对齐明确报错，不偷偷 buffered fallback。本机用 Debug、Clang14、ASan/UBSan/LSan。受限环境使 LSan 的线程检查报 ptrace 错误，正式执行移到允许此检查的同机环境；没有关掉 sanitizer 把失败算通过。未进行 TSan/真实裸设备/物理掉电或共同性能测试。

## 十、再次复审：读取错误和混合来源预算

本节区分首轮实现和本次修正：先检查代码逻辑，再补 T11/T12；没有把原有54项通过当作本次修正的验证。
