2026-10-08（Asia/Shanghai）。基准提交 `055198eab6a426053c3f5b40b0087cf184caac28`，叠加已授权 S12.2 和本轮修改；当前未 commit。协议、开源内化及完整 prompt 见 [S12.3](s12_log_cleaning.md)，前置整合见 [S12.2 审查](s12_integration_execution_20261008.md)。

## 1. 实际修改及先行逻辑审查

本轮用户选择“只整理连续尾部，维持旧格式”。没有新增段顺序格式、第二份日志目录或后台线程。

| 位置 | 本轮修改 | 解决的问题 |
| --- | --- | --- |
| `ObjectLogStore::Maintain/PlanCleaning` | 先对发布范围外的一条映射做 Unmap，再选择正净收益的连续尾部 | 失效内容无需先搬动有效正文；不能将已可直接释放的字节重复计为搬迁收益 |
| `ObjectMappingSnapshot::EstimateRewrite` | 有界统计仍被当前映射触及、没有持久共享引用的完整分配单位 | 按真实分配粒度估算，包含单位内余量；共享给别人的单位不能冒充立即可释放空间 |
| `ObjectLogStore::Cleaning` | Read/Create/Write/Publish/Retire 分轮执行；源 lease、候选目录、工作额度跟随任务 | 复制期间允许前台修改，过期候选不得发布；暂满重试和退出不能遗漏所有权 |
| `LogStore` 与对象后端 | 共用原有锁及其寿命；复制 IO 在锁外、最终发布核对代次 | 删除初版重复嵌套的日志锁；关闭外层接口时，已接纳维护仍有合法同步对象 |
| `RaftObjectStorage::Collect` | 日志维护与对象退役轮转，复用原 F22 调度；满 ownership 容量报告 Busy | 一个候选不独占整个回收轮；暂时压力不直接升级为节点损坏 |
| `GarbageLoop/Collect/Maintain` | 进展资格限定到安全释放、已写正文的发布及候选收尾；搬迁准备走普通额度 | 避免可选新任务长期占用已提交任务的完成保留 |

先核对以下逻辑，再编写场景：

1. 已失效的前缀/尾部不会重新发布；无失效尾部的对象仍可正常追加增长。只有对象实际长度等于发布尾端时才原对象追加。Unmap 不改变对象长度，因此已选失效尾部不能变成新的追加目标。选择时持同一日志锁，避免把前台未发布的追加当作垃圾。
2. 单一维护调用者执行后台状态机；跨轮候选保留源对象 lease。前台只更新当前目录，不接触后台候选。复制完成后再次比较代次，任何追加/后缀替换/裁剪使旧计划退出。
3. 候选包含完整 entry 的连续尾部，最多一个 IO chunk，重新编码后不会超过原有效片段总字节。新对象编号大于保留前缀，旧格式的恢复顺序继续成立。
4. 每个可失败步骤成功后才推进阶段；读失败重试会重新组装，完整读取前不替换候选位置索引。数据空间不足取消可选候选，IO 错误、损坏和不明确提交继续报错。
5. 旧读者、持久共享引用及实际 IO 的安全释放仍由 F14 判断，估计值不授予释放权。候选重启清理由已有 Own 状态接续。

复审修正了两项设计冗余/冲突：初版额外日志锁并入原锁；GC 线程整体进展资格改为操作级资格。未新增调度器、allocator、引用目录、缓存、Manifest 或 ResourceBudget。

## 2. 测试全景

源包内 `tests/cleaning_test.cpp` 定义下列 10 项（T9/T10 为本次复审新增），均为阶段 integration/regression，不能统称共同业务 E2E。

| 标识 / 测试名（均以 `F29Cleaning.` 开头） | invariant / 具体 bug |
| --- | --- |
| T1 `PrefixUnmapPreservesPinnedBytesWithoutZeroingOrCopyingLiveTail` | 失效前缀解除映射、旧 pin 仍保护正文，零净收益不写 Data；防止擦零、无效复制和漏 Unmap |
| T2 `PositiveNetGainWaitsForOldReaderThenMakesRealSpaceReusable` | 自动维护发布新段后仍等旧读者退出，才让空间满足真实新分配；防止过早复用或“只改清单未释放空间” |
| T3 `ConcurrentAppendInvalidatesPreparedRelocationWithoutBlockingBodyIO` | 复制 IO 暂停时前台追加可推进，旧候选不能覆盖追加；防止持锁慢 IO 和丢新后缀 |
| T4 `CrossSegmentContinuationSurvivesPrefixCleaningAndRecovery` | 跨段 entry 仍能完整读取和重开；防止把续片当作独立 entry 或丢掉所需首片 |
| T5 `SharedAllocationIsNotCountedAsRelocationGain` | 共享给另一对象的单位不计入搬迁收益；共享退出后才能产生对应收益 |
| T6 `InterruptedCandidateDoesNotReplacePublishedHistory` | 候选正文写入中退出进程，不替换已发布日志；防止恢复选中未发布候选 |
| T7 `MissingStagingSpaceLeavesHistoryUsableAndCleanupCanResume` | 无临时 Data 空间时可选整理让步，释放空间后接续；防止将可恢复容量压力升级为节点致命错误 |
| T8 `OptionalRelocationLeavesCompletionCreditsAvailable` | 普通内存额度用尽时，搬迁准备不借用完成保留；防止后台新候选挤掉已提交工作的资源 |
| T9 `HeldReadResultsYieldCleaningThenResumeWhenIOSlotsReturn` | IO 名额暂满只让出维护轮，释放结果后接续；防止误报节点故障 |
| T10 `SmallerFeasibleTailRespectsAtomicPublicationCapacity` | 按能原子发布的容量选择尾部；防止因最大候选超限而丢掉较小可行计划 |

共同路径是 `LogStore → ObjectLogStore / RaftObjectStorage → NodeStorage → 对象事务/映射/引用 → B/Journal/F02/Direct 文件`。T2 经正式 `SetStoreMaintenance` 进入既有 GC 角色；其余手动调用正式 Collect 控制时序，便于定位风险。没有模拟日志存储或把 map 容器当数据库。

## 3. 逐项：目标 → 输入 → 执行 → Oracle → 失败含义

### T1：直接释放与延迟覆盖

- 目标：移除逻辑映射即可回收，不能为这个操作提前擦除正文。
- 输入：第一条正文为两个实际分配单位，第二条约三分之一单位；保留第一条所在范围的读保护，再将日志 base 推进到 1。
- 执行：真实 Append、InstallSnapshotBase、Collect 和重新 Open；仅测试链接层统计 Data 区 `pwrite`。直接读文件旧物理字节是辅助观测，不代替正式日志读取。
- Oracle：发布映射变成 hole、Data 写次数不增长、受 pin 的旧字节不变；剩余 entry 与独立输入逐字段/正文比较，重开后也相同。原始字节前后比较只证明“未改写”，日志正确性依赖独立输入。
- 失败：可区分漏解除映射、额外复制/擦零、破坏旧读者、损坏恢复。变异已要求先检查写次数，不能让后面的对象查询异常冒充这个判据。

### T2：真正归还空间及引用保护

- 输入：设备 Data 仅 4 个单位，分配单位取发现值的两倍；用后缀替换制造两个短段，保留旧范围读者，另用一个单位放普通对象。
- 执行：设置正式 Store 维护回调，等待其自行完成发布；期间申请两单位，退出读者后再申请并读回。
- Oracle：退出读者前两单位申请明确 NoSpace；退出后两单位实际写入持久化成功且正文正确；原日志仍与输入一致、可重开。清单段数仅作等待发布的阶段信号，不是最终空间 oracle。
- 失败：未接入自动角色、复制未产生净空闲、释放过早或读者退出后空间仍不可用。此项不只测 bitmap 计数。

### T3：锁外复制及过期计划

- 输入：两个有合并收益的短段；链接层停住整理第一次真实 Data 写。
- 执行：另一线程正常 Append 第四条，必须在释放暂停写之前完成；然后让整理完成并重开。
- Oracle：有界等待确认前台完成；LastLogIndex 和四条完整 entry 等于独立输入。代次变异必须命中“丢第四条”的断言，不能只记异常。
- 失败：复制持有前台锁，或旧清单覆盖新追加。它只证明该明确交错，不穷举所有并发历史。

### T4：跨段边界

- 输入：段大小 1024；非空 entry 正文 173、3771、118 字节，第二条跨多个段；裁剪第一条。
- 执行：正式清理、读取剩余范围、关闭重开。
- Oracle：剩余两条的 index/term/正文严格等于输入，不从生产 Encode/Decode 生成 expected。
- 失败：片段范围、完整记录起点、尾部选择或重开顺序出错。此用例主要保护大 entry 被保留/跳过的分支，不证明所有跨段组合都能成功搬迁。

### T5：持久共享与临时 pin 分别处理

- 输入：把一个旧段的 64 字节共享到另一个对象，使一个旧单位在日志搬走后仍不能释放。
- 执行：维护时观察不写 Data、共享正文仍可读；删除共享目标，再维护。
- Oracle：有共享时净收益为零，不发生正文搬迁；解除后产生 Data 写且日志完整。共享正文以前后读值比较未改变，完整日志另外用独立 entry 模型核对。
- 失败：把持久共享单位计入收益、破坏别的对象内容，或共享解除后仍永远跳过。不是 T2 的 RAM pin 重复：共享影响收益估计，pin 主要推迟实际释放。

### T6：候选中断及恢复入口

- 输入：相同有收益尾部，先关闭父进程存储，再 fork 子进程独立打开。
- 执行：子进程完成一次候选 Data `pwrite` 后 `_exit`，未发布 Manifest；父进程重开、继续清理、再次重开。
- Oracle：明确子进程到达预期退出点；两次重开均返回原输入日志。
- 失败：未发布内容变成恢复依据、旧入口被提前删除、孤儿妨碍继续服务。仅模拟进程中断；内核和设备缓存仍存在，不能称为真实掉电验证，也未遍历所有 Flush 崩溃点。

### T7：临时空间不足

- 输入：3 单位设备被两个日志段和一个普通对象占满。
- 执行：先尝试清理，确认节点仍可用；Unmap 普通对象后继续清理，再提交真正的两单位新写入。
- Oracle：满设备时日志仍等于输入，节点无错误；最终写入成功且日志未丢。只接受明确 NoSpace，其他错误不能统称容量不足。
- 失败：无法取消可选候选、永久误报故障或候选泄漏导致恢复空间后仍不能推进。与 T1 零收益跳过不同：本项有收益但缺临时空间。

### T8：完成额度不被可选工作消耗

- 输入：显式 4 MiB 共享预算、其中 1 MiB 完成保留；用既有 ResourceAccount 取得普通剩余额度，并创建对应实际内存。该场景把周期调度间隔设为 1 小时，由测试控制 Collect 步骤。
- 执行：制造并先解除失效尾部，耗尽普通额度后推进真实 F29 规划，再释放压力接续。
- Oracle：用原 Reserve/Release 接口观察相同完成申请可获得的总额度，前后不减少；压力解除后日志仍正确。没有 getter，也不检查账本内部字段。
- 失败：可选候选侵占完成保留。它是可控资源竞争的集成测试，不是进程 RSS 或硬件内存耗尽试验；固定 1 KiB 探测粒度只用于测试预算，不作为设备对齐假设。

T9/T10 的逐项目标、输入、生产路径、Oracle、失败含义及稳定性见 §9.2–9.3。

## 4. Production pollution 与接口审查

| 新增/修改项 | 正式消费者与删除测试后的价值 | 结论 |
| --- | --- | --- |
| 公共 `ObjectMappingSnapshot::EstimateRewrite` 和返回结构 | F29 需要 F13 判断真实分配粒度及共享所有权；仅靠 Resolve 不知道 SharedUnit，复制内部编码到 Raft 层会破坏分层 | 合理生产查询；有界估计，无释放权限 |
| 私有 `RaftObjectStorage::AttachLog` | LogStore 打开后绑定既有 Store 维护；weak 引用不制造环形所有权 | 正式生命周期接口，未开放测试 getter |
| 内部 `ObjectLogStore::Maintain` 与构造锁依赖 | GC 调用，后台/前台共用同步；不是新公共 storage API | 有真实调用，不保留多余锁层 |
| LogStore 的锁改为共同持有 | 后台任务不能持有已析构 facade 的 mutex；文件后端保持原互斥行为 | 不修改 public 参数、默认值或磁盘 ABI |
| 完成额度的作用域 | GC 和 Deferred 收尾的真实进展保证 | 非测试控制流 |

没有新增 production test-only hook、默认路径、getter、透传 wrapper、`#ifdef TEST`、测试专属配置项或测试反向依赖。`pwrite/fdatasync` 暂停、计数和退出都在阶段二进制的链接包装器内。夹具额外参数只在临时适配文件中。唯一磁盘格式仍是现有 Manifest v1。

## 5. 重复测试和跨模块兼容

- 直接复用原 S12 的 47 项和 F25 组合的 35 项，不复制 workload/oracle。只适配历史 S8 夹具的显式部署/缓冲/预算参数；历史源码包保持不变。
- T1/T2 都涉及引用，但前者保护“不擦除、零收益”，后者保护“自动调度、真正再分配”；T2/T5 分别保护临时读者和持久共享。T3/T6 分别是运行期过期计划和进程中断恢复，不合并。
- T7/T8 分别限制设备临时空间和普通 RAM 额度，不用一个含糊“资源不足”测试替代。
- T4 与原 S8 跨段编解码有公共输入形式，但新增风险是 F29 活跃时不会误删续片；没有重新测试 CRC 算法或 FULL/FIRST/MIDDLE/LAST 的独立格式矩阵。
- 清单 owner 编号及段数量仍用于夹具寻址/同步，属于阶段耦合。长期 C/P E2E 接管这些风险后可简化此层辅助观察；不能声称现有共同 E2E 已经涵盖它们。

## 6. 定向变异与发现力

隔离编译对应生产文件，链接替换单个对象文件，不改仓库源码。必须正常编译、运行到指定场景并出现 assertion；崩溃、编译失败、非预期 C++ exception 不算检出。

| 最小变异 | 预期检出 |
| --- | --- |
| 跳过 DeadSpan 的 Unmap 提交 | T1 映射未成为 hole |
| 计算净收益时将新分配量当作零 | T1 出现不该有的 Data 写 |
| 禁止创建整理计划 | T2 自动维护无法发布，也不能得到要求的新空间 |
| 跳过候选目录代次核对 | T3 第四条日志被旧目录覆盖 |
| 将候选长期 RAM 记入 progress 类 | T8 完成额度减少 |
| 重新抛出 ObjectIOBusy | T9 报告暂时 IO 压力逸出 |
| 将不合容量的可选尾部直接报错 | T10 报告未选择较小可行尾部 |

T4/T5/T6/T7 有明确断言和对应风险，未为每项另造一套变异矩阵。T6 不穷举所有持久化中断点，T4 不穷举所有片段组合；不能以 7 个指定变异推断所有错误都可发现。

## 7. 稳定性、运行证据和限制

所有输入使用固定生成规则，无随机 seed 漂移；每项独立临时设备文件，关闭后重开；全局链接暂停器要求本二进制按默认方式串行运行，禁止同时运行这些测试用例。暂停器用 condition_variable 和 RAII 解锁，不靠 sleep 制造关键并发窗口。维护轮和等待自动发布使用 2 ms 轮询、10 s 上限，重载机器可能触及时间界限，应保留超时而非当作通过。

Direct 文件需要本机文件系统支持，分配/对齐从设备能力派生，T2 另用两倍分配粒度；真实网络回归需 loopback 权限。没有测试生产默认路径修改。ASan 开启、LSan 关闭；TSan、裸设备、真实掉电、共同 C/P 和 SS/RS/PL/GT 性能本轮未跑。

历史诊断必须与最终结果分开：首轮测试编译中 `Value` 命名歧义已改成 `s5::Value`；共享夹具最初建立长度 0 的目标，依法被生产拒绝，改成实际需要的 64 字节；零收益变异最初先触发对象已删除异常，已把 Data 写断言提前，不能把原异常算作有效 mutation。上述是测试修正，不是生产缺陷。

最终运行计数、命令、XML、压缩包和清理见 [结果目录](../../test-results/storage-f29-20261008/README.md)。仅以该目录最终证据为准。

## 9. 再次复审：IO 暂满与最终发布容量（2026-10-08）

首轮 8 项测试和 90/5 计数是历史证据。此次先分析调用链，找到并修正两个确切缺口，再补充下面的生产路径场景；最终结果以结果目录本次运行记录为准。

### 9.1 生产修改

1. **`RaftObjectStorage::Collect` 漏识别 IO 暂满。** F29 读取正文经过 `ObjectIO::Read`；共享 RAM 暂满会抛 `MetadataCommitBusy`，IO 名额/缓冲被占用则抛另一类型 `ObjectIOBusy`。原 Collect 只捕获前者，后者进入 `StoreRound` 的真实错误分支，错误地停止对象服务。现在精确捕获两种暂时压力，保留候选阶段并退出本轮；不把所有 `ResourceUnavailable`、损坏或设备错误统一重试。没有新增错误类型或重复重试线程。
2. **`ObjectLogStore::PlanCleaning` 先选收益最高候选、随后才检查能否发布。** 三个短段全部搬到一个段可能收益最高，但清单含旧段退出记录，会超过一次控制事务的数量限制。原实现此时抛错，即使两个段的较小尾部本来可提交。现在每个改善评分的候选先用已有 `CheckControlBatch` 预检，超限只排除该候选，保留此前可提交的尾部；删除原选定后重复预检。只在这个纯容量检查调用周围捕获 `invalid_argument`，真正提交的错误继续上报。
3. **修正不准确的说明。** “发布范围只会收缩”不适用于正常追加。准确规则是：已经失效的前缀/尾部不会重新发布；对象实际长度等于发布尾端时仍允许追加增长。代码注释、协议和本审查已同步，不改追加语义。
