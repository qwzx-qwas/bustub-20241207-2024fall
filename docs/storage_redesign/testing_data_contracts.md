## 2. 数据内容和访问分布分开设计

### 2.1 共同业务形状（建议）

采用一张简化的业务状态表：

| 字段 | 用途 | 重复或变化方式 |
| --- | --- | --- |
| id | 唯一主键，定位记录 | 每条记录不同 |
| tenant_id | 租户/业务分组 | 从有限集合选择，多行重复 |
| kind/state | 类别或业务状态 | 少量枚举值，重复出现 |
| version | 成功修改次数或版本 | 初始可相同，更新时通过数据库运算递增 |
| last_op | 最近写入的业务操作标识 | 由逻辑请求身份确定，重试不变；区分内容相似的不同更新 |
| payload | 备注或配置正文 | 共享模板、相同正文及带差异字段的正文并存 |

这是待核对的字段草案，不强制引入新 SQL 类型、索引、JSON 功能或生产 API。正文可以是普通字符串；全部输入为合成数据，不引入真实个人数据。

- 小字典提供重复的地区、类别、状态和配置模板；一部分记录完全共享同一个正文，另一部分在模板中加入独立字段。模板比例须冻结后执行，不能用“看起来真实”代替参数记录。
- 候选长度分布：60% 为 64 B、30% 为 256 B、10% 为 1,024 B，平均正文约 217.6 B。D1 的 100,000 条记录正文约 20.75 MiB，其他字段、索引、编码及日志另计。此分布是本项目讨论起点，不是生产轨迹统计，也不是 Ceph/etcd 默认值。
- 有限数据集按固定数量分配长度档位并确定性打乱，记录实际字节数；不要依赖随机抽样刚好达到目标比例。
- 当前 [TableHeap](../../src/storage/table/table_heap.cpp) 不接受单页放不下的 tuple。首期长度必须在整行可容纳范围内，不照搬对象系统的 MiB 级值；快照总量和请求/响应上限另行核算。
- 数据内容、访问键、操作类型分别使用固定种子/独立随机流。改变 payload 生成细节不能无意改变访问序列；重试不能重新抽取正文。
- 固定生成器版本、字典版本、种子和分布，并保留少量人工可核对的样例。判定模型不调用生产执行/恢复代码来生成 expected；关键样例独立列出字面结果，避免只用同一个生成器自证。

### 2.2 缓存与更新（建议）

首期只保留两种访问模式：均匀访问全部有效记录；80% 请求访问固定 5% 热记录，其余 20% 请求访问冷记录。80/5 是候选参数，不是业务真实比例，也不意味着 80% 缓存命中率。

- 热点集合是可复现的逻辑记录集合，记录插入顺序/逻辑聚集方式。热点页占用还受行长度、邻近记录和索引影响，不能仅凭热键数量断言工作集已放进缓存。
- 读取阶段重复访问同一记录，内容不变也正常。不同记录的相同正文不自动共享页缓存；缓存考察与压缩/去重考察分别定义。
- P2 首期可以主要做小字段修改（version/last_op）；P3 承担正文替换、长度变化和删除/插入的空间周转。不要为了“真实”把每次更新都改成整段全新随机正文。
- 热点迁移、Zipfian 分布和时间相关负载留作有明确问题后的扩展，不把所有数据/访问/更新组合全部运行。

## 4. 现有请求契约：代码核对结果

### 4.1 写入成功

[HandleWrite](../../src/distributed/node.cpp) 对应请求已经进入 SessionTable，且其提交位置不大于 `PublishedAppliedIndex` 后，返回外层 `COMMITTED` 和内层写入结果。[RaftNode](../../src/raft/raft_node.cpp) 的提交路径检查多数派复制，持久化提交进度，再 Apply/发布；[LogStore](../../src/raft/log_store.cpp) 通过 durable append 保存日志。

建议客户端一次写入成功须同时满足：

1. 完整且合法的正式响应属于这次请求。
2. 外层为 `COMMITTED`，内层状态/请求号/提交位置合法，并与已发布位置相容。
3. 在约定故障范围下，该操作效果可由持久化恢复链保留，并按正式强一致读取可见；由 C1–C5 核对，不将响应字段本身视为证明。

这不要求三份业务页都已写到最终位置，也不要求此刻所有 Follower 已 Apply；Raft 日志与恢复点提供的可恢复性属于允许的持久化基础。缺少受影响行数的正式字段时，用前置存在性和后置业务结果验证，不增加测试 API。

### 4.2 读取成功

[HandleRead](../../src/distributed/node.cpp) 的 `LINEARIZABLE` 路径等待 ReadIndex 并检查发布边界，再执行查询。业务强一致用例使用此模式，核对 `OK`、结果结构及业务值；status 请求的 `OK` 不算业务读取成功。

唯一候选例外是 C5 的副本内容核对：停止新业务写、处理完未知写、确认目标 Follower 已发布到固定边界后，可通过已有 `STALE` 读取其内容。它只证明副本在该边界的内容，不作为强一致读证据。不能在适配器中隐式把强一致读改成 STALE。

### 4.3 SessionTable 的约束

[SessionTable::Classify](../../src/distributed/session_table.cpp) 只保留每个 client_id 的最近提交请求与结果；下一条 request_id 必须恰好加一，相同号不同正文被拒绝，更早请求或跳号也会被拒绝。[指纹计算](../../src/distributed/request_fingerprint.cpp) 包含完整 SQL 字节。

因此建议：每个写客户端同一时刻最多一条尚未解决的逻辑写请求，多客户端提供并发。client_id 固定非零，request_id 从 1 连续增长；装载客户端与并发工作客户端分开。上一请求未确认前不能前进编号，也不能换一个 client_id 把它伪装成新操作。

相同请求的重试复用完全相同的 SQL 字节、client_id 和 request_id。不能重新生成正文/时间值或重新格式化 SQL。重试的已提交业务结果应一致；外层服务节点、当前任期和进度字段可变化，不能要求整个响应帧完全相同。

当前 [客户端协议](../../src/include/distributed/client_protocol.h) 明确每条 TCP 连接承载一请求一响应。首期按这一正式模式比较，不为压测修改生产协议实现连接复用。

这里描述的是旧版本的共同基线契约，不是新系统永久只能支持一个未解决请求。单客户端多结果窗口和全局多提案是两个独立的演进方向，代码核对、开源参考及候选方案见 [F35 §5](modules/raft-pipeline.md#51-两种现有限制代码核对事实)。前后共同负载保持相同语义；未来单客户端多请求的新增能力另行验收，不能由适配器拆分 client_id 来伪造旧版支持，也不能在取得旧基线前为测试放宽生产限制。

## 5. 超时与重试建议

区分“逻辑业务请求”和“网络尝试”。一条逻辑写可能多次尝试，性能成功数只计一次，记录每次尝试和总体耗时。

| 观察结果 | 解释 | 建议动作 |
| --- | --- | --- |
| 合法 COMMITTED | 已确认写成功 | 更新模型/逻辑请求结果，才允许该客户端提交下一编号 |
| NOT_LEADER | 可能在追加本次写入后失去 Leader 身份；本次及之前的尝试均不能据此判为未提交 | 用正式发现/提示找到 Leader，按原身份和正文重试；直接测试旧 Leader 时不自动转发掩盖原响应 |
| TIMEOUT、断连、客户端截止 | 请求可能已提交 | 标为未知；允许重试的场景中仍用原身份/正文，不当作已取消 |
| UNAVAILABLE | 不可用，可能含持久化异常 | 保存错误、节点状态和未知结果；按该故障场景的恢复流程处理，不能作为普通 SQL 失败继续推进 |
| REJECTED | 语法/业务拒绝，或身份/顺序不合约 | 正常正向场景失败并保留原因，不改正文后自动重试；不能用本次拒绝否定同一身份的早先提交 |
| 非法帧、校验/请求号不匹配 | 协议或数据错误 | 明确失败，不归为可忽略的超时 |

重试控制的候选方式：100 ms 起、逐步退避到 1 s 上限，抖动规则可复现；每次尝试时限、最大尝试数和逻辑请求总截止均有上限。具体值要与冻结后的服务端请求超时、选举时间和场景恢复时限一起确定，不能先写死生产默认值。

- 健康性能主场景建议单次尝试，正常选主在计时前完成；错误不靠重试抹去。并发继续产生排队，不能制造无限重试放大请求量。
- C3/C4 等故障场景允许在明确恢复窗口中用原身份解决未知请求；同时保留初次失败及恢复耗时。超过总截止仍未知时停止该客户端后续写，保留未解决状态，不能声称“执行零次”。
- 读重试不要求返回相同值；中间可能有合法写。每次完整观察都进入历史，未知读不能伪造业务结果。
- “场景失败后重新跑到通过”和“场景内明确约定的协议重试”不同；前者不能掩盖失败。
- 线性一致历史需要保留所有客户端可见完成和真实时间先后；不能任意合并重试时间区间或删去未知请求以得到通过结果。具体检查器编码仍需审查。

## 6. C1–C5 的独立预期建议

### C1：精确的状态变化

初始 id 为 0 到 2,047：更新 `id % 4 == 0` 的记录；删除 `id % 4 == 1` 的记录；再重新插入 `id % 8 == 1` 的记录并使用新的写入标识/正文。最终应为 1,792 条，但还必须逐条比较，而不只核对 count。

独立模型分别验证：已更新记录的新值、未触碰记录不变、真正删除的记录不存在、重插记录没有旧版本复活或索引重复。范围查询在停止写入的稳定边界执行，并按正式返回的完整字段比较。

### C2：存在合法执行顺序

只在少量已存在键上进行原子字段更新和强一致读取，暂不混入删除，使每次写都命中。模型包括 version、last_op 和正文；更新序号由数据库递增，不能由客户端先读再算来冒充原子更新。

模型寻找一个同时符合业务转换和客户端真实先后的顺序。A 已返回后 B 才开始，则 A 必须先于 B；重叠操作可以有多种合法顺序。读取不得出现新 version 配旧 last_op 等没有被任何合法操作产生的混合状态。

最终状态一致只是附加条件，不能替代历史检查。返回的 Raft index 可作诊断，不能用生产报告的顺序直接生成“独立”正确答案。共享键数、历史长度和合法分段方式待定。

### C3：故障中的安全与可用性分别判断

- Leader 故障/隔离前的确认结果仍属于历史，后续合法覆盖允许；多数派恢复服务后继续验证真实读写。
- 确认隔离已生效后，向旧 Leader 直接发起一个新请求；不允许自动跟随重定向来冒充旧 Leader 成功，也不能因它仍自报 Leader 就直接判定安全性失败。
- 响应丢失变体使用专用记录的非幂等增量（如 10 加 1）：在原身份重试最终确认后应为 11，不应为 12；测试使用专用记录避免其他合法写使计数含糊。只使用覆盖成固定值无法证明没有重复执行。
- 未解决请求保留未知；历史合法但恢复服务超过约定时限，应单独报告可用性不满足，不能标为整体通过。

### C4：重启后的业务与请求去重

保存客户端已确认历史，再终止三节点进程。恢复后先核对稳定业务状态，解决尚未知的请求，再允许各客户端提交下一编号。

让一个客户端保留其最后已提交身份，重启后原样重试；应返回同一已提交业务结果，且专用增量记录不重复变化。它检验业务状态及去重恢复链，而不依赖读取 SessionTable 文件。该结果不等同于掉电测试。

### C5：追赶路径真实发生且目标副本正确

短落后场景确认日志仍可追赶；长落后场景确认目标缺失范围超过可用日志，且快照安装/发布确实发生。正式协议的外部流量或状态可作为路径证据，具体观察方式由适配器方案解释，不读取 B/Journal 私有格式生成预期。

收尾时停止业务写并解决未知写，取得固定的已确认/发布边界；等待目标节点达到它，再核对该节点的完整业务结果，最后验证集群可继续工作。只看到 Leader 查询正确、Follower 进程存活或 index 增长不算通过。

若还要证明该 Follower 收到的去重状态可用于接管，需要它通过正常协议成为 Leader 后重试原身份。可靠的控制方式未确定前，该项作为明确覆盖缺口，不能用当前 Leader 的去重结果代替。
