## 2. 实现组织

- `content.py`：共同业务内容；仅更新性能契约版本。
- `adapter.py`：真实生产客户端协议适配，保留写身份；正确性场景仍默认至多 8 次尝试。
- `delivery.py`：性能专用 `PerformanceIO`，持有绝对期限、阶段预算、原写身份及逻辑请求记录。性能重试由总期限限制，退避 100/200/400/800/1000 ms，之后每次 1000 ms；所有尝试、查找 Leader、等待计入总延迟。非传输/换主类异常不自动重试。
- `runtime.py`：测试拥有的进程、真实在途请求和资源边界。Python 超时不等于底层 Send 结束；名额等实际结束/桥接进程退出后才释放。
- `performance.py`：独立的 P1–P4 场景与阶段。业务失败不自动退出整个测量窗口；写身份不能推进时停住该客户端，其余客户端继续。
- `arrival.py`：P4 固定到达率、计划时间、有限队列、未发出/被阻塞的计划记录。停止窗口后不继续启动排队请求；已有在途请求有界收尾。
- `report.py`：网络尝试与业务操作分别汇总；吞吐以完整窗口为分母，重试不增加成功操作数；晚于窗口的成功单独保留。
- `run.py`：配置冻结、独立运行、清理和结果归档。区分观测是否完整、服务表现、业务核对、测量环境错误。

P2 在每个成功操作后推进独立业务模型，不再靠“所有尝试成功”才能重建模型。结束核对对不确定写入使用原身份确认；确认可能发生在窗口之后，不回填窗口吞吐。P4 从逻辑成功记录重建模型，同一操作的重试仅应用一次。

## 3. 时间与结果

默认：单个逻辑操作 60 s；准备 1800 s；最终核对 600 s；P1 预热 30 s、P1/P2 正式窗口 180 s；P3 工作观察 3600 s；P4 形成落后量 1800 s、恢复观察 600 s。单次客户端网络超时仍为 6000 ms，生产节点超时 5000 ms；逻辑期限与网络期限不同。

每阶段有独立预算，最外层 watchdog 覆盖阶段预算之和及启动/清理余量。参数在运行前写入配置并计算哈希；不能运行中因结果不好而增加时限。资格运行与正式基线分开，资格结果不改名冒充正式基线。

- `SUCCESS`：收到并校验成功响应，记录实际端到端时间。
- `FAILED`：收到终止性拒绝，记录真实失败响应时间。
- `UNCONFIRMED`：观察截止仍未确认；显示实际观察时长加 `+`。不表示未提交/已取消。
- `NOT_ISSUED`：未发出，例如排队期限已耗尽；不伪造服务端耗时。
- 畸形响应、模型不匹配、测试器/资源错误另行保留，不吞为普通超时。

`t+` 不进入成功延迟样本，不按 t 算完整总体平均值。报告成功延迟、失败延迟、未确认比例、观察下界；总体 p99 缺少完整结果时留空。通过的操作不足 10,000 个时 p99 标为探索性。

借鉴 [NIST 的右删失记录](https://www.itl.nist.gov/div898/handbook/apr/section1/apr131.htm)：保存观察边界与未完成标记，不编造最终事件时刻；本项目不据此假定某种概率分布或外推最终执行时长。

借鉴 [YCSB 的 intended start measurement](https://github.com/brianfrankcooper/YCSB/blob/master/core/CHANGES.md)：P4 保存预定到达时间，端到端延迟包括排队，所有计划的拒绝/未发出都可追溯。解决服务变慢后压测器自动降低负载并遗漏等待时间的问题。

## 4. 场景边界

- P1：保留热点/均匀两种分布；预热实际完成量单列，不从零成功推断缓存已热。
- P2：保留 1/2/4/8 客户端；不确定写入停住该客户端，记录停滞时间。全停滞也观察完整 180 s，允许真实吞吐为零。
- P3：20 万操作目标与轮次不变。保留部分轮的操作数、空间、已知模型状态；不满足完整轮次/保留周期条件不得称空间稳定。不能继续写时保持空间观察到该阶段期限。
- P4：有完整且业务核对通过的旧 P2 单客户端资格结果时，可冻结其逻辑有效吞吐的一半；错误数量不是资格门槛。没有正速率来源时使用明确固定的 1 op/s 档位（80% 读/20% 写），或运行前显式指定 `--fixed-rate`。新系统使用同一个已冻结值，不能重新标定。恢复前需形成 256 次已确认写入的落后量；前置条件未完成不能记成恢复超时。恢复开始后到期才记恢复时间下界。

配置改变的是测试交付/观察协议，不改变业务内容；旧 `t0-c-1` 结果保留为历史。测量有效不等于零错误，业务核对未完成的结果不标为完整验证的比较基线。

## 5. 跑测试前审查（本次静态复审）

已逐项检查：

1. 生产 `src` 文件指纹与本轮开始一致；归档生产 diff 与当前版本一致。没有调整 Raft 超时、单提案限制或数据库锁。
2. 未确认写入保留 client/request/SQL；不使用新身份绕过去；核对阶段的提交不进入窗口吞吐。
3. 窗口结束不继续生成业务，网络重试只服务原操作；没有通过成功样本隐藏超时，也不扣除停滞时间。
4. P4 队列最多 64，六个业务工作者；底层最多八个真实在途调用。超时后不新增无界线程。
5. P3 部分轮与 P4 尚未形成恢复前提单独报告；业务错误仍按错误处理。
6. 所有原始失败保留；不同场景不会因普通服务错误互相阻塞。机器资源/测试器损坏则停止批次。
7. 新自检保护请求去重、期限统计和观察窗口；脚本响应仅检查测试器自身，不作为数据库正确性证据。真实系统结论仍来自非空业务 E2E。
8. 删除/替换了旧性能路径中的首错即停、全部成功才能核对及 P4 零错误速率门槛；保留仍供 C 测试使用的既有 FaultIO，不复制正确性模型。
9. Python AST 与 `git diff --check` 静态检查通过；此时尚未运行自检或 E2E。

实施顺序：测试交付/资源边界 → 场景与统计 → 上述静态复审 → 测试器契约自检 → 真实三节点资格与性能运行 → 保存、复核及按既定规则归档结果。

补充字段解释：`stalled_client_seconds` 是写入观察期限耗尽后，该客户端停止发新请求至窗口末的时间；原请求等待时间已计入其逻辑延迟，二者不重复相加为请求延迟。
