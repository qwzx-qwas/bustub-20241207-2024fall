# S8：Raft 日志、HardState 与快照对象存储

日期：2026-10-02（Asia/Shanghai）。用户已授权收录最近讨论、实施和必要测试。S7 基线为 `3a69338`。本文统一 F23/F24/F25/F33/F34 的交接协议；授权不等于已经实现，完成证据另行登记。

## 1. 范围与复用

本轮将 Raft 持久化接到现有 NodeStorage、S7 对象事务、B/F07 和 F02/F01。顺序为共同恢复协议 → F23 → F24 → F25 → F33/F34 节点接入。保持当前三节点一套 Raft，不引入 Multi-Raft、额外设备线程池、第二份 FS WAL 或模拟 POSIX 文件系统。

- F23 解释 entry、段和有效日志范围；普通日志正文是 Data 区域中的对象，不是 F06 Journal 槽位。
- F24 解释 term/vote/commit_index；小型 HardState 通过 B 的控制记录持久化。
- F25 管候选正文、完整性、发布、接收和保留；取得一致业务状态仍由状态机/F28 负责。
- F13/F14/F12 负责对象到设备映射、引用与物理回收；Store 不复制这些机制。
- FS 已接收、正文 durable、本地元数据发布、Raft 多数派提交、业务 Apply 分别确认。S8 保持现有 Store 同步成功语义；F35/S13 才迁移协议线程的异步等待。
- 小尾部继续 COW；IO 对齐不能作为原地更新的掉电保障。Common 的正文与 B/Journal 是两个持久化依赖阶段，不宣称整次追加只需一次 Flush。

## 2. F23：段、索引与有效清单

当前 `LogStore::ReplaceSuffix` 和 `InstallSnapshotBase` 会调用 `RewriteJournal` 重写保留历史。新后端采用段对象及有效清单，保留没有变化的旧前缀，只准备新后缀并切换引用。

| 内容 | 归属 | 存储与意义 |
| --- | --- | --- |
| entry | F23 | 复用 index/term/命令与记录校验；正文进入段对象 |
| segment | F23 | 日志字节的普通对象容器；按字节轮转，不固定每段 entry 数 |
| 位置索引 | F23 | RAM 中 index → 对象/逻辑偏移/长度，可含 term；从有效记录重建 |
| 有效清单 | F23/B | 活动及封闭段、有效 entry/字节范围、快照基点、发布代次 |
| extent 映射 | F13 | 对象逻辑范围 → 物理地址；不暴露给 F23 索引 |

有效末尾不是 commit_index：本地日志可以包含尚未提交的条目。对象/分配身份也不是 Raft index；同一未提交 index 可以被另一任期的 entry 替换。

### 2.1 追加与发布

1. 检查 entry 连续性及预算，编码正文，提前准备提交后索引发布所需内存。
2. 规划段和对象写。多个 entry 的片段合并为段内字节，按有界 IO 块提交 Common 追加；每次 S7 原子发布该块的对象映射，Raft 有效范围仍保持旧清单。
3. 正文全部 durable 后，B 一次原子提交本批的有效清单及对象归属；F23 在其同步接口返回前发布一致内存目录/索引。Common 映射先于 Raft 清单持久化不代表 entry 提前可见；恢复及读取始终服从清单范围。
4. 读取以同一版本的清单及索引定位，再由正式 ObjectIO 读取。不能混用新目录和旧索引。

这里的“位置”是逻辑记录的位置，不要求一条 entry 只占一个段：若正文跨段，目录和索引必须能够继续定位其全部片段，且只能将完整 entry 对外返回。具体表示在段格式中确定，不能只实现一个对象/偏移三元组，却宣称支持跨段记录。

S7 每批每对象至多一项修改，不能直接在同批对新段 Create 再 Append。新段先作为候选对象建立，未加入有效日志清单；正文完成后发布引用。候选必须有可恢复的归属记录，失败和重启后才能清理，不能依赖仅存 RAM 的列表。

段目标大小不自动成为单条 entry 上限。同一 Append 接受多条 entry，段内合并正文，并且只最终发布一次 Raft 清单；数据块使用现有 Common 事务逐块准备。S8 不增加跨调用的等待凑批，也不声称所有正文共用一次 Flush。单条/总量/候选/索引内存有显式上限，不能为跨段引入无限积累或无限等待。具体上限与格式在执行细节冻结时写明，不用测试参数作为生产默认。

### 2.2 后缀替换、恢复和回收

例如原段保存 141～150，要替换 145 起的未提交日志：保留原段 141～144 的范围，新段写 145～153，最后原子切换清单。已提交前缀禁止替换；旧 145～150 即使字节和 CRC 完整，也不能越过有效清单复活。

恢复先读有效清单，只接受对应身份、范围、连续 index 和 term/校验正确的记录，再重建 RAM 索引。必要已提交日志缺失不得靠降低 commit_index 绕过。仅在完整快照已验证、且覆盖必须恢复的提交状态时，沿既有 verified-snapshot 规则重建日志基点。

逻辑裁剪由 Raft/恢复边界决定；Apply 过不等于可删除。F23 持久退出引用，F14 等待读者/IO，F12 释放完整分配单位。段整体无效可删对象；部分失效先维护有效范围，已有范围释放能力须满足正式接口和引用条件。存活 entry 搬迁、稀疏段整理由 F29/S12 接续，不把“清单不引用”误报为已物理回收。

### 2.3 与现有 S7 的实际交接

- S7 的控制记录是任意字节值；FS 不会解析其中的对象引用。F23/F25 必须在自己的清单/候选生命周期中保留仍被需要的对象，满足退出条件后再正式提交删除/裁剪；不能期待写一个 Control 值就自动建立 F14 引用。
- S7 对同一控制 owner 排序，不会判断调用方事先构造的清单是否过期。沿用 Store 的串行修改职责，使“读取当前清单 → 准备修改 → 等待 durable → 发布 RAM 状态”不会被另一次同 Store 修改穿插覆盖；不在这里擅自增加第二套事务或测试专用版本接口。
- 跨多次提交准备候选后，最终清单变化本身仍须在一次受支持的原子提交内。候选正文可以分块，不代表任意大小的清单都能发布；其预算必须涵盖当前 B/S7 的控制值和事务限制，不能只给正文分块后让最后一步必然超限。

## 3. F24：HardState

保留 current_term、voted_for、commit_index 及格式/代次，复用现有合法性和单调性约束。整体作为 B 控制值提交，不另存一份相同 Data 正文或额外 WAL。B 的 WAL/checkpoint 不是不必要的重复副本，而是现有元数据恢复机制。

更新顺序：校验 → 控制事务 → B durable/发布 → 更新内存状态 → 同步接口返回。依赖 term/vote 的响应不能越过持久化；commit_index 必须有已持久化日志或有效快照支持。本地成功不等于多数派成功。

S7 入队返回 Accepted 时，旧 Store 调用尚未成功。S8 的兼容同步调用等待票据；worker 不因此被 Store 等待占住，但当前 Raft 调用线程仍等待，不能宣称已消除协议线程阻塞。不确定提交保留原错误和恢复责任，沿现有 Raft 停止服务策略处理，不静默重试。

## 4. F25：流式候选正文与发布

快照包含一致的已应用状态，以及身份、格式、last_included_index/term、长度、校验和正文对象引用。先创建候选对象，分块写入，校验完整正文/业务格式，然后发布当前清单。旧清单在最终提交前仍有效。

- 发布将同一候选正文变成正式正文，不复制整份内容到另一个“正式”对象。
- 已写半份的候选不当作 Latest；失败候选有可恢复清理依据；提交结果不确定时不能按取消删除正文。
- 块接收成功、正文接收完整、快照发布、状态机安装是不同事实。重复块验证身份/范围/内容，冲突不静默覆盖；收到最后块仍需完整性与业务验证。
- 本轮保持进程重启后从零重新接收；持久候选归属用于清理，不作为续传游标。重复块处理不代表重启续传。
- 传输/安装的读取保护与长期保留分开。旧快照退出前，仍需保存其恢复所依赖的桥接日志；先持久退出旧恢复入口，再解除引用并回收。

### 4.1 当前代码的真实接口边界

现有 `RaftStateMachine::{CreateSnapshotFile,ValidateSnapshotFile,InstallSnapshotFile}`、`DurableFileSlice` 和 bundle codec 均依赖文件路径。新对象后端必须适配正式的有界正文写入/范围读取，不能临时把完整对象导出成文件来掩盖接口未接通。

当前 CanonicalSnapshotBuilder 仍用业务 DiskManager 构建规范化数据库临时文件。S8 的流式适配消除整份 bundle 的中转及发布复制；业务页与 canonical 数据库文件本身迁移属于 S9/F26 与 S11/F28，不声称 S8 已消除所有临时文件、全表扫描或全部 OS 文件 IO。

S8 先可靠发布；共享 extent、压缩、增量在 S11，均不由 COW/对齐自动产生。

### 4.2 复审补足的恢复和寿命边界

1. **候选完整不等于已发布。** 旧文件后端 `SnapshotStore::Recover()` 可以扫描已形成的快照文件寻找恢复版本。对象后端只能依据持久发布清单及明确保留的恢复入口选取正文；不能扫描候选对象、挑代次最大且 CRC 正确者作为 Latest。复用的是业务恢复判据，不是文件后端的挑选算法。
2. **整次读取与单次 IO 分开保护。** `ObjectMappingSnapshot` 只保留元数据视图；F14 的读许可覆盖实际提交的 IO，不自动覆盖两个块之间的等待。F23 一次跨段读取、F25 一次传输/校验/安装必须有相应的 Store 使用期，使用期内不能删除后续仍会读取的对象；每块实际 IO 继续交给 F14/F02 保护。具体接入复用现有 Store/传输上下文，不另造全局引用服务。进程重启后哪些内容仍须保留，由持久清单而非 RAM 使用期决定。
3. **重复块检查覆盖接收完成后的重发。** 实施前的 `StageChunk()` 在 `download.complete_` 时提前返回 `DUPLICATE_COMPLETE`，没有比较此次重发的正文。S8 已修正该分支：重复块先检查身份、范围和内容，再返回幂等结果；对象和旧文件后端遵守同一约定。

## 5. 三个 Store 的共同恢复协议

先恢复 B → 普通对象服务 → 找到并核对本节点 Raft 持久入口 → 读取 HardState/快照/日志清单 → 验证业务快照和日志边界 → 安装快照 → 重放已提交后缀 → 开放节点服务。NodeStorage 的本地可用不代表 Raft/SQL 已就绪。

复用 `RecoverRaftPersistentState` 的恢复判据，包括旧快照桥接、snapshot index/term、effective_commit，以及先完整校验业务正文再进行破坏性修复。新后端可以利用 B 原子提交表达相关变化，但不能以“都有事务”代替这些协议条件；先保留已有有序过渡及其恢复规则。

例：快照 140，HardState commit 155，日志 141～160，恢复安装 140 后仅应用 141～155；156～160 保留为未提交日志。缺少必需的 148 应报错，不能自行降到 147。

旧文件部署兼容、启动选择/初始化入口、格式及根目录位置必须显式规定。不得通过自动格式化、自动迁移、隐式回退旧文件后端解决打开失败。

### 6.1 本次复审要求的具体判据

- 后缀替换、段轮转和跨段读取使用非空且互不相同的正文，预期来自输入序列和明确裁剪边界；不能以编码后再解码的自洽性代替内容与历史判断。
- 已确认成功必须恢复新状态；明确未提交必须保留原状态；只有提交结果不确定才允许合法的完整旧/新结果，并且不能丢失此前已确认的内容。不能在所有故障用例里都宽泛接受旧/新两种状态。
- 快照至少区分“正文完整但未发布”和“已发布”；CRC 正确、代次更大的未发布候选不得成为 Latest。重启接收从零开始，不允许从候选长度推导续传进度。
- 同一快照在接收中及完成后各检查相同块可重发、不同正文被拒绝；后者不能只换 snapshot_id 或 checksum，否则没有进入“相同身份但字节冲突”的分支。
- 在多块读取的两块之间尝试退出旧版本，仍在使用且没有被取消的读取必须得到原先承诺的完整正文，不能把中途读到已回收位置的错误当作通过；只暂停某一块在途 IO 无法证明整次使用期受到保护，不能用小于一个块的输入替代。
- 既有 `LogStoreTest.DurableLogicalSuffixReplacement`、`StableStoreTest.AtomicGenerationRoundTrip` 和 `SnapshotStoreTest.ChunkStagingPublicationAndRecovery` 中的业务预期可以复用；它们当前走文件后端，不能直接计入对象路径覆盖。`CorruptCurrentScansImmutableGeneration` 的文件扫描预期及 `SnapshotBasePhysicallyCompactsJournal` 的单文件布局预期不得机械照搬到新后端。
- 成功时机和失败注入须使用已有正式路径或测试侧机制，不增加 production 暂停/getter/hook。后续八项审查要列出实际断言、最小变异及稳定性证据；本节只是验收要求，不能记为测试通过。

## 7. 开源参考及具体内化

- [etcd/raft 存储契约](https://raw.githubusercontent.com/etcd-io/raft/main/doc.go)：把持久化依赖与可发送响应分开，异步存储仍可靠有序地交付完成。内化到 F24 及 S8 同步成功边界；协议 event loop 留给 F35/S13。
- [Raft 论文 Figure 2、§7](https://raft.github.io/raft.pdf)：持久状态、快照 index/term 与后续日志衔接及分块安装。内化到 F24/F25 与已有恢复判据；保留本项目额外持久化 commit_index 的契约。

## 10. 2026-10-03 接续：沿用 Manifest，补齐执行协议

本节是用户认可讨论的实现细化，不重新提出已在总方案 §9.3 / F25 中规定的 Manifest 发布，也不新建同职责服务。

- **持久 Manifest / RAM 目录：** LogManifest 和 SnapshotManifest 使用 B 控制记录；只更新受影响记录，不给同一目录再加独立 WAL/CURRENT 文件。RAM view 是 Store 的一致目录版本，可以从 B 重建；它不是 MON/OSDMap，也不是 NodeStateController 的服务状态。发布前准备 RAM 状态，durable 后整体切换。
- **归属与回收：** 有效/候选/待删除状态可恢复；Control 字节不会自动建立物理引用。Store 管业务保留；传输/安装/跨块读取持有整个使用期的许可，实际 IO 仍由 F14 保护。获取使用许可与进入删除状态互斥，锁不跨 IO/网络。已发布正文不可改写；活动日志只追加，后缀替换不覆盖旧读者内容。内存使用计数不逐次写 Journal。
- **候选发布：** 对象建立与候选归属一起提交；分块 durable 后校验，再原子更新 Manifest。完整候选不是 Latest；只按发布入口恢复。提交不确定时隔离并恢复，不按取消删除可能已发布内容。退出有效入口与待删除记录一起提交；删除任务可恢复且有界。
- **跨段：** entry 片段在逻辑日志流中连续、不穿插其他 entry；片段表达 FULL/FIRST/MIDDLE/LAST、长度及完整性。RAM 索引保存首片位置、完整长度和 term，读取固定目录并沿有序段目录找后续片段，不按对象编号加一猜测。单 entry 可超过一个 segment，IO 完成可乱序，完整发布不能乱序混拼。F23 段是普通对象，不复用 F06 物理槽身份。
- **预算：** 增量目录按段存 B；开始准备正文前核算最终控制事务的大小/操作数及 RAM 索引额度。永久超限直接拒绝，不伪装队满反复重试。超大目录的分批准备/切根协议不纳入本轮隐含实现。
- **接收：** 完成后的重复块也比较身份、范围和对应正文。相同内容可幂等确认，冲突拒绝。进程重启从零接收，旧候选进入可恢复清理。
- **生产接口：** 必要的有界 Control 遍历、正文范围读/顺序写由真实恢复、传输和安装消费者使用；不暴露测试 getter，不把完整对象导出成临时 bundle 掩盖接口缺失。旧文件部署继续显式选择，不自动迁移或格式化。
- **代码与验证：** 先分析实现逻辑和持久化顺序，再写必要测试。不要过多纠结于边界条件和防御性编程，不通过兜底掩盖错误。沿用总方案复用性/隔离/安全性、接续冗余清理及八项测试设计审查；临时模块测试最终仅保留按模块压缩的源码和证据，不修改共同 C/P 场景。

### 开源机制与本项目落点

1. [LevelDB MANIFEST/CURRENT](https://github.com/google/leveldb/blob/main/doc/impl.md)：有效文件集合与磁盘存在性分离。内化为 F23/F25 的 B Manifest；复用已有 B/F07，非独立目录日志。
2. [LevelDB log format](https://github.com/google/leveldb/blob/main/doc/log_format.md)：物理片段的边界及完整组装。内化为 F23 entry 分片；跨对象顺序仍由本项目 Manifest 定义。
3. [RocksDB Delete Stale Files](https://github.com/facebook/rocksdb/wiki/Delete-Stale-Files)：旧版本仍被使用时延迟删除。内化为 Store 整次使用许可与有界清理，物理范围仍交 F14/F12。
4. [TiKV snapshot lifecycle](https://github.com/tikv/tikv/blob/master/components/raftstore/src/store/snap.rs)：登记生成/发送/接收/安装的使用状态。内化为 F25 上下文寿命；本项目发布资格由自己的 Manifest 定义。
5. [TiKV Raft Engine](https://github.com/tikv/raft-engine)：追加、内存位置索引、批量写入与协作 GC。内化为 F23/F29；不引入多个 Raft group。

来源已在本轮前置调研核对；具体实现及测试证据以执行记录为准，不用方案说明冒充完成状态。


## 11. S8 实现格式、预算及部署

### 11.1 格式与职责

新后端在显式创建的普通对象空间中保留以下 Control owner；它们是 B 的键值记录，不是新的文件层：

| owner / item | 内容 |
| --- | --- |
| 0 / 0 | `BSTRAFT1`、版本 1、下一个正文对象编号、segment 字节数 |
| 0 / 1 | 节点编号、静态 group 标识及有序 voters；节点首次绑定后不能改为另一成员 |
| 1 / 0 | LogManifest 版本、发布代次、base index/term、last index |
| 1 / segment 对象编号 | 该段仍有效的 `[begin,end)`；只更新变化的行 |
| 2 / 0 | 复用 `HardStateCodec` 的完整状态 |
| 3 / 0 | SnapshotManifest 的 latest/previous 及各自正文对象、index/term、长度和 checksum |
| 4 / 正文对象编号 | 正文种类和 Candidate / Live / Retired 持久归属 |

正文对象编号从 16 起，分配计数和 Candidate 创建原子提交，永不在同一空间中复用编号。目录按分配顺序排列，可以存在编号间隙；定位后继使用目录，不计算 `object_id+1`。它们与 F06 的循环 Journal 槽位没有对应关系。

段内片段头为 `type:u8 + length:u32 + crc32c:u32`，随后是正文；类型 1/2/3/4 为 FULL/FIRST/MIDDLE/LAST。CRC 覆盖类型、长度和片段正文；完整 entry 仍沿用 LogCodec 的格式及校验。完整 entry 和片段合法性属于恢复边界，不为每一字段再建立单独测试。

恢复以 B 清单为权威。已发布快照正文损坏会报错，不扫描候选“找一个看起来好的”；既有旧文件部署保留其原恢复规则。新的快照保留前一版本及桥接日志，是正常发布/安装的有序恢复依赖，不宣称本轮实现损坏情况下的自动旧版本替换。

### 11.2 预算与并发

`RaftObjectOptions` 所有值由部署显式传入：段大小、块读写大小、存活日志编码字节/entry 上限、单次 Append 的条数/编码字节上限、快照字节上限、候选/有效/已退役正文对象的总量上限。段大小写入根记录，重新打开必须一致；其余是运行预算，不以测试数值作生产默认。IO 仍由 F01 查询实际对齐，逻辑 segment 大小不是设备对齐值。

- LogStore 沿用自身互斥锁串行修改；一次读完整 entry 期间不允许本 Store 裁剪其目录，保持整次读取寿命。
- SnapshotStore 由 Raft 节点既有串行调用域使用；`SnapshotInput` 保有整次使用许可，各块再经 F14/正式 ObjectIO。源仍有使用者时 GC 不能删对象。
- 一个 Raft 对象空间只有一个已打开的 Store 组/上下文。Store 同步等待 Durable，不在 S8 私自改成 Accepted 成功。设备 worker 与 S7 仍是原有有界执行机制。
- 所有者记录有总数上限；`Collect(limit)` 每次最多执行 limit 个检查/裁剪步骤，节点一个后台维护执行者调用。仍有整次使用许可的对象不动；退役正文由 F13 `PlanTailTrim` 定位最后一条映射或尾部空洞，每步最多触及一条映射且裁掉不超过 `io_chunk_bytes`；只限制字节不足以限制映射记录数。该查询复用 B 前驱查找，只返回逻辑裁剪位置，不扫描整个对象、不向 Raft 暴露物理地址。对象缩短与范围退役由原 S7/B 原子提交；持久长度就是重启进度，Ownership 保持 Retired。最后小段的 Remove 与删除 Ownership 同批提交，才计入返回的完成数；部分进展可返回 0。内存游标仅是查找提示，部分裁剪后继续该对象，没有独立 GC 日志或持久游标。错误上报节点停止服务；不锁住节点等待 GC IO。
- 最终清单预检复用 F15 的正式 `CheckControlBatch`，涵盖 S7 操作数/字节与 B/F13 单值/批次上限；它不承诺空闲页、Journal 或设备永不耗尽。控制提交与正文创建均可明确失败，不能无限重试。
- 正文若准备成功而最终发布未成功，旧清单仍有效。候选有持久归属，可在已知失败或下次打开后退役；结果不确定时先停止新的提交，不能按“失败”删除可能已正式发布的正文。

### 11.3 部署和阶段边界

首次部署：显式 `NodeStorage::Create` → `InitializeObjects` → `CreateObjectSpace` → `RaftObjectStorage::Create`，再关闭初始化上下文。服务启动使用 `DistributedNodeConfig::object_storage_ = RaftObjectDeployment{...}`，只 Open 已有设备/空间，绑定成员身份后进入共同恢复。不在 Open 中格式化、迁移或因失败回退旧后端。

本轮接通真实 C++ `DistributedNode` 生产组装及 TCP 请求路径；现有命令行工具参数仍选择旧文件部署，没有新增未讨论的设备格式化 CLI。未配置 object_storage 的旧部署不改变默认行为。业务 A 仍有工作数据库文件及 canonical 构建临时文件，归 S9/S11。

维护只接通对象所有权退出/删除，再由 S7/F14/F12 完成单位回收；全节点统一预算、Journal checkpoint 压力调度、稀疏日志段搬迁仍归既有 S12。这里不宣称长期满盘负载已验证，也不提前改 F35 的单提案或 event loop。
