节点控制器允许服务不等于存储已恢复，也不能凭控制器发出的停止命令销毁执行器；实际恢复/排空完成是能力发布的依据。

### 6.2 数组目录、工作库身份及外部许可关闭

[F26 数组子方案](array-buffer-pool.md) 定义目录及 PathCache 的所属身份。持久数据空间身份用于重启后正确寻址；打开实例的运行身份隔离旧缓存和回调。普通重启同一数据空间不必换持久身份，快照安装产生的新工作集必须与旧工作集隔离。身份可由目录上下文承载，不要求塞入每个 TranslationEntry，也不等同 Raft term。

切换前保证候选工作库及目录已就绪；旧任务核对所属身份，不能向新工作库发布结果。PathCache 在解引用叶指针前核对有效 owner 和目录代次，不能用已经释放的指针检查自己是否失效。

关闭先停止新的前台请求/预取及其许可；已经接受的工作、必要写回和恢复收尾仍可使用保留额度完成准备与提交，不能过早封死其 IO 入口。等这些生产者不再产生任务后，提交或放弃剩余 Prepared 许可，再 Shutdown 排空执行器并处理完成事件；随后等 PageGuard、翻译访问、F26 发布保护及外部许可结束，才释放目录/FrameArena，并在实际调用排空后关闭设备。具体依赖按阶段定义，不能持控制器/全局映射锁等待，也不能仅凭 Shutdown 返回就解除仍被 Prepared 句柄保留的内存。

普通 hole punching 保留虚拟地址，不等于关闭目录；整个映射释放须走上述访问退出协议。风险复用 F26/translation-lifetime 和 F02/external-buffer，不重复建立关闭测试。

### 6.3 引导副本异步修复

2026-09-23：F03 的 BootstrapStore::StartRepair/Status/Close 已实现；F34 后续只负责触发、汇总和关闭顺序，不再实现另一套修复 worker。关闭 F03 后再 Shutdown F02、关闭 F01。此处为 2026-09-23 的待接入记录；本地 owner 已由 §11–12 完成，业务节点接入仍待 S8/S9。

关闭先停新修复和重试，未提交意图可放弃，已提交 IO 必须排空后再释放设备；不要求关机前完成全部修复重试。重新格式化/切换布局须先隔离并排空旧写入，不能只靠回调代次检查。后续可变恢复根接入时重新核对权威来源与引用保留；不从固定布局副本修复推定可回退任意旧 checkpoint。本地编排现状以 §11–12 为准，业务节点接入仍未完成。

### 6.4 checkpoint 入口选择与修复的接续顺序（2026-09-26）

启动时读取 F03 固定槽及静态区域 → B 经 F07 验证所选 checkpoint/必要后缀、恢复页并校验完整视图 → 才允许对该动态入口启动后台修复 → 开放对应本地能力；节点服务仍须完成业务与 Raft 恢复。不能在目标未验证时，把一份看似较新的引导引用先复制到另一槽。新旧代次共存不等于冲突，同代次矛盾或静态身份/布局不同仍拒绝。

正常运行中 Checkpoint 发布和修复在 F03 内串行实际槽 IO，不占 B 普通读锁；调用方不把修复完成当成前台服务开放的条件。发布失败且结果不明确时，旧 Bootstrap/B 实例停止接纳相关工作；重新打开设备引导上下文后再恢复，不能用旧缓存里的入口假装完成重开。普通提交恢复、关闭排空与 F02/F01 生命周期仍按 §6.1–6.3。

B 可用后才能按逻辑身份打开 A 的独立恢复描述，见 [F28 §6.3](business-checkpoint.md#63-a-的入口与-b-引导隔离2026-09-26-补充)。这是 2026-09-26 完成 B 组件恢复时的边界；2026-09-30 已完成 §11–12 的本地 F34 编排，A/业务接入仍待 S8/S9。

### 11.1 接口与所有权

- `NodeStorageOptions` 显式携带现有设备、IO、身份、Journal、B、修复预算，复用原参数，不给设备对齐或容量增加假默认。
- `Create(layout)` 只按明确请求格式化；`Open()` 只打开并恢复，失败不自动 Create。每轮重新构造 device、executor、bootstrap、B/Journal，旧格式继续由 F07 正式兼容路径识别。
- `Read/Commit/Writeback/Checkpoint` 通过生命周期接纳门取得本次调用资格。其正式价值是持有上下文直到调用完成、将实际错误与完成结果汇总到状态；不暴露 B 原始指针以绕过关闭协议，也不另写恢复或提交算法。
- `State()` 返回一个完整值：运行代次、phase、全部 conditions、主原因、元数据读/写/维护能力及原错误。状态不授权 Raft Leader 写入或线性一致读。
- `Close()` 可取消正在打开实例的发布，等待启动/已接纳调用退出，再关闭 B、F03、F02、F01。物理 IO 不强制取消；旧 RAM 快照仍按 B 原契约可读。再次 Open 必须在 Close 返回后发起。析构前调用者应结束并发访问；显式 Close 才是关闭错误的报告入口。

### 11.2 状态、故障与并发

| 项目 | 当轮含义 |
| --- | --- |
| Starting → Recovering → Serving | 打开基础依赖 → 恢复 B → 仅开放本地元数据能力 |
| Draining → Stopped | 已拒绝新调用 → 实际已接纳工作/修复/IO 排空并关闭 |
| Failed | 恢复失败或数据持久化失败，拒绝新调用；先 Close 再重开 |
| RecoveryFailed / IOFault | 严重限制；保留原异常，不能被较晚成功完成覆盖 |
| BootstrapRedundancyLost / BootstrapRepairFailed | 反映现有 F03 状态，可与其他条件共存；已有有效来源时不独自阻断 B 服务 |
| ResourcePressure | 记录最近观察到的资源准入拒绝；由实际 B 决定每次接纳，不凭此永久禁写或阻断 checkpoint；成功 Commit/Checkpoint 清除此提示 |

主原因优先顺序为恢复失败、IO 故障、修复失败、资源压力、冗余不足；此顺序只用于展示。各条件保留，清除一个不清除其他条件。压力表示观察到的拒绝，不冒充实时内存/设备容量计量。

F33 当前是 F34 内部的 `NodeStateController`，由同一个短状态锁串行修改，不新建一个线程/消息总线。F34 的 IO 等待、恢复和关闭都在锁外；普通请求不进入控制器事件队列。调用完成携带运行代次，关闭先换代；旧完成不能开放 Serving，也不能清除新一轮条件。同一轮排空期间发生的真实故障仍保留，但不把 Draining 改回 Failed/Serving。

现有 F03 已有自己的异步修复 worker。只有 B 实际验证目标和日志后才首次调用 StartRepair；将这个非阻塞调度与 Close 的停止决定串行，关闭已开始就不再启动修复。修复不阻塞 Ready；State 读取 F03 的短锁状态进行汇总，不增加第二个轮询线程。Close 排空修复后、释放上下文前还须采集最终修复状态，不能依赖调用方恰好在此时查询 State 才保留错误。线程创建等调度错误也作为修复失败保留，不冒充修复已开始。

### 11.3 代码前推演与复用

阅读入口：`bootstrap_store.cpp` 的 Open/StartRepair/Close，`metadata_engine.cpp` 的 Open/Commit/Checkpoint/Close，`io_executor.cpp` 的 Shutdown。已确认 F03 Create 后仍须显式 Open 绑定区域；B Owns Journal，F34 不再单建第二个 Journal。

生产代码逻辑审查优先于测试：核对取消启动时不能发布 Ready/启动新的修复、持久化失败不能继续接纳、关闭期间必须保留错误、部分启动失败按依赖释放、IO 等待不持状态锁。本轮据此修正了“B 恢复完成后 Close 已到达却仍启动修复”的顺序，以及关闭期间原始错误不能因代次改变而丢失。后续收尾审查进一步区分主动取消与恢复失败，并显式传递部分启动清理产生的 Close 错误，避免仅靠析构吞掉错误。

本轮 F33 继续借鉴 [Kubernetes Conditions](https://kubernetes.io/docs/reference/node/node-status/#conditions)：原项目把 Ready、内存压力、磁盘压力等分别记录，避免一个标志遮蔽多个事实；本项目内化为节点本地并存条件和完整状态快照。锁、代次、准入与排空协议由本项目数据依赖决定，不移植 Kubernetes 的分布式调谐、周期心跳或控制平面。F34 复用本项目 F03/F07/B 现有机制，没有引入新的外部算法/依赖。

### 11.4 当轮必要验证与退出

只沿正式 `NodeStorage → B/F03 → F02 → F01` 路径，用非空数据及独立输入模型：

1. 创建、checkpoint、关闭重开能恢复实际数据；恢复中不能读，完成才开放能力。
2. 必要恢复内容损坏时明确失败；若仅一个引导副本有效，仍不能在验证目标前修复它，Open 失败不格式化。
3. 暂停真实 checkpoint Flush，Close 必须等待，Draining 后拒绝新操作，老 RAM 视图保持原内容；成功与失败都须实际收尾，失败不能因关闭换代而丢失。
4. 恢复被 Close 取消后，迟到完成不能开放能力或启动修复；实际 IO 退出后才能完成关闭。主动取消不报恢复故障，清理时的真实关闭错误仍须由 Close 报告。
5. 暂停异步修复不阻断 B 服务；真实资源拒绝、数据 IO 故障与冗余不足可以并存，主原因不能掩盖其他条件，失败后拒绝新工作。 若修复写在 Close 排空期间失败，停止后的视图仍保留该原始错误；不通过中间轮询替生产完成汇总。

优先复用 S5 的非空输入/独立模型和相关原组件回归，不新增枚举排列、私有函数、第三方或每层镜像测试。只在测试二进制链接故障控制，不改生产 API 以方便注入。判据应检查数据、接纳与实际完成，超时只作防挂起。完成后执行主方案 §1.5 八项审查，最终模块源码和结果分别压缩；仅留最终版本，常驻共同 C/P 不改。节点业务、裸设备及真实掉电仍按各自实际接入条件验收。
