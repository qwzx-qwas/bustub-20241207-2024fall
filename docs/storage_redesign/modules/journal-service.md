## 6. 讨论后的方案与待冻结边界

以下为本轮收录的设计方向和约束；具体字段、数值、接口及当轮验收未确定前，不能把它们补成默认实现。

### 6.1 原子批次与刷盘分组

一个 CommitBatch 是恢复原子单位，多个 batch 可共享一次持久化屏障；合并物理 IO 不自动合并业务事务。批次边界、完整性与提交有效判定仍须保留，不能把一个递增 LSN 或设备单次 write 当成完整提交。

完成仅确认屏障实际覆盖且前置数据依赖满足的批次，连续 durable 边界不能跳过空洞。Common 正文先达所需 durable，再提交元数据；Deferred 正文和恢复信息在统一批次。S3 的条数/字节上限显式配置、不等待凑批；后续调优待讨论，低负载及时提交，错误返回仍可能为未知结果。

### 6.2 与 Raft 日志和执行层的区别

F23 的最终日志段存 entry 正文，本模块存 FS 元数据/控制/Deferred 恢复信息；不是所有 Raft 日志都再经本模块复制一次。F02 共用 IO/屏障能力不等于二者共用业务提交语义或一份恢复格式。当前 BusTub LogManager 的占位实现仍需按 S3/S4 补齐，不能只修改接口宣称已有 WAL。

### 6.3 第二轮审查补充

批次是原子范围，LSN 是日志位置；不强制为两种含义各持久化一个独立计数器，可用提交记录位置唯一标识批次。记录边界、完整性和覆盖依赖仍不可省略。提交前状态、结果未知和已 durable 状态分开；超时/同步失败不自动授权回滚或重用空间。

日志编码需要协同 F06 保护已经确认的前缀；不能依赖“尾部损坏则截断”丢掉此前成功提交。F08 的元数据恢复记录与 F27 的任务/正文组成同一个有效批次，恢复不能分别采纳两半。混合 Common/Deferred 的批次要等 Common 数据 durable 后再形成有效提交。

### 6.4 复合原子性与系统调用边界（2026-09-23）

一个 struct 或一次写入不等于原子提交。F07 须定义完整有效批次的编码、前缀保护、提交识别与重放；Common 前置正文 durable 后才能提交，Deferred 的正文和元数据恢复不能分开采纳。Flush 失败/超时仍可能留下有效提交，不按确定未提交释放空间。业务元数据不用 setxattr；参见[总方案 §6.1](../README.md#61-原子提交不是合并系统调用2026-09-23)。F04 的区域 IO 不承担这些职责。

### 6.5 完整记录、分片和跨段位置

F08/F19 提交完整逻辑记录或 CommitBatch；F07 与 F06 在日志子系统内部完成空间安排与分片。F06 给出可用位置/容量，F07 编码片段头与正文，F06/F04/F02 执行合法范围。上层不选择槽位、不拼接失败后的半条记录。

FULL 是完整记录，FIRST/MIDDLE/LAST 描述被拆开的记录；LAST 不表示事务提交、格式单元写满或 segment 封闭。每个片段有明确边界/长度/完整性依据；写入单元的段身份共同排除旧尾部。未封闭缓冲中，下一条 FULL/FIRST 可紧接 LAST，剩余不足头部时按格式填充。具体字段与格式单元大小见 S3 §6.9，不能直接等同于设备对齐。

第一版同一记录的片段在逻辑流中连续，不与别的记录任意交错；完整请求预留位置、缓冲和结果容量后再接纳。逻辑输入可大于单段，但受最大记录、在途字节、可预留段容量约束。大快照/普通正文继续走数据对象，不因支持跨段就全部内联 Journal。

恢复验证完整片段顺序、长度、段身份、校验及批次提交依据；全部满足才交消费者。LAST 或一次 F02 Flush 不单独证明原子提交；缺片不能应用半批，已确认范围损坏不能按未提交尾部静默截断。

### 6.6 失败收尾与重试

| 判定 | 返回与后续 | 空间/缓冲处理 |
| --- | --- | --- |
| 未接纳、未发 IO | 明确拒绝，资源可用后重试 | 退还预留，外部许可仍归调用者 |
| 能证明未提交且恢复不会采纳 | 返回明确失败，不必等待全部 GC 完成 | 残留逻辑失效，排空相关 IO、解除保留后再复用 |
| 有效提交 | 依发布契约完成通知 | Journal 仍按恢复/Deferred 保留，完成状态可另行释放 |
| 结果不确定 | 不返回普通未提交结论，不换新业务身份盲目重发 | 保留判定所需内容；未知不等于已取消或已回滚 |

首次方向是写入/Flush 错误造成提交不确定时隔离这条 Journal 的新提交，排空相关 IO，通过有效记录和恢复协议判定，再恢复提交或上报故障。仅观察者超时不必宣告设备损坏，也不停止仍有效的已接纳工作。不能在未解决的日志空洞后持续确认新提交。

重试由持有事务身份的协调层决定；物理重试也须保留原位置、稳定正文和访问权并受故障策略约束，F06 不自行生成业务操作。业务 Raft 已提交的命令不会因本地失败而取消，恢复后继续 Apply；客户端重试/去重仍归上层契约。S3 的错误与开放条件见 §6.9；S5 扩展 checkpoint 恢复。

### 6.7 异步完成与有界状态寿命

位置/顺序分配保持短小，编码与独立 IO 可有界并行；不持全局锁等待设备。每批只跟踪位置、剩余 IO、错误、屏障覆盖和结果交接，不复制第二份恢复正文，不逐项持久化执行历史。

A 完成、B 未完成、C 完成时只推进到 A；保存 C 的有限完成事实，B 完成后继续推进。顺序责任、发布/通知及引用交接完成后释放逐批状态，仅保留必要边界。已完成未消费结果同样占额度，前方卡住或消费者不释放时入口背压，不能不断扩展窗口。

IO 工作缓冲、批次完成状态、磁盘 Journal 内容分别按设备访问/消费者、顺序交接、恢复与 PayloadRef 条件释放。外部许可沿用 F02 终态前归还，自有结果沿用最后所有者归还预算；F07 不把历史 IOBatch 长期留作日志索引。连续 Journal durable 边界不跳洞，并不建立跨独立对象/业务的全局发布锁。

### 6.8 裁剪、跨段保留与阶段交接

F07 汇总本 Journal 恢复链、完整记录/批次及 PayloadRef 保留，给 F06 可执行的范围许可；F10 提供 checkpoint 的持久依据。不同使用者须先转换成同一 Journal 地址空间才能求保守边界，不混合 Raft index/事务时间戳。边界落在中间片段时保留所需起点及提交验证范围。

首次沿有效日志顺序回收前缀整段；若旧 Deferred/读者拖住大量空间，优先推进其依赖并上报有效/受保留无效字节及阻塞时间。S5 新恢复入口/裁剪许可发布前保留旧恢复链，发布后也不能回退到依赖已复用段的入口。任意孔洞复用或活片段搬迁不是当前默认。

S3 先提供有界追加与扫描，尚未具备可靠回收时满容量明确背压/失败；S5 与 F06/F10/F11 完成基础回收，S7 接入 F22 同一执行能力，S10 扩展 F27/F14 保留。不能等 S12/F29 才回收 FS Journal。前进资源与位图边界见 [F06 §6.4–6.6](journal-backend.md#64-逻辑释放复用与回收条件)及 F31。

### 6.9 S3 已批准的单份追加协议（2026-09-24）

本轮授权 F06/F07 及 F16/F31 局部准入，实现及当轮验收已完成。普通 Journal 只有一份追加内容；撤回“正文 Flush、A 边界 Flush、B 边界 Flush”的候选。F03 两份固定引导信息仍沿用原协议；不能混淆引导副本与普通 Journal。S4 B WAL、S5 回收、S10 Deferred 未实施。

正常提交组：预留整批资源和位置 → 写入全部批次（允许各段并行）→ 等全部必要 IO 完成 → 一次 Journal Flush → 按顺序通知。每批仍单独验证完整性；同组不是跨批业务事务。正文和批次提交记录放在同一追加流，不重写提交边界。错误叫“提交结果无法确认”，保留底层异常；不能改称确定失败或自动重发。

**保护旧前缀：**每批从全新的格式单元开始，不改写已经提交单元的尾部。单元满足实际设备对齐，但不假定单次写原子。F07 一旦观察到投递、写入完成或 Flush 错误，立即隔离此 Journal 新提交，不等组内其他批次排空才关闭入口；结果通知仍须等待所有已发 IO 排空。F02 尚未交付错误完成结果时可能接纳有界排队请求，这些请求在失败后不能再投递；未发请求明确未提交，已发请求保守报告无法确认。观察超时不取消。Close 排空而非强制取消设备操作。

**恢复采取保守拒绝：**先完整扫描验证，再交付完整批次；任何非零坏单元、缺片、错误身份、顺序空洞、半批都阻止 Open，不自动截尾或假装旧承诺未发生。全零后方必须全部为零。完整有效记录可能来自尚未获得响应的请求，Open 对验证过的流再 Flush 后才开放。本阶段不能自动区分撕裂尾部和后来损坏，代价是部分崩溃需人工/上层恢复。整个后缀被一致地擦成零或回滚，在没有独立见证时无法检出；CRC 也不是抵抗任意篡改的证明。S5 再定义可靠 checkpoint/裁剪，不用 Raft 日志冒充本机物理映射。

#### 6.9.1 有界格式与寻址

所有尺寸显式配置，无固定 4 KiB 假定：格式单元 U 至少 256 字节，满足设备偏移/长度对齐；段 S 是 U 的整数倍。Journal 区完整槽位至少两个。槽 0 是不可变格式区，第一单元记录魔数、版本、Bootstrap 的 storage/device 身份、显式非零 Journal 身份、S/U/容量、段编号预留上界及恢复输入上限；其余为零。Create 必须先验证全部完整槽位为空，再写描述并 Flush；Open 不格式化。

S3 不复用槽：初始化一次保留数据槽 1..N−1 的身份范围，段编号等于槽号；重开继续同一个段的未使用位置，不把它重新分配成新段。Journal 身份+段编号确定段身份，单元也带此身份。没有每组更新的编号计数器。原先“动态成批领取新编号、重启跳过余量”的方向只在 S5 真正换代复用时讨论。

v1 全部整数大端编码，不依赖 C++ struct ABI。格式单元头 64 字节：magic[8]、version:u32、有效负载长度:u32、Journal ID[16]、段编号:u64、段内偏移:u64、batch 起点:u64、前一 batch 起点:u64；末尾 CRC32C:u32 覆盖前 U−4 字节，中间未用位置补零。

片段头 16 字节：类型:u32（FULL=1/FIRST=2/MIDDLE=3/LAST=4/COMMIT=5）、片段长度:u32、记录序号:u32、完整记录长度:u32。普通记录是不透明的非空字节串，B/F19 后续定义其业务类型。COMMIT 正文 24 字节：batch 起点:u64、记录字节总量:u64、全部普通片段头和正文的累计 CRC32C:u32、保留零:u32；其序号等于记录数，完整长度字段为零。COMMIT 必须是最后一个片段；其所在单元后方补零。LAST 后可以继续同批下一条记录，不把段大小当记录大小。batch 起点本身是 LSN/身份，不额外持久化一个同义计数器。

#### 6.9.2 接口、线程及资源

F06 PlanAppend 将已选定的连续范围拆为合法段内请求；F07 拥有追加游标、格式、批次完整性和恢复。F02 增加显式 TryPrepareFlush：只预留一个操作名额，不分配数据缓冲，沿原执行器调度。它只覆盖调用者已经等完的写入，不暗含其他队列任务的屏障；原 TryPrepare 的空批拒绝不变。

JournalService 的 Create/Open/Close 由生命周期拥有者安排；成功启动后 TryAppend 可并发使用。一个协调线程取当前队列内有界组，投递给原 F02 worker 并行 IO，不新增设备线程池、不等待凑够批次。位置安排串行，设备等待不持队列锁。max_record_bytes、max_batch_bytes、max_records_per_batch、max_group_bytes、max_group_batches、max_pending_batches、max_pending_bytes 均显式提供。

接纳前预留全部 F02 数据缓冲、结果、位置和一个 Flush 名额，编码逐单元使用有界临时缓冲，再复制进入这些 F02 缓冲；不再保留第二份完整编码批次，不宣称零拷贝。规划描述符和单元临时缓冲只由一个准入执行者持有，受最大组/记录数/单元大小限制，额度计量不能忽略这部分短期内存。预留失败不发 IO、不占用追加位置。已接纳不保证设备成功，只保证正常运行的自身预算不会卡死于缺少刷盘名额。组内多余 Flush 预留释放，只执行一次 Flush。完成后及时释放 IO 缓冲；结果票据保留期间仍占 max_pending_batches，以防无人消费导致无界增长。F02 统计实际对齐分配，F07 的字节预算用于限制工作量，不把两者相加当实际 RAM。

空间耗尽返回 NoSpace，不覆盖旧段。故障后返回 Faulted；未接纳 Full/Stopped 与已发 IO 的 Indeterminate 有明确区别。消费者放弃票据或 WaitFor 超时不取消写入。恢复按两次有界扫描完成：先验证整个流，再逐批交付，内存受记录/批次上限约束；回调失败不开放该实例，调用者丢弃其部分恢复上下文。S3 没有任意位置 PayloadRef 读取、checkpoint 或段复用，分别由 S4/S5/S10 接续。

#### 6.9.3 参考的机制与差异

- [LevelDB Write](https://github.com/google/leveldb/blob/main/db/db_impl.cc)：追加组和一次 Sync、Sync 失败隔离。内化为 F07 组 Flush 和 Indeterminate；不沿用可跳过坏记录的扫描策略。
- [LevelDB log format](https://github.com/google/leveldb/blob/main/doc/log_format.md)：完整/首/中/末片段。内化为跨单元、跨段记录；新增本项目身份、批次 COMMIT 和完整链校验，不照搬其 32 KiB 格式。
- [SQLite WAL](https://www.sqlite.org/fileformat.html#wal_file_format)：流内提交标识和身份/校验，说明提交识别不必每次更新两份外部边界。采用这一思路，不照搬 SQLite 帧布局或读锁。
- [RocksDB recyclable WAL](https://github.com/facebook/rocksdb/wiki/Write-Ahead-Log-File-Format)：记录携带日志身份排除旧尾部。内化为每单元 Journal/段身份；S3 不声称已有循环复用。
- [FAST18 Protocol-Aware Recovery](https://www.usenix.org/system/files/conference/fast18/fast18-alagappan.pdf)：讨论崩溃尾部与损坏的歧义。内化为无法证明安全时拒绝开放，不借用论文的小标记原子写假设，也不新增自动跨节点物理恢复。
