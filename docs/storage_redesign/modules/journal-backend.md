## 4. 开源参考与本项目落点

- [LevelDB 日志格式](https://github.com/google/leveldb/blob/main/doc/log_format.md)：在一个日志文件的 32 KiB 格式块间拆分记录。内化为 F07 的 FULL/FIRST/MIDDLE/LAST 分片与重组，F06 提供跨段空间；32 KiB 不是本项目 segment 大小、设备对齐或原子写保证，LevelDB 本身不提供本项目的跨槽位复用协议。
- [RocksDB 可复用 WAL](https://github.com/facebook/rocksdb/wiki/Write-Ahead-Log-File-Format)：用日志编号识别复用文件内的新旧内容。内化为段身份及独立校验单元的身份核对；不是仅给段头加一个计数器。
- [SQLite WAL Reset](https://www.sqlite.org/fileformat.html#wal_reset)：在安全重置后用新的 salts 排除未覆盖旧帧，可保留文件而不截断。内化为安全标记可复用、换代覆盖、通常不清零整段；本项目不照搬 SQLite 锁模型。
- [SeaStore SegmentedJournal](https://github.com/ceph/ceph/blob/main/src/crimson/os/seastore/journal/segmented_journal.cc)：段序号、扫描身份及提交阶段分别承担职责。内化为 F06 的段身份与 F07 的顺序推进分工，不据此声称已获得跨段事务协议。

核对：2026-09-23。以上为机制参考，不引入依赖或复制完整后端；编号分配和失效恢复协议由本项目单独证明。

## 6. 讨论后的方案与阶段边界

2026-09-24 用户已授权下列 S2 范围及 §7 测试；S3/S5 的格式、控制区和恢复细节不能在 S2 自行实现。

### 6.1 segment、记录和 IO 的区别

segment 是 Journal 的空间与生命周期管理单位，可以容纳多条记录，一条记录也可以跨段。逻辑 record、物理 fragment、CommitBatch、格式块与设备 IO 单元分别表达内容、分片、原子恢复边界和 IO 组织，不能混成同一个大小。

F07 接收完整记录/批次，F06 提供合法位置集合，F07 根据位置容量编码片段，再经 F06/F04/F02 执行。F08、F19 等调用者不自行理解段尾及跨段拼接。底层每个成员仍须落在单个合法段内；一个 batch 可以包含多个段的成员，总字节数不以单段大小为上限，而受资源预算约束。

S2 的范围适配器只执行已给出的合法位置。自动选择新段、预留跨段空间和记录语义在 S3 与 F07 接续，不把这些工作交给业务调用者，也不声称 S2 已有跨段原子追加。

### 6.2 段身份、旧尾部与持久格式

固定槽位表示物理位置，段序号表示一次使用及日志顺序，format_version 表示编码格式。方向是每启用一个段取得新的全 Journal 单调段序号；候选宽度 64 位，禁止静默回绕。段身份还须受所属存储/Journal 身份约束，不能与对象、帧或业务工作库的代次混用。

独立校验的写入单元携带段身份、位置/顺序和有效长度，关键头部与正文共同校验。一个单元可容纳多个片段，不强制每个小片段重复整份身份。仅段头换代不能排除旧尾部；引用和恢复扫描也要核对所属段身份及有效日志链。

S3 段身份在同一次使用内可以继续追加，但不能重新分配给另一次使用；其静态预留见文末。S5 动态换代的候选方案是先可靠持久化一批编号的预留上界，再分配其中编号，重启跳过未用余量。直观例子：先在盘上记下“100～199 已领走”，运行时用到 123 就重启，下一次从 200 开始；124～199 不再使用，以免重复发出可能已被写入的号码。号码跳过不占用相应数量的物理段。允许编号空洞，不能把编号连续性当作 durable 连续性。S5 可变控制区、发布及损坏处理待冻结；不能仅凭内存计数或未经证明的“最大合法头 + 1”恢复。该控制信息必须可直接定位，不能依赖尚待 Journal 恢复的 B 普通对象映射。

S3 在解释已有 Journal 前，须从确定入口识别段大小、格式和身份并检查配置一致性。S2 构造只验证几何，不创建/打开有效日志；S3 不能把任意 S2 字节自动认作已格式化 Journal。F03 v1 不因本方案获得新字段，若需引导格式变化应按 F03 的接续方案明确实施。

### 6.3 追加尾部与对齐

采用未提交尾部缓冲内合并、按约定对齐单元封闭写出的方向。LAST 仅表示一条记录结束，尚未封闭的缓冲后面可以接下一条记录；已确认写入单元不因填空而原地改写，后续从新单元继续，并不废弃整个 segment 剩余空间。

实际对齐来自 F01/F04，不固定为 4 KiB，也不把对齐当作掉电原子性。一次写出的有效范围及必要填充必须初始化；失败的新单元由完整性协议识别。若后续需要复用已确认单元的余量，另评审尾块 COW 或经证明的保护协议，不默认为普通 RMW。Raft 日志的尾块策略仍由 F23 接续，本节不隐式改变其业务格式。

### 6.4 逻辑释放、复用与回收条件

生命周期区分“仍被使用 → 待回收 → 可复用 → 新身份使用”。这些是语义阶段，不要求另设全局状态服务。仅逻辑删除不能标为空闲；恢复/持久引用已解除，且旧读者、任务、IO 都退出后才可复用。

顺序：所有者证明不再需要 → 可靠发布恢复/裁剪依据 → 禁止旧身份取得新引用/发起新 IO → 等待已有访问退出 → 允许分配 → 初始化新身份 → 接纳追加。入口关闭、检查引用和分配必须同步，不能只检查一次零引用。超时、丢弃观察句柄或过滤旧回调都不能替代排空旧设备操作。

首次回收采用沿有效日志顺序推进的前缀整段复用；不在仍有活内容的段内任意覆盖小洞。回收许可的唯一证据不得只保存在将被覆盖的段内；有效恢复入口也不得回退到依赖已回收日志的旧 checkpoint。S5 与 F03/F07/F10 共同落实；此前容量不足应背压或明确失败，不循环覆盖有效段。

可复用后通常保留原始字节，新的内容以新身份覆盖；旧的更长也不默认整段清零。剩余段内空间供本轮后续追加；恢复依据身份、长度、校验及有效链排除旧尾部。可选 discard/清零也是设备 IO，若未来引入，必须与重新分配同步，不能迟到后破坏新内容。

段空闲 bitmap 可加速搜索，高层摘要可重建；空闲权威由本协议给出。F12 管普通数据 extent，本模块管固定 Journal 槽位。F26 的 HPArray 归还翻译数组 RAM，文件系统 punch-hole 归还宿主文件块，均不等同于本模块的使用权复用。

### 6.5 跨段保留与空间效率

仍需完整恢复/读取的记录或 CommitBatch，要共同保留其必要片段；边界落入中间片段时回退到所需起点。具体引用由 F07 定义，S10 与 F14/F27 衔接。

整段回收存在少量有效内容拖住大段的保留浪费，前缀策略还可能阻塞其后的段。支持跨段不等于强制塞满每段尾部：大记录可以跨段，小记录是否跳到新段由后续布局阈值决定。优先推进阻塞 checkpoint/Deferred/读者，统计有效字节、无效但受保留字节和阻塞时间。FS Journal 内有效内容搬迁为后续待评估优化，须先解决引用原子切换和恢复依赖；不自动并入 F29 的 Raft 日志整理。

### 6.6 与失败、预算和调度的交接

F02 报告实际 IO 结果并保留尚在使用的缓冲；F07 决定明确未提交、有效提交或结果不确定，见 [F07 §6.6](journal-service.md#66-失败收尾与重试)。部分写成功不授权释放整个段。F06 只能执行已取得回收许可的物理复用，不能自行重发业务请求或取消已提交 Raft 命令。

S3 的准入预留完整请求所需空间、工作缓冲、成员与完成名额；大小可以超过单段，但必须有显式上限。预留回收/恢复操作的前进资源，不能等 Journal 满后才发现完成记录无处写入。S5 基础回收不依赖 S7 的完整 F22；后续 F22 接入同一能力统一安排，不能复制第二套段生命周期。

### 6.7 S2/F06 当轮执行范围（2026-09-24 已授权）

目标是把“Journal 槽位＋段内范围”安全转换为已有 F04/F02 IO；S3/S5 的记录和持久格式尚不实现。

1. 构造绑定现有 RegionManager 的 Journal handle，并显式接收 segment_bytes；无默认段大小、默认路径或第二个设备/executor。
2. 段大小非零、不超过区域容量，并满足实际偏移/长度对齐；段数为完整槽位数，区域不足一段的尾部不可寻址。内存对齐继续由 F02 校验/分配，不能混同段大小。
3. 正式请求 JournalIORequest 包含 uint64_t segment_slot_、IOOperation operation_、uint64_t offset_/size_；一次可传多段的多个成员。检查槽位、非空范围、越界及算术溢出后，按 slot × segment_bytes + offset 转为区域相对范围。
4. 全批范围先验证，再进入 F04/F02 准入；自有缓冲与显式外部许可分别复用现有 TryPrepare/TryPrepareExternal，返回原 IOPreparation/IOBatch。非法或拒绝不消费外部许可，不发 IO。
5. 正式类 JournalBackend(RegionManager&, uint64_t segment_bytes)，提供 SegmentCapacity() 及两种准备入口；不增 Submit/Flush 转发器、缓存、队列、线程或事务状态。
6. 使用原 executor 提交批次；独立范围可并发，同范围冲突由所属调用者排序。析构不取消已接纳 IO，设备替换/格式化前沿用现有停止入口和排空规则。
7. S2 不分配/复用槽位、不持久化段头、不编码 FULL/FIRST/MIDDLE/LAST、不提供 Append(record)。单成员跨段仍属非法物理范围；这不能被写成 Journal 逻辑记录长度限制。S3 的位置预留和分片组合继续在本模块与 F07 内完成。
8. 已有 F01–F05 接口可支持上述目标；生产修改优先局限新增后端和正常构建接入，不为测试添加 hook/getter 或修改默认行为。

## 7. S2 当轮测试与验收（2026-09-24 已授权）

1. 正式 F03 → F04 → F06 → F02 → F01 Direct 文件路径：不同槽位/偏移写入不同非空正文，包含一个 batch 的总范围大于单段、但各成员合法的情形；覆盖自有与外部缓冲接入，持久化并重开读取。测试侧独立计算预期设备位置和内容，检查 Journal 外哨兵未改，不能只用同一生产地址转换写入再读回自证。
2. 非空批次包含非法槽位、单成员越界、溢出或不合实际对齐的成员时，整批无 IO、外部许可仍归调用者；区分完整末槽与区域余尾，构造依据实际几何，不把本机 512/4 字节等查询结果写死。
