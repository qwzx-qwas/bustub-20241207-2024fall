### 6.1 第二轮审查补充

Superblock 候选不仅需要自身校验通过，还要满足区域、checkpoint 和保留日志的恢复依赖。新入口发布前旧入口及日志必须仍能恢复已经确认的本地提交；不能因新入口损坏就任意选择一个较旧但可读的入口，静默丢掉已确认内容。

副本数、原子发布布局、故障模型与回退判据须在 S2/S5 冻结。未知格式或设备身份冲突时明确失败；Create/Format 不得由 Open 失败隐式触发。

### 6.2 基础引导讨论记录（2026-09-23）

本节保留前次讨论的范围；用户随后再次要求执行 F03 和测试，本轮具体规则以 §6.4 为准。

**已授权的范围：** 单设备固定布局引导；显式 Create 与只读 Open；身份、格式、区域边界及冗余记录检查；按 §6.3 异步修复已确认可修复的副本；实际 IO 复用 F02/F01。F03 本轮不提供在线区域迁移、任意重新格式化、普通对象映射或业务恢复。第一轮完成只能标“基础引导阶段已完成”；S5 恢复根发布仍未完成。

职责安排：

1. F03 持有引导对象的格式和已知位置定义，建立范围受限的引导寻址；所有实际读取、写入和 Flush 使用同一 F02 执行链，不另建同步设备后端。
2. F03 保存并检查基础区域描述；F04 后续接管区域寻址和管理，F05/F06 使用该描述定位元数据页和 Journal。普通调用者不能从引导接口获得任意地址写权限。
3. 初版布局创建后不在线改变，不提供按“最高代次”猜测恢复状态的接口。可变恢复入口必须与 checkpoint、日志保留条件一起在 S5 冻结。
4. 记录布局采用明确字节序与长度，不直接序列化 C++ struct。记录位置是格式约定；IO 对齐来自 F01 查询，二者不可混淆。
5. Open 成功仅表示已识别有效引导信息，不表示 B 已恢复或节点可以服务请求。

**前次讨论的候选（本轮落实见 §6.4）：**

| 项目 | 候选规则 |
| --- | --- |
| 副本布局 | 两个固定 64 KiB 槽位，偏移分别为 0 和 1 MiB；区域分配不得覆盖它们 |
| 完整性 | 复用现有 CRC32C，明确覆盖范围；不把校验通过当作掉电原子写 |

| 打开冗余 | 一份有效副本可用时返回布局并报告冗余不足；未知格式或有效副本冲突拒绝打开 |

### 6.3 异步副本修复（S2 已实现）

用户要求修复不阻塞正常流程。本节记录执行与生命周期约束，具体格式与实现以 §6.4 为准。F03 后台驱动现已完成；F34 的整节点调用接入仍待实现。

**前提及返回：** 完成必要的引导读取，确认存在匹配当前设备/存储身份、格式可识别且布局合法的副本，同时不存在需拒绝的有效副本冲突或未知格式，才返回可用引导信息和“冗余不足”条件。Open 自身保持只读，不同步等待修复成功、后台队列腾位或修复重试。F34 可以继续打开后端和恢复 B；对外服务仍以各自恢复、Raft 和可见性条件为准。两份均不可用或无法确定权威来源时，不能用异步修复作为继续启动的理由。初始 Create 的双份持久化成功合同保持。

```text
Open 校验 → 返回有效布局 + 冗余不足
                  ├→ 继续后续恢复/正常工作
                  └→ 登记有界修复意图 → 有资源时提交 F02
                        → 写坏槽位 → Flush → 读回校验
                        → 当前实例确认成功后解除冗余不足
```

**职责：** F03 负责修复任务和后台驱动，判断修复是否安全、固定源内容并验证目标；F34 只负责生命周期与触发；F02 负责实际 IO、缓冲和完成结果；F31 约束后台资源，F33 接入时只汇总服务条件。F03 当前阶段只实现实际需要的接入，不提前建完整节点控制器或第二套 IO 执行器；§6.4 的一个按需协调线程服务本轮真实修复任务，不为每个重试或每个 IO 创建线程。修复不需要通过逐 IO 的全局状态审批。

**非阻塞和预算：** 每个打开的设备实例至多保留一个修复意图/任务，重复发现合并；意图、准备、在途及未处理结果都受限。后台暂无额度或 F02 返回 Full 时保留有界 pending，返回给正常流程，不同步等待、不反复忙轮询。使用受限后台额度及调度机会，并给修复保留进展机会；具体额度、退避和驱动方式在实现前冻结，不能声称当前 F02 已有前后台优先级。线程不会持全局锁等 IO，F02 IO worker 不得同步等待同一执行器中的后续修复任务，避免占满 worker 后死锁。异步去除正常调用链的修复等待，不承诺共享设备上零延迟影响；写入、Flush 与读回仍会消耗带宽和队列容量。

**安全及失败：** 保持有效源副本不变，只重建已判定可覆盖的目标保留槽位；完整写入、Flush 和读回一致后才发布修复完成。校验通过不单独证明来源权威。失败保留冗余不足及错误原因，按有界策略重试；未知格式、有效副本冲突和持续设备故障不循环覆盖。仅副本冗余不足不自动禁止所有正常操作；底层错误若表明已无法维持正确性，则沿相应模块规则限制服务，不以“后台任务”掩盖真实设备故障。

**代次与关闭：** 任务绑定存储/设备身份、当前打开实例和源内容。迟到回调不能清除新实例的条件。关闭时可放弃尚未提交的修复意图，已提交 IO 必须排空后才能释放缓冲、关闭设备；不得为完成整个重试周期拖住关闭。重新格式化或更换布局前，也必须隔离并排空旧 IO，仅丢弃旧回调不能阻止旧写入破坏新内容。修复中断后，下次 Open 重检副本即可重建任务，不为可推导的修复进度新增 Journal。上述来源判断适用于当前固定布局；后续可变恢复入口须另行满足 checkpoint/日志的权威与保留条件。

### 6.4 本轮实施规则（2026-09-23，已获执行授权）

前两轮已说明固定布局、双副本、Create/Open 分离、异步修复归属及代价。用户再次明确要求执行，本轮采用以下具体化；尚未实现的 checkpoint/普通对象/节点接入不随之扩张。

#### 格式 v1 与位置

保留此前讨论的两个 64 KiB 槽位，偏移 0 和 1 MiB。固定字段合计 112 字节，槽位剩余部分为零填充；64 KiB 是格式容量及所支持 IO 长度的工程取舍，不是字段需要这么大、性能最优或硬件原子写证明。每次读写整个槽位；F01 实际偏移/长度约束必须整除两个位置及槽位长度，内存由 F02 按实际对齐分配。不兼容明确失败，不挪动槽位、不降级。

整数复用 ByteWriter/ByteReader 的大端编码，标识符为原始 16 字节，不直接保存 struct。CRC32C 复用 common/byte_codec，覆盖槽位前 65532 字节（含 magic、版本、布局和零填充），最后四字节存大端 CRC。

| 偏移 / 长度 | 字段 |
| --- | --- |
| 0 / 8 | ASCII `BUSTBOOT` |
| 8 / 4 | 版本 1 |
| 12 / 4 | 固定字段长度 112 |
| 16 / 4 | 特性位 0；本版不接受未知特性 |
| 20 / 4 | 保留字段 0 |
| 24 / 16 | 存储实例身份（不可全零，由正式调用者显式提供） |
| 40 / 16 | 设备身份（不可全零，由正式调用者显式提供） |
| 56 / 8 | 格式化时设备容量；本版必须与 F01 报告一致，不隐式扩容 |
| 64 / 16 | 元数据区起点、长度，各 8 字节 |
| 80 / 16 | Journal 区起点、长度，各 8 字节 |
| 96 / 16 | 普通数据区起点、长度，各 8 字节 |
| 112..65531 | 零填充，非零视为未支持内容，不擅自抹除 |
| 65532 / 4 | CRC32C |

三个区域必须非空、满足设备偏移/长度约束、无地址溢出、不超过容量/系统地址界限、互不重叠且不覆盖两个引导槽位；不要求填满整盘。区域描述是 F04 的输入，本轮不实现区域扩展或页分配。预留槽位不能被普通数据分配使用。

#### 接口与错误

新增 BootstrapStore，绑定一个已有 IOExecutor；新增 IOExecutor::DeviceInfo 供正式引导消费者核对容量和对齐，避免由调用者传另一设备的 Info。F03 内部用副本索引解析受限槽位，再调用已有范围批次；不暴露任意设备地址写 API，不建立与 F02 并列的 IO 实现。

- Create(layout)：验证后读取两个槽位，仅两个全零才写入；两个写入及所需 Flush 均成功才返回。失败可能已留下非零内容，不自动清空/回滚。调用者持有专用设备的独占初始化权；两个槽位全零不证明整个设备为空。
- Open(expected_identity)：检查两个槽位，返回布局及冗余是否不足。先识别全零/CRC 损坏，再检查完整记录的格式和语义。校验有效但未知 magic/版本/特性、非法布局、身份冲突或两份有效内容不一致均拒绝；仅全零或 CRC 损坏的槽位可作为后台修复目标。实际读 IO 失败直接上报，不将未知读取结果当成可覆盖槽位。
- Create 不自动 Open；一次实例只允许一次成功 Open。已 Open 后禁止 Create/换布局/再次 Open，以对象寿命固定任务所属身份；失败的 Open 可在无任务时重新尝试。旧实例 Close 完成后才允许对同设备重建或开启替代实例。
- Status() 返回对上层有意义的冗余条件、修复阶段、尝试次数和最后错误；不暴露内部队列/计数以方便测试。格式/准入错误有结构化原因，底层 IO 错误保持原异常及范围/进度信息。
- Create/Open/StartRepair/Close 由生命周期所有者串行调用；Status 可并发读取，修复与普通范围 IO 可并行。多个引导实例或其他设备写入者的独占权由上层管理，不通过 F03 偷加全节点锁。

#### 后台驱动和资源

StartRepair(options) 是显式的非阻塞启动入口，Open 本身始终只读。重复启动合并；每个打开实例最多启动一个协调线程和一个修复意图，同一线程完成其全部重试后退出，Close 汇合。没有独立设备线程池，没有每个 IO/重试一个线程；协调线程可以等待 F02 结果，F02 的 IO worker 不等待自己队列的后续工作。无任务的正常实例不创建线程。

options 显式提供尝试次数上限、重试间隔、单阶段准入等待上限，均须为正；不增加隐藏默认值或测试配置。后台一次最多一个 F02 批次，最多两个槽位成员。额度不足通过可被 Close 唤醒的定时等待重试接纳；每阶段达到准入等待上限后算一次失败，再按总次数决定重试/终止。没有忙轮询或无限 pending，不能假称目前存在节点总预算/后台优先级。任务图像与临时编码有固定上限，计量与 F02 工作缓冲分别说明；后续 F31 接入时按实际所有权统一记账。

修复流程：重新读取并确认源/目标仍符合当前打开实例的固定布局；两份已一致且没有本任务尚未确认持久化的写入时可正常结束，否则只写原来确定的目标 → Flush → 读回两份 → 检查都与固定源一致 → 成功后清除冗余不足。**若前次写入或 Flush 失败，即使随后读到相同字节，也必须重新写目标并成功 Flush、读回，不能把可读当作 durable。**修复前检查及写后读回都必须验证固定源；任何阶段发现有效冲突、未知格式、源丢失或布局不匹配都直接失败，不进入普通目标校验失败的重试。IO/校验失败和资源暂缺可按上限重试；最后错误保留。正常已接纳 IO 不被强行取消，设备永久不返回时不承诺有限时间关闭。

Close 停新修复/重试并唤醒等待：未提交意图放弃，已提交批次先排空；不要求再发读回或完成整个重试周期。协调线程结束后才能销毁本实例，之后上层再停 F02/关 F01。没有跨实例回调，迟到完成由汇合边界阻断，不能仅丢弃回调却留下写入。修复进度不另写 Journal，重启后重新 Open 推导。

本轮只交付独立 F03 实际 IO 路径和后台驱动。F04/F05/F06、完整 F31/F33/F34、Raft/SQL 接入仍未完成；Open 成功不宣称节点恢复完成。
