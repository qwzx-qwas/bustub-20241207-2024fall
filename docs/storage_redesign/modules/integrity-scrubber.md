## 2. 已讨论的职责与边界

1. 校验检测与修复能力分开描述。
2. 扫描受后台预算约束，不能破坏正在使用的数据。
3. 恢复来源不足时报告损坏，不把 checksum 等同于可修复性。

## 11. 原候选讨论（2026-10-08，已由共同协议落实）

目的：让冷数据的损坏也能被有预算的后台检查发现，不必等业务恰好读取。检测和修复分别授权，不把发现 checksum 错误等同于已经找到可修复副本。

建议顺序：

1. **列清楚已有依据。** B 持久页/Journal 已有恢复校验，Raft entry 有 CRC、片段和日志顺序检查，快照有完整性校验。普通 Data 的通用映射目前没有统一正文 checksum，单纯成功读出不能证明没有静默位翻转。先确定本轮是否补充它的写入/读取校验、校验粒度和旧格式兼容；没有依据的对象必须标成未覆盖，不能重新计算一次 CRC 就宣布正确。
2. **复用原所有者。** F30 安排扫描，B/Journal/LogStore/SnapshotStore 的格式检查由原模块提供，F21 继续解析来源；不另存一份对象目录、checksum 权威表、线程池或回收器。需要抽取生产校验入口时，与现有恢复/读取共用实现。
3. **固定要检查的内容。** 一小批取得明确版本及实际读取保护，按对象/记录边界检查，再释放。与更新、Deferred 落位及 GC 并发时，不能混用两个版本，也不能只读缓存就声称检查了设备正文。固定范围和读取位置要分别说明。
4. **有界后台推进。** 沿 F22/F31/F02，限定一轮读取字节、记录数与在途资源；资源暂满保留进度、让出执行，真实 IO/校验错误上报 F33。扫描不得消耗已提交任务的完成保留。最初的游标是否只保留内存、重启重扫可否接受，需在本轮协议明确。
5. **验证真实风险。** 已知非空正文，损坏其中一个实际持久位置；验证既有校验可检测、报告能定位，不能让自动修复掩盖失败。再验证健康扫描、并发更新/回收和低预算退让。复用已有格式损坏和 IO 错误场景，不复制 CRC 算法/位图单元测试。

以上是授权前的候选说明。当前以 [共同协议](../s12_integrity_protocol.md) 覆盖原待定项，按先逻辑审查、再测试的顺序完成；实际覆盖和局限见 [执行记录](../s12_integrity_execution_20261008.md)。
