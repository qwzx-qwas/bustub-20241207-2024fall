### 6.1 第二轮审查补充

redo 是用于重做的恢复信息，Deferred 是先持久化恢复信息、再落位数据的正常写入策略。运行中 F27 消费已提交待落位任务，重启时 F11 重建这些任务；B 页的 redo 消费者是 B/F09，不交给本模块重写所有元数据页。

任务必须标明目标身份/分配代次、保护范围、版本和 PayloadRef。若落位重写整个物理单元，正文或其他保留恢复来源须覆盖全部可能受损的有效字节；仅保存更新的几个字节不能修复邻近旧内容。具体方案与 F18 冻结，未证明时不能启用原地 Deferred。

最终数据 durable → 完成状态 durable → 切换/解除旧来源保留；实际释放再等待读者/IO。F10 暂停 B 新修改时须保留必要完成通路或不等待这些落位完成，避免 checkpoint 与 Deferred 互等。

### 6.2 跨段正文与推进回收

一个待落位 PayloadRef 可以跨多个 Journal 段；执行/读取需按 F07 已验证的完整内容处理，不能把 FIRST 或 LAST 单独当完整任务。跨段保留由 F07/F14 归并，不复制第二份正文来简化寻址。

最终数据 durable、完成状态 durable 且来源切换后，才能解除正文的持久保留；已取得旧来源的读者/IO 继续阻止复用，F06/F22 不能仅因落位写完就释放。优先推进长期阻塞 Journal 前缀回收的任务，但遵守同范围依赖和 F31 后台预算。

完成事务和错误收尾需要预留 Journal/内存/IO 资源，不允许普通写入耗尽后令落位任务无法记录完成。空间不足不能授权清除仍唯一保存已提交内容的日志；与 F10 暂停准入的交接沿用 §6.1。
