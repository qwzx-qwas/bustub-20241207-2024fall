## 2. 已讨论的职责与边界

1. 已提交命令按序 Apply，完整发布后返回成功。
2. 线性一致读取得安全 ReadIndex 后等待已发布应用位置。
3. 多提案需处理旧值前置条件、冲突和请求去重，不能只删除单提案限制。
4. 两项改进统一归本模块：全局有界多提案流水线，以及单客户端多请求跟踪、多结果保留和安全重试/回收。前者细化原有目标，后者补足原方案仅笼统提及的去重能力；具体协议、参数和算法仍待讨论。

### 2.1 唯一归属与协作边界

| 改进 | 负责的现有组件 | 阶段与方案归属 |
| --- | --- | --- |
| Leader 全局从一个未完成写提案扩展到多个有界提案 | DistributedNode 请求跟踪、SqlCommandPreparer 的业务依赖、RaftNode 的提案/复制/提交推进，以及状态机按序应用与发布 | F35 / S13；包含旧值冲突、切主和未知结果的处理 |

本文件是上述两项会话/提案改进的详细方案唯一入口，不为它们新增模块、独立服务或 S14。独立的 A 记录与表页空间管理归 F36，职责不同。F35 是改造工作的归属，不表示把这些职责实现为一个新的大类；代码继续按请求入口、会话表、业务准备与 Raft 协议分工。

- F23 LogStore（S8）提供日志持久化及有效范围语义；是否接受下一条业务提案、如何判断重复请求归 F35。
- F25 SnapshotStore（S8/S11）保存、发布和传输快照；F28 业务 Checkpoint（S11）捕获与业务状态一致的会话恢复状态。请求窗口的含义及可回收边界由 F35 定义。S13 扩展会话格式时要同步现有重放、快照与 checkpoint 的兼容和恢复验证，不新建第二条恢复链。
- F31（含 S13）提供共用资源预算机制；F35 使用它限制提案、等待对象和结果窗口，仍由 F35 判断哪些结果允许回收。
- F19 CommitPipeline 与 F17 Sequencer 管 FS 本地存储事务和对象范围依赖；F35 管业务请求、SQL 依赖和 Raft 推进。F26 的页 IO 并发也不替代 F35 的业务并发。这些组件不能互相承担对方层次的提交、排序或去重决策。

前置阶段按当时明确的存储和恢复契约实现，并审查是否无意写死“只能一个结果/提案”；不因此提前实现未讨论的客户端协议或推测接口。S13 所需的跨模块兼容调整由 F35 牵头，记录在受影响模块中，沿用同一实现。

补充归属：SQL 只读候选计划复用与 event-loop/worker 调度都在本模块；A 的 tuple/页物理整理属于 [F36](table-space-management.md)，不新增第二套会话、SQL 或共识服务。

## 4. 开源参考与本项目落点

- [SQLite 查询计划](https://www.sqlite.org/eqp.html)：UPDATE/DELETE 等语句同样可选择索引搜索或扫描，解决少量目标行仍扫描全表的问题。内化为现有 Optimizer/只读 Executor 接入 SqlCommandPreparer，不引入 SQLite 或第二套查询引擎。核对：2026-09-21。
- [etcd/raft 异步存储接口](https://github.com/etcd-io/raft/blob/main/doc.go)：用本地 append/apply 消息与完成响应分离协议和耗时执行，同一目的路径可靠有序。内化为 F35 阶段队列和完成依赖；有界 pending、完成预留及公平调度由本项目补齐，示例通道不能直接当作本项目的非阻塞实现。核对：2026-09-21。

- [etcd/raft](https://github.com/etcd-io/raft/blob/main/README.md)：为允许协议与 IO 协作推进，分离协议决策和外部执行，并保留必要依赖。 内化为协议处理与异步执行分离；保留持久化、复制和 Apply 依赖。 来源核对日期：2026-09-20。
- [Apache Ratis OrderedAsync](https://github.com/apache/ratis/blob/master/ratis-client/src/main/java/org/apache/ratis/client/impl/OrderedAsync.java)：用滑动窗口跟踪多个请求，用信号量限制未完成请求数量；[RetryCacheImpl](https://github.com/apache/ratis/blob/master/ratis-server/src/main/java/org/apache/ratis/server/impl/RetryCacheImpl.java) 按调用身份保存正在等待或已完成的结果。内化为客户端有界并发、服务端重复请求共享完成结果的候选设计。该缓存有过期策略，不能把它单独当作跨重启、无限时间的去重保证。来源核对日期：2026-09-20。
- [RAMCloud / RIFL 论文](https://pages.cs.wisc.edu/~ra/Classes/739-sp20/papers/rifl.pdf) 第 3–5 节：完成记录与业务修改原子持久化；客户端上报最早尚未收到结果的请求号，使服务端回收已经确认的前缀；租约处理客户端消失后的清理。内化为 SessionTable 的多结果保留、确认边界与恢复一致性候选约束；不自动引入 RAMCloud 的独立租约服务或多对象事务协议。来源核对日期：2026-09-20。
- [etcd API guarantees](https://etcd.io/docs/v3.6/learning/api_guarantees/)：明确超时和网络中断时客户端可能不知道操作是否完成。内化为本项目未知结果、原身份重试和不能因等待超时清除提案身份的边界；Raft 流水线本身不替代业务去重。来源核对日期：2026-09-20。

### 5.1 两种现有限制：代码核对事实

| 限制 | 当前代码 | 影响 |
| --- | --- | --- |
| 每客户端只保存最后一次已提交请求和结果；下一请求号必须连续加一 | [SessionTable::Classify / RecordCommitted](../../../src/distributed/session_table.cpp) | 同一客户端应等待未知请求解决后再前进；后继请求提交后，更早请求不能再取回原结果 |
| 当前 Leader 同时只能推进一个尚未提交、应用并发布完成的新业务写提案 | [HandleWrite](../../../src/distributed/node.cpp) 的单个 `active_write_`；[RaftNode::Propose](../../../src/raft/raft_node.cpp) 的稳定边界检查 | 不同客户端的新写也需要排队；增加客户端数量不会自动得到多个在途提案 |

它们是本项目 V1 的约束，不是 Raft 协议必须一次只能处理一个客户端请求。`HandleWrite` 的条件变量等待会释放互斥锁；这里限制的是新写提案的推进，不是声称所有连接、心跳或请求都无法运行。客户端等待超时也不等于该提案取消。

单提案限制还保护业务准备阶段：[SqlCommandPreparer](../../../src/distributed/sql_command_preparer.cpp) 会先读取旧行，生成包含旧版本、旧内容和新内容的修改；[BusTubStateMachine::ApplyUpdate / ApplyDelete](../../../src/distributed/bustub_state_machine.cpp) 在应用时核对旧值。两条递增请求若同时从值 10 准备，都会生成“10 改为 11”；第二条在第一条应用后会触发旧值不符。不能通过删去检查使它们进入日志。

### 5.2 会话多请求窗口（候选，未批准实现）

- 在现有 SessionTable 上演进，按会话身份和请求号保存一段结果；请求号仍可递增。请求正文指纹继续绑定身份，同号不同正文必须拒绝。
- 正在处理的相同请求连接到同一个完成结果；已经提交的相同请求返回保留的业务结果。内存中的等待对象与需要恢复的完成记录分别管理。
- 保留结果与执行顺序分别设计：缓存多个结果不自动允许同一客户端乱序执行。可以继续按会话请求号排序，同时允许多个请求在途；乱序到达、缺号、窗口满和切主后的处理需明确。
- 客户端确认可回收的连续前缀。例如已收到 42、43 的结果，但 41 仍未知时，不得确认到 43。回收结果后仍保留拒绝旧请求的边界，不能将迟到重试重新作为新操作执行。
- 结果和业务修改必须具有同一个逻辑恢复边界，纳入现有 Raft 日志重放及快照恢复链；不另建一套独立提交的去重日志。只更新内存缓存不能满足切主和重启后的去重。
- 限制每客户端及全局的记录数量、字节数和在途资源。未确认记录不能只因窗口满而直接遗忘。客户端永久消失后的会话关闭、失效与旧身份拒绝，需要确定复制和恢复规则，不能各节点凭本地 TTL 独立删除后接受旧请求。
- 客户端重启后如何保留请求身份、未知操作和确认承诺，以及协议/快照格式兼容方式，均需后续讨论。

### 5.3 服务端流水线与实施关系（方向已收录，接口待冻结）

1. 全局单提案和单客户端单请求分别演进。可以先保持每客户端一条未解决请求，允许多个客户端的安全提案在途；之后再扩展单客户端窗口。
2. 将单个 `active_write_` 演进为有界的请求跟踪集合，关联请求身份、提案位置/任期和完成结果；数量和字节预算共同限制积压。切主、日志覆盖和未知结果不能只凭本地等待对象判定。
3. 业务准备必须先建立可靠的依赖判断。已证明无冲突的操作可重叠；相同行、范围谓词、唯一索引和 DDL 等依赖需要排序，无法证明独立的请求保守等待，再基于新的有效状态准备。只比较当前命中的行不足以处理范围内新插入等影响。
4. 在持久化、复制和应用的必要依赖内进行批量处理与阶段重叠；已提交命令仍按序 Apply，完整业务发布后再回复成功。按序应用不要求等待前一请求的客户端收到响应才推进下一条。
5. 参考 etcd/raft 的批量日志、复制流控和协议/IO 分工；初期不把其所有并行落盘优化同时引入，也不把本项目业务冲突判断交给 Raft 库。

这部分属于 F35 / S13，接口与验收仍待冻结。本轮共同旧系统观测已归档，下一步是 S0，不能因发现瓶颈跳过既定阶段。FS 接入、只读访问路径和 Raft 流水线变化分别记录版本边界，不能将其收益全部归因于 FS。

基线共同负载继续使用多个客户端、每客户端一条未解决请求，前后语义相同。单客户端多个在途请求、结果乱序到达、确认回收及其故障恢复属于新增能力；旧版本可标注不支持，测试适配器不能将一个客户端拆成多个身份来伪造等价支持。具体测试仍待审查。

## 6. 讨论后的方案与待冻结边界

以下为本轮收录的设计方向和约束；具体字段、数值、接口及当轮验收未确定前，不能把它们补成默认实现。

### 6.1 已核对的当前路径

- [SqlCommandPreparer::Prepare](../../../src/distributed/sql_command_preparer.cpp) 只经过 Binder/Planner，UPDATE/DELETE 随后手动遍历 TableHeap；它接受的过滤计划形状不能直接接上任意优化计划。
- [ExecuteReadSql](../../../src/distributed/raft_state_machine.cpp) 已调用 Optimizer、`BeginReadAt(published_applied_index)` 与 ExecutionEngine，并持生命周期/可见性保护。复用这些能力，不拼接一条新 SELECT 再解析。
- [索引规则](../../../src/optimizer/seqscan_as_indexscan.cpp) 已处理列与常量等值、左右互换和同列 OR，尚不从 AND 提取等值条件；当前只检查索引首列，复用时须核对单列主键等适用约束、NULL/转换及索引类型。
- [IndexScanExecutor](../../../src/execution/index_scan_executor.cpp) 点查核对索引键并处理可见性，不能假定它已检查任意剩余条件。[FilterExecutor](../../../src/execution/filter_executor.cpp) 可用于完整谓词检查。
- [ExecutionEngine](../../../src/include/execution/execution_engine.h) 的结果收集不保留独立 RID/TupleMeta；Executor 的 `Next(tuple, rid)` 已提供 RID。新增薄收集层即可，不另建扫描算法。
- [RaftNode::Propose](../../../src/raft/raft_node.cpp) 当前同步调用业务校验和日志持久化，状态机的进度/读取方法也可能取得生命周期锁。因此只在 DistributedNode 外包一层事件队列仍会阻塞，须逐个核对协议回调中的耗时调用及其依赖。

### 6.2 只读准备链

```text
Binder / Planner 生成原 UPDATE 或 DELETE
 → 提取找到目标行的只读子计划
 → 复用 Optimizer 与扫描/索引/过滤 Executor
 → 在同一受保护视图中取得完整旧行、RID、旧版本
 → 计算新行并生成现有逻辑命令
 → 按业务依赖检查后才进入 Raft 提案
```

只执行读取子计划，不能在 Prepare 调用普通 Update/DeleteExecutor 修改业务数据。保留主键、旧版本、旧内容、新内容的复制格式、既有约束错误和规范化命令顺序；物理 RID 不进入跨节点复制命令。计划范围先限定到现有单表确定性语义；不能证明适用的条件保留扫描。

扩展主键等值 AND 其他条件时，显式保留完整过滤。复用的是执行能力，不能混淆优化前后的输出 schema、列编号和完整业务行。tuple 与元数据读取处于同一可见边界；只调用 BeginReadAt 并不自动保留旧行，当前版本依赖可见性锁。将来若允许读取期间 Apply，必须先实现历史版本保护或其他已证明的读取视图。

本子项可在单提案语义下独立验收，仍属于 S13。它减少查找工作，不自动授权并发 Prepare；新请求读取过时旧值时应在提交前按已定冲突策略等待/重新准备，不能把可能失败的旧值验证直接推到已提交后处理。

### 6.3 事件推进与阶段执行

F35 event loop 负责协议决策和请求状态；Prepare、日志持久化、Apply、Snapshot 经各自有界工作队列执行。节点 mutex 不跨耗时 SQL/IO 持有；移交时固定必要输入、身份、视图与资源所有权。仅删除外层锁会破坏生命周期/可见性，必须保留对应保护。

- 投递采用非阻塞尝试；队满时在已接受请求上下文中保留 pending，继续处理协议和完成事件。入口可按正式契约有界等待或拒绝尚未接受的新请求，不能把已接受/可能提交的请求伪装成普通拒绝。
- pending、已排队、执行中及未消费完成结果共同受数量/字节上限约束；队列传递引用，正文不重复持有两份。F31 提供预算，F35 决定业务准入和阶段依赖。
- 接受工作时保证最终完成结果有容量。候选实现为任务自带结果槽及预留完成额度；结果可靠保存，唤醒通知可以合并。具体结构/额度待冻结，不以队满丢事件，也不让 worker 和 event loop 相互等待队列。
- 每轮处理数量/时间有界，协议计时、网络、完成和请求公平推进，不能无限清空一个队列饿死心跳。具体调度比例待讨论。
- F35 接收日志批次持久化、业务 Apply 发布等阶段事件；具体页 IO 完成由 F02/F26 处理，F33 汇总服务条件，不建立逐 IO 全局审批链。
- 协议循环使用完成事件发布的进度/结果视图，不同步调用可能被 SQL/快照持有生命周期锁的状态机查询。同步业务校验和落盘改为有完成依赖的阶段动作；不能一边声称协议异步，一边在 Propose/收包/计时回调里继续直接等待磁盘或数据库。

### 6.4 顺序、失效与退出

Prepare 只有在视图和业务依赖允许时并行；日志/HardState 遵守持久化与消息依赖；初期单执行角色按序 Apply；Snapshot 固定一致边界后开展耗时工作。阶段间可重叠不等于同阶段都可乱序。

任务和完成关联操作身份、对象/状态机代次及必要任期。旧完成不能覆盖新任务；也不能仅因任期改变丢弃已提交 Apply 的完成或已发生的持久化事实。过期结果仍需释放资源并按任务类型归并。关闭先限制入口，再排空或按恢复协议保留已接受工作；完成通道、错误和关闭资源要保留前进空间。不能要求仅内存 completion 跨进程崩溃保存，重启仍依靠正式持久状态恢复。

客户端成功仍要求多数派提交、按序 Apply、完整发布；线性一致读保留安全 ReadIndex 与已发布位置等待。旧请求未知时沿用原身份处理，不能因请求等待超时取消已提交工作。

实时顺序要求：X 成功返回之后才调用 Y，则合法线性化顺序必须 X 在 Y 前（`<H ⊆ <S`）。流水线可重叠并发请求，不得把回调顺序当作业务顺序。读达到 ReadIndex 下界后仍须固定合法发布视图；当前 ExecuteReadSql 只接受等于当前 published index 的时间戳，不能把较旧 ReadIndex 直接当成任意历史视图。持续写入期间如何等待/固定当前视图、处理角色变化，在本模块冻结，不能仅检查一个进度数字就宣称线性一致。
