## 2. 已讨论的职责与边界

1. 已提交命令按序 Apply，完整发布后返回成功。
2. 线性一致读取得安全 ReadIndex 后等待已发布应用位置。
3. 多提案需处理旧值前置条件、冲突和请求去重，不能只删除单提案限制。
4. 两项改进统一归本模块：全局有界多提案流水线，以及单客户端多请求跟踪、多结果保留和安全重试/回收。前者细化原有目标，后者补足原方案仅笼统提及的去重能力；具体协议、参数和算法仍待讨论。

### 2.1 唯一归属与协作边界

| 改进 | 负责的现有组件 | 阶段与方案归属 |
| --- | --- | --- |
| Leader 全局从一个未完成写提案扩展到多个有界提案 | DistributedNode 请求跟踪、SqlCommandPreparer 的业务依赖、RaftNode 的提案/复制/提交推进，以及状态机按序应用与发布 | F35 / S13；包含旧值冲突、切主和未知结果的处理 |
| 单客户端从最后一个结果扩展到有界请求/结果窗口 | 客户端协议及请求管理、SessionTable、业务状态机中的去重及完成结果恢复 | F35 / S13；包含请求身份、会话顺序、确认回收、会话失效与兼容规则 |

本文件是两项改进的详细方案唯一入口，不增加 F36、独立服务或 S14。F35 是改造工作的归属，不表示把这些职责实现为一个新的大类；代码继续按请求入口、会话表、业务准备与 Raft 协议分工。

- F23 LogStore（S8）提供日志持久化及有效范围语义；是否接受下一条业务提案、如何判断重复请求归 F35。
- F25 SnapshotStore（S8/S11）保存、发布和传输快照；F28 业务 Checkpoint（S11）捕获与业务状态一致的会话恢复状态。请求窗口的含义及可回收边界由 F35 定义。S13 扩展会话格式时要同步现有重放、快照与 checkpoint 的兼容和恢复验证，不新建第二条恢复链。
- F31（含 S13）提供共用资源预算机制；F35 使用它限制提案、等待对象和结果窗口，仍由 F35 判断哪些结果允许回收。
- F19 CommitPipeline 与 F17 Sequencer 管 FS 本地存储事务和对象范围依赖；F35 管业务请求、SQL 依赖和 Raft 推进。F26 的页 IO 并发也不替代 F35 的业务并发。这些组件不能互相承担对方层次的提交、排序或去重决策。

前置阶段按当时明确的存储和恢复契约实现，并审查是否无意写死“只能一个结果/提案”；不因此提前实现未讨论的客户端协议或推测接口。S13 所需的跨模块兼容调整由 F35 牵头，记录在受影响模块中，沿用同一实现。

## 4. 开源参考与本项目落点

- [etcd/raft](https://github.com/etcd-io/raft/blob/main/README.md)：为允许协议与 IO 协作推进，分离协议决策和外部执行，并保留必要依赖。 内化为协议处理与异步执行分离；保留持久化、复制和 Apply 依赖。 来源核对日期：2026-09-20。
- [Apache Ratis OrderedAsync](https://github.com/apache/ratis/blob/master/ratis-client/src/main/java/org/apache/ratis/client/impl/OrderedAsync.java)：用滑动窗口跟踪多个请求，用信号量限制未完成请求数量；[RetryCacheImpl](https://github.com/apache/ratis/blob/master/ratis-server/src/main/java/org/apache/ratis/server/impl/RetryCacheImpl.java) 按调用身份保存正在等待或已完成的结果。内化为客户端有界并发、服务端重复请求共享完成结果的候选设计。该缓存有过期策略，不能把它单独当作跨重启、无限时间的去重保证。来源核对日期：2026-09-20。
- [RAMCloud / RIFL 论文](https://pages.cs.wisc.edu/~ra/Classes/739-sp20/papers/rifl.pdf) 第 3–5 节：完成记录与业务修改原子持久化；客户端上报最早尚未收到结果的请求号，使服务端回收已经确认的前缀；租约处理客户端消失后的清理。内化为 SessionTable 的多结果保留、确认边界与恢复一致性候选约束；不自动引入 RAMCloud 的独立租约服务或多对象事务协议。来源核对日期：2026-09-20。
- [etcd API guarantees](https://etcd.io/docs/v3.6/learning/api_guarantees/)：明确超时和网络中断时客户端可能不知道操作是否完成。内化为本项目未知结果、原身份重试和不能因等待超时清除提案身份的边界；Raft 流水线本身不替代业务去重。来源核对日期：2026-09-20。

项目代码的直接复制、依赖引入、版本或许可处理若在后续需要，应在讨论后的方案中明确；这里记录的是机制参考。

### 5.1 两种现有限制：代码核对事实

| 限制 | 当前代码 | 影响 |
| --- | --- | --- |
| 每客户端只保存最后一次已提交请求和结果；下一请求号必须连续加一 | [SessionTable::Classify / RecordCommitted](../../../src/distributed/session_table.cpp) | 同一客户端应等待未知请求解决后再前进；后继请求提交后，更早请求不能再取回原结果 |
| 当前 Leader 同时只能推进一个尚未提交、应用并发布完成的新业务写提案 | [HandleWrite](../../../src/distributed/node.cpp) 的单个 `active_write_`；[RaftNode::Propose](../../../src/raft/raft_node.cpp) 的稳定边界检查 | 不同客户端的新写也需要排队；增加客户端数量不会自动得到多个在途提案 |

它们是本项目 V1 的约束，不是 Raft 协议必须一次只能处理一个客户端请求。`HandleWrite` 的条件变量等待会释放互斥锁；这里限制的是新写提案的推进，不是声称所有连接、心跳或请求都无法运行。客户端等待超时也不等于该提案取消。

单提案限制还保护业务准备阶段：[SqlCommandPreparer](../../../src/distributed/sql_command_preparer.cpp) 会先读取旧行，生成包含旧版本、旧内容和新内容的修改；[BusTubStateMachine::ApplyUpdate / ApplyDelete](../../../src/distributed/bustub_state_machine.cpp) 在应用时核对旧值。两条递增请求若同时从值 10 准备，都会生成“10 改为 11”；第二条在第一条应用后会触发旧值不符。不能通过删去检查使它们进入日志。

### 5.2 会话多请求窗口（候选，未批准实现）

- 在现有 SessionTable 上演进，按会话身份和请求号保存一段结果；请求号仍可递增。请求正文指纹继续绑定身份，同号不同正文必须拒绝。
- 正在处理的相同请求连接到同一个完成结果；已经提交的相同请求返回保留的业务结果。内存中的等待对象与需要恢复的完成记录分别管理。
- 保留结果与执行顺序分别设计：缓存多个结果不自动允许同一客户端乱序执行。可以继续按会话请求号排序，同时允许多个请求在途；乱序到达、缺号、窗口满和切主后的处理需明确。
- 客户端确认可回收的连续前缀。例如已收到 42、43 的结果，但 41 仍未知时，不得确认到 43。回收结果后仍保留拒绝旧请求的边界，不能将迟到重试重新作为新操作执行。
- 结果和业务修改必须具有同一个逻辑恢复边界，纳入现有 Raft 日志重放及快照恢复链；不另建一套独立提交的去重日志。只更新内存缓存不能满足切主和重启后的去重。
- 限制每客户端及全局的记录数量、字节数和在途资源。未确认记录不能只因窗口满而直接遗忘。客户端永久消失后的会话关闭、失效与旧身份拒绝，需要确定复制和恢复规则，不能各节点凭本地 TTL 独立删除后接受旧请求。
- 客户端重启后如何保留请求身份、未知操作和确认承诺，以及协议/快照格式兼容方式，均需后续讨论。

### 5.3 服务端流水线与实施关系（候选，未调整阶段）

1. 全局单提案和单客户端单请求分别演进。可以先保持每客户端一条未解决请求，允许多个客户端的安全提案在途；之后再扩展单客户端窗口。
2. 将单个 `active_write_` 演进为有界的请求跟踪集合，关联请求身份、提案位置/任期和完成结果；数量和字节预算共同限制积压。切主、日志覆盖和未知结果不能只凭本地等待对象判定。
3. 业务准备必须先建立可靠的依赖判断。已证明无冲突的操作可重叠；相同行、范围谓词、唯一索引和 DDL 等依赖需要排序，无法证明独立的请求保守等待，再基于新的有效状态准备。只比较当前命中的行不足以处理范围内新插入等影响。
4. 在持久化、复制和应用的必要依赖内进行批量处理与阶段重叠；已提交命令仍按序 Apply，完整业务发布后再回复成功。按序应用不要求等待前一请求的客户端收到响应才推进下一条。
5. 参考 etcd/raft 的批量日志、复制流控和协议/IO 分工；初期不把其所有并行落盘优化同时引入，也不把本项目业务冲突判断交给 Raft 库。

这部分属于 F35 / S13 的待讨论方案，不是当前测试设计阶段允许开始的生产改造。先审查测试并取得旧系统有效基线；FS 接入与 Raft 流水线变化要记录版本边界，不能将流水线收益全部归因于 FS。

基线共同负载继续使用多个客户端、每客户端一条未解决请求，前后语义相同。单客户端多个在途请求、结果乱序到达、确认回收及其故障恢复属于新增能力；旧版本可标注不支持，测试适配器不能将一个客户端拆成多个身份来伪造等价支持。具体测试仍待审查。
