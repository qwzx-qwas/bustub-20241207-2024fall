### 6.1 S0 的工作目标

共同旧系统观测已按约定执行、归档，限制见 [最新报告](../testing_execution_20260921.md)。S0 形成各模块对同一术语、身份和完成结果的一致解释，并实现有实际消费者的最小类型；不实现 F35/F36 或裸设备后端来代替契约工作。

### 6.2 建议讨论顺序与交付物

1. **身份和范围表**：普通/基础/引导对象、逻辑 offset/length、物理 extent、对象/帧代次、ObjectRef/PayloadRef、页号/RID、Raft index/Journal LSN 的职责、所有者及允许比较的范围。extent 单段物理连续，对象可多段；不把数据库空闲页摘要等同 FS bitmap。
2. **完成语义表**：接受/排队、缓冲被可靠接管、IO 完成、本地 durable、本地事务发布、Raft 多数派提交、按序 Apply/完整业务发布。每个结果说明能否释放输入、能否供读者访问、崩溃后承诺和谁确认；不能仅用一个 bool 混称成功。
3. **原子与顺序表**：一个 CommitBatch 的恢复原子性、多个 batch 共享刷盘、同页/范围依赖、Common 正文与元数据发布、Deferred 元数据与正文日志、快照清单和引用切换。物理 IO 合并不扩大业务原子性。
4. **资源与失败表**：借用/移交/保留缓冲的结束点；数量与字节预算；未接受拒绝、已接受后错误/结果未知、取消/超时、部分写入、持久化失败、关闭及重复完成的边界。异步任务不得在成功前丢失完成结果或被提前释放。
5. **回收与兼容表**：逻辑删除、解除持久引用、读者/IO 静默、物理可复用与 discard 分开；A 记录存活性归 F36、页生命周期归 F26、物理范围归 F22/F12。已有 DurableStorage 文件接口与新对象接口的迁移边界、旧格式识别和禁止隐式格式化。
6. **最小验证与实施 prompt**：确定当轮共享类型/接口的实际使用者、必要行为验证和受影响回归；不存在调用方且未冻结的猜测接口不先建。后续模块细节只冻结必要约束，不一次决定所有磁盘格式和阈值。

### 6.6 身份、位置与版本分开

| 概念 | 建议表达的含义 | 防止的问题 |
| --- | --- | --- |
| 对象身份 | 存储实例/命名空间、对象编号、对象生命周期代次 | A/B 或重建工作库的相同 page_id 落到同一旧对象 |
| 逻辑范围 | 对象内字节 offset/length，检查越界与加法溢出 | 把字节偏移当页号、溢出绕过边界 |
| extent | 设备身份、物理起点、长度；分配代次由分配/映射保护表达 | 把旧 IO 写进已复用给别人的空间 |
| 内容版本 | 本次固定读取或发布的对象内容版本 | 同一对象不同更新之间串读或覆盖 |
| ObjectRef | 指向需保留的对象版本/范围，持久保留由 F14 管理 | 只有对象编号，却不知道应读哪版 |
| PayloadRef | Journal 实例/段代次、记录范围及完整性依据 | 日志段复用后引用到另一条正文 |
| 操作身份 | 请求及运行代次，关联完成和资源释放 | 迟到完成误修改新帧/新请求 |

这些是逻辑信息，不要求每个 struct 都重复保存全部字段；可由受保护句柄或所属上下文承载。对象代次、内容版本、帧代次、Journal 段代次和 Raft term 不互相代替。持久身份重启后仍可恢复，运行代次主要隔离本次打开期间的回调。

ObjectRef/PayloadRef 的值本身不自动建立持久引用，也不证明已 durable；建立/解除引用须进入所属事务，运行中另持临时保护。普通调用者不能自行传物理地址覆盖 Superblock/Journal；普通、基础、引导通路统一 IO 表达但保留寻址权限边界。具体 C++ 名称、位宽、序列化格式和校验编码暂不冻结。

### 6.7 完成是几项事实，不是一条通用枚举流水线

| 事实 | 说明 | 确认者 |
| --- | --- | --- |
| Accepted | 系统接受了责任并预留相应资源；尚无落盘承诺 | 准入/接口所有者 |
| BufferReleased | 本次异步操作不再访问调用者缓冲；可以复用或释放该缓冲 | 持有缓冲的执行层 |
| IOCompleted | 指定范围的 IO 已结束，包含真实错误/短 IO 信息 | F01/F02 |
| LocalDurable | 恢复该次本地提交所需的数据、日志和寻址信息达到约定持久化边界 | F07/F19；设备层仅证明其覆盖范围 |
| LocalPublished | 当前进程的读路径已能一致看到新版本及其数据来源 | F20 |
| RaftCommitted / AppliedPublished | 多数派提交，以及按序应用/业务完整发布 | Raft/F35 与业务状态机 |

这些是语义名称，不要求生成六次回调。借用输入可能到 IO 结束才归还；复制到有界自有缓冲可以较早归还；转移所有权则调用者从接受时起不再使用。归还早晚不改变 durable 承诺。只读请求没有提交阶段，拒绝请求也不会经过后续阶段。

本地事务提交成功返回时同时具备 LocalDurable 和 LocalPublished；内部可分别通知。底层“数据 extent 已 durable”不代表对象事务成功，因为对象映射可能还没提交。业务成功仍需 RaftCommitted 和 AppliedPublished；不要求全部 A 脏页在每次业务返回前都成为独立恢复点，现有快照加 Raft 日志恢复承诺继续成立。

设备屏障需说明所属设备/打开实例及覆盖的写入集合或连续边界，不能只返回最大完成序号。多个设备若未来引入，分别满足依赖后才能合成事务完成。F01 的后端选择在 S1 冻结；S0 不把普通 write、O_DIRECT 或对齐当作 durable/原子写保证。

### 6.8 本地事务与顺序契约

```text
Common：新位置正文 durable → 映射/分配/引用批次 durable → 一致发布
Deferred：元数据＋任务＋可恢复正文同批 durable → 一致发布
          → 最终位置 durable → 完成状态 durable → 解除日志保留
混合：Common 数据依赖满足＋Deferred 恢复正文齐备 → 同批提交/发布
```

CommitBatch 表示一次全有或全无的恢复变更范围，Journal LSN 表示日志位置/顺序，不能互相替代含义；表示可以复用，例如以提交记录位置识别批次。多个批次共享一次屏障不合并其原子性，序号递增不代表前面的 IO 已成功。首次阶段可单元数据写入角色，独立规划和数据 IO 仍可并行；同范围、同元数据页及读后写依赖必须保留。

Mixed 请求必须显式加入同一事务才有共同原子性；多个普通写调用不会因碰巧一起刷盘而自动变成事务。所有读固定一致版本和引用；未提交的 COW extent 不可见，已提交 Deferred 以 Journal/受保护缓冲为来源，不能读出最终设备位置的旧内容。

安全前提：覆盖写的恢复内容覆盖可能损坏的有效字节；日志尾部追加保护旧 durable 前缀；元数据 FULL/PATCH 能从有效恢复基础重放。S0 规定这些承诺，具体记录格式、写入粒度和证明在 F06/F07/F08/F18/F27 冻结，不用“已有 redo”跳过它们。

### 6.9 错误、超时与关闭

错误原因和提交结果分开表达：无空间、设备错误、校验失败说明原因；未接受/确认未提交、确认已提交、结果未知说明可以如何重试。建议原则：

1. 接受前拒绝：未转移资源责任，未产生已提交修改；可按上层规则重试。
2. 接受后失败：只有能够证明未提交才可报告“未提交”；超时或同步失败不自动证明磁盘没有内容。
3. 已 durable 后发布失败：不能撤销成普通拒绝并释放其持久内容；限制相关服务，由恢复/发布协议处理。返回结果说明已知进度，不诱导调用者盲重做。
4. 取消等待不等于取消设备操作；缓冲、范围和空间保护到实际 IO 结束或后端确认安全中止才释放。
5. 正常运行时一个操作对外收敛一次最终结果；重复/迟到通知仍需正确结束其资源责任。进程崩溃后靠持久状态恢复，不承诺内存回调跨进程存活。
6. 关闭先停止接纳，再处理已有任务；不能销毁仍被 IO 访问的对象，也不能等待被自己关闭的完成通路。

现有 DurableStorage 采用异常，DiskScheduler 使用 promise<bool>，客户端另有响应状态；S0 不统一替换整个项目的错误体系。后续边界适配只转译能够证明的含义，尤其不能把旧 scheduler 的 true 包装为 durable。FS 本地操作身份不替代业务 client_id/request_id 去重协议。

### 6.10 读取、删除与释放

- 普通对象读取必须区分对象不存在、超出长度、明确的逻辑空洞、IO 短读及损坏。只有对象格式明确承诺空洞为零时才可返回零；设备短读不能伪装为新空页。F26 的新页初始化应显式组织。
- 逻辑删除后当前视图不再寻址该范围；已固定的旧读者和快照仍可保留旧内容。
- 解除持久引用、临时读者/IO 结束、允许物理复用是不同条件；GCService 等待并调度，所有者提供各自依据。
- 物理范围可复用不等于内容已安全擦除，discard 也不作为保密擦除承诺。是否发送 discard 归设备/空间策略。
- 已提交解除引用后若尚未物理回收即崩溃，应可重新发现待回收范围；提交结果未知时不能把范围提前发给另一个对象。

### 6.11 与当前项目的接入次序

1. S0 记录现有契约和最小共享表达，保留 SQL、三节点协议、文件格式与既有公开接口。
2. S1/S2 建立 F01/F02 与基础寻址；此时只有基础/引导通路，普通对象映射到 S6 才接入，不形成 B 自寻址循环。
3. S8 迁移 Raft Store 时保留 Append/Update 返回前 durable 的现有保证；新后端可内部异步，但兼容包装不能提前返回。S13 再引入经过讨论的异步协议推进。
4. S9 迁移业务页，仍按 canonical snapshot＋Raft 日志重建 A；新工作库用独立身份，不能因某些页曾 durable 就直接 Open 为完整业务恢复点。
5. S11 再由 F28 发布可直接恢复的一致业务根。现有 DurableFileSlice 的文件路径引用只在明确迁移边界替换，不能在 S0 静默改变快照协议。

当前 page_id_t/lsn_t 是 int32_t，Raft index 是 uint64_t。建议新 FS 身份和 Journal 位置采用各自强类型并明确容量上限，不直接重定义全局别名，也不把现有 Page::SetLSN 用到 B+Tree 页头。具体位宽及编码由使用者需求冻结。

### 6.13 S0 当轮实施范围（用户授权后落定）

S0 完成标准限定为：共享契约、现有接口兼容表、实际使用的最小字节范围类型、必要测试及审查证据。对象身份的持久编码、BufferReleased 回调结构、Journal/FULL/PATCH 格式等分别属于其消费者阶段，不在 S0 建无调用方的类型或伪执行器；这不表示这些运行能力已经实现。

**共同契约固定**：§6.6 的身份/位置/版本分工，§6.7 的独立完成事实和本地事务成功边界，§6.8 的原子/顺序，§6.9–6.10 的错误/资源/释放约束，§6.11 的分阶段兼容。具体表示尚无消费者时保持语义约定，不冻结磁盘 ABI。

**最小代码**：增加 `StorageByteRange`，位置为 `src/include/storage/byte_range.h`，使用现有文件范围的 `uint64_t` 字节偏移/长度。它仅代表已校验的半开区间 `[offset, offset + size)`，不代表对象身份、持久化、所有权或任何磁盘格式。

| 接口 | 契约及实际用途 |
| --- | --- |
| `Create(offset, size)` | 检查区间终点是否能由 uint64_t 表达，失败返回空 optional；不分配正文、不抛 IO 错误 |
| `Subrange(relative_offset, size)` | 仅在子范围完全属于父区间时返回绝对范围；先用减法检查再计算绝对偏移，防止溢出/逃逸 |
| `Offset()` / `Size()` | 把已验证范围交给现有 DurableFileSlice/ReadFileRange，不增加未使用的 End/比较/序列化接口 |

空范围允许，位于父区间终点的空范围有效，终点外无效；其意义是范围表达，是否接受零长度设备操作仍由未来后端约定。任何非空子范围都不能越过父区间。此处延用当前 uint64_t 文件范围，不修改 page_id_t、lsn_t 或 Raft 类型。

**现有消费者**：`BusTubSnapshotBundleCodec::DecodeFile` 接受 `DurableFileSlice` 后验证整个区间；所有嵌套正文、长度字段、校验范围都通过 `Subrange` 派生。保留公开接口、合法 V1 字节格式、流式读、正文内容及既有 `std::runtime_error` 拒绝路径。这样范围类型有真实生产用途，不只为测试存在。现有 ByteReader 面向已经载入内存的字节，本类型面向文件/未来设备的绝对位置，两者不重复实现解码。

**兼容与排除**：不改变 AppendFile/SyncFile、LogStore/StableStore 的 durable 承诺；不把 DiskScheduler 的 bool 转成新状态；不引入对象格式、后端、FS 服务、线程池、WAL、GC 或测试专用生产分支。合法内存版/流式快照应继续匹配既有独立 golden，并能安装及重放后续命令。

**文件清单**：新增上述头文件和 `test/storage_redesign/storage_range_contract_test.cpp`；在 `src/distributed/raft_state_machine.cpp` 接入；只在测试 CMake 增加用途标签；新增 `test/storage_redesign/README.md` 并同步测试入口、F00 和总方案。测试归档到模块验证目录，不改共同 C/P 测试内容。
