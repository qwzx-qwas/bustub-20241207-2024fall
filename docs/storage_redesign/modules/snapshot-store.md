## 4. 开源参考与本项目落点

- [RocksDB checkpoint](https://rocksdb.org/blog/2015/11/10/use-checkpoints-for-efficient-snapshots.html)：同文件系统共享不可变 SST、另保存清单/必要日志以降低一致快照复制成本。内化为 F28 固定边界、F14 保留版本、F25 引用发布；BusTub 可变页/canonical 格式不能直接硬链接获得相同效果。核对：2026-09-21。

- [Btrfs reflink](https://btrfs.readthedocs.io/en/stable/Glossary.html#term-reflink)：为让多个视图共享数据，使用 extent 引用和修改时 COW。 内化为后续共享 extent 与 COW 视图；不直接复用 Btrfs 文件系统。 来源核对日期：2026-09-20。

项目代码的直接复制、依赖引入、版本或许可处理若在后续需要，应在讨论后的方案中明确；这里记录的是机制参考。

## 6. 讨论后的方案与待冻结边界

以下为本轮收录的设计方向和约束；具体字段、数值、接口及当轮验收未确定前，不能把它们补成默认实现。

### 6.1 已有方向，不新增模块

S8 已定方向是正文直接进入不可变对象，durable/校验完成后发布清单引用，避免临时正文再复制一次；S11 才结合 F28/F14 讨论共享 extent、压缩和增量。原方案已有 Btrfs reflink 参考，本轮 RocksDB checkpoint 是补充依据，不新建快照引擎。

### 6.2 共享前提与阶段边界

F28 固定包含表/索引/Catalog/会话/分配状态/applied index 的一致边界；F14 保留对象版本/映射根和内容引用，后续修改通过 COW 保留旧内容；本模块发布/保留/传输这一恢复起点。对可变 BusTub 页直接硬链接不提供该保证。

当前 canonical 正文是规范化重建格式，不等同物理页布局。页格式适配、索引物理保存或重建、可移植性仍须讨论；压缩能减少容量/传输，不会自动省去 canonical 扫描。增量发送必须验证接收端具有相同基础内容，引用共享也不等于跨节点无需传输。

### 6.3 清理与兼容

F36 清理/复用 A 活动页面前须服从已固定的旧版本引用；快照保留/传输引用解除后才能进入 F22 回收。F35 扩展会话窗口时同步格式和恢复，不重新定义会话语义。共享单位、版本清单、校验、断点/重试与安装原子边界未冻结，沿用既有安全路径直到新链验证。
