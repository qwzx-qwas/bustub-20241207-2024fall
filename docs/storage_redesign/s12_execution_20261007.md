依据：[共同协议及实现 prompt](s12_resource_gc.md)。本轮按先生产逻辑审查、再编写场景、再运行和变异的顺序执行。结果入口见 [压缩证据](../../test-results/storage-s12-resource-gc-20261007/README.md)。不自动实施 S13。

## 1. 实际改动与方案覆盖

| 位置 | 原行为 | 本轮行为及边界 |
| --- | --- | --- |
| `resource_budget.h` | 组件各自限制容量 | 一个 ResourceBudget 成批授予多个 ResourceAccount；普通额度不能占用进展保留。释放保留小额局部缓存，压力时收回闲置额度；不回收其他所有者的活内存 |
| `io_executor.cpp` / `IOBudget` | executor 内部上限 | 原上限继续生效，再检查共享自有内存及普通/进展名额；借用帧只限制保留压力，不重复计算 RAM；结果持有者仍占额度 |
| `object_io.cpp` / 预算预检、`NodeStorage::PageIO` | 按 executor 总容量报告 | 普通对象预检/页 IO 能力扣除进展保留，与实际准入一致；不能给上层一个永远无法满足的批量大小 |
| `metadata_engine.cpp` / `NewImage` | B 仅按活页数限制 | 页附带 ResourceCharge，旧 B 视图仍持有的页继续计账；私有版本复制保留自己的 charge，不能复制旧页的计账对象 |
| `object_transaction.cpp` / `Submit` | 只有在途请求/正文局部上限 | 为拥有的输入、组装和 Deferred 复制上界预留共享额度；借用输入不重复记正文；完成或未接纳时归还 |
| 同文件 / `GarbageLoop` | CommitLoop 周期执行 GC | 新增独立回收执行角色；从原持久退役目录有界读取，每轮一个候选，受阻后游标仍前进；删除原提交角色周期 GC |
| 同文件 / `DeferredLoop` | 原持久任务与重试 | 标记进展工作，解码正文先预留；不足时保留已 durable 任务再试，复用原落位/完成记录/回收路径 |
| `node_storage.cpp` | 独立局部限额 | 可显式组装共享预算，注入 IO、B、对象流水线；State 合并共享压力提示，关闭停止新回收并等待已认领工作 |
| `buffer_pool_manager.cpp`、`lru_k_replacer.cpp` | 驻留命中分别锁替换器两次 | `RecordPinnedAccess` 一次锁记录访问历史，并仅在 pins 0→1 取消可淘汰；访问历史没有采样或跳过 |

用户确认的内存正文不可变路线 B 已写入 F26/S13，旧的“原地原子正文与不可变正文并列待选”已修正；当前没有删掉条目锁、组锁或 PageGuard。GC 的物理存活性仍由 F14 判断，F12 仍是唯一 Data 分配器。

## 2. 先做的逻辑审查

- 寿命：自有 IO 结果、B 旧视图随最后所有者释放；线程完成不读取提交线程 TLS。借用许可沿原回调保留底层对象。未提交失败不会遗留额度；已提交 Deferred 不因压力丢弃。复查修正完成记录 ResourceUnavailable 被当作 fatal 的旧分类；Data 成功后只重试元数据完成，不重新写正文。NewImage 的额度申请与 new 失败共用原活页计数回退路径。
- 锁序：局部账本→节点账本；压力收回先复制弱引用、释放节点锁，再逐个访问账户。不会持节点锁回调组件，额度锁内不等待 IO。没有给热读取新增全局预算锁。
- 推进：普通/进展容量分别限制；永久单批超限报错，暂时不足返回 Full；普通未提交请求共享内存不足时可结束并释放输入。额度不是“所有等待必然消失”的证明，长期读者和过低 B 局部上限仍会阻止推进。
- 回收：每轮只保留候选身份及游标，不跨等待持有旧 B 视图；处理前取新视图，由 F14 重新核对持久引用、读者和分配身份。冲突/Busy 可重试，实际错误进入原错误链。关闭先禁止新轮次，再等待在途角色退出。
- 去重：移除 CommitLoop 原周期 GC；没有另建退休数据库、bitmap、Journal、设备执行器、快照清单或通用队列框架。课程替换器接口仍有生产/既有调用者，不因为新增合并入口就删除。

## 3. 测试全景

新增源码只存在 `F31-F22-resource-gc.tar.gz` 内的 `tests/resource_gc_test.cpp` 和 `tests/deferred_pressure_test.cpp`，不注册常驻 CMake 目标。全部为真实组件 integration，具有 regression 保护价值；不是 SQL/Raft 完整 E2E。

| 名称（S12Resources） | invariant / 防止的具体 bug |
| --- | --- |
| OwnersShareRAMButBorrowingDoesNotChargeItTwice | 两个 executor 共享内存上限；借用不重复算一份；保留结果不能提前退账 |
| IdleCreditsCanMoveToAnotherOwner | 空闲额度可交给其他组件，防止总量有余却因局部囤额一直拒绝 |
| OrdinaryWorkCannotConsumeCompletionSlots | 普通任务不能占掉完成工作预留；跨线程/作用域释放仍使用接纳类别 |
| OldMetadataViewsHoldCreditsUntilReleased | 旧 B 视图的活页仍占内存，不能只计算当前树；退出后可以提交和恢复 |
| PinnedGarbageDoesNotStarveOtherReclaimAndReuse | 旧读者挡住本范围但不挡住其他候选；保护退出前不复用，退出后可真实写入并重开 |

另外新增 `S12Deferred.CompletionWaitsForRAMWithoutDroppingDurableTask`：B 完成记录遇到真实共享内存压力后，任务仍能继续、正文仍可恢复。

再次复审增加 `S12Reclaim.ActiveOperationLimitReturnsBusyAndRecovers`：一个真实回收调用占满 F14 并发名额时，竞争调用得到可重试 Busy，退出后原引用/正文仍可读取和恢复。当前合计七个新增场景，具体见第 12 节。

复用：F27 12 项、F19 10 项、F26 页路径 9 项、现有 LRU-K 1 项。F27 仅通过测试部署设置新增共享额度/进展名额，原请求、故障、恢复、判据不变；特定混合读取场景仍保留原 64u 普通额度，进展余量另加；测试的输入与判据没有复制到新套件。其他归档原样编译。它们分别保护 Deferred 来源/完成/错误、异步提交与关闭、帧 IO/预取/正文一致性及替换规则。

## 4. 逐项：目标 → 输入 → 路径 → Oracle → 失败含义

### T1 共享内存及借用

- 目标：受管真实内存总和不越界；借用不是新分配，保留结果确实占空间。
- 输入：真实文件查询对齐；u 是合法 IO 单位，q=u+内存对齐余量。普通总额为 3q，两个 executor 先持有 1q 和 2q。写入确定的非空非零正文。
- 路径：IOExecutor Prepare/Submit→BlockDevice Direct write/Flush/read；外部许可保留已完成 batch 的缓冲所有者，随后退出。
- Oracle：第四份拥有缓冲被拒绝，但借用同一块已记账内存可以成功；仍持有结果时不能超额，退出后可申请；最终读回等于测试生成的原字节。再次复审增加本次共享拒绝原因：后来成功准入清除全局提示，旧结果仍保存原原因；普通单次四份永久超过其三份总容量时必须报错，同样大小的进展工作在总四份容量内可以实际写完。
- 独立性：额度由显式部署参数和 F02 公共对齐计量契约计算，不读私有计数；正文预期不由 production 解码器生成。q 与契约相关，是必要的准入边界而非 malloc 的实现测试。
- 失败：归属漏记/重复记账、过早退账或错误 IO 正文。不同断言区分相应问题。

### T2 闲置额度转移

- 目标：曾授予但已不用的额度不会永久阻挡其他组件。
- 输入：A 准备一份后退出，B 一次请求占满普通总额的三份；A 保留少量局部额度是正式优化。
- 路径：两个实际 executor 的 Prepare/释放→共享账本收回闲置→B Direct 批量写→读回。
- Oracle：B 被接纳并持久写完，独立生成正文读回一致。没有检查 grant 数值或强制返回每一小份额度。
- 失败：局部囤额不可调节，或资源转移破坏实际缓冲。

### T3 完成预留

- 目标：普通工作不能消耗进展名额，IO 类别随已接受任务保存。
- 输入：总四个 IO/四份缓冲，留一份；普通先占三份，再投递完成工作。离开 ProgressWork 作用域后才执行、释放该 batch，然后重复一次。
- 路径：正式资源类别→IOBudget→工作线程→实际 Flush/完成；读回最终设备字节。
- Oracle：普通第四份 Full、进展 Accepted；返回额度后普通仍不能借走保留。再次复审先让另一个实际 executor 遇到共享 RAM 不足，再验证这里的局部名额 Full 不被误标成共享 RAM 拒绝。不是检查线程局部变量本身，而是检查生产准入结果。
- 失败：保留被普通请求借走、释放时使用错误类别或真实写入出错。完整恢复任务所需的 Journal 上界由原 F07/F27 场景协作验证；本项不声称任何配置都能完成任何大小的 checkpoint。

### T4 旧 B 视图

- 目标：每个仍存在的 B 页像均占预算；旧视图内容保持，释放后可前进。
- 输入：384 KiB 共享额度，更新同一非空元数据值并持有旧视图，直到明确 ResourceUnavailable；不固定“第几个版本必须满”。同时保存每次请求字节作为独立模型。
- 路径：NodeStorage→B 私有页/Journal/Direct；释放视图→再次真实提交→checkpoint→Close/Open。
- Oracle：出现资源拒绝；每个旧视图和当前值等于各自提交输入；释放后新提交成功，重开仍得到最新确认值。
- 失败：漏算旧页、错误共享可变正文、额度未归还或恢复错误。不是用 B 页数量 getter 验证自身。

### T5 受阻回收及真实复用

- 目标：被保护范围安全保留，其他候选继续回收。
- 输入：Data 只有 32u；三个对象各写 8u；保护 A、删除 A/B；D 需要 16u，必须回收 B 后才放得下；E 需要 8u，A 保护退出前必须失败。
- 路径：NodeStorage/S7→F22 独立扫描→F14 引用判定→F12 原子释放→正常新分配及 Direct 写；Close/Open 后读 C/D/E。
- Oracle：容量关系与独立正文；不看 bitmap、不强制物理偏移、不手工调用 Reclaim 模拟后台完成。只重试明确 NotCommitted+NoSpace，其余错误不隐藏。
- 失败：后台没推进、错误提前复用保护范围、回收丢数据或恢复不一致。能证明实际空间重用；不能由此证明回收与前台完全无锁/IO 竞争。

### T6 Deferred 完成遭遇真实内存压力

- 目标：已 durable 的对象修改不能因完成元数据暂时没有 RAM 被当作节点错误或丢掉任务。
- 输入：复用 F27 的测试侧真实 Data syscall 暂停门；对象已经提交、后台 Data 写暂停时，由另一个真实 executor 的 Prepared 缓冲占住同一预算。它没有虚构计数或直接改内部字段。
- 路径：NodeStorage/S10 提交→实际 Data 写→B 完成记录遇到共享预算不足→归还竞争 IO 的缓冲→原任务完成→读取/关闭重开。
- Oracle：生产 Pressure 只是准入中的提示，不能证明拒绝已经返回；观察提示后仍持有竞争缓冲，通过一次真实 B 提交参与同一写入串行顺序并确认明确的资源拒绝。完成记录受阻时，另一个实际 executor 应能取得已完成 Data IO 缓冲与已不用解码正文所释放的容量；只重试 Full，15 秒为进展期限，不读取私有计数。随后归还竞争缓冲，要求节点无错误、来源切换、正文和重开正文等于独立输入。没有用 Pressure 自己证明恢复正确。
- 失败：把可重试完成压力当 fatal，或恢复/来源切换丢失已确认正文。沿用 F27 门的条件变量和 cleanup；最终进展用有界条件等待，没有以固定睡眠判定完成。

## 6. 重复与变异能力

- T1 是跨所有者 RAM 和保留结果；T2 是 idle credit 转移；T3 是进展通道，三个准入案例有不同故障方式。
- T4 的旧视图含义与 T1 的 IO 结果相同在于寿命，但生产所有者不同，旧 B COW 页存在独立漏账风险，不重复建立每层私有计数测试。
- T5 接续 F14 安全回收和 F19 自动 GC 的既有风险，新增“小容量＋受阻候选＋另一个候选成功＋重开”。没有复制底层 bitmap 或引用计数测试。将来完整业务空间 E2E 覆盖同一受阻场景后可合并/退出阶段案例。
- LRU-K 原测试校验策略；F26 原页场景校验实际 Guard/IO/查询消费者。未新增“调用合并函数次数”测试，不把省了一次锁当正确性 oracle。

定向变异在隔离源码副本编译，生产工作区未改坏：去掉 IO 共享内存接入→T1 的 Full 断言失败；普通请求忽略进展占用→T3 的 Full 断言失败；跳过回收候选→T5 在有界等待后报告确实无法写入。T6 首版只等 Pressure 提示便释放资源，错误实现也可能通过；变异发现此漏检后，改用真实 B 写入串行顺序确认拒绝，重跑原场景及变异。把完成记录资源不足重新改为 fatal→T6 指定失败。runner 同时检查执行用例数、未跳过、退出码及指定失败内容，不能把编译错误/任意崩溃记为检出。

T2 删除压力收回、T4 不给 PageImage 计账也是最小反例，逻辑上会令其准入断言失败；本轮不宣称这两项已执行变异。没有证明所有可能 bug 都能被这些场景发现。

## 7. 稳定性、环境和剩余风险

- 独立 mkstemp 文件；相同环境也无共享路径。查询实际 Direct 对齐；fixture 对过大设备粒度明确报超出资源范围，不伪装通过。
- 数据确定生成，无随机 seed 漂移；GC 用有界条件重试（5 秒期限、5 ms 轮询），不用固定 sleep 后猜完成。极端慢机器仍可能触及期限，日志不能将它解释成逻辑错误定论。
- 没有新增故障注入 hook。原 F27/F26 复用的链接器 syscall 包装只在测试可执行文件内，故障/阻塞范围与 cleanup 沿原套件。
- 最新复审重新执行 39 项正常场景和 8 项定向变异（此前 38/7 等为历史执行），AddressSanitizer 启用。首轮五项断言通过但 LeakSanitizer 在沙箱进程跟踪环境退出失败；该次单独作为环境诊断保存。另一轮给特殊 64u 读取容量场景加入 2 MiB 保留时产生了无效测试部署；已将保留另加并维持原普通容量，失败属于测试适配、未以此修改生产校验。旧课程 PIE 可执行文件在输出日志前退出，改为与其他用例相同的非 PIE 编译；第三方 gtest 按原 CMake 的 system include 处理其警告。复用课程测试正文未改，失败均未计通过。最终 `detect_leaks=0`，不声称泄漏扫描或 TSan 通过。
- 没有跑原共同 C/P 或 SS/RS/PL/GT 性能比较，不宣称吞吐改善。未验证裸设备、真实断电、全节点内存覆盖或所有长期读者/压力组合。资源保留不能代替依赖解除与有效部署配置。

## 10. 再次复审：请求拒绝原因不能由全局提示推断（2026-10-07）

### 先分析得到的具体问题

`ResourceBudget::Pressure` 会被不同账户设置和清除。原 `Drive` 在捕获 `ObjectIOBusy` 后读取这个全局提示，决定是否继续重试，存在两种交错：

- 本次因共享 RAM 不足被拒绝，另一线程成功申请后清除提示；本请求可能继续占住输入，等待自己持有的资源。
- 本次只是局部 IO 名额暂满，其他组件设置共享压力；本请求被错误归类而放弃原本可以等待的局部名额。

这不是多加一层同步就应该解决的问题。拒绝发生处已经知道原因，应由结果带回来；无需让流水线再查全局状态推断一次。此外，单请求大于其工作类别的共享总容量时，原 Reserve 仍返回 false；等待其他请求释放也不可能使它成功，不能把它归为暂时压力。

- **污染/稳定性：** 不修改生产路径来暂停；测试可执行文件的链接器包装复用 F27，门由真实 IO 到达通知，Cleanup 先放行再等待异步调用结束。15 秒是失败期限，未用固定睡眠猜测是否已占名额。未证明任意并发负载下无饥饿，也不是完整 SQL/Raft E2E。
