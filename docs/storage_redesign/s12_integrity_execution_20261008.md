2026-10-08。基于 `0b3c870`；本轮未 commit/push。协议：[F30 共同方案](s12_integrity_protocol.md)。

最新审查见 §14，本次没有新增生产或测试修改；运行结果仍为 §13：修正写回/checkpoint 接手 B 扫描失败的结果与节点状态后，41 项正常场景及 10 个变异全部重新验证。§7、§9–§12 保留历史审查结论，当前压缩证据由 §13 的完整复验替换。

## 1. 结论与具体改动

**已完成本轮 F30 范围**：新建对象格式 v5、按实际分配单位保存 CRC32C、正常读取验证、可选的有界 Data/B/Journal 后台检查、压力退让及损坏上报。未实施自动修复、旧格式迁移或新的业务恢复协议。

| 落点 | 改动与理由 |
| --- | --- |
| `object_mapping.cpp` / 私有 schema | 每个原所有者/分配单位保存 allocation identity + CRC；映射拆分/共享沿用原依据。Prepare 在正文 IO 前检查实际提交形状，Apply 重新验证并发布；不把预检当持久化成功。 |
| `object_io.cpp` | 从最终正文和初始化尾部计算 CRC；自有/外部缓冲/预取共用验证；小片读取必要时读全单位。S6 的分阶段 Write/Publish 同样提交 CRC，S7 Common/Deferred 原子发布。 |
| `object_reference.cpp` | 复用注册保护→核对当前所有权的交接，供扫描固定原物理范围；回收同时删除被释放单位的 CRC，不动仍存活/共享单位。 |
| `object_transaction.cpp` | 原 GarbageLoop 轮询扫描；Data、B 页、Journal 按轮次交替，无新增线程池/目录；普通资源不足让出，IO 在途时不等待。 |
| `metadata_engine.cpp` / `journal_service.cpp` | B 的扫描/恢复共用 `CheckDiskPage`；Journal 的正文读取与只校验共用 `Decode`，`Verify` 不再复制整份正文。B 写回与扫描交接，Journal 扫描持有原批次保留。 |
| F33 / NodeStorage | 新增 Corruption 条件及扫描累计信息；CRC 不符报告原对象、分配、Data 偏移、预期/实际值，并沿 fail-stop 停止服务。 |
| 接口清理 | 删除无生产调用的 `ObjectMappingStore::Replace` 公共入口。它不能携带 v5 必需的校验依据；发布统一从实际 IO 路径进入私有 bridge。旧设备仍通过 NodeStorage 正常读写，不自动迁移。 |

启用后台扫描：在已有 `ObjectTransactionOptions` 中设置 `integrity_scan_=true`，轮询沿用 `gc_interval_`。默认关闭可选后台扫描，**新格式的写入生成 CRC 和正常读验证始终启用**。不为测试改默认设备或路径。

## 2. 先做的代码逻辑审查

测试编写前先检查以下交接，未以回归测试替代推理：

- Common 的 CRC 来自已完成组装的正文；对齐尾部算入 CRC，实际写缓冲也填零；数据 durable 后，CRC/映射/位图在同一 B 提交中发布。
- Deferred 的 CRC 和任务同时发布。任务存在时检查 Journal，不检查尚未落位的 Data。Data durable 后再提交完成事实；来源变化不改变内容身份。
- 读者先登记保护，再验证当前所有权。元数据旧视图不能独自复活已释放范围。校验按原 owner/allocation 定位，不能误用别名或同地址新分配的 CRC。
- F02 完成回调在成员 IO 全部停止后校验。外部缓冲另持有原内容许可；通知页预取成功前先验证，丢弃票据不能提前释放在途资源。
- B 扫描按自己的写回互斥规则固定一个已持久页；写回遇到已有扫描先完成该页验证。Journal 选择不超过 B 已提交边界的批次，并在退出定位锁前取得保留。
- 游标只在内存；扫描期间插入到游标之前的内容下轮再查，不声称全库瞬时一致。关闭停止接纳并排空实际 IO。
- 归档前寿命复核修正：事务终态先释放 CRC 向量，再归还内存额度，防止完成票据保留正文辅助数据却已退账。
- 校验向量和读验证描述符有局部上限及共享内存额度；后台不借用完成工作保留。校验依据缺失/不匹配不会转成零、现场重算覆盖依据或无限重试。

## 5. 重复、稳定性及价值判断

- 三种正常读入口共用一个参数循环，输入相同但完成通知和缓冲许可不同；可能出现独立漏检，保留。
- 冷 Data、B 页、Journal 三项分别检查独立的设备读取/保护路径，不能拿其中一项替代其余两项。
- Deferred 新测试接管“扫描在两个来源间正确交接”；旧 F27 的掉电恢复/事务原子性场景保持原有 oracle，不再复制一套。
- 新共享测试保护校验依据与部分释放的组合；旧 F29/S8 保护日志/快照退役、实际容量和业务恢复，失败边界不同。
- 没有随机 seed 漂移；正文由固定 seed 生成。每项独占临时文件和 Node；系统调用门均清理。状态轮询有 15 秒期限，2ms 只为让出 CPU，不作为延迟性能断言。关闭测试先观察 Draining，避免把“线程还没运行”当作正确阻塞。
- 依赖 Linux、支持 Direct IO 的测试文件系统和可用运行资源；这不是裸设备/真实断电测试，也没有给出性能提升结论。

## 9. 再次审查（2026-10-08）：压力分类与混合提交预检

先从代码逻辑确认两个真实缺口，再扩展原测试；没有先堆回归测试寻找问题。

### 具体改动

1. **读取保护名额耗尽。** `ObjectReferenceManager::Register` 原来抛通用 `ObjectMappingError(ResourceUnavailable)`；F30 会把它当不可恢复错误，导致临时占满就停服。改为现有 `ObjectReferenceError(Busy)`，沿原扫描/事务退让路径处理。`max_leases_` 注释明确此语义。未新增异常类别或生产接口；配置本身不合法、损坏和 IO 错误仍按原规则处理。
2. **Deferred 预检遗漏对象层额度。** 原 Prepare(preflight) 只在最终 B 字节预估里增加任务占位，没有让任务描述经过 `Changes` 的对象层上限。现统一构造真实任务描述；预检与正式提交共用同一条数/字节检查，只在正式提交时附加正文。B 的 PayloadRef 仍单独计入 B 预算，没有重复计入任务描述。
3. **Journal 暂忙复核。** 初查怀疑的另一条压力路径，经追到 `ObjectMappingAccess::ReadPayload` 确认已有 ResourceUnavailable→ObjectIOBusy 转换；未增加重复 catch 或重试层。

### 测试调整与独立判断

- 扩展原容量场景：1U Common＋7U Deferred 在省掉任务描述时恰好满足 16 条，加入任务描述后超限。检查 NotCommitted、**没有实际 Data pwrite**、两个对象均未改变及后续小写入成功。不只检查最后是否报错，能够发现“Common 正文已先写”的缺口。
- 扩展原压力场景并更名：保留原共享 RAM 压力；接续使用生产 `ProtectObject` 持有唯一读取保护名额，检查扫描让出、节点仍 Serving，释放后 Data 验证进度继续。没有手工改扫描内部状态。
- 新增两个定向变异：恢复旧的读取保护错误分类；预检再次跳过 Deferred 描述。要求原场景在指定断言失败；编译失败、空选择、超时或 sanitizer 故障不算检出。
- 正常场景总数仍为 41，其中新模块 11 个；没有按每种额度再复制一份完整测试。
