## 2. 共同业务数据与判定基础（候选）

### 2.1 数据形状

使用项目正式支持的简单表：唯一 id、整数版本/值、非空 payload。优先使用现有主键索引；额外索引、复杂事务与 SQL 语法须先核对正式支持范围。

- payload 根据固定种子和约定规则生成，包含共享模板、重复字段及差异内容，不把全部记录填成同一个常量，也不强制所有字段都唯一。独立的写入标识用于定位版本；内容重复与记录访问重复分开配置。
- 相同记录的反复访问用于考察缓存；不同记录即使内容相同，通常仍是不同页/对象身份，不能靠相同 payload 替代热点访问。
- 顺序用例知道每次插入、覆盖和删除后的预期；更新/删除必须作用于已确认存在的记录。
- 不在客户端读取旧值再拼新值来假冒数据库原子更新。若验证增量更新或重复请求，使用已有正式支持的业务操作和请求身份。
- 校验使用独立状态/历史模型。查询结果经适配器只做约定的解码和排序，不能删除重复行或忽略错误；原始响应仍保留。
- 大结果按固定范围分批核对，控制客户端内存；每批验证键、版本、payload 和行数。查完整数据集时在稳定边界执行，避免把多个时刻的合法结果拼成错误预期。

### 2.2 两个候选数据规格

| 规格 | 建议起点 | 用途 | 限制 |
| --- | --- | --- | --- |
| D0 | 2,048 条记录，非空、变长的业务 payload | 可逐条核对的 E2E，足够跨越多个页 | 长度分布见候选细化；不是大规模或设备吞吐结论 |
| D1 | 100,000 条记录，沿用同一生成模型与长度分布 | 初步性能、空间周转及有内容的恢复 | 以冻结后的分布计算正文、索引、编码、日志；资格运行确认当前快照上限与预算 |

首期优先验证 D0；D1 只有在资源、装载及快照预算确认后才固定为基线内容。数据量跨版本固定，不能为让新版跑得更快而缩小。

## 3. 正确性候选表

| 编号与主要目标 | 场景 | 预期结果与判定 | 故障范围 | 资源建议 |
| --- | --- | --- | --- | --- |
| C1 业务结果正确 | 装入 D0；查询；更新一组已知记录；删除另一组；重新插入部分记录；核对点查和有序范围结果 | 不丢失/重复行；已改与未改记录均符合独立模型；更新/删除确实命中；输入与完成数非零 | 无故障 | L0；一个顺序客户端，完整核对在各阶段边界执行 |
| C2 并发可见性 | 2–4 个客户端对小组共享键读写，同时对其他键施加有效负载；记录调用与返回 | 就已约定的单键/操作集合检查线性一致性：若 A 返回后 B 才调用，历史中 A 必须先于 B；读值与某个合法执行顺序一致 | 首期无故障，专门隔离并发语义 | L0；共享键和历史长度有上限，检查器离线执行；不直接声称覆盖任意 SQL 事务 |
| C3 成员故障与请求结果不确定 | 非空业务运行期间，分别做 Leader 进程终止、Leader 与多数派隔离；另以同一模型讨论丢失客户端响应后的重试变体 | 已确认操作不被回滚；多数派恢复服务后新请求正确；孤立旧 Leader 不能确认故障隔离后新发起且无法取得多数确认的写；重试按正式身份语义不重复执行 | 单次一种进程/网络故障；不声称介质故障 | L0；D0，2–4 客户端；代理/隔离权限及“故障已生效”证据待定 |
| C4 整体进程重启的恢复 | 建立已确认业务边界，在约定在途请求下终止三个节点；使用原数据目录重启，核对恢复结果并继续写读 | 已确认操作的效果在合法后续操作作用后仍正确；在途未知请求按历史解释；恢复后的服务可继续使用 | 三个进程退出，OS 和设备仍运行 | L0；D0；检查器在集群外保存历史，不使用旧进程内存作恢复证据 |
| C5 落后节点的两种追赶 | 停止一个 Follower 并继续有效写入；短落后时恢复一次，另一次在保留日志不足、已有有效快照后恢复 | 分别确认日志追赶和快照安装确实发生；在已追平的正式进度边界核对该节点数据与后续服务，不只查询 Leader | 单 Follower 离线；日志仍可用/日志已不足是两个有独立目的的变体 | L0 从 D0 起，必要时 D1；足够触发正式快照/裁剪，阈值与观察方式待定 |

C3 的响应丢失变体沿用已有请求身份及去重承诺，不能由适配器偷偷改成新请求；没有约定重试行为前不实现。C2 的模型可以供 C3 使用，不复制一套检查器。

对于 C2/C3，有效历史应包含并发请求和已完成读写；不能因为全部请求超时就给出“历史合法”的通过结果。安全性与恢复服务的时限分别判定；恢复时间阈值在协议定时器及运行预算确定后讨论。

并发历史检查借鉴 [etcd robustness](https://github.com/etcd-io/etcd/blob/main/tests/robustness/README.md) 的请求历史和独立模型方法：这里将模型限制在项目明确承诺的操作集合，不引入其故障钩子。客户端调用/返回尽量由同一运行器的单调时钟记录；跨机器时不能仅依赖未证明同步的墙钟推断先后。长历史如何分段及衔接状态仍需讨论，不能任意切片后声称整体正确。

## 4. 性能候选表

详细负载、计时、错误处理和比较口径见 [P1–P4 性能细化建议](testing_performance.md)。其中比例、并发和时长仍为待审查建议，不能直接作为执行配置。

下表“预期结果”指应得到什么证据，不预设新版一定更快。任何错误、超时和未覆盖均保留；失败运行不能作为满足相同保证的性能收益。

| 编号与主要目标 | 场景 | 预期结果/指标 | 故障范围 | 资源建议 |
| --- | --- | --- | --- | --- |
| P1 读取与缓存成本 | D1，固定点查；分别读取小热点和较大工作集，两种模式顺序运行 | 成功吞吐、延迟、节点/缓存内存和外部可见读取量；说明哪层缓存受到压力 | 无故障，无特意启动的后台干扰 | L0 或 L1；业务 BufferPool 可从 1,024 页约 4 MiB 讨论，热点大小与大工作集固定 |
| P2 写入并发与排队 | 对 D1 的已存在记录做固定大小更新；客户端并发依次 1、2、4、8，使用相同操作/连接/重试规则 | 吞吐与延迟曲线、错误/拒绝、CPU、IO；找出吞吐不再增长而排队增加的边界 | 无故障；自然快照等背景行为记录，不擅改生产行为消除它 | L0 或 L1；每档资源相同，避免一次取全部参数组合 |
| P3 空间回收与长期成本 | 保持有效记录数量大致固定，按固定规则更新、删除和补入；重复多个数据周转周期 | 业务结果正确；同等累计操作下的峰值空间、占用趋势、可复用空间证据和持续吞吐；观察是否达到稳态 | 无故障，正常 GC/快照/裁剪可以发生 | L0 从 D1、10 个周转周期讨论；有总空间/时间上限，未稳态就报告未稳态 |
| P4 后台工作的业务影响 | 固定前台负载，经历“背景平稳—快照或 Follower 追赶—恢复平稳”；一次只选一种背景事件 | 各阶段前台吞吐和 p99、事件持续时间；节点恢复服务与恢复完整副本进度分别记录 | 快照变体无故障；追赶变体只暂停/恢复一个 Follower | L0/L1；复用 P2 负载定义和 C5 进度判定，前台速率不随新版能力自动增加 |

### 4.1 不重复的具体落实

- P1 负责读/缓存，P2 负责写入容量，P3 负责持续空间周转，P4 负责后台干扰。每个场景同时采集多项指标，不为单个指标再建相同负载。
- P4 与 P2 可以共享负载实现，P4 与 C5 可以共享追赶判定，但它们的主要问题、计时和数据检查强度不同；不复制客户端或恢复逻辑。
- 两个缓存模式、并发档位及故障变体是需要解释的参数点，不能展开没有明确问题的大规模组合。
- 前台、后台按场景并行；不同性能场景串行执行。统计重复与失败重试分开。

### 4.2 计时、样本与稳态

- 对 P1/P2，候选起点为预热 30 秒、采集 180 秒、预先安排 3 次重复；这些数字尚未确定，也不保证足够进入稳态或估计尾延迟。低吞吐/后台积压时应讨论调整，调整后新旧都重测。
- 排队、超时、连接和重试的耗时计入预先定义的端到端口径；吞吐按实际成功完成统计。记录样本数，样本不足时不能只展示一个看似精确的 p99。
- P2 首期建议固定并发模式：每个客户端完成一个请求再发下一个，得到饱和曲线。它不能回答固定到达速率下无限排队的问题；若再做后一项，必须另列有界队列、发出/延迟/丢弃计数及不同目标。
- P3 同时按累计完成操作/周转周期及时间展示曲线，不能只按运行分钟比较不同吞吐版本的空间。一次周转的操作数与比例固定；若预算耗尽，保留完整结果，不假定 GC 已稳定。
- P4 用外部可观察条件定位事件阶段；未触发或未确认快照/追赶则该目标未覆盖，不能把安静窗口当作后台影响很小。前台速率可在旧版资格运行后选择一个可持续值，再对新旧固定。
- 停止发请求后的在途排空、后台积压和收尾空间单独记录，避免只测把数据暂存内存/Journal 的突发速度。若无法确认后台排空，报告限制。
- 对原始完成记录计算整体分位数，不将多个窗口的 p99 简单平均为总体 p99；各次运行分别报告及汇总，不只选择最好的一次。

### 4.3 不能混淆的观察量

P1 中，几十 MiB 的工作集大于 4 MiB BufferPool 仍可能全部命中 OS 缓存，所以首期只称“较大工作集读取”，不称“冷盘随机 IO”。若要验证设备读路径，应另行确定内存上限/设备条件并核实实际读取，不能通过扩大到超出旧版支持范围来制造对比。

P3 中，文件后端的已分配文件块与裸设备 FS 内部已分配 extent 不是自动可比的同一统计。至少同时记录对外预留容量、逻辑有效数据、外部可见占用；内部可复用量有正式观察能力才报告。预分配空间不缩小不能直接判定 GC 失效，固定容量内无法持续完成有效周转也不能由“逻辑删除成功”掩盖。

## 5. 故障分级与第一阶段范围建议

| 等级 | 场景 | 可支持的结论 | 建议顺序 |
| --- | --- | --- | --- |
| F0 | 正常运行和正常背景任务 | 业务与并发表现 | 首先 |
| F1 | 杀进程、暂停节点、外部网络隔离/断连 | 指定进程/链路故障下的安全性、恢复和可用性 | 首期 E2E |
| F2 | 独立 VM/机器中断、受限测试存储上的 ENOSPC/EIO 等 | 仅声明实际实施并观察到的故障模型 | 环境、正式错误语义和场景单独讨论后 |
| F3 | 丢写、乱序、撕裂、真实掉电 | 模拟证明指定协议模型；真实设备另有证据范围 | 裸设备与 Journal 方案明确后补充 |

推荐先建立 F0/F1 基线，但不能将它标为所有持久化风险已验证。新 FS 的 Journal、COW、RMW、Deferred 最终需要相应 F2/F3 证据；E2E 原则不取消这些风险，只要求通过真实生产链路配合外部故障环境验证。不得靠生产钩子解决目前尚未确定的注入方式。

## 6. 资源档位建议

以下是待审查的预算目标，尚未配置任何限制，也未证明能够达到。外部限额工具不可用时记录为未施加硬限额，不能声称资源已受控。

| 档位 | 环境与用途 | 内存建议 | 数据/空间建议 |
| --- | --- | --- | --- |
| L0 本机 | 现有 WSL2；三个进程；D0 正确性及 D1 初步对比 | 三节点合计约 3 GiB（含能归属的页缓存）；客户端/运行器约 512 MiB；其余留给 OS、编辑器等；离线历史检查不与重型压测并行 | 本次场景产物合计先设 10 GiB 预算讨论，需先核实 Windows 实际空余；单快照可从低于 256 MiB 的保守目标评估 |
| L1 独立测试主机 | 原生 Linux 或合适 VM；候选 8 vCPU / 32 GiB，能使用独立数据盘 | 节点预算由 L0 资格结果推算；比较时新旧总限额一致，不自动把更多内存都给新版 | 容量由三副本、日志/快照和临时空间推算；可访问块设备才能验证目标后端 |
| L2 多主机 | 三台节点主机/VM，客户端独立或有独立预算 | 每节点按相同配置固定，记录 CPU/内存配额 | 分别记录每节点设备、网络、是否共享宿主/存储；用于跨主机结论 |

L0 预算不足时先报告哪里消耗资源，讨论调整数据或环境；不能在适配器中关掉持久化、压低副本数、缩短保留规则或隐藏失败。内存预算中的页缓存只能按一种口径计账，不能与已含页缓存的外部限额重复相加。

硬件选择依据及 WSL/云平台资料见 [总体方案第 13 节](testing_plan.md#13-硬件条件与资源核算)。这些环境参考用于明确资源和证据边界，不决定场景成功条件。换到 L1/L2 后，旧版也必须在该档位重新测量。

## 7. 场景登记卡与完成证据

每项候选通过讨论后，补齐以下信息再编写测试：

| 字段 | 必须说明的内容 |
| --- | --- |
| 身份 | 场景编号、内容版本、唯一主要问题、复用组件 |
| 输入 | 数据规格、种子、操作规则、有效装载/命中的确认方法 |
| 保证 | 请求何时算成功、独立预期/历史模型、超时和重试语义 |
| 故障 | 外部实施方式、生效与目标阶段的证据、明确排除的故障 |
| 资源 | 三节点与客户端预算、存储/缓存层次、时长、空间/队列上限 |
| 计时 | 预热、起止边界、在途排空、后台状态、监控开销 |
| 判定 | 正确性条件、性能统计、不满足前置条件/环境失败/未覆盖的区分 |
| 对比 | 旧/新适配差异、同语义检查、配置与源码/二进制标识 |
| 结果 | 原始响应/历史、全部运行结果、故障时间线、资源曲线及结论限制 |

最后的执行顺序仍是：讨论登记卡 → 审查代码 → 经约定资格运行 → 固定内容并建立旧基线 → 改造 → 同条件复测。当前文档的建立不代表这些步骤已经完成。
