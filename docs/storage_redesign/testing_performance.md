**状态：历史性能讨论稿。** 当前以用户已确认的 [实施提案](testing_implementation_proposal.md) 为准，[A 批次](testing_batch_a.md) 的 P2 已编写，列长度阻塞已修复，计时内的预期模型锁已移除，性能场景未运行。下文早期候选不作为当前配置；[T0-C](testing_batch_c.md) 的 P1/P3/P4 已编写并统一审查，尚未资格运行，正式参数须资格运行后冻结。真实 E2E、测试侧适配和不得侵入生产的约束继续有效。

后续开源调研及参数收敛见 [T0 测试实施提案](testing_implementation_proposal.md#7-p1p4-场景与计量)。该提案已获用户确认，区分读预热与固定操作量的写预处理，明确 P3/P4 的计量与观察限制；不能将本页早期候选与新提案拼成隐含配置。

主要问题只有四个：P1 读取/缓存成本，P2 写入容量/排队，P3 空间周转，P4 后台工作干扰。同一场景采集多个指标，共享数据与请求实现，不为页、日志、快照各重建一套相同目标的主基准。微基准及外部性能采样仅在有明确归因问题时另行讨论。

## 2. 共用数据、链路与准备过程

采用 D1 候选规模（100,000 条），字段、重复模板、变长正文和种子规则沿用[业务数据方案](testing_data_contracts.md)。首期候选正文分布为 64/256/1,024 B，占 60%/30%/10%；不得将本项目建议称为真实业务采样。

```text
测试内容 → 测试侧协议适配 → 真实客户端入口 → 三节点 Raft / BusTub → 实际存储
    │
    └→ 测试侧计时、外部资源采集、独立结果核对
```

一次独立运行分为：启动并就绪 → 通过正式请求装载 → 校验装载 → 约定预处理/预热 → 采集窗口 → 停止发新请求并排空 → 收尾校验/后台观察。

- 装载、校验与重型历史分析不计入正常请求延迟；装载结果、预热操作量和耗时仍保留。采集的处理成本对新旧保持一致，客户端自身资源另外统计。
- 冻结装载顺序、逻辑内容、索引配置、预处理操作序列和选主完成条件；各自通过正式路径建立新目录，不要求新旧磁盘格式相同。
- 写入预处理宜固定操作量。若按固定时间预热，两个版本完成量不同可能留下不同碎片、日志与快照状态，必须报告并讨论是否适合作为相同起点。
- 每个参数点的初始逻辑状态及准备方式一致。P2 不把高并发档直接接在低并发档累积出的不同状态上；P3 的持续状态变化则是测试本身，不能中途重建库抹掉空间历史。
- 当前客户端协议每连接一请求一响应，见 [client_protocol.h](../../src/include/distributed/client_protocol.h)。计时包含这条正式路径的连接与协议成本；不能为压测改成长连接或绕过 Raft。
- 写请求以合法 COMMITTED 作为确认，读请求使用约定的 LINEARIZABLE 模式并得到合法业务响应。全量业务结果在采集前后核对；运行中保留必要的有效性检查，不能关闭持久化换吞吐。

## 3. 每次运行共同采集什么

| 指标 | 口径 | 注意事项 |
| --- | --- | --- |
| 成功吞吐 | 采集窗口内成功完成的逻辑操作数/窗口时长，读写分列 | 一次业务操作多次网络尝试仍只计一次；分别记录发出、完成、失败、未知和在途数 |
| 延迟 | 从客户端开始执行请求（包括连接）到完整响应；p50/p95/p99 与样本数 | 超时/错误单列，不因只保留快速成功而声称整体低延迟 |
| CPU 成本 | 节点 CPU 总时间与每个成功操作的 CPU 时间；客户端另列 | 满载时 CPU 更高可能只是完成更多工作，需要归一化比较 |
| 内存 | 三节点、能归属的相关页缓存、客户端及峰值；资源限额一起记录 | 不重复计算已经包含页缓存的 cgroup 用量；无法归属的缓存说明限制 |
| 设备读写 | 明确设备边界的读写字节/次数，及每成功操作的读写成本 | 单机三进程和三块独立盘分开说明；测试产物 IO 不能误算为生产写入；宿主/SSD 内部写放大不可直接推断 |
| 空间 | 逻辑有效数据、预留容量、外部可见已分配量；内部可复用量有正式观察能力才报告 | 裸设备总大小不等于有效占用，文件不缩小不等于未回收 |
| 积压与收尾 | 在途请求、可观察的后台进度、停发后的额外时间/写入/空间变化 | 区分短时吸收与持续处理能力；无法确认积压排空时保留限制 |

对采集边界预先固定：窗口吞吐只统计窗口内完成；窗口结束仍在途的请求继续跟踪并单列其延迟/结果，不能丢掉慢尾，也不能把排空期的完成数除以原窗口时长虚增吞吐。正式窗口分位数、在途尾部和重试后的逻辑完成统计应明确区分。

计量单位首期以业务操作/秒和字节/业务操作为主。若报告写放大，先定义分母是哪些成功业务变更字节，分子在哪个设备层、是否合计三副本，以及相关后台 IO 的计入窗口；不把此值标成 NAND 写放大。

## 4. P1：读取与缓存成本

### 4.1 建议负载

- 对已有主键执行点查，固定投影包含 version、last_op 与 payload，保证读取实际业务内容。
- 使用两种访问模式：均匀访问全部记录；80% 请求访问固定 5% 热记录。采用同一份数据及固定种子，不再叠加多个热点比例。
- 首期固定 4 个客户端作为候选，每个客户端一条在途请求；两个模式分别准备、预热、采集。是否扩展读并发曲线根据实际问题再讨论，避免首期参数组合过多。
- 不注入故障或主动发起快照/GC；正常生产后台行为记录在结果中，不修改生产默认行为消除它。

### 4.2 应得到什么结论

分别比较新旧的成功吞吐、p99、内存、CPU/操作与设备读取/操作。可以得到“该工作集和资源条件下的整体读取成本是否改善”，不能仅凭 RSS 下降断言消除了多少次复制或重复缓存。

工作集超过 BufferPool 仍可能命中 OS/宿主缓存；数据相同不等于页身份相同；热点请求比例也不等于缓存命中率。没有正式命中统计时不添加测试专用生产计数器，使用外部 IO/内存证据并说明观察不足。真正冷设备读取的环境、数据规模和缓存控制另行讨论，不能仅重启节点便称冷盘。

## 5. P2：持久化写入并发、排队与容量

### 5.1 建议负载

- 对已存在记录做小字段更新，例如在一条受支持 SQL 中递增 version 并替换固定长度 last_op；正文保留。避免每次重写全部随机正文掩盖小修改的成本。
- 首期固定一种键分布；建议采用均匀访问，把热点变量留给 P1。客户端并发点候选为 1、2、4、8；资格阶段决定是否需要扩展，之后对新旧冻结相同点。
- 使用固定并发模式：每个客户端得到本次结果后才发下一条；不同客户端使用不同 client_id，各自请求号连续。
- 健康场景单次尝试，计时前发现 Leader。发生未知写不能跳号继续该客户端；保留错误和未完成情况，该档不能被当作无错误的持续容量。不能用无限重试隐藏系统过载。

### 5.2 应得到什么结论

绘制同一组并发点下的成功吞吐、延迟、错误及资源曲线。重点比较吞吐是否继续增长、p99 何时上升、单位成功操作的 CPU/设备写入，以及吞吐提升是否伴随后台积压持续增长。

同时回答两种比较问题：同并发下哪个版本更好；在相同可承受负载或相同已约定延迟/错误门槛下，容量怎样变化。后者需要额外固定比较条件或补充同负载点，不对稀疏曲线任意插值后宣称已测到。

当前 [RaftNode::Propose](../../src/raft/raft_node.cpp) 和 [DistributedNode](../../src/distributed/node.cpp) 存在单个待完成写入的限制。客户端并发不等于服务端真正并行。结果首先代表 E2E，FS 提升可能被上层限制遮住；不能从 E2E 无变化推断设备后端一定没有改善，也不能把后续 Raft 流水线收益全部归因于 FS。

固定并发时，系统停顿会使客户端自然少发请求。这套曲线用于其明确的固定并发模型，不据此推断固定到达速率时的排队延迟。

## 6. P3：长期空间周转和回收成本

### 6.1 建议负载

初始装入 D1，保持有效记录数在固定范围。候选操作比例为 70% 正文/字段更新、15% 删除、15% 插入，删除和插入配对编排。每次确实修改或删除存在记录，插入预期空位；并发工作者可分配互不冲突的键范围，使有效操作比例不因冲突漂移。

- 每轮的逻辑操作数、键选择、正文生成及长度档位分布固定。长度变化应配平或遵守固定的目标分布，不能把正文总量持续变大误判为 GC 失效。
- 一次删除/插入配对是两个正式业务操作，分别计时，另记录完成配对数；不宣称两条 SQL 自动组成原子事务。
- 候选按完整数据周转周期运行；已有“10 周期”仅为讨论起点。资格阶段先估算耗时，设总时间和磁盘预算。预算耗尽仍未达稳态，明确报告，而不把最后一小段平坦当作稳定。
- 不为这项测试增加主动 GC 生产接口，也不在每轮后重启或重建数据库帮助回收。后台按正式行为运行。

### 6.2 应得到什么结论

空间曲线同时以累计成功操作/已完成周转和时间为横轴，比较有效数据量相同的检查点、峰值占用、增长趋势、持续吞吐和尾延迟。不同版本若在时间上限内完成的周期不同，只在共同完成范围比较，并单独报告完成能力。

停止发新请求后，以预先约定的相同时间/可观察完成条件记录后台收尾。旧日志/快照的保留规则和在途引用必须说明；不能只对新版多等待 GC 或对旧版多保留快照。

新 FS 可以管理 extent，但若 BusTub 没有释放空页或调用释放接口，业务空间不一定下降。P3 验证整条回收链；底层 allocator 的单独成功不能替代业务空间改善。空间释放到内部复用与归还给 OS/设备分开评价。

## 7. P4：快照、追赶对前台的影响

### 7.1 建议负载

前台采用固定读写混合，候选为 80% 强一致点查、20% 小字段更新；数据与热点规则复用共同方案。选择旧版可稳定承受的绝对请求到达速率，资格阶段确定后对新旧固定，不分别使用各自最大吞吐的某个百分比。

每种后台事件独立运行：平稳前台窗口 → 一个已确认发生的后台事件 → 恢复平稳。首期两种事件为正常配置触发的快照、同等逻辑落后量的 Follower 追赶，不把两者同时注入以免无法解释归因。

- 测试侧按计划时刻生成请求，保留有界队列/在途上限。节点变慢时记录调度延误、队列等待和未能按期发出的请求，不能悄悄降低发请求速率。
- 同时记录“计划时刻到完成”和“实际开始请求到完成”两种耗时，以及实际发送速率。队列上限触发时明确记录未发出/过载，不能只统计成功发出的快请求。
- 写客户端仍遵守单条未解决写的 SessionTable 约束；队列、读写客户端分配与重试策略由内容层明确。健康阶段不隐藏错误；追赶场景若约定重试，沿用原身份并计入逻辑耗时。
- 追赶的业务数据、已确认操作落后量与负载保持一致；实际传输字节可以因实现优化而不同，应作为结果记录。
- 后台事件开始/结束由已有正式状态或外部可审查证据确定；只能观察粗阶段时说明粒度，不能声称测到了内部精确构建时间。

### 7.2 应得到什么结论

分别报告事件前、中、后的读写 p99、成功吞吐、错误/排队及资源；记录快照可观察完成时间或目标 Follower 达到固定追平边界的时间。Follower 追赶期间 Leader 一直服务时，不把 Follower 追平时间叫作整个集群恢复服务时间。

不能只看全程平均值：短时 p99 尖峰、积压和长时间恢复均需要时间线。也不能只看前台影响：后台被饿死可以让前台很好看，但恢复冗余变慢；两个目标必须一起展示。

## 8. 时间、重复与判定建议

候选起点仍为 P1/P2 预热 30 秒、正式采集 180 秒、预先安排 3 次重复。它们不是已确认足够的稳态/统计门槛。P3 依赖周转与预算，P4 依赖事件完整覆盖，不强行统一成三分钟。

- 小规模资格运行在用户审查实现和执行方式后进行；用于确认生成器不是瓶颈、数据/缓存范围、故障观察能力和预算，不能直接追认为正式结果。
- 预先安排的重复保留全部运行；失败重跑到成功不能抹去原失败。不只挑最好的一次，也不简单平均多个 p99 作为总体 p99。
- 同一台机器上新旧分开运行；条件允许时交替顺序减少环境漂移。每次使用相同准备流程，并记录云实例、CPU 配额、设备与其他负载。
- 不预设“新版必须提升 30%”等没有依据的数字。先建立旧版分布与波动，再讨论回归容忍度、延迟/错误门槛和收益目标；新的门槛必须事先固定，不能见到结果后挑选。
- 正确性错误不能换取性能结论。过载导致的超时/拒绝可以是容量曲线的数据点，但不能被标成满足无错误服务条件的性能。
- 一项改善伴随另一项退化时同时报告，例如吞吐增加但 p99、CPU/操作、写入成本或空间恶化；不压缩成一个掩盖代价的总分。
