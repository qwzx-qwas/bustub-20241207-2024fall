# S12.3 / F29：先解除失效映射，再整理连续尾部

2026-10-08（Asia/Shanghai）。用户已授权方案、实现及测试，并明确选择 **只整理连续尾部，维持旧格式**。本协议覆盖 F29/F23/F22/F13/F14/F12/F31 的交接，旧文档中“部分有效就搬迁”“必须新增段顺序格式”的提议由本文取代。具体执行证据另见本轮执行审查，不能把本文授权等同于验收完成。

## 1. 回收语义

`Unmap` 移除当前对象的逻辑映射，不擦除正文、不缩短对象、不调用文件系统打洞或设备 TRIM。F14 根据持久共享引用、读者和实际 IO 判断完整分配单位能否释放；受阻范围暂缓，不让前台一直等待。F12 将释放事实与剩余所有权原子提交后，空间立即成为可分配空间。旧字节可以留到下一次正常写入时覆盖。延迟的是擦除/覆盖，不是一直推迟归还分配权。

空洞读零，旧受保护版本仍可读取旧正文；新对象未写字节不能暴露上一任内容。对齐缓冲初始化与整段清零、空间回收分别处理。RAM 翻译数组的 hole punching 不是这条设备空间回收路径。

## 2. 单一权威及实施顺序

1. F23 保持现有 Manifest 格式、内存 entry 索引及跨段编码。F29 是 ObjectLogStore 内部维护角色，不另建日志目录、空闲 bitmap、恢复日志或线程池。
2. 已发布段的 `[begin,end)` 为有效范围。每轮最多选一个段、一条映射、`io_chunk_bytes` 字节，将范围外的已映射内容 Unmap。先处理前缀，再处理失效尾部；已经形成的空洞就是持久进度，不另存清理游标数据库。
3. 已经失效的前缀/尾部不会重新变成有效内容；无失效尾部时，前台仍可以从原对象末尾追加，使有效尾端增长。前台仅在对象长度等于已发布尾位置时原对象追加。Unmap 保持对象长度，因此一个已有失效尾部不会变成未来追加目标。选择期间持原日志状态锁，提交 Unmap 时退出锁；前台正在准备未发布追加时不能据旧清单误删它的正文。
4. 整段无用仍沿原 Own→Collect→F14/F12 退出。它与段内 Unmap 共享原有调度。
5. 只有直接 Unmap 已无法消除候选内的失效映射后，才计算尾部搬迁收益。

## 3. 本轮搬迁范围与计算

候选必须是当前段目录的连续尾部，首位置必须是完整 entry 的起点；首段只有续片时向前纳入必要段，预算不允许则本轮不搬。选中正文重新编码后装入一个新段。保留前面原段，新段编号天然大于此前编号，重启仍按原对象编号顺序解析。兼容旧格式读写，不迁移 Manifest，不通过额外顺序表扩展到任意中间段。

使用现有 `io_chunk_bytes`、`max_batch_bytes`、`max_batch_entries` 限制候选正文和元数据规划规模；本轮新正文不超过一次 IO chunk。对改善评分的候选先用既有 CheckControlBatch 验证最终清单容量，再选中它。较大尾部的清单超限时保留已通过预检的较小尾部，不把可选整理的容量选择失败升级为节点故障。查询超出 F13 的现有查询预算时放弃可选整理，不扩大配置或全表扫描。

- `F`：候选当前有效映射触及、且没有持久共享引用的旧分配单位字节数。同一单位只计一次，已 Unmap 的完整单位不计。包含仍被少量有效正文占住的单位内余量。
- `N`：新段正文和片段头按实际分配单位取整后的分配字节。禁止假定分配单位固定为 4 KiB。
- `G=F-N`：净空间收益；`G<=0` 不搬迁。例如 8 MiB 段直接解除 7 MiB 后，移动剩余 1 MiB 到新的 1 MiB，净收益为零。
- `R`：源段的有效片段头及正文逻辑字节；候选排序使用 `G/(R+N)` 作为有界规划阶段的成本代理。它不包含各次实际读取的对齐扩展和重复读取，不能称为设备 IO 实测。后续按实际 IO 计量校准，不将逻辑字节直接冒充物理字节。
- B/Journal 的实际写放大不混同正文 IO；沿用最终 Controls 的编码容量预检及 F07 提交/完成保留。上述排序分数不是精确设备服务时间或包含全部 Journal 字节的性能测量。

F13 `EstimateRewrite` 只提供当前映射的有界估计，不发布空闲事实，不授权释放。F14 的真实引用检查继续是唯一释放依据；RAM 读者可能推迟旧空间释放。估计与执行间发生的新引用只能降低实际收益，不能绕过 F14。

整体策略仍保留“空间低/高水位、最低收益、用实际服务耗时排序”的后续调优方向。本轮没有这些阈值的测量依据，因此不拍定百分比，也不新增尚无消费者的配置；采用上述正净收益、小批次、既有维护周期和准入限制。不得把本轮称为已实现压力自适应清理器。

## 4. 状态交接及资源

现有 Store `Collect` 在日志维护与对象退役之间轮转；F22 仍安排其有界步骤及一次物理回收，不新增周期线程。没有日志工作时继续处理原退役目录。

搬迁分阶段：

```text
固定目录代次、源对象 lease，预检发布容量、预留工作 RAM
→ 锁外读完整 entry、组装新段
→ 创建既有 Candidate
→ 写入并持久化新正文
→ 核对目录代次，原子发布 Manifest/所有权
→ 替换同一份内存索引、退出源 lease
→ 原 Collect/F14/F12 回收旧内容
```

复制和正文 IO 不持日志状态锁。前台与后台共用 LogStore 原有的一把锁，不在 ObjectLogStore 再套一把锁；后台已接纳工作共同持有锁的寿命。最终小型控制发布与前台变更串行，仍可能等待 B 持久化；完整协议异步化属于 F35，不能宣称全过程无锁无等待。追加、裁剪或后缀替换导致代次变化时，候选改为退役，不把过期目录覆盖回去。

工作缓冲和目录副本经既有 ResourceAccount/ResourceCharge 计量，额度跟随候选寿命。读阶段暂满后重试，不能沿用半份新位置索引。IO 名额/缓冲占用返回的 ObjectIOBusy 和共享额度/提交占用返回的 MetadataCommitBusy 都让出当前维护轮，保留阶段；不按宽泛 ResourceUnavailable 错误码吞掉永久超限或真实错误。候选创建、正文写入、最终发布分轮执行；已提交候选的清理不因预算暂满而丢失。搬迁暂时没有新 Data 空间时取消可选候选，沿旧目录继续服务；真实 IO/损坏/不明确提交仍沿现有故障处理，不能吞掉。宕机留下的未发布 Candidate 由原 Open 的 status=0→retired 接续。

可选搬迁的目录副本、正文准备、候选创建和正文 IO 使用普通额度；Unmap、已有正文的最终发布、取消候选和物理回收使用进展资格。GC 线程不整体继承进展资格，避免新搬迁长期占住原本留给已提交任务完成的额度。沿用同一 ResourceAccount/ProgressWork，不新建优先级模块。

本轮资源限制不能证明全设备满时所有搬迁仍能前进；搬迁必须先取得临时空间。未来水位调度必须在耗尽前运行，必要时限制新写入。

## 5. 开源参考与内化

- [TiKV Raft Engine](https://github.com/tikv/raft-engine#design)：追加日志、内存位置索引及上层协作 GC。内化为沿 F23 唯一索引确定有效 entry，沿现有 Store/F22 调度清理；不增加 Raft group。
- [RocksDB BlobDB](https://github.com/facebook/rocksdb/wiki/BlobDB)：在整理中搬迁有效正文，以写入成本换取空间回收。内化为净收益与有界成本选择；本项目先支持范围 Unmap，不能照搬整个 blob 文件的垃圾比例阈值。`G=F-N` 及本轮排序是本项目设计，不宣称来自其公式。
